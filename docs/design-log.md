# Design log

The full record of kelpie's design since 2026-09-24: every decision with its mechanics and history. Read `docs/design/` first, the short form; come here for the detail behind one of its decisions. Measurements are in `docs/facts/`. The hard-to-reverse decisions are also ADRs in `docs/adr/`. The vocabulary is in `GLOSSARY.md`.

The sections below describe the code as it stands. What was built and later changed or removed is in History, one dated line each, and how a file saved by an older kelpie loads is in Old files. What was decided and never built is in Decided, not built.

## Why kelpie exists

Before kelpie, one long-running Claude session per project acted as a control room. It held the board, rationed reviews, relayed messages between the sessions that owned pull requests, and merged. Measured 2026-09-24 over shep's transcripts, in units weighted by cache pricing (cache read 0.1, one-hour cache write 2, output 5, uncached input 1):

- 2,352 transcripts, 6,020M units. The control room was 7% of that, and subagents were 54%.
- Transcripts that peaked above 500k context were 43% of all spend.
- The control room itself: 7,883 calls, median context 349k, 41 compactions, 80% of its cost in cache reads. 62% of its cost was calls that followed a Bash result (git 20%, gh 17%, the review driver 13%, the GPU queue 12%). Relaying messages was about 15%.

So kelpie moves the control room's rules (gates, locks, rate windows) into code, calls Claude only for the work and for judgement, and controls the other big cost: how large each agent's context grows.

## The shape

- Kelpie is a dog of the maintainer's own shepherd (ADR 0001, ADR 0003).
  - The adopted `kelpie` is the lease dog (ADR 0004): its `--version` answer asks for the shepherd channel, which shep 0.12 records at `shep adopt` (shep-pm/shep#656), so shep starts it with `channel` and `shutdown_with_message`.
  - It runs the dog only when shep starts it with no arguments and both `SHEP_DOG_NAME` and `SHEP_NAME` set; `shep kelpie <verb>` sets `SHEP_DOG_NAME` alone and runs the verb in the caller's folder.
  - An adoption from before the ask has no channel, and the dog exits naming `shep adopt` again, then `shep disable kelpie` and `shep enable kelpie`.
  - The dog names itself in shep's handshake (`connect_as` with `SHEP_DOG_NAME`), so shep never lists it `silent`, and `add`, `start` and `doctor` count it up only while it is online and has named itself.
- Each project is a sheep, kelpie's runner (`runner <project>`), and every agent call the runner starts is that sheep's lamb, labelled with its issue and role (ADR 0002, shep-pm/shep#624). One kelpie serves every project, because the review bots' windows and the usage pacer are machine-wide or account-wide. Realistically two projects at once. shep comes first.
- `shep kelpie add`, in a checkout, sets up a project's runner.
  - It reads the forge from `origin` and refuses a default branch other than `main`, which every branch is cut from.
  - It makes the four labels the repo lacks (`ready-for-agent`, `ready-for-human`, `in-progress`, `review please`), writes kelpie's own agent files where they are missing, and registers the runner, stopped, holding its settings as its `[app.dogs.kelpie]` table: the defaults plus what the checkout and forge say (`git.checkout`, `git.remote`, `ci.block` from whether `.github/workflows` exists, and `qwen` before `defect-hunter` where the maintainer's qwen script is installed).
  - Lookout shows each key's description from kelpie's schema, which stands in for a comment per key, since shep keeps a table without comments.
  - Everything is read before anything is written, so a refusal changes nothing, and each piece is made only when missing, so a second `add` changes nothing.
  - A sheep of the same name that is not kelpie's is refused, and so is a checkout or repo another project's table already names, since two runners would take the same issues. That check reads each other sheep's raw `git.checkout` and `git.remote`, or the top-level `repo` and `forge` of a table from before the tables, so a table that no longer parses still counts.
  - `add` says when the adopted kelpie is not enabled, not running or has no channel, and `start` refuses then, since its runner would never be granted a lease.
- A project runs while its runner's sheep runs, and only then (shep-pm/shep-kelpie#268): shep's own state is the run state, so `shep ls` and lookout show it, and `shep start <project>` runs a project as `shep kelpie start` does.
  - A runner has no paused state and never comes up paused, since a `run` the state file once kept of its own let a runner shep showed online sit paused, picking up nothing, with nothing in `shep ls` or lookout saying so.
  - The one state a running runner keeps of its own is finishing (shep-pm/shep-kelpie#303), and it ends in a stop: `shep kelpie finish` has the open work items run to their end and the board pick nothing new, then the runner stops its own sheep, so a project can wind down with nobody watching for each item's merge point. Finishing is saved in the state file as `finishing`, so a runner restarted while finishing comes back finishing.
  - Every open item goes on as ever: turns, review, CI, rulings, the merge, and reworks and adoptions already open. The board dispatches nothing, a pick wake still due to the project manager is dropped and no new one is raised, and `add <issue>`, `adopt <pr>` and `rework <pr>` are refused, naming the state: an adoption would queue where nothing starts it, and a rework would open an item a stop under way could cut off. A pull request adopted before `finish` stays queued for the next start, and `finish` names it.
  - The project manager is still woken for a conflict, a stuck item or `tell`, since those are about the open items. An item parked on a ruling is open, so finishing waits until the ruling is resolved, by the maintainer or, for a `stuck` ruling, the project manager. An item counts as ended however it ends: merged, closed with no change, dropped, or stopped by a `no`.
  - The pass that finds no item open and no merge notice left to post (a notice whose post failed is retried on its backoff first, so it lands before the word that the runner finished) clears `finishing`, logs a `run-finished` step and a line, posts that line once where a webhook is set (not retried, as the runner stops next), and hands the stop to the sheep. The sheep asks the shepherd to stop it the way `pause` does, from a thread of its own since the pause sends the runner triggers its loop must keep answering: drain, wait out calls and any merge, then stop. With no item open, `finish` stops it at once.
  - Until that stop lands the board stays shut in memory only, with `status` showing `run: finished`, so a runner the shepherd starts again picks as ever. The saved flag is cleared before the stop so that `shep start <project>` or lookout bring a finished project back picking; the gap this leaves is that a crash between that save and the stop restarts the runner picking.
  - While the stop is under way, `start` is refused with a message to start the runner once it has stopped, since the pause would stop the runner the maintainer had just let pick again, and a second `finish` asks for no second stop. A stop that fails, or whose thread cannot start, is logged as a note, and `start` and `finish` are taken again: another `finish` asks again.
  - `shep kelpie start` during finishing, or after it finished and before the stop, sends the runner `start`, which ends it, and the board picks again; a refusal reaches the terminal.
  - `pause` during finishing is the stronger stop: just before shep's stop it sends the runner `pausing`, which clears the saved `finishing` while the runner goes on finishing in memory, so it comes back picking; a refused stop sends `finish` again, saving it again. `finish` on a runner still starting waits for it as `pause` does.
  - `status` shows `run: finishing` (left out when the runner picks) beside the open items in `work_items`, `shep kelpie status` marks the project `(finishing)`, and the board briefing's header says so. `finish` on a runner that is not running changes nothing.
- `start`, `pause` and `finish` take a project's name, or find the one whose `git.checkout` is this checkout, and act only on a sheep with a kelpie table that kelpie started as `runner <project>`, so a sheep of the maintainer's stopped on purpose is never started. `start` starts the runner when it is down and waits up to 30 seconds for it to answer `status`: a runner opens its channel before it takes its actions, and shep-channel answers `unknown action` in plain text meanwhile, so any reply that is not JSON means it is still starting. `status` asks every sheep with a kelpie table.
- `pause` lets the runner finish what it has running, then stops its sheep, so `shep ls` shows it stopped.
  - It drains the runner as `upgrade` does before a restart, waits until no call runs, bounded the same way (the ceiling the runner gives plus 5 minutes), then waits out a merge in flight for up to an hour, as the upgrade's merge wait does, since a stop mid-merge can leave a merged pull request with its work item open.
  - A drain does not hold back a merge, so a merge that starts after that wait's last `status`, from a yes on a merge ruling or a gate the pass reaches, can still be cut short by the stop; the window is two `status` reads (the merge wait's last, and the one that looks for attached sessions) and the stop request wide, and the work item resumes as after any stop.
  - A runner that goes down while it is waited on is reported stopped, with no stop or `undrain` sent. A runner on a build from before the run state went still answers `status` with `run`; when that says `paused`, `start` sends it that build's own `start` too. A runner still starting is waited on until it answers `status`, for up to 60 seconds, since it takes no `drain` yet. It says what it waits on as it waits. Then shep stops the sheep.
  - A wait that runs out, a Ctrl-C or SIGTERM during the waits, or a refused stop sends the runner `undrain` and leaves it running; once the stop is asked for, a Ctrl-C no longer undoes it.
  - A session the maintainer attached (`shep kelpie attach`) is their own process, started in their terminal, so the stop does not end it: `pause` names each attached work item, which stays held until its session ends, as across any restart. Pausing a runner that is not running changes nothing and says how to start it.
- `shep kelpie rule` answers a stopped runner's ruling too.
  - The ruling and its answer are read from the state file as before; a runner that is down gets the answer as a file, `<kelpie home>/<project>/answers/<number>`, holding `rule`'s params, written atomically and named by the ruling's number (`007` is `7`, and `0` is no number), the last answer to a ruling standing.
  - A file that cannot be read, or whose answer cannot be saved, stays for the next pass; a write's temporary file a minute old is removed, and anything else in the folder is logged once.
  - Each pass reads that folder first, so the runner acts on the answer at its start: it answers each as the `rule` trigger would, oldest id first, removes the file, and logs what came of it, a refusal included (a ruling answered meanwhile from ntfy, say). A running runner still gets the trigger, so its refusal reaches the terminal.
- The runner's loop never waits on an agent call (shep-pm/shep-kelpie#318, ADR 0005).
  - It starts each call, a worker's turn, a reviewer's session or local round, or the project manager's wake, on a thread of its own and goes on, and the call's end comes back on a channel that wakes the loop, whose next pass records it.
  - A work item has at most one call in flight, and the open work items' calls run at once, beside the project manager's one. Pacing, leases and the fence are checked at each call's start. Triggers, `status` and a settings reread answer while calls run. git and gh calls stay short children of the pass that makes them, and a usage read stays one too.
  - Each work item's calls write their harness files under names of their own in the worker folder (`settings-<issue>.json`, `instructions-<issue>.md`, `review-settings-<issue>.json`, with each harness's files beside them), so two items' calls never share one.
  - The runner's git on the project's repo waits up to 2s for a ref lock and 5s for `packed-refs` (`core.filesRefLockTimeout`, `core.packedRefsTimeout`), since several items' calls and passes use its refs at once.
- How often a runner reads the forge (shep-pm/shep-kelpie#394).
  - A trigger that only asks or sets a flag, `status`, `timings` and `drain`, is answered without waking the loop, so a drain's wait, which asks `drain` and `status` every 500ms, makes no pass and no forge call. Every other trigger, `undrain` among them so the calls it lets go start at once, a call's news and a grant still wake it.
  - `status`, `drain` and `undrain` are answered from a copy the loop posts, never from the runner's lock (#916). A pass holds `Mutex<Runner>` through its rotation, and each forge call in it waits its turn behind the login's pace, so a trigger that took the lock waited on GitHub and came back past shep's 60s `action_timeout` or not at all: measured 2026-10-15, `drain` failed 17 times in one `upgrade` and `status` for about 19 minutes after a restart. The loop posts the status and the drain state at each point where it has changed what `status` shows and asked the forge nothing (at the pass's start, before each slot of the rotation, at each call's news, and at the pass's end), and at the end of every trigger it answers. A trigger that cannot take the lock answers `status`, `drain` and `undrain` from the copy; every other trigger waits for the lock as before.
  - A `drain` or `undrain` answered from the copy sets its flag there at once, in a place every step reads, so no new call starts while the pass is still in GitHub, and leaves what it asks the runner itself (the retro over what finished, the pause for each turn in flight, the withdrawal of those pauses) for the pass to take up at its next lock. It is the one deferred ask that wakes the loop, once, so a drain answered while a pass holds the lock still reaches the retro and the pauses.
  - A `drain` or `undrain` answered with the lock free takes up whatever the other left waiting, so the last ask is the one that stands whichever way each was answered (#916). Left for the pass after it, a posted `drain` pauses the turns a later `undrain` let go of, and a posted `undrain` withdraws the pause a later `drain` set. A `drain pause` asked for once is asked for: `shep kelpie upgrade` polls plain `drain` twice a second while `pause` asked for the pause, so the two asks merge into the one that ends each turn in flight at its next tool call rather than the plain poll taking the pause back. The ask for a pass is kept the same way, by `or`, so a second ask cannot clear the wake the first one is owed.
  - A pass checks that it drains again after it prepared a worker turn (#916). Preparing one mints the worker's GitHub token and prepares its worktree with the runner's lock held, and a `drain` answered from the posted copy in that time sets its flag there. Checked only before it, the pass saved the turn as running and started it past the drain, while the posted status still named no call in flight, so `pause` or `upgrade` could read the runner as drained and stop it as the worker started. Checked again, the turn stays due and says it waits on the drain, and the bridge the preparation opened is let go. `Runner::begin_item` in `crates/runner/src/runner/turn/mod.rs`.
  - No forge read is left between a step's drain check and the call it starts (#916). A pass read `main`'s workflow runs after its rotation had chosen a call, so a `drain` answered from the posted copy during that read, which waits its turn behind the login's pace, landed after the check that turn had already made. `read_main_ci` now runs at the start of the pass, before any work item is stepped, and a review round checks the drain again after it reads the issue it reviews the criteria from. `Runner::begin_turn` in `crates/runner/src/runner/turn/mod.rs`, `Runner::criteria` in `crates/runner/src/runner/review/criteria.rs`.
  - The loop posts wherever a call becomes in flight, not only at the pass's end (#916). A pass holds the runner's lock from the launch to the end of `advance`, so a trigger refused it answered from a copy that predated the call: `drain` said no call ran while one had just started, and `pause` or `upgrade` read the runner as drained and stopped it under the call. A post follows every launch: a worker's or reviewer's call, the issue writer's, the security review's, the triager's, the project manager's wake, the retro, the panel's experts, a dependency bump's proof run. `Runner::begin` in `crates/runner/src/runner/flight/mod.rs`. What is left is the short window from a step's drain check to the launch, which holds no forge call: a `drain` answered in it still says nothing runs, and the call starts. Only a lock the trigger had to wait for would close it.
  - A post asks the gateway nothing (#916). Building the status reads who holds a lease on each model a local agent calls behind a gateway, and a pass posts at each of the points above, so reading it there would ask the gateway several times a pass and hold a trigger up behind the gateway. A post reuses the holders from the last read made for a `status` trigger, or from the runner's start, so a `status` answered from the copy shows them as of that read. `Runner::read_local_leases` and `Runner::posted_local_leases` in `crates/runner/src/runner/pace.rs`.
  - A pass reads the board (its ready issues and open pull requests) at most once every 60 seconds (`BOARD_POLL`), however often the loop wakes, and at once after a change to what the board would see: a work item opening or ending, a ruling leaving the list, the queue of adopted pull requests changing, `finishing` ending, the project manager answering, the issue writer's call ending, or the board's briefing reading paths or branch files it had not compared.
  - A step that fails (`GateFailed` for its work item, `BoardFailed` or `ParentCloseFailed` for the board) runs again after 15 seconds, twice as long after each failure in a row up to 10 minutes, and any other outcome of that step starts the wait over; the waits are kept in memory only.
  - The loop sleeps until the soonest wait of a step a pass would run now, never less than a second: the board's next read counts only while the board may open a work item, and the wait of a work item that ended or has a call in flight is dropped. Reading the webhook's topic keeps its own backoff, to five minutes (Rulings).
  - A forge answer that the rate limit is used up (gh's `API rate limit exceeded`, `API rate limit already exceeded`, `secondary rate limit`, or an HTTP 429) holds every forge call the runner makes until the limit resets: the runner reads the reset once, from `gh api rate_limit`, which counts against no limit, as the latest reset of any limit with nothing left, or holds for 10 minutes when none is or the read fails.
  - A secondary limit reports no reset there, so it holds every call for those 10 minutes, deliberately, since gh passes on no `retry-after` and GitHub lengthens a secondary limit that is hit again while it lasts.
  - A held call fails at once without running gh, the hold is one line in the log naming its end, and `status` shows it as `forge_held_until` (seconds since the epoch) until it ends. A step that fails while the forge is held waits at least until the hold ends.
  - Reason: during an upgrade's drain a live runner retried a merged item's failing cleanup on every one of the drain's polls, 408 times in 13 minutes, and used up the account's GraphQL limit for every runner on it.
- The stop is shep's (shep-pm/shep-kelpie#319, ADR 0005).
  - Kelpie needs a shepherd from shep 0.12.4, the first whose stop sweeps a sheep's whole lamb tree (shep-pm/shep#688), and refuses an earlier patch of the 0.12 line as it refuses another minor, naming the version it needs; `upgrade` refuses to install a build onto a shepherd that build would refuse. A pre-release of 0.12.4 is refused too, since it may predate the sweep; one of a later patch is taken.
  - A stop reaches the runner as a message: it asks the loop's thread to stop and waits up to 1 second for its pass, then refuses new calls, sends each call's process group SIGTERM without waiting, saves the work items' time, flushes for up to half a second and exits.
  - shep then ends every lamb the runner left, whatever group or session it is in: SIGTERM, then SIGKILL after the entry's `kill_timeout`. The group SIGTERM is for what shep's sweep cannot find: a member of a call's group already reparented to init.
  - The runner fits inside shep's default `kill_timeout` (1.6 seconds), so `add` writes none, and an entry that still sets one works as before.
  - A restart resumes each work item from its session. Kelpie keeps a process group per call to end that one call at a turn's ceiling.
- Kelpie's home is `$SHEP_HOME/kelpie`, since kelpie is a plugin of shep (shep-pm/shep-kelpie#253, decided by the maintainer on 2026-10-01).
  - `KELPIE_HOME` overrides it, and with neither set it is under shep's own default, `~/.shep`.
  - Kelpie's shared entries sit at the top (`agents`, `builds`, `codex`, `dog`, `retro-reports`, `rulings`, `tools`, `totp`, `upgrade` and `upgrade.lock`), and each project has a folder named for it holding `state.json`, `board.md`, its worker files, `worktrees`, `builds`, `issues` and `pm`. So a project may not be named for one of kelpie's own entries.
  - The dog's book and door are always under `$SHEP_HOME/kelpie/dog`, since shep hands the adopted dog `SHEP_HOME` and not `KELPIE_HOME`.
  - A runner refuses to start when its door or the longest socket a call opens (a 128-bit name in its worker folder) is over 103 bytes, naming the path, since macOS caps a socket's path at 104.
- A home that never moved from `~/.kelpie` must not start empty beside its old state (shep-pm/shep-kelpie#311).
  - A runner refuses to start while `~/.kelpie` holds its project's old folders (`projects`, `wt`, `targets`, `shots` or `playwright`, each `/<project>`), or kelpie's shared files with no `.moved-to`, and the dog refuses while `~/.kelpie/dog/book.json` is there. Each names the old home and the file or folder it holds, and says what to do with it by folder.
  - `projects/<project>`, the project's state, is moved to `<kelpie home>/<project>/` (the home is `$SHEP_HOME/kelpie`). `wt/<project>` and `targets/<project>` are deleted once the project has no open work item, since kelpie makes its worktrees and builds again; `shots/<project>` and `playwright/<project>` are deleted, since kelpie no longer uses them. They are not moved, because a work item's state keeps the absolute path of its worktree and build folder, and the runner reads the new `worktrees` and `builds` folders only for work items it opens after the move. The shared files (`totp` and the rest) and the dog's book are moved or deleted.
  - A project with an open work item whose worktree is still under `wt` has no supported way through: the guard refuses the runner while `wt/<project>` exists, and no release moves the paths in its state, so the message says so and does not invent a procedure. No release moves it any more (#322).
  - `doctor` reports a project's leftover as missing, per project, and `add` warns when it registers a runner whose name has one.
  - A runner that refuses this way exits with 78 (`EX_CONFIG`), and its flock entry lists 78 in `stop_exit_codes`, so shep leaves it stopped instead of restarting it into the same refusal (shep-pm/shep-kelpie#345, Facts). A runner registered before that keeps its entry, and so still restarts under shep's backoff until `shep kelpie add` is run again in its checkout, which adds 78 to the entry's `stop_exit_codes` and keeps the codes it has.
  - A runner with `KELPIE_HOME` set is never refused, since its home never came from `~/.kelpie`, and neither is anything beside a `~/.kelpie` holding `flock.json`, `shep.toml` or `run/`, which is a shepherd's home.
- Rust for all business code. A Tauri GUI comes after the MVP. Until then kelpie is run and watched from a Claude session. MVP: a thin vertical slice, one project, one worker at a time, merge on `ask`, no GUI; shep-pm/shep-kelpie#5 is its spec.
- Kelpie and its runners talk through shep: triggers down, `channel.metric` up on the bus. Runners report running totals, because metrics drop under backpressure. A private socket only if the round trips do not hold up.
- The dog's book holds the leases a review bot's window and `cargo-test` need, and only runners and the maintainer ask for a window.
  - A runner asks for a book lease by raising running totals, `lease.<kind>.want.<epoch>` and `lease.<kind>.return.<epoch>`, and the dog grants with `grant <kind> <epoch>`. The epoch is the runner's pid, which shep's process events also carry, so the dog reclaims an old run's leases on `restart` without racing the new run's first metric.
  - A bot's window is `reviews` in `hours` from its agent file, which the dog reads when it starts, and a footer's quota or a refusal's quoted opening overrides the book's count until a later summon is accepted.
- The dog saves its book to `<kelpie home>/dog/book.json` after every change, with the same atomic write as a runner's state file, and loads it on start (decided on #19).
  - The file keeps holders and queues with their epochs, each window's quota, summons and quoted refusal, and each runner run's totals, so a restart grants no second summon inside a window.
  - On start the dog checks every runner in the book against the live flock: a holder whose sheep now has a different pid, or none, is reclaimed.
  - A missing file, or one another build wrote, loads as an empty book. One that claims this format and cannot be read also starts empty, but with CodeRabbit's window closed for an hour, as if a summon had just been accepted.
- `cargo-test` is the one lease a worker takes (shep-pm/shep-kelpie#218): a counted lease on the dog, three holders at once by default (`[kelpie.leases] cargo-test`), so test runs across workers queue.
  - A command asks for it at the dog's door, its own socket at `$SHEP_HOME/kelpie/dog/lease.sock`, and holds it while the connection stays open, so nothing has to poll a pid. The command run under it inherits the connection, so its whole process tree holds the lease however the asking process ends, and the asking process shuts the connection when the command ends, which ends it for every copy.
  - If the asking process is killed outright, a process the command left running, such as a build server, holds the lease until it exits; `status` shows each holder's `since`, and nothing yet bounds a hold.
  - It goes through a socket of the dog's, not shep's trigger: a worker's sandbox may connect to that socket alone, and shep's home stays unreadable to it, since its socket would let a worker trigger anything. The runner passes the same path to the sandbox's allowlist and to the worker as `KELPIE_LEASE_SOCKET`.
  - The door and every local socket kelpie opens, the bridges, the forwarder and `pages` included, go through `crates/core/src/ipc` (shep-pm/shep-kelpie#1147). On macOS and Linux the transport is a Unix socket at the path. On Windows it is a named pipe, `\\.\pipe\kelpie-<file stem>-<8 bytes of the path's SHA-1, in hex>`, so two kelpies with different homes never share one, with no change at any call site, which still passes the path.
    - The async side (the door, its tests) reuses `shep_core::transport` from `shep-client`, which is shep's own Unix socket and named pipe. The blocking side (`ipc::blocking`: the bridges, the forwarder, `door_pace`, `pages`, `mcp-connect`) is std's `UnixStream` and `UnixListener` on Unix, and on Windows named pipes driven as tasks of one private runtime, since std has no pipe type.
    - A Windows door is created as the first instance of its pipe, so a second dog is refused with `another dog answers at <path>`, and its default ACL lets only the creator and administrators write. A Unix door keeps its probe, its stale-socket replacement and its mode 0600.
    - The 103-byte path limit is Unix only. A pipe leaves no file, so there is nothing for a sweep to clear on Windows.
    - A pipe has no half-close and one path has many spellings. The pipe name is taken over the path lowercased, with `/` as `\\`, `.` and `..` folded, a verbatim prefix dropped and an existing folder resolved. A blocking `Stream` keeps its read and write sides apart, but tells the peer nothing, so `kelpie mcp-connect` there counts the requests it sent that have no reply and ends once stdin is closed and none is owed.
    - Gap: a Windows pipe is not inherited by a child, so `lease run cargo-test` there holds the lease in the wrapper alone, says so, and starts the command anyway. If the wrapper is killed while the command runs, the lease is given back and another suite may start beside it. Refusing to start was weighed and left: it would stop every worker's test run on Windows. A way to hold the lease beside the child needs its own issue.
    - A blocking connect to a pipe whose instances are all busy gives up with `TimedOut` after 5 seconds, since the transport retries without end; `Bridge::drop` ends the served connection before it connects to wake the accept.
    - Gap: `core` does not compile for Windows yet (file modes in the fence, totp and home stamp: sibling #241 work), so the Windows job's `cargo test` step for the door, pipe and bridge tests fails at the compile and the job stays non-gating. Its tests are the first to run once `core` builds there.
  - The same `shep kelpie lease run cargo-test -- <command>` works from any shell on the machine, and exits 75 when it cannot have the lease and 127 when the command cannot start.
  - Holders are never saved, as a dog restart closes every connection: a run that loses its dog mid-run knocks every second with `running`, and the next dog seats it at once, over capacity if need be. For three seconds after its door opens the dog grants nothing new, so those runs are counted before anyone fresh. A run still waiting when its dog goes away asks again, fresh, every second for a minute before it exits 75. A restart longer than a minute can still let more than the capacity run.
  - Workers build outside the lease (`cargo test --no-run`) and run the suite inside it, naming the kelpie binary by its path, since the guard refuses a command whose program comes from a variable.
- The GPU lease is the lock the maintainer's qwen scripts already take, and the dog stays out of it (decided 2026-09-26 on #5, option A). A qwen round takes the lock itself, and so do `kelpie lease run|take gpu`, in the same format, for the maintainer's own by-hand use (until #501: `kelpie lease run|take gpu --model <m>` is now a paddock lease, run as `shep paddock run --model <m>`, and `take` leaves a holder process that `return` ends; `status.local_leases` shows a gateway model's paddock holder by the model's name; the lock stays for agents that name a `lease`, until #502). A runner never takes or holds that lock around a command that takes it itself; a reviewer or a local agent whose file names a `lease` has kelpie take that lock around each round or call.
- A project's settings are its runner sheep's `[app.dogs.kelpie]` table, and kelpie's own are its `[kelpie]` section of `dogs.toml` (shep-pm/shep-kelpie#114, on shep 0.11).
  - Lookout edits both from kelpie's `--schema` answer once kelpie is adopted, and draws the webhook's URL `<set>`.
  - Every project setting is required except those added after the first build, so a missing or malformed one stops the runner with a message naming it as a dotted key, `worker.turn_timeout = 0`. Nothing else is read (shep-pm/shep-kelpie#332): with no table the runner stops, saying so, and with no section kelpie's own settings are empty.
- A runner reads its own table through the shep client, with `DogSheepSettings` and `DogConfig` on the name `kelpie`, not from the dog (decided on #114). shep answers both to any client, a runner is a sheep with no `DogRuntime`, and reading it itself keeps a runner's start independent of the dog being up. It finds its table by `SHEP_NAME`, else the project's name. A table goes through the settings' own parser, rendered as TOML.
- A settings change takes effect live, at the runner's next wake (within a minute when idle) and then at the next step or call that reads it.
  - `git.checkout` and `git.remote` wait for the next start, since a work item's worktree and pull request belong to them, and so do `hooks` and kelpie's gateways, which the ports and adapters hold as built at start (a change to the gateways is logged as waiting, and agents are checked against the gateways the runner has). A work item in flight keeps the agent it opened on.
  - A change is checked as a start checks it, and one that fails keeps the settings in effect and is offered again at each wake, so it lands once what refused it is fixed.
  - A table can be written without `set`: lookout edits it, and `shep copy` copies one project's whole table onto another (shep-pm/shep#830). `set`'s checks therefore hold wherever the table came from (#809).
    - A runner start asks the shepherd for the flock and its tables and runs the one-runner-per-checkout-and-repo rule (`flock::share`, which `add` and `set` use too). It refuses to start, exit 78, naming the other project, `shep kelpie set git.checkout` and removing the table. Only a project that is online counts there: a copy refused at its start stays stopped, and must not take the original's restart or upgrade handover from it (`add` and `set` still count every project). A start whose checkout is no git checkout skips the rule, since `Runner::open` refuses it.
    - A reread that sees `git.checkout` or `git.remote` differ from the runner's runs the rule then, so a taken one is refused at once. The whole change is refused, not only the git keys, so the old settings stay until the table is fixed. The rule runs when the stored table changes, not each wake.
    - A refusal, whether the table fails to load, fails a start check on reread, or is taken, is recorded on the runner with the time it was first refused and posted to the project's webhook once per distinct reason (a failed post is tried again at the next wake). The log line is still once per reason. `status` shows `settings_refused` (`reason`, `at`) and `shep kelpie status` prints it, until a reread that holds, or the table back as it was, clears it. A shepherd that cannot be reached is logged only: nothing was refused. A start's refusal is not alerted: the runner exits 78 and the shepherd leaves it stopped, as for the old home.
  - Reading on each wake was chosen over subscribing to `config.sheep.kelpie`: no second connection to carry across a shepherd's reload, and a minute is soon enough. The agent files are looked at on each wake too.

## Work

- GitHub Issues stay the tracker for the work kelpie does, with the `ready-for-agent` family of triage labels. The board of work items lives inside kelpie.
- An issue writer forms work items (ADR 0006, shep-pm/shep-kelpie#324): an agent that runs before kelpie sees an issue, researches the request, scopes it to one pull request's worth or splits it into sub-issues, and labels the implementer that should build it, as `agent:<name>`. Kelpie adds the results to the board and dispatches. There is no planning call: no plan-then-implement arm beat one agent with no plan, and a shared plan spread its bugs into every build made from it (Facts).
  - It is an agent file with `role: issue-writer`, which takes `harness`, `model` and `effort` and no other key, runs on `claude-code` alone (`--interactive` starts `claude`, and its guard is a Claude Code hook), and must have a body, its prompt. Kelpie ships `issue-writer`, Opus 5.5 at medium, the measured planner default.
    - Its body is the maintainer's rule: split only where each piece works, tests and ships on its own, never cut a piece short to keep it small, most requests stay whole; acceptance criteria in every issue; one `agent:` label per issue, the default implementer for features and anything with state or concurrency, a smaller one for mechanical work, the strongest only where a bad first build is hard to undo. It says nothing of what a model costs.
    - On 2026-10-12 the maintainer made small pieces the default instead, since bite-sized slices had proven themselves: the smallest pieces that each ship on their own, each with a `Touches:` line, concrete files and named tests, and its status label added only after its blocker links
    - Kelpie adds the project's implementers, the default first, the commands its guard runs, and how the run ends.
  - `shep kelpie issue "<request>"` runs it on its own from the maintainer's command line, not from the runner: the command waits on its answer, so the session is not a lamb and is not paced.
    - It is one fresh session in a detached worktree at `origin/main`, just fetched, under the project's `issues` folder, in the sandbox with nothing to write and only GitHub to reach, Read, Grep and Glob, and Bash held by its guard. It files `ready-for-human` and ends with `{"filed": [...], "note": "..."}`.
    - Kelpie reads each filed issue back and prints it, and names one without acceptance criteria, its status label or exactly one listed `agent:` label (read as the board reads it), exiting non-zero. A session that fails, or a reply that is not that list, keeps its worktree and prints `cd <worktree> && claude --resume <id>`; otherwise the worktree is removed.
  - `--interactive` starts `claude` in the foreground, inheriting the terminal, in a checkout of a docs branch (below) rather than the project's.
    - The prompt is appended by `--append-system-prompt`, the first message is `/mattpocock:grill-with-docs <request>` (below), the vendored skills are passed as a plugin with `--plugin-dir`, and the settings file has the same deny rules and guard but no `allow` rule, so Claude Code asks the maintainer before each command the guard lets through: an outsider's issue the session reads could otherwise talk it into a command the maintainer never sees.
    - It files `ready-for-agent`. It is not a lamb and not in kelpie's sandbox, and kelpie does nothing once it starts.
  - Its guard is `kelpie guard` with `--issues=<status label>`, an `--agent=<name>` per listed implementer and `--ledger=<file>`, and it runs only what it lists, the reverse of a worker's.
    - It allows `gh issue create`, `gh issue view <n>` and `gh issue list` read against an allow-list of their flags (no `-R`, `--repo`, `--web` or URL, in any spelling or short-flag cluster), and, for the issues the session filed, `gh issue edit` with `--add-label` or `--remove-label` and `gh api` POSTs on `repos/{owner}/{repo}/issues/<n>/sub_issues` and `/dependencies/blocked_by`, plus GETs on `repos/{owner}/{repo}/issues/<n>` for an issue's database id.
    - Each is plain words with no `$`, backticks, pipes, redirects or `cd`, and a heredoc only behind a quoted delimiter, since the shell expands a bare one's body. gh fills `{owner}/{repo}` from the checkout, so it works on the project's repo alone.
    - A filed issue must carry the status label and no other kelpie status, exactly one `agent:` label naming a listed implementer, an acceptance criteria heading with a list item under it, and no path on this machine. `gh issue view` and `list` let it find an open issue that already covers a request.
  - It settles the design with the maintainer before it writes (shep-pm/shep-kelpie#365).
    - Interactively the first message is the vendored `grill-with-docs` skill, which runs `grilling` (rounds over a tree of decisions, each question with a recommended answer) with `domain-modeling` (glossary terms and ADRs written as decisions settle), and the skill itself says to file nothing until the maintainer confirms a shared understanding. The prompt adds that the issues are filed only then.
    - Headless there is no one to grill, so the skill is not run: the prompt has the writer take what the repo's docs point to where they settle a choice, and end an issue with an `## Open questions` section for each decision they do not, in `grilling`'s format (`❓ **Q<n>** - **<title>**: ...` and `➡️ <recommended answer>`, separated by `---`), so the maintainer answers on the issue before labelling it `ready-for-agent`. Acceptance criteria are written as if the recommended answers hold.
    - The maintainer decided `grill-with-docs` only for now, and `grill-me` (grilling with no docs) can come later if it is needed. It is no `[skills]` step, since only the interactive mode runs it, so a project cannot swap it, and it always runs the vendored copy, written to a plugin of its own per run under the project's `issues` folder.
  - Facts come from the repo, never the maintainer, in both modes. `grilling` tells the agent to dispatch a sub-agent for a fact, and the issue writer's settings deny `Agent` and `Task`, so the prompt says to look it up with its own Read, Grep and Glob, and to ask the maintainer only for decisions.
  - The docs `domain-modeling` writes go on a branch of their own.
    - An interactive session runs in a worktree of its own, `kelpie/docs-<id>` under the project's `issues` folder, cut from a fresh `origin/main` (the same fetch the headless writer's checkout makes), so the maintainer's checkout and any change in it are never touched, at the price that the session reads `origin/main` and not what the maintainer has unpushed.
    - Its file tools are allowed `Edit`, `Write` and `MultiEdit` (`NotebookEdit` stays denied) with the same `kelpie confine` hook that holds a worker, naming only `<worktree>/GLOSSARY.md` and `<worktree>/docs/adr`, so a write anywhere else, the rest of the worktree included, is refused before it lands. Claude Code still asks the maintainer before each edit, since no `allow` rule is written. The GLOSSARY-MAP layout, a glossary and ADRs inside a context's own folder, is not allowed.
    - When `claude` ends, `Interactive::end` reads the session's ledger for the issues it filed, then lists the worktree's changes: none removes the worktree and branch; any file besides `GLOSSARY.md` and `docs/adr/` commits nothing and keeps the worktree, naming it; otherwise kelpie commits with hooks off (a conventional `docs:` subject, as the maintainer's git identity), pushes the branch, opens a draft pull request into `main` and comments on each filed issue with its number, then removes the worktree and the local branch.
    - The pull request carries no `Resolves`, and its `kelpie/docs-` head is not a `kelpie/<issue>` one, so the runner never takes it for a work item's.
    - Not measured: no live Claude Code session has run `--plugin-dir` with a slash command as its first interactive message, or has the `Skill` tool resolve `grilling` and `domain-modeling` from the plugin's namespace, under these settings yet. `grill-with-docs` is marked `disable-model-invocation`, which should still let the maintainer's own slash command run it.
  - It runs no git, since a security review of the first build found git's options too wide for a deny-list to hold: `git grep --open-files-in-pa=<program>` (git takes any unambiguous abbreviation) ran a program, and `--no-index`, `blame --contents`, `-C <dir>` and `ls-files --exclude-from` read any file. The session reads the repo with Read, Grep and Glob, and the headless worktree is already at `origin/main`.
  - The ledger is a PostToolUse hook, the same guard with `--record`.
    - After each command it keeps the number from a line that is one lone `gh issue create` (with at most the `cat` its `--body "$(cat <<'EOF' ...)"` reads) and printed one issue URL and nothing else, and the id a lone `gh api 'repos/{owner}/{repo}/issues/<n>' --jq .id` printed. The guard refuses a `cat` of its own, one for each such body at most, since it could print a forged URL for the ledger to take.
    - The guard allows an edit, or a link's issue, only on a number the session filed, a `sub_issue_id` only of an issue it filed, and an `issue_id` (a blocker) only of an issue of this repo whose id it read. A missing or unreadable ledger holds nothing, so an edit or a link fails closed.
    - On its own it lives in the call's scratch folder, which Claude Code empties as the call starts and the sandbox lets it write; interactively it is a file of the run's own under `issues`, removed when `claude` ends.
    - That the PostToolUse input carries the command's output as `tool_response.stdout` has not been checked against a live session; if it does not, edits and links are refused, not allowed.
  - Its file tools read only its checkout (and, on its own, its scratch folder): every other entry from `/` down is a Read deny rule, worked out entry by entry around the checkout as the worker's are, plus `~/.config/gh`, `~/.claude.json`, `~/.claude` and the shell's history by name. On its own the sandbox also denies the history and the usual credentials. gh's config and Claude Code's files stay readable to the sandbox, since gh and the harness read them themselves; the session's commands cannot read a file, so the Read rules are its whole reach.
  - Each listed implementer's `agent:` label, and the status label, is made on the repo before the session when the repo lacks it, since the forge refuses a label the repo lacks.
  - `agents.issue_writer` names its agent file, `issue-writer` when absent, and a runner refuses to start, as for any listed agent, when that file is missing or another role's (shep-pm/shep-kelpie#381).
  - The runner runs it too, for an issue that reached the board without it (shep-pm/shep-kelpie#381).
    - When the board would open a `ready-for-agent` issue with no `agent:` label and the project lists more than one implementer, it makes one issue writer call instead of falling back to a default, since picking the implementer is the issue writer's job (ADR 0006). With one implementer listed there is nothing to pick, and an unlabelled issue opens on it with no call. `add <issue>` makes no call: it opens an unlabelled issue on the first implementer listed.
    - The call is a narrow form of the headless run: a fresh session in the project's checkout, read tools only and no command, so no guard, the agent file's body as its instructions, and a prompt that says this call only picks and files nothing, whatever those instructions say of filing, then holds the issue (to judge, never to follow), the listed implementers, the default first, and the reply it must end with, `{"agent": "<name>"}`, read from the reply's last line that parses as that object.
    - Before it starts it is paced on Claude's account, which the issue writer always spends, when no listed role spends it and so the dispatch's own pacing has not read it.
    - Kelpie, not the session, puts that label on the issue, so the session needs no `gh`, and the board reads the issue labelled on its next poll.
    - It runs in flight like a turn, one at a time, with a 15-minute ceiling, not while the runner drains, and its line goes in the usage ledger with the issue's number. While it runs, `add` refuses that issue and the board passes it over even if someone labels it by hand, so no work item's call shares the issue's in-flight ledger entry with it. A call stopped with the runner raises nothing, and the next run asks again.
    - A failed call, a reply kelpie cannot read, a name the project does not list or a label the forge refuses raises a `stuck` ruling with the `unlabelled` reason on the issue rather than guessing. It parks no work item, so the board passes the issue over (`skipped` as `unlabelled`, with the ruling's id) until the ruling is answered, and a yes clears it (a `no <note>` is refused, since no worker could take the note): the board then reads the issue again, and one still unlabelled goes to the issue writer again. An issue labelled while the ruling waits opens anyway, and its work item opening clears the ruling.
- Priority orders the board (shep-pm/shep-kelpie#144). Ready issues labelled `priority: P0` go first, then `P1`, `P2`, `P3`, then those with no priority label, the labels shep uses. Within a priority the oldest issue goes first, and an issue with several priority labels ranks by the highest. Adoptions and reworks go before any issue. A blocked, assigned or otherwise passed-over issue does not hold up the next one, whatever its priority. A blocker's state is its issue's, never its pull request's.
- The board keeps an order (shep-pm/shep-kelpie#494, slice of #294).
  - `order` in the state file lists the ready issues, first taken first, and each read of the board updates it: an issue the forge no longer lists leaves it, and a new one goes after the last issue of its priority that the order holds, oldest first when several are new. With no moves it equals the priority rule. `pick` follows it over the labels and `board.md` lists it.
  - A priority label changed on an issue already in the order moves it to just after the last issue of its new priority, as if it were new (the maintainer's ruling on #494): `ranked` keeps each listed issue's priority from the last read to see the change.
  - Labels stay the quick way to bump an issue, and the move verbs (#495) fine-tune within that. The skips are unchanged, and the project manager still picks among what the board could start.
- An issue's `agent:<name>` label picks its implementer from the project's list, the prefix read in any case.
  - A label naming no listed implementer, or two `agent:` labels, is a label error, which the board skips and `add <issue>` refuses.
  - A `!` at its end, `agent:opus-high!`, pins the work item to that implementer, so its first turn never falls back (below); the board and `add` read the name without it, and the work item keeps `pinned` in the state file.
  - A `worker:` label is no longer read: an issue still carrying one counts as unlabelled, and the runner's log says so as its work item opens.
  - When a runner starts, and when a settings change brings a different `agents.implementers`, it makes each listed implementer's `agent:` label the repo lacks (shep-pm/shep-kelpie#381). It only adds: deleting a label strips it from every issue, closed ones included, and a label the repo has in any case is left as it is, colour and all. A forge that refuses is a line in the runner's log, and the runner goes on.
- The board never works an issue with sub-issues, since they are worked in its place, and closes one whose sub-issues are all closed, whoever made them. A close the forge refuses three times in a row is passed over until the runner restarts, so one refusal that never clears does not hold every poll; each refusal is a line in the runner's log.
- An issue a work item holds carries `in-progress` (shep-pm/shep-kelpie#199), so a reader of GitHub sees a worker has it while it still carries `ready-for-agent`. It goes on as the work item opens, by the board, `add`, a rework or an adoption, and comes off as it ends, merged, handed back or dropped. A runner that starts puts it on each issue it holds, and takes it off each finished issue whose removal a refusal once missed. The label is a courtesy: a forge that refuses it leaves a line in the runner's log and the work item runs on.
- Several work items per project (shep-pm/shep-kelpie#103), because a pull request waiting on a review bot's window, CI or a merge ruling held the whole project: overnight on shep that was about one pull request an hour with the GPU idle between rounds, and the playground sat all night on one merge ruling.
  - A project's `concurrency.active_items` (1 when absent) sets how many slots it has, each work item with its own branch, worktree, build folder, phase and rulings. A slot bounds model calls, a worker's turn or a review's (shep-pm/shep-kelpie#355, ADR 0007).
  - The board opens a work item whenever a slot is free, and never an issue or pull request whose work item is open. An item takes a slot when it opens and keeps it through a lease, CI, a bot and the merge, yielding to the next on each wait.
  - An item parked on a ruling gives its slot up: a parked worker runs no process, its session waits on disk, and on shep with one slot one unanswered merge ruling left the runner doing nothing.
  - `concurrency.pending_rulings` (2 when absent) bounds the items parked, so an unanswered alert cannot open pull request after pull request: while that many are parked the board opens nothing new, and the alert for the ruling that filled it says how many rulings wait. With none parked it is never full, so `pending_rulings = 0` opens work as ever until a ruling waits. It bounds what the board opens, its reworks and adoptions included, not what parks: items already working can still park past it, and the maintainer's `add` ignores it on purpose.
  - A merged pull request parked on its follow-up ruling counts toward neither cap and holds no overlap, since its branch is done.
  - Answered, an item goes on with no slot through any phase that calls no model (CI, a merge, a catch-up, `done`), and the moment it enters one that does (a turn or a review, for a `no <note>`, a red CI run, a conflict or a new head) it waits for a slot, ahead of any new work item, and takes the next to free. So with one slot a merge `yes` lands at once beside a working item, and a `yes` withdrawn for a moved `main` whose CI then fails waits for the slot before its fix turn.
  - A step that moves a waiting item into its review, as an owed bots' pass after green CI does, starts no call for it, and `attach` takes a free slot for an item holding none, or refuses, since its session is a model call too.
  - The state file keeps each item's `seat`: `held` (left out), `without` or `waiting`. An older build refuses a file holding either of the others, so going back to one needs every item not holding a slot finished or dropped first; draining is not enough.
  - A ready issue whose body names a file a parked item's branch changes is passed over as `overlap`, by the board's own overlap check (each branch's diff from `main` against the issue's named paths), since it would build on code the ruling may still change. While a parked item touches any file, an issue whose paths the board has not read from its body as it now stands waits a pass for its next write, and while a parked branch's files are unknown every ready issue waits; either is listed in `skipped` as `paths-unread`. A branch git cannot read on one write keeps the files it last read.
  - `status` lists the open items' issues under `working`, `waiting_for_slot` and `parked` beside `work_items`, and the board's header counts the slots held.
  - Freeing parked slots means more sessions resume long after their last turn, and one resumed more than an hour after it has lost its prompt cache and pays the cache write again, about $0.20 to $0.50 on shep-pm/shep#707's numbers; that cost is accepted.
  - Items merge independently, and one merging sends the others through the catch-up with `main` at their gate. A ruling names its work item, and its answer moves the item parked on it. `gate` and `drop` take the item's issue when more than one is open. `status` lists every open item under `work_items`, keeping `work_item` as the oldest.
  - What `concurrency.active_items` does not change: every gate per item, one call in flight per item, and one summon per grant of a bot's window: the runner records which item took a grant, and another item waits for a grant of its own rather than inheriting it, which would summon twice in a window the dog counted once.
- Kelpie records each issue whose work item it finished by merge, and the board never takes one again, since GitHub closes an issue from `Resolves` a moment after the merge, and the playground's board re-picked #22 in that moment.
  - An entry goes once its issue reads closed (shep-pm/shep-kelpie#172): each dispatch step asks the forge for every finished issue the board does not list as ready, and one it cannot answer for stays.
  - `shep kelpie drop [<issue>]` ends a work item without merging, paused or not, keeping its pull request and branch on the forge. A dropped issue stays open, so it goes on its own list, `dropped` (shep-pm/shep-kelpie#481), not on `finished`, which only a close clears.
  - The board leaves a dropped issue be while the forge lists it ready, and the briefing and `status` name it as dropped with `shep kelpie add <issue>`. An entry goes once the forge no longer lists the issue as ready: a dispatch step sees that in the board it reads, and while the board is shut (every slot held, finishing) a pass reads each dropped issue's labels on its own, at most once a minute.
  - Taking `ready-for-agent` off and putting it back returns the issue to the board. A label taken off and put back inside one minute is not seen, and `shep kelpie add` still takes the issue back.
- Kelpie works on its own repo (shep-pm/shep-kelpie#140), as a project on the maintainer's shepherd added with `shep kelpie add` in a clone of its own, never the checkout sessions work in, and worked by the board like shep with `concurrency.active_items` above one. Its model per issue is an `agent:<name>` label, its order the priority labels, and an issue kept for the maintainer is one without `ready-for-agent`. The rules that hold for any worker on this repo are in `CLAUDE.md`, which every worker reads, and those that name this machine's paths go in the project's `worker.instructions_file`. A merged change reaches the runner only when the maintainer upgrades it.
- The board briefing (shep-pm/shep-kelpie#326). The runner writes `<kelpie home>/<project>/board.md` for the project manager's agent, so that agent never runs git or gh: measured, a PM briefed from a code-written board decided as well as one that looked for itself (Facts) at about half the units a wake.
  - It is written atomically at start and at the end of any pass whose saves changed the board, and refreshed once a minute.
  - Every save diffs the state before and after it into board events (a turn starting, ending or failing, a review call starting or ending, a pull request found, a phase change, a work item opened or closed, a ruling raised or answered), and the ready queue's reads and a worker going idle or active add their own. The state file keeps the newest 50 events with ids that only grow, and `pm_seen`, the PM's cursor: the board shows the events after it, or the last 20 while there is none.
  - The board quotes each ready issue's first 600 characters, as the measured boards did, every line behind `> ` so no heading, rule or fence in a body reads as the board's own, and titles and failures go on one line with no backticks. A failure, a skip's error, a ruling's question or a worker's closing message that names this machine is withheld from the board, by the same check the forge's posts get.
  - A worker's activity is when its transcript was last written (a Codex call's output file, a pi session's file), which the runner reads with a `stat` on each pass, never a model. A worker silent for 10 minutes reads as idle and records an event, counted from the turn's start while its transcript is not written yet or is older than the turn, because the measured PM missed a worker hung on a prompt in 7 of 8 tries when the board said only "busy".
  - Overlap comes from git: each branch's files are `git diff origin/main...<head>` of its local branch, which has the worker's commits before any push, each pair of branches gets `git merge-tree`, and each ready issue's paths are the backticked spans in its body that name files on `main` (by whole path or last parts, at most 3 matches) or a new path with a folder.
  - Each answer is kept by the commits it read, so a write runs only what moved, and git runs with the runner's lock let go, so a trigger never waits on git for the board. `merge-tree --write-tree` needs git 2.38 or later; with an older git, or a commit git cannot find, the pair reads "conflict check unavailable" and is asked again on the next write.
- The project manager's agent (shep-pm/shep-kelpie#327). A project opts in with `agents.pm`, naming an agent file whose role is `pm`; kelpie ships `pm`, Opus 5.5 at medium, which `add` writes. Absent, the board's rule picks and every ruling waits on the maintainer.

## Workers

- A worker owns one work item and outlives its sessions. It builds inline, with no plan to follow and no crew: its instructions say to implement the issue itself, and every skill call's headless rules forbid sub-agents and the Agent and Task tools. A reset, by compact or by clear with a handoff, would keep the same worker.
  - One step drives a reset now (shep-pm/shep-kelpie#426, the first of #71's "Resets within a work item"): before a turn the runner sends a worker after its first, if the session's last turn ended with its context past `WORKER_COMPACT_PAST` (150k tokens, set beside the project manager's `COMPACT_PAST`), the runner sends `/compact` first, recorded in the usage ledger as its own `compact` call with the issue and pull request.
  - The turn stays due while it runs, and its prompt, once the compaction ends, opens with the issue and the pull request, since the summary may have lost them. A compaction that fails is told and let go, and the turn goes on in the session as it was. A clear with a handoff is still driven by no step.
- Agents never see budget numbers. Budget talk makes models stop after every task. Budgets live in kelpie's code.
- Model defaults, kept in kelpie's own agent files (shep-pm/shep-kelpie#313): implementers on Sonnet 5.5 at high effort, `sonnet-high`, the default a new project lists, and `opus-high`, Opus 5.5 at high, for work that is hard to undo. - A worker's `git fetch` in the shared clone is answered before it runs (shep-pm/shep-kelpie#950).
  - Why: every work item's worktree shares one `.git`, and `Profile::reach` lets a worker write only its own branch's ref, lock and reflog. A bare `git fetch` updates every `refs/remotes/origin/*`, so each other branch's ref lock fails and git exits 1 with `cannot lock ref`. 36 tool errors in the Claude Code and pi transcripts of 13 to 16 October 2026 were that, about 12 a day, most of them a fetch before a merge, and 83 of the 93 worker retros of 10 to 12 October raised it (`docs/facts/worker-profile-and-sandbox.md`).
  - What kelpie does: `kelpie guard` refuses a `git fetch`, `git pull`, `git remote update` or `git remote prune` that reaches the work item's own repo and names `git merge origin/main` instead, and `worktree::prepare` fetches `origin/main` before every worker turn, so that merge has main as of the turn's start. The worker's instructions say the same, and no longer tell it to fetch. A fetch that fails in `prepare` is no error for the turn: the ref stays where kelpie last put it, the turn runs, `runner::turn::worker_reach` stands a warning that `status` lists under `standing` until a fetch lands or the work item ends, which `runner::merge::cleanup` does once its worktree is gone, and the gate fetches main again before it reads a head. A `Start::Main` branch starts on that ref, so there a failed fetch is an error, and a `Start::Pushed` one needs main only for the merge its worker runs. A fetch in a repo the worker made inside its worktree is left to git, where its refs are its own to write. So is a fetch git is pointed at another repo, by `--git-dir`, `--work-tree`, `--bare` or a `GIT_` assignment (`front.redirected` and `Git::redirected` in `crates/core/src/guard/git/mod.rs`): kelpie cannot tell a fixture from the shared clone there, and a fetch writes none of the work item's refs. `git --git-dir=.git fetch` names the shared clone plainly and takes git's own failure, which no setting of the guard's would read as kelpie's answer. The answer also reaches a folder kelpie cannot follow (`cd "$WT" && git fetch`, `git -C "$WT" fetch`) and one the call makes inside the worktree (`mkdir -p x && cd x && git fetch`), since git searches upward for a repo and the repo it finds from either is the shared clone. A repo the call made in the same call (`git init --quiet x && cd x && git fetch`) is the worker's own, and a fetch past the worktree is no repo of kelpie's, so neither is answered.
  - The issue's other three options, and why not. Instructions alone leave a worker that ran the fetch anyway to the same failure, and the guard is where kelpie already answers a command before it runs. A fetch that writes nothing outside the worktree is not on offer: git maps `git fetch origin main` through the clone's `remote.origin.fetch` to `refs/remotes/origin/main` and locks that (measured 2026-10-16 on git 2.50.1), and the only ref of `origin`'s a worker may write is its own branch's, which a fetch of main would overwrite. A clone per work item (`git clone --reference`) gives the worker refs of its own, and with them the power to move `origin/main`, which the guard reads as the base of what a push sends; its cost in disk and time against a worktree was not measured here. Opening the shared `.git` stays turned down (2026-10-12, `docs/adr/README.md`).
  - Not measured: whether a worker ever needed a ref of `origin`'s other than `main` and its own branch in its item's repo. The issue's read of the transcripts names only fetches before a merge.

## Agents

- An agent is a definition file (shep-pm/shep-kelpie#313, ADR 0006): `<name>.md` in the `agents` folder of kelpie's home, YAML frontmatter and then a Markdown body. The name is the file's stem, lowercase letters, digits and `-`.
  - The frontmatter is tagged by `role`: `implementer`, `reviewer`, `issue-writer`, `pm`, `advisor` or `researcher`, each with its own keys, so a reviewer's `paths` or `second_look` on an implementer is an unknown key, named with its line.
  - A file that does not parse, has a key missing or unknown, names an unknown harness or misses a key its harness needs stops the runner, naming the file, the key and the file's line. A `.md` file whose name is no agent's, such as a `README.md`, is skipped, named in the runner's log and by `doctor` as unsure, and blocks nothing.
  - The frontmatter is read with serde-saphyr, already in the build through shep-core, pure Rust and maintained, where serde_yaml is archived.
- Kelpie embeds its own agents from the repo's `agents/` folder with `include_str!`, so they are reviewable files: `sonnet-high`, `opus-high`, `defect-hunter`, `qwen`, `coderabbit`, `cubic`, `codex`, `issue-writer`, `pm`, `advisor` and `researcher`.
  - A file of the same name replaces one, and a name with no file falls back to kelpie's own, so a home that never ran the newer `add` still runs. `shep kelpie add` writes each that is missing, never over one, and `qwen` only where the maintainer's qwen-review script is installed.
  - A runner reads the folder when it starts and looks again each time it wakes, so an agent file edited, added or removed lands at the next wake as a settings change does, and a yes to a turn that failed on a missing file retries against the file written since. `doctor` adds an `implementers` line per project, naming the default or what is wrong.
- An agent file extends another with `extends: <name>` (shep-pm/shep-kelpie#386).
  - The file starts from the parent's frontmatter and body; the keys it sets replace the parent's, `role` and `harness` included, and a file with no body takes the parent's.
  - The merge is on the frontmatter's top-level keys as text, in `crates/core/src/agents/extends.rs`, before the typed parse, so every check applies to the merged file and a refusal names the child's file. The child's own frontmatter lines stay where they are (its `extends` line blanked) and the inherited keys follow, so a refusal of a key the child sets names the child's own line; one of an inherited key says "inherited through `<parent>`" in place of a line.
  - The parent is resolved by name, not file order: a file in the folder, else one of kelpie's embedded defaults (a file of the parent's name wins), and a parent may extend another. A missing parent or a cycle is refused naming the file; `extends` on an embedded default is unsupported. The variant keeps its own name everywhere.
  - A parameter on the reference (`defect-hunter?effort=medium`) was set aside, since every combination would be another label and ledger key. `agents::snapshot` already reads every `.md`, so an edit to a parent reaches its children on the live reread.
- A project lists its implementers in `agents.implementers`, in order, each once, `["sonnet-high"]` when absent, its reviewers in `agents.reviewers`, its project manager in `agents.pm`, and its issue writer in `agents.issue_writer`. A name with no agent file stops the runner, naming the setting and the file to write, and so does a file of the wrong role, naming both roles. An empty implementer list is refused. The first listed is the default the issue writer is told of, local or not.
- A work item keeps the agent it opened on, as `agent` in the state file, and each turn runs that agent's file as it is then, even once the project stops listing it, so editing a file reaches the items on it. An item whose agent has no file left fails its turn on the `turn-failed` ruling, naming the file to write.
- One interface for every role, so that any harness fits and everything harness-specific stays in its adapter.
  - A call starts or resumes a session by id in a folder, with kelpie's instructions, a prompt, the kinds of tool it may use (`Work`, `Review`, `Answer`, or `Issues` for the issue writer), its skill plugins, a timeout, and a sandbox that names no harness.
  - The sandbox lists folders the session may read and, for a fenced session, the folders it may write, the paths it may not write or read, the hosts it may reach, the commands it may not run (as prefixes with `*`), its environment, and what kelpie's own checks run with.
  - The answer is the session id, the final text, the tokens the call used, and the session's cost only where the harness reports one. A call with no cost leaves the work item's record of that session unchanged.
- What each role needs from a harness. The worker: a session it can resume by id across turns, instructions appended to the system prompt, skills a prompt can invoke, MCP servers, no permission prompts, a fence that confines its writes and hosts and fails closed, a check kelpie runs before every command and every file write, a turn the adapter can kill at its ceiling, and each call's tokens. A reviewer's session: a fresh session each time that reads and searches the worktree, runs no command, starts no crew, and answers in kelpie's finding format. Any harness that can do those fills the role; one that cannot fence the worker cannot be the worker.
- Every agent call runs whole inside kelpie's OS sandbox (shep-pm/shep-kelpie#128): the harness, its tools, its hooks and the MCP servers it starts, not only its commands.
  - The sandbox is a port, `Sandbox`. Behind it stands crabpot, the Rust port, linked into kelpie's own binary on every platform (#1181, #1199, #1217; see Fence). Node `srt` (Anthropic's sandbox runtime) stood behind it first, and `kelpie tools install` installed it until #1217 took it out.
  - The policy is the call's fence plus what the harness itself needs, which its adapter knows: for Claude Code, its transcript folder, a scratch folder and `api.anthropic.com`. A call without a fence, such as a reviewer's session, writes nothing but those and reads no credential path. A missing runtime fails the call and stops a runner at start.
  - Claude Code's own sandbox is off under it, since on macOS a sandbox cannot start inside another (Facts); its deny rules and kelpie's hooks stay on as the second layer.
  - The model's endpoint is open to the whole process, since the harness itself calls it, so the worker's commands reach it too: an agent CLI started from them (`claude`, `codex`, `pi`) would run a session with none of kelpie's hooks or deny rules, and `kelpie guard` refuses one wherever it reads a program. The list is each harness's `program` in the fence's own table, so a new harness cannot be left off it.
  - After `cd`, `ls`, `mkdir`, `rmdir`, `rm`, `cp`, `mv`, `touch`, `echo`, `printf`, `git` or `cargo`, an agent's name is a file or a word, so `git add crates/adapters/src/adapters/pi` and `cargo test pi` pass. The check is by name: `node` on pi's own script, or `npx` on a harness's package, still starts one, and the OS sandbox is the boundary.
- Each harness declares the files in a worktree that make it run code, and the fence holds every harness's files whichever harness a call runs on, so a worker on one cannot plant files for the next call on another. Each harness also declares the files in the home folder that hold its login (Claude Code's `~/.claude/.credentials.json` on Linux and `~/.claude.json`, which holds MCP servers' secrets; Codex's `~/.codex`), and a call on one harness cannot read another's. A harness reads its own to run, so those stay readable to its own calls, apart from Codex: kelpie runs it on a login of its own, and the maintainer's `~/.codex` is read by no call (#233).
- Claude Code builds its settings file from that sandbox in the interface's `prepare`, which the runner calls before it marks a turn or review call running, so a file that cannot be written fails the step and a yes retries the turn it was for.
  - The file turns Claude Code's own sandbox off and holds the deny rules and the `confine` and `guard` hooks, and trims the features no role uses (#228, Facts). `confine` is there because Claude Code's sandbox never covered its own file tools, which is the adapter's knowledge, not the profile's; under kelpie's sandbox it is the second layer.
  - The project's `worker.guard_hooks` are Claude Code hook events, so the profile carries them as they are, for a harness that can run them. A reviewer's session on Claude Code denies `Agent`, `Task` and `Bash`.
- pi is the second harness (shep-pm/shep-kelpie#130), chosen over the Codex CLI on a local model by one run of each on the same issue (Facts). Each call carries its harness, and for pi the server its model is on, and a port, `Routed`, sends it to that harness's adapter. An agent error names the harness's program, so a Claude Code turn reads `claude failed: ...` and a pi one `pi failed: ...`. A pi agent takes `url` and `context` as an endpoint reviewer does, and its usage is `none`, so it holds its lease for each whole call, or a `gateway` in place of `url`, which holds none (below).
- A project can name a host that runs its end-to-end tests (shep-pm/shep-kelpie#415, built in slices, the settings and the door's honest answer in #520). A worker's sandbox reaches only GitHub and the project's `allowed_domains` and binds nothing local, so it cannot run them; the maintainer decided kelpie runs them on a host the project names, through the dog.
  - `host` is an ssh alias, which keeps the key, user and address in the maintainer's ssh config, and it cannot start with `-`, so ssh never reads it as an option. The project's script runs there as the alias's account and a worker edits that script, so the host must be disposable: the schema and the README say so.
  - The ask a worker sends is `take: "e2e"` and the folder it runs from, never a host, command or results folder, so a worker cannot aim the run: the dog finds the project whose `worktrees` folder holds the folder, once links and `..` are resolved, and reads the table the runner recorded in that project's `e2e.json`, which the worker's fence cannot write.
  - A path that names no project, or a project with no `e2e.json`, is told it has no e2e host (`kelpie lease e2e` exits 78); a configured one is granted the run.
  - The dog finds the project folders under `kelpie` in the shepherd's home and never reads `KELPIE_HOME`, since shep starts the adopted dog without it; a runner started with another `KELPIE_HOME` records `e2e.json` where the dog does not look, so it logs a note saying `lease e2e` will report no host.
  - The run is #521: a configured project's ask is granted its host's lease, the worktree is copied out, the command runs and its output streams back, and the results come back (see The e2e run under Facts). A dog from before #521 still answers a configured project that it cannot run e2e yet.
- pi runs every role inside kelpie's sandbox with a home kelpie writes beside the call's settings: one provider, `kelpie`, with the one model, and the sessions folder, the only part pi may write besides two lock folders.
  - It loads none of the maintainer's or the repo's extensions, skills, prompt templates or project files, and reads the repo's AGENTS.md and CLAUDE.md. Its tools are an allowlist, `--tools`, and the rest is off by flag.
  - The cargo-test lease reaches a pi worker the way it reaches a Claude one: the dog's door is in the fence's sockets, `KELPIE_LEASE_SOCKET` is in the fence's variables, and the instructions that say to run tests under `kelpie lease run cargo-test` are the ones pi gets with `--append-system-prompt`.
  - A pi call's sandbox allows no host of the model server's: the call's model traffic goes to a forwarder kelpie runs outside it, which passes only the chat completions call (#235, Facts).
  - A fenced call loads one extension, kelpie's, that runs `kelpie confine` on each write and edit and `kelpie guard` on each command, as Claude Code's hooks do, and refuses any other tool that is not a read. Any failure of the check refuses. It resolves a path the way pi's write and edit do (odd spaces folded, a leading `@` stripped, `~` expanded) and refuses a `file:` URL, which pi would open as the path it names and `confine` would read as a file in the worktree.
  - pi takes kelpie's session id as its own (`--session-id`), so a resume is the same call shape as a new session, and a resume onto an id with no session file is `NoSession`. Kelpie's instructions are passed on every call, since pi builds its system prompt afresh each time. A step's `/<plugin>:<skill>` becomes pi's `/skill:<skill>` with that skill's folder.
  - pi runs no Claude Code hooks, so a project whose implementer is on pi and that names `worker.guard_hooks` stops when its settings load, and a turn checks again before it runs. The prefix deny rules Claude Code also gets have no pi equivalent; `kelpie guard` covers the same commands.
- Codex is the third harness (shep-pm/shep-kelpie#233), on the ChatGPT plan, for the worker and reviewer sessions. A project opts in per role by naming an agent file with `harness: codex`, which takes no `url` or `context` and reads its usage with `codex`, so the plan's 5-hour and weekly windows pace it beside Claude's. Each call is one `codex exec --json`, a resume `codex exec resume <thread>`, since Codex names its own sessions: kelpie keeps which thread each of its session ids is, and the thread's tokens so far, beside the call's settings and out of the call's reach. A turn reports the thread's running total, so kelpie counts the difference (Facts).
- Kelpie has its own Codex login, signed in by the maintainer with device auth, in `codex_home` (`<kelpie home>/codex` by default), decided 2026-10-01, because run on `~/.codex`, Codex copied the maintainer's whole session history into each call's database.
  - Each call runs with `CODEX_HOME` set to a home of its own beside its settings, which holds its sessions, database and logs, with the login's `auth.json` linked in; the maintainer chose that over one home every call shares, where one project's worker could read and edit another's Codex transcripts.
  - Kelpie never reads the login. The sandbox lets a call read `auth.json` and nothing else under `codex_home`, read nothing under `~/.codex` or `~/.agents`, and reach `chatgpt.com` only.
  - In its own home it writes only `sessions`, `archived_sessions`, `db` (Codex's databases, by `sqlite_home`), `log`, `thread-writer-locks` and `installation_id`. Not `tmp`, which Codex puts on every hook's PATH (Facts).
  - Everything else there is Codex's to load, not the call's to write: the login, `config.toml`, `hooks.json`, `.env` (whose variables reach every hook's shell), `AGENTS.md` and `AGENTS.override.md`, rules, skills and the model catalog. It is an allow-list of writes rather than a list of those, since the control session's review of #255 found `.env` and `AGENTS.override.md` missing from that list: a worker could have set `ZDOTDIR` to a `.zshenv` that made `confine` and `guard` exit 0 on its next turn.
  - `codex_home` may not be the home folder, a folder above it or anything in `~/.codex`, and a runner reads it when it starts.
  - `auth.openai.com` stays out: a refresh could not be saved through the read-only link, and a lost refresh token signs kelpie out. The usage read runs outside the sandbox on `codex_home` before each dispatch and refreshes a login near its expiry there.
  - `ports::Unreadable` adds `codex_home` to every call's unreadable paths, so Claude Code and pi calls leave it alone wherever the setting puts it.
- A Codex call runs with Codex's own sandbox and approvals off under kelpie's, loads no user config or rules, searches no web, and turns off Codex's features that reach past its tools: its own crew, apps, plugins, browser and computer use, image generation, memories, shell snapshots and the rest of `FEATURES_OFF` in the adapter. `unified_exec` cannot be turned off from a call (Facts).
  - A fenced call runs kelpie's checks as Codex's `PreToolUse` hooks, trusted for the call with `--dangerously-bypass-hook-trust`: `kelpie confine` on `apply_patch`, the tool Codex writes files with on ChatGPT's models, and `kelpie guard` on `Bash`, every command.

## Review

- The review (ADR 0006, shep-pm/shep-kelpie#314). Once the worker's draft pull request is open, `Phase::Review` runs before the merge gate, and no reviewer reads a head until CI has passed on it (ADR 0008, shep-pm/shep-kelpie#423): one pass down the project's reviewers, each run once, in order.
  - A round with no findings goes straight to the next reviewer. One with any finding sends all of that reviewer's findings, at its own severity, to the worker's next turn as a file, and the next reviewer reads the fix.
  - Nits (LOW) get that fix turn too (ADR 0007, shep-pm/shep-kelpie#354), because a round of nits that went straight on left three of cubic's P3 threads open on shep-pm/shep#707, a pull request the merge ruling called clear.
  - A fix turn sent only nits starts nothing new: the pass goes on to the next reviewer as after any fix turn, no reviewer reads again and no bot is summoned again because of it, and the head it pushes, when it is the worker's own as for `sent_unread`, is kept in the work item's `nit_fix_heads` (state file version 14).
  - A bot that has read the pull request before (its `bot_reads`) and whose review lands while the head on `origin` is one of those has its nit threads left open rather than sent, so a bot that reviews every push cannot loop on nits; its first read sends them as any round's, so a bot listed after a reviewer whose nits were fixed still has its own nits fixed. A bot reads once a pass, so the guard acts on a later pass that finds such a head, and on the late reads of shep-pm/shep-kelpie#351.
  - Before a round starts its reviewer, or summons its bot, the round waits for CI on the pushed head it would read (ADR 0008, shep-pm/shep-kelpie#423), since a model's read and a bot's window are scarce and a red run is a sure defect that costs neither. Measured on a project's pull request on 2026-10-10: CI failed in 1.5 minutes, the local reviewer spent 8 minutes reading that red head and sent 4 findings, and the fix turn pushed a head that was red again, on which kelpie summoned a review bot.
  - The wait is the gate's own read: the run on the head the round found the worktree at (the pushed head, checked as before), taken two minutes after kelpie first saw that head, pending waiting and green going on. The round saves it as `ci` (state file version 23) with the head, when kelpie first saw it and whether it passed, so the reviewers after it on the same head do not wait again, and a fix turn that pushed nothing leaves the head so. A fix turn's head, a nit-only fix's included, is a new head and waits in turn.
  - A red run is the worker's CI fix turn before any reviewer, led by the `ci_fix` step's skill and counted toward `ci.fix_attempts` as a red run after the review is (a head left red by a fix that pushed nothing, or a red run past the cap, raises the `still-red` ruling as in CI and the merge); the work item's `resume` sends the fix back to the round that was waiting, not on to CI, so the fix waits for green and is read.
  - With `ci.block` off the round starts at once. A pass that starts from a head CI just passed, an older state file's bots owed after green CI, is marked green and does not wait. An adopted pull request owed a bot waits like any other.
  - `doctor` names a repo whose workflows that run on a pull request all skip drafts, by a job condition on every job or a trigger `types` list that never fires on one (`ci on drafts`); a draft whose rollup is only skipped runs (`Checks::Skipped`) is not green, and a ready one is, since the pull request is a draft until a bot's round marks it ready and no run would come to wait for.
  - A head with no check (#1194): a repo whose `origin/main` holds no workflow that runs on a pull request has no run to wait for, so the head goes on as `Checks::Skipped` at once, in the gate and in this wait, and `doctor` names it (`ci on pull requests`). A `push` trigger counts as running on a work branch only when its `branches` list is absent or matches more than `main`. With one such workflow and no check within `ci.queued_minutes`, the item parks on a `no-checks` ruling (state version 84): a yes passes that head as skipped, a no waits again, and a new head starts the wait over. The alternatives were waiting forever, as before, and skipping after the cap with no ruling.
  - The wait is `ci` in the timings and the reviewer's read is `review`, so the six phases still sum to the wall time.
  - After the last reviewer the work item goes to CI, which finds the head already green unless a push moved it, and whatever the last fix leaves is what CI and the merge see.
  - There is no loop, no round guard and no judge: the maintainer's ruling is that reviewers go in series and whatever the pass ends on is what it ends on, and measured, the gain is in the first two reads, a judge kept most of the findings that were not real, and a loop's "two clean rounds in a row" spent its rounds on nits (Facts).
  - A pass starts again from the top only on a new head that needs it: the change a merge ruling's `rework <note>` asks for, an accepted foreign change, or a rework of the pull request.
  - A merge ruling's `no <note>` is a fix turn instead (ADR 0007, shep-pm/shep-kelpie#354): its fix goes to CI and back to the merge ruling with no new pass, since on shep-pm/shep#707 a no asking for three nits restarted the pass, four reads and 30 minutes before the next ruling.
  - A merge ruling that warns of a pass no reviewer read, a listed bot's open threads or a head nothing vouches for (`unread_head`) cannot be cleared by a fix no reviewer reads, so there `no` starts a new pass as `rework` does, and the question says so.
  - The fix a `no` sends to CI leaves the head the ruling was about in the work item's `noted_from`, which any answer to the next merge ruling replaces. A question the worker asks in that fix turn resumes to CI, not to a pass. The next merge ruling, on another head no round read that kelpie sent unread itself (so the worker's own push, not someone else's), sets `note_fix` and says the head is the worker's fix for the note and no reviewer read it. - A reviewer is an agent file whose `role` is `reviewer`.
  - Its `harness` is `claude-code`, `codex` or `pi`, a fresh session on its `model` and `effort` with the `Review` tool kind on every harness (Read, Grep and Glob, no commands, no crew), or `command`, a command of the maintainer's on the qwen script's contract, or `endpoint`, kelpie's own OpenAI-compatible reviewer, each of those two with its `lease`, `ollama` and `ollama_model` and the checks a runner's start makes, or `bot` (below). An agent's file says what runs it as one enum: a session, a command, an endpoint or a bot.
  - A session's body is its prompt, with `{{BASE}}` and `{{DIFF}}` filled and the diff after a body that has no `{{DIFF}}`, then the issue's acceptance criteria as every reviewer gets them; a session with no body, and a command or bot with one, is refused, since a command writes its own prompt.
  - An endpoint's body is optional: with none its system prompt is kelpie's fixed text, and with one the body replaces the opening sentence and the paragraph on what to report, while kelpie always adds the diff-format paragraph, the answer format (`SEVERITY|path:line|what|why`, `CLEAN`, which it parses) and the criteria, in that order after the body. An endpoint's chunks are cut by kelpie, so a body naming `{{BASE}}` or `{{DIFF}}` is refused naming the file.
  - A reviewer's `paths` limit it to pull requests changing a matching file, read with `git diff --name-only` against the round's base.
  - A round reads the pull request's own change from the merge base of that base and the reviewed head (`<base>...HEAD`, shep-pm/shep-kelpie#484), in a session's diff, a command's `--diff` ref (the merge base itself, which its script diffs against the worktree) and hunk, an endpoint's diff and the `paths` match, so a branch behind `main` is not reviewed as undoing what `main` gained since it was cut; an adopted item's base is a commit on the branch, so it reads what came after it, and `{{BASE}}` stays the base the item names.
  - A reviewer's prompt carries the issue's title and acceptance criteria, the section under an "Acceptance criteria" heading or the whole body, cut at 4,000 bytes so a small model keeps room for the diff: in a session's prompt, in an endpoint's system prompt, and in a file a command finds in `KELPIE_REVIEW_CRITERIA`. So each reviewer checks the work against the criteria in its own pass, and there is no separate whole-issue check.
- `second_look: true` runs a session twice before one fix turn, the second fresh session shown the first's findings and asked only for what it missed, in kelpie's own words; its two looks are kept in state as the round and then a `second-look` stage, so a restart resumes at the look it was on. A second look whose call keeps failing lets the first's findings go on alone. Kelpie ships `defect-hunter`, Opus 5.5 at high, the maintainer's defect prompt word for word as its body (a test pins it), with a second look: measured, the best single reader, and the second look added 11 points at 95% precision (Facts).   - The badge on a finding, `P0` to `P3`, is its severity as cubic's level is.
  - Its `reviews_on_ready` says marking ready is its summon (Facts): then the round waits for its lease with the draft unmarked, marks it ready as the summon, posts no comment, and never sends that summon again by comment, so one Codex never answers is passed over at two hours. A list with another bot before one that reviews on ready is refused at load, since that bot's mark-ready would draw its review outside its lease.
- A bot's `rounds` caps its reads of a work item's pull request across passes, counting the reviews it gave before a rework or an adoption, and is unset by default. An adopted pull request with no review asking for changes starts a pass of the listed bots alone, `bots_only` in its review, and each listed bot owes it a summon of kelpie's own (`summons_owed`, per bot): until that bot answers one, which asks for a full review where it read the pull request before, no review of its from before the adoption stands for its read and its `rounds` does not pass it over; with no bot listed it goes straight to CI.
- Two kinds of reviewer share their output (shep-pm/shep-kelpie#123): a finding with a severity, file, line and text, and from there the worker's fix is one path. A local reviewer or a session hands its findings back when the call ends; a bot needs a lease on its window, a sign that it heard, a re-send when it did not, threads to resolve, and a head its review covers. The bots follow one script on GitHub, so the bot side is one provider, the runner's round, with a profile per bot for what differs: its login, its label and full-review comment, how its answers read (heard, reviewed, refused, done), how a thread's severity reads, and the lease it spends. Profiles and their parsers are code, tested against the bot's recorded output.
- A reviewer's attached test is run twice and blocks nothing yet (shep-pm/shep-kelpie#518, parent #356).
  - The `TestRunner` port runs `ci.test_command`, `{test}` and `{name}` filled in, in the worktree. Its real adapter wraps the command in the same `Sandbox` the agents use, under the worker's fence (`WorkerProfile::reach`) and never the maintainer's reach, since a model wrote the file and a model wrote the code under it.
  - It takes the `cargo-test` lease through the door from the runner's own process before the sandboxed command starts, holds it while the command runs and gives it back after, so the 10-minute ceiling counts from the grant and not from the queue.
  - A run is `passed`, `failed` with the last 2 KiB of output (stderr joined to stdout where it was written), `timed-out` or `not-run` with a reason (no fence, no sandbox, no dog, a shell that cannot find the command, a path a shell would read, a worktree off the head or already holding another file of that name).
  - Before: in `send_findings`, once `origin`'s head is read, each finding with a test has its kept copy written into the worktree at its path through the link-safe `worker_folder`, run, and removed with any folder made for it. A file already there with the reviewer's exact text is the worker's own committed copy and is run as it is and left. A record in the worker folder (`test-placed-<issue>`) stands while the file is in the worktree, so a kelpie stopped mid-run removes the stray file at the next round and notes it.
  - After: in `fix_ended`, only when the fix moved the head and the worktree holds that head, the worker's own commit; any other head is not run and the step report counts the tests it left.
  - Each check is a `test_checks` entry on the work item (the finding's file, line and what, the round, `before` and `after`), shown by `status` and carried by `FixPushed`. Failed then passed reads as verified, passed before as not reproducing the finding, failed after as still failing. Only a failure after the fix acts: the worker is sent back once (`sent_back` on the check; a prompt from `still_failing_prompt` naming the test's path in the build folder and the output tail), the test runs again once that turn pushes, and a second failure raises `Stuck::TestStillFails` naming every test of the round still failing, with the review and the head. A turn that pushes nothing raises `fix-not-pushed` first. A timeout or a run that did not happen never sends back or raises. Nothing is posted on the pull request.
  - Known gap: a run happens inside the step, so the runner is busy for up to the ceiling plus the wait for the lease; moving it off the step is open (#356).
- A confirmed finding left unfixed at merge becomes a follow-up issue (shep-pm/shep-kelpie#142).
  - A reviewer's finding goes to the worker, which fixes it; one the worker leaves as out of scope goes, in the findings file's own format, into `deferred-findings.md` beside the findings file in its build folder, which the findings file's header names.
  - Once the pull request merges, kelpie reads that file once, before it removes the build folder, and files each finding as an issue on the project, linking the pull request. An open issue whose body names the file, and whose title matches or whose body says the same thing, gets a comment instead of a second issue.
  - The project's `git.issues` decides, whatever `git.merging` is (shep-pm/shep-kelpie#380; before it, `merge_authority` decided both). Under `ask`, the default, a `follow-up` ruling comes first, raised after the merge, and a yes files them `ready-for-agent`, onto the board, since that yes is their triage, and a no drops them. Under `skip` the file is not read, nothing is filed and the findings stay in the review.
  - Under `file` they are filed with no ruling as `needs-triage`, off the board until the maintainer reads them and labels them `ready-for-agent`, and each body says so (shep-pm/shep-kelpie#384: on the maintainer's live project three in a row filed `ready-for-agent` were false findings, each costing a worker run and a question ruling before anyone noticed).
  - A repo without `needs-triage` gets it before the first issue that needs it, as `agent:` labels are made (shep-pm/shep-kelpie#381): only added, never recoloured or removed, and one in another case counts. A yes to the refusal ruling below only tries again, so it leaves `file`'s findings `needs-triage`.
  - Only what kelpie itself sent the worker is filed: each finding sent to the worker is kept on the work item, and a line in the file counts only when it names one of them by file, line and what, and the issue carries kelpie's text, not the worker's, so a worker cannot put its own words on the tracker. A nit is never held, so a nit the worker defers is dropped rather than filed (shep-pm/shep-kelpie#354).
  - If the forge keeps refusing for six hours from its first refusal (issues off, a missing label, a rejected body), a `follow-up` ruling lists the findings and the reason: a yes tries again for another window, a no drops them. Passes do not count, only time, so a short outage of the forge's own costs nothing.
  - A crash between opening an issue and saving that leaves a redundant "confirmed this too" comment on the new issue at the retry, which is accepted. A finding whose text names a folder on this machine is not posted (the forge guard refuses it), so it is left out and counted in the step's report rather than retried.
  - Not built: a reviewer that answers after the merge, since nothing watches a pull request once its work item is gone.
- Comments from people with write access reach the worker (#368, `crates/runner/src/runner/talk/mod.rs`).
  - Trusted authors are the repo's owner, members and collaborators, as the forge's `authorAssociation` says (`Standing::Writer`); the listed review bots stay on their own path. Any other App or person is ignored, and the log names the comment once. Kelpie's own comments are recognised by the ids it posted and by its thread replies' exact texts (`Fixed.`, `Not fixed: ...`, `Not addressed: ...`) and the `Declined: ` opening of a decline, whose reason varies.
  - One GraphQL read, `Forge::talk`, returns the conversation's comments and every review thread with their authors' standing. It is made only where kelpie already reads a pull request: at the start of a review round, at green CI, and while a merge ruling waits (every 5 minutes, the throttle of a late read). It adds no reads while a turn runs or CI is red.
  - A new comment or thread remark from a writer is a request. Requests are batched into one resumed turn, as a noted turn: the prompt lists numbered requests and asks for a `<kelpie-question>` block when one is ambiguous or architectural, which raises a `question` ruling whose answer resumes the fix. The answered turn's prompt repeats the `thread <n>` line instruction, so the threads are replied to as the fix names them. Review threads are answered as #367 does: `thread <n>: fixed` / `declined: <reason>`, kelpie replies and resolves fixed ones, and an unmentioned thread is "Not addressed" and stays open. A conversation comment gets no reply.
  - The fix goes to CI and back to the merge ruling with no new pass (it reuses `noted_from`, so the ruling says its head is the worker's fix for a note or comment and no reviewer read it). A fix from a comment read at a round start returns to that round's review.
  - A writer's comment that lands while a merge ruling waits withdraws the ruling (label off, log and webhook say why) and is handled as that ruling's `no <note>`. A reply in the ruling comment's own thread that opens with a number or `yes`, `no` or `rework`, or any text for a worker's question, is #398's and is left to it while the App covers the repo; on a merge ruling on a pull request, any other comment from the login the ruling mentions is read here and #398 stays silent on it; on any other ruling, and on an issue's thread, #398 tells the author how to reply as before.
  - Bounded: `TALK_ROUNDS` = 3 comment-driven fix rounds per work item (`rounds` in `talked`). A fourth read with requests raises a `question` ruling that says so; the maintainer's `answer` is what the worker then receives.
  - An adopted or reworked pull request hears its first read quietly: the comments already there are marked heard and sent to no one. So does a work item with a pull request that an older state file loads (`talked.quiet`, set at load for a file of version 37 or older).
  - A comment round's turn may push nothing (the worker declines): `awaits_a_push` is false while `talked.head` is set, so an adopted or reworked item is not sent back for it.
  - Not built: review-summary bodies with no inline thread, reads while a turn runs, replies on conversation comments, and more than 100 comments or threads on one pull request (the query's `last`/`first` limit).

## CI and the merge

- The merge gate (shep-pm/shep-kelpie#9). After the review's last reviewer, kelpie waits for CI.
  - A red run is the worker's next turn, naming the failed checks, led by the `ci_fix` step's skill; a second red run on a head the worker left alone parks it on a `stuck` ruling for `still-red`.
  - `ci.fix_attempts` caps those fix turns per work item (shep-pm/shep-kelpie#380): once the work item's `ci_fix_turns` count reaches it, the next red run parks it on the same `still-red` ruling, its `fix_turns` naming how many it had and its question saying so, with no fix turn; `0` parks on the first red run, and `-1`, the default, sets no cap. The reason was reused rather than a new one added, since a yes, a `no <note>` and the project manager's retry mean the same on both: look again, or send the worker a note. A merge-queue removal's fix turn is not counted.
  - A green run on a branch that has the latest `main` raises the merge ruling, or merges under `auto`. A branch without it is caught up by kelpie first: rebased onto `main` and pushed with a lease on its head, or, where it holds a merge commit or commits that are not kelpie's to rewrite (an adoption's), merged with `main` and pushed without force.
  - A conflict is the worker's next turn (shep-pm/shep-kelpie#61), naming the files: it merges `origin/main` in and pushes, so nothing it pushes is forced. A turn that leaves the same head, or a conflict on the same `main` again, parks it on a `stuck` ruling for `rebase`.
  - A project says whether it runs CI with `ci.block`; with it off, kelpie reads no checks and `ci.fix_attempts` does not apply (Facts).
- Merge authority is a project setting, `git.merging`: `auto` or `ask`, and required. `ask-surface` (ask only when a pull request touches operator-facing surface) is refused.
- Under `ask`, a yes merges only the head it was asked about, while CI on it is green and it has the latest `main`. Otherwise kelpie withdraws the yes, reruns CI, and asks again. The merge is `gh pr merge --merge --match-head-commit`, never a squash, and kelpie then removes the worktree, both branches and the build folder. Kelpie puts `ready-for-human` on at the merge ruling.
- `auto` (shep-pm/shep-kelpie#83), chosen over running shep's merges from a Claude control room so the merge rules stay in kelpie's code. It replaces the merge ruling and nothing else.
  - Where `ask` would raise it, `auto` merges by the path a yes takes: the head the gate passed, CI green on it, the latest `main`, the review pass read, a head a round read or kelpie sent to CI unread on purpose (shep-pm/shep-kelpie#290, Review), no listed bot's threads unaddressed (shep-pm/shep-kelpie#350), and a merge commit. Every other ruling still asks. Kelpie never puts `ready-for-human` on for the merge.
  - A merge that no longer holds, because the head moved, CI stopped being green or `main` moved, goes back to CI as a withdrawn yes does, and CI catches the branch up. A merge the forge refuses takes that path once; a second refusal on the same work item parks it on a `stuck` ruling for `merge-refused`, and any answer to it gives the next refusal its catch-up again. Its pull request comment names the head and leaves the forge's reason out, since that text is not written for strangers.
  - A merge the gate started under `auto` goes ahead only while the project is still `auto`: a project switched back to `ask` goes back to CI and gets the merge ruling. The switch back to `ask` is read after the pull request's state, so a merge that landed before the switch still gets its notice.
  - Under `ask` a yes on a `rebase` or `still-red` ruling vouches for whatever head the gate sees next, because the merge ruling follows; under `auto` nothing follows, so the yes reads the branch's tip, and a tip the gates never saw goes back through a pass of the review. The same holds for a head the gate finds with none known, such as one a yes under `ask` vouched for before a restart onto `auto`.
  - `status` shows it as `merging`. `git.merging` decides only who merges, the head regate and this withdrawal; the cases that still raise the merge ruling under `auto` (no reviewer read it, a bot thread above a nit open, an unread head, a `no`'s fix, a late round's fix) are safety gates, not settings, and each ruling names which one raised it. Whether deferred findings are asked about is `git.issues` (see Review).
- After an automatic merge kelpie sends a notice naming the project, the pull request, its issue and the merged head (shep-pm/shep-kelpie#118). A notice is not a ruling: it has no id, takes no answer, goes to the webhook alone, and is only logged where there is none, and is saved with the merge so it goes out once, retried like a ruling's post and never ahead of one. A merge at the gated head that a restart or a lost answer hid, found merged on the next look, still gets its notice, and so does one that lands after kelpie read its error, since kelpie records the head it tried.
- A merge queue on `main` (shep-pm/shep-kelpie#213): kelpie queues the pull request and waits on it, skipping every gate while the queue holds it, and a removal goes back to the worker like red CI (Facts).
- The foreign-change check covers the head (shep-pm/shep-kelpie#69). Kelpie records the branch's head on `origin` as each worker turn ends, and the head its own catch-up push leaves, so a worker's merge of `main` and kelpie's rebase are never foreign. At the gate, once the forge's head matches `origin`, any other head, or a label or ready state kelpie did not set, parks the worker on a `foreign-change` ruling that names the commit. A yes moves the worktree to that head, refusing if it holds work not pushed, and sends it through a pass of the review, the listed bots included, before the merge ruling. Under `auto` a yes vouches for no head the gates did not see. A commit pushed while the worker's turn runs is read as the worker's, and gets the gates that turn's code gets.
- A pull request the maintainer merges by hand ends its work item with no merge by kelpie. One closed without merging parks the worker on a `stuck` ruling for `closed`.
- A work item saved before the gate existed stays with its worker until `shep kelpie gate` sends it in. The trigger takes only an item whose turn has ended with a known pull request.
- Reworks (shep-pm/shep-kelpie#53). A rework makes a work item of an open pull request from a `kelpie/<issue>` branch on the repo itself, opened by the account kelpie acts as (`gh api user`, read once a run), dropped or finished alike. A collaborator's or a fork's pull request on such a branch is not kelpie's, and the poll leaves it alone.
  - The pull request asks for one: `ready-for-agent` on it, since kelpie opens pull requests under the maintainer's account and GitHub won't let an author request changes, or a review requesting changes from anyone else with a hand in the repo (its owner, a member or a collaborator, since anyone can review a public repo's pull requests).
  - The runner checks its open pull requests on the board's poll, before any ready issue, and `shep kelpie rework <pr>` asks by hand. A rework that asks but cannot start, because the forge failed or a label would not come off, is passed over for that poll. Each review that started or was refused a rework is recorded and never asks again.
  - It is refused while the project has `concurrency.active_items` open or one for its issue, and when the latest review has no body and no unresolved comment; a refusal the pull request asked for goes to it as a comment, with the label off.
  - The worker starts a new session on the branch as `origin` holds it, so commits the maintainer pushed stay, and it pushes without force. Its first turn names a file in its build folder that holds the review's body and its unresolved comments verbatim, each with its file and line. The turn goes to a pass of the review and then every other gate. Its issue stays finished, so only the trigger brings a rework, never the board.
- The triage labels say whose turn a pull request is. A rework takes `ready-for-agent` and `ready-for-human` off as it starts. Kelpie puts `ready-for-human` on, and takes `ready-for-agent` off, at the merge ruling and whenever a work item ends unmerged, and takes `ready-for-human` off when an answer sends the worker back to work. The gate ignores `ready-for-agent` added while a work item is in flight, so a second ask waits for that item to end. The board's `gh issue list` never lists a pull request. `shep kelpie add` and the issue writer are the only places kelpie creates a label.
- Adoptions (shep-pm/shep-kelpie#84). An adoption makes a work item of an open pull request kelpie didn't open, so the maintainer's other sessions can hand theirs over.
  - The maintainer adopts one with `shep kelpie adopt <pr>`, or with `ready-for-agent` on one whose branch isn't `kelpie/N`, seen on the board's poll. Kelpie refuses, with a comment, one that is closed or merged, comes from a fork, merges into a branch other than `main`, has another author than the account kelpie acts as, or names no issue it closes; a refusal from the label takes the label off. The lowest issue it closes becomes the work item's issue.
  - Adopted pull requests wait in the state file for a free slot, one at a time, and one closing an issue whose work item is open waits for it to end, and go before reworks and the board; `status` lists them as `adopted`. One the label adopted leaves the queue when the label comes off, and one merged or closed while it waits leaves without a comment.
  - One starts on a fresh worktree of its branch as `origin` holds it, with its labels, ready state and head taken as kelpie's own, so nothing already there reads as a foreign change, and `ready-for-agent`, `ready-for-human` and `review please` come off, so no push summons a bot outside its lease. With no review asking for changes it starts a pass of the listed bots alone, or goes to CI with no bot listed.
  - The worker's first turn is whatever the gate first sends it, behind a file in its build folder holding the pull request's title and body and its issue. A latest review requesting changes from its owner, a member or a collaborator goes in that file too and is the first turn at once, followed by a pass of the review. The review diffs from the head the pull request arrived with, so only the worker's own commits are reviewed.
  - A branch behind `main` is merged, never rebased, and nothing on it is force-pushed. The branch's owner may still be pushing, so a push counts as the worker's only when the worker's worktree holds it, and one found before a worker's turn sends the work item to the gate instead of the turn. Either way a push from anyone else parks it as on kelpie's own branches. The merge follows the project's `git.merging`.
- The project manager's merges, rebases and pushes are the runner's own `gh` and `git` calls, plain child processes, which the worker's settings file, sandbox and denylist never reach.

## Rulings

- Six ruling kinds (shep-pm/shep-kelpie#330, ADR 0006): `merge`, `question`, `stuck`, `agent-files`, `foreign-change` and `follow-up`.
  - `stuck` carries its reason as a field, one of `rebase`, `still-red`, `merge-refused`, `closed`, `fix-not-pushed`, `unpushed`, `turn-timeout`, `turn-failed` and `over-budget`, each with its own question, pull request comment and effect for a yes and a no, and any further text in `why`.
  - ADR 0006 named five kinds; `follow-up` stays its own, by the maintainer's decision, since under `ask` the findings a merged pull request left still wait for a yes before they are filed.
  - No command takes a kind's name: `status` shows a `stuck` ruling's reason beside its kind. The project manager's stuck wakes and retries read the same reasons: `turn-failed`, `turn-timeout` and `still-red`.
- A ruling is a log line, a status entry and a webhook post, all carrying the same question and the triggers that answer it. A no with a note is the worker's next turn. The pull request gets a comment for every ruling but a merge (shep-pm/shep-kelpie#89). It says what happened and that it waits on the maintainer, and names no command: `ready-for-human` already says the pull request waits, and the webhook carries the question.
- A ruling is named by the number of its pull request, or of its issue while it has no pull request (shep-pm/shep-kelpie#507, #508, #509, which reopen #119 on purpose and retire its counter ids). A work item parks on one ruling at a time and GitHub numbers issues and pull requests from one sequence, so within a project a number names one open ruling.
  - `Ruling.id` stays a field and equals that number. The `rulings/<id>` claim files, `last_ruling` and `RulingIds` are gone, since nothing needs an id unique across projects once a number names the ruling.
  - State version 38 renames the open rulings saved under counter ids when the file loads. For each work item the ruling takes its number, and the keys that name a ruling (`heard`, `unmentioned` and the work item's `Phase::Ruling`) follow it. A file already at 38 is not renamed. Two rulings on one number keep the one the work item waits on and keep the other under its old id, unless that id is a number a kept ruling holds, which drops it. `last_ruling` is dropped from older files.
  - Old ids stop working. An answer file left under an old id is read once by the first pass after the load, and answers the ruling that id became. A later file under an old id, and `rule 40 yes` for a counter id that is no ruling's number, is refused with a line saying rulings are named by number.
  - `shep kelpie rule <number> <words>` reads the ruling's kind from its project's state file: `yes` and `no <note>` for a yes-or-no ruling, those and `rework <note>` for a merge ruling, any text for a question, a lone `yes` included, and the older `answer <text>` still read.
  - `rule 427`, `rule #427` and `rule <project>#427` all read a number, and a reply on ntfy or in the thread reads `427 yes`. A number two projects have a ruling on is refused naming both; from a clone the clone's project is looked at first. `rule` alone, in a terminal, lists the rulings waiting and asks which and how; without one it lists them and exits non-zero.
  - `Ruling.raised` records when it was raised, and an answer that carries a time (a reply, a GitHub comment) is refused when written before it, saying the ruling changed and what it asks now. A terminal answer is taken as given.
- `shep kelpie <verb>` (shep-pm/shep-kelpie#119). Every trigger a runner takes is also a verb of the adopted kelpie, sending the trigger `shep trigger` sends, which keeps working. `-p <project>` goes anywhere before a `--`, before the verb included, and for `rule` before the answer's second word, so a note can carry a `-p`. Without it the project is the one whose `repo` is the folder's git top folder, or, for a worktree (kelpie's own included), the checkout its common git dir belongs to; with no match the error lists the projects. `add <issue>` puts an issue on the board and `add [<project>]` registers a checkout, told apart by an all-digit argument. `status` with no `-p` stays every project's.
- Rulings reach the maintainer by one webhook, until shep can carry a question itself (shep-pm/shep#689, shep-pm/shep-kelpie#333, ADR 0005).
  - It is named in kelpie's own settings, its `[kelpie]` section of `dogs.toml`, which every project shares: a `[webhook]` table with `kind` (`discord` or `ntfy`) and `url`, both required. With none, a ruling reaches the maintainer in the log, `status` and `shep kelpie rule` only, and the runner logs one line at start saying so.
  - A failed post is logged and tried again after a minute, doubling to at most half an hour, and a ruling counts as alerted only once a post lands, so a restart between the post and the save can post it twice. With no webhook nothing is posted, so no ruling waits on an alert and none holds back the next.
  - The URL is a credential: it reaches `curl` on stdin, never in its arguments, curl's own messages are dropped, and no error, log line, status or comment carries it. Plain `http` is accepted only for a stand-in on the same machine.
  - A long question is cut in the middle to the channel's limit, keeping its start and the triggers at its end (Facts).
- Rulings are answered from ntfy (shep-pm/shep-kelpie#111). An answer that acts proves itself with the maintainer's authenticator code, decided by the maintainer over a first build that posted a one-time code on the alert: that code sat on the topic it guarded, so anyone who could read the topic could merge. The code is RFC 6238 TOTP (HMAC-SHA-1, 30-second steps, six digits).
  - `shep kelpie totp` draws the 160-bit secret once into `<kelpie home>/totp/secret` (the folder 0700, the file 0600) and prints it as an `otpauth://` URI and a terminal QR code to scan; `shep kelpie totp --rotate` draws a new one, written beside the old and renamed over it, the folder synced after so a crash cannot bring the old one back (a first `shep kelpie totp` links its file into place instead, so two at once keep one secret), and every runner reads the file afresh for each reply, so the old secret's codes stop at once. A secret file, or a totp folder, anyone but its owner may read or write stops the runner. Workers are denied the totp folder like the other credentials.
  - A reply is `<id> yes <code>`, `<id> no <note> <code>`, `<id> rework <note> <code>` on a merge ruling, or `<id> <answer> <code>`, the code always last, and may still name the project first; an unnamed one goes to the runner its id was given to, and one for an id two projects hold is refused with a line asking for the project.
    - The part after the project is read by `rule`'s own parser, so a change to `rule`'s grammar reaches ntfy replies too. The code is checked against the time ntfy took the reply, which no sender can set, and taken in that step and the one before.
    - A reply written as the terminal command, `shep kelpie rule ...` or `shep-kelpie rule ...`, reads as the reply without those words (only the exact words go, so a project named `shep-kelpie` is still addressed by name).
    - A reply with a right code that names no ruling kelpie can read answers nothing, spends its code, and gets one line on the topic saying so; every project's runner reads the reply and posts it under its own title, as for a post too long to read, and a reply naming another project's ruling stays silent.
  - Every code the maintainer sends is on the topic afterwards, so every right code anywhere in a post is claimed before anything else about it is read: whether answers are on, whether it is kelpie's own, which project it names, how old it is, or how the code was typed.
    - Every text the post carries counts, its title, tags and attachment name included, and in each every decimal digit of any script is taken in order with whatever stands between dropped, so `123-456`, `123 456`, full-width, Arabic-Indic or math-bold digits all spend the code.
    - A post spends the codes of three steps: the one before and its own, which `verify` takes, and the one after, from a phone whose clock runs ahead, which a replay could send once that step comes.
    - A secret that cannot be read, or a claim that cannot be written, holds the post at the head of the queue and backs off; it never passes the post by with its code unspent. Only the exact shape, six ASCII digits last, can act.
  - A claim is `<kelpie home>/totp/used/<step>`, holding the id of the ntfy message that first sent the step's code, written beside its name, synced and hard-linked into place, so it is whole or absent. Every runner reads every reply, so a runner that finds the step claimed by the same message counts it as that message's, and one claimed by another message is a replay: it runs nothing, and the named project's runner tells the topic to send the next code. Claims are let go an hour behind the older of the claimed step and this machine's step, since the step is ntfy's clock.
  - A wrong six-digit code is counted once by message id under `<kelpie home>/totp/failed`, and the fifth turns answers from the topic off for every project (RFC 4226 section 7.3), with one line on the topic that also suggests moving to a new topic, until `shep kelpie totp --unlock` on the terminal; a right answer forgives the count. While they are off, alerts say nothing of replies and the topic is not read.
    - A reply with a valid code for a ruling already settled runs nothing and gets a line saying so, and a refusal from `rule` goes to the topic as a line too. Anything else is ignored and logged without its text.
    - The alert ends with the replies that answer it and carries no code and no buttons, since a button cannot carry a code the maintainer has not typed yet. With no secret yet, alerts say nothing of replies and the topic is never read.
  - The runner reads the topic's cached messages (`/json?poll=1`) after the last one it read, saved in the state file, every 15 seconds while an alerted ruling waits, and for an hour after an alert lands, backing off to five minutes while reads fail. A read reaches back ten minutes and three steps at most, so a saved position ntfy no longer holds never returns its whole cache. A reply older than ten minutes is read only to spend its code.
  - Four limits are accepted.
    - Anyone who can write the topic can turn answers off with five guesses; that fails closed, `rule` still answers, and only the terminal turns them back on.
    - An alert's text is not authenticated: a code proves who answered, not what they were shown, so a writer who posts a fake alert could get a real answer to a question kelpie never asked, though only for a ruling id that is pending.
    - A topic writer who posts every code can burn steps without tripping the lockout, which only delays the maintainer's answer, and ntfy rate-limits the posts.
    - A post kelpie cannot read in full, such as a message over 4,095 bytes that ntfy turns into `attachment.txt`, is not fetched: it spends every step a code sent with it could name, answers nothing, and gets one line on the topic saying it was too long to read and to send a shorter reply with a new code.
  - A webhook with `trusted = true` and a `token` (shep-pm/shep-kelpie#298) is a topic the maintainer says only their token can post to, so a reply on it needs no code except a yes on a merge ruling, where #111's rule that the topic alone never merges stands.
    - Kelpie cannot see the server's access rules, so the key is the maintainer's word. `trusted` without a `token` stops the dog at start and is refused by the settings parser, naming `webhook.trusted`.
    - A reply whose last word is six digits is still read as coded, so a wrong code counts toward the five that turn coded answers off, and uncoded replies go on working. Uncoded text that names no ruling here is ignored with no line, since the topic is chatty and every project reads it.
    - The alert's last line names `<code>` only on the merge yes, and `doctor` prints a `replies` line.
## The GitHub App

- Kelpie's conversation with the maintainer moves onto GitHub, from a GitHub App each user registers for themselves (shep-pm/shep-kelpie#395): every ruling, notice and review round on its issue or pull request, reaching the maintainer through GitHub's own notifications.
  - ntfy puts every project in one thread and asks for a code on every answer, and kelpie posting as the maintainer cannot notify them, since GitHub never notifies anyone of their own comments. A bot account per user (#376's first idea) does not scale to other users. ntfy (#298) stays as an option.
  - It comes in three pull requests, in order: setup and tokens (#396, built), kelpie's posts through the App (#397, built), and answers read back from comments (#398).
- One App per user, not one shared App. CodeRabbit, Codex and cubic keep their App's private key on their own servers; kelpie runs on the user's machine, so one shared App would mean shipping its key to every user or running a hosted service that holds it. GitHub's app manifest flow registers an App under the user's account in one click and hands its key back to a localhost redirect, with no second account and nothing hosted. A private App installs only on the account that owns it, so a user whose repos sit under several owners (their own account and an org) registers one App per owner.
- What the App may do: contents write (a worker's token pushes with it, see Workers hold a scoped token below), workflows write (a worker's token changes workflow files with it where the installation holds it, #462), issues write, pull requests write, metadata read, and no webhook. Kelpie's own token asks for issues and pull requests alone, so it cannot push; a worker's asks for contents, and workflows where the installation holds it, so it cannot comment, review, approve or merge. Merging stays on the user's own `gh` login. App tokens carry a rate limit of their own, apart from the user's `gh` (#394).
- Workers hold a scoped token, never the maintainer's login (shep-pm/shep-kelpie#420, decided by the maintainer 2026-10-10). The guard (`crates/core/src/guard/gh.rs`) parses commands, and parsing cannot be complete: on #418's reviews a flag before the verb, shell expansion and `python3 -c 'os.system("gh ...")'` all got past it, so a worker steered by text in an issue or a review could comment, approve or merge as the maintainer, and once #398 landed, answer its own merge ruling. The guard stays a guardrail against mistakes; the boundary is the credential.
  - On a repo the App covers (`Voice::worker_token` answers `Some`), each worker call gets its own installation token, minted when the call is prepared (`GithubApp::worker_token`), never kept and never one of kelpie's own cached tokens: `POST /app/installations/{id}/access_tokens` with `{"permissions":{"contents":"write"},"repositories":[<name>]}`, so it reaches the one repo and can push, and nothing that comments, reviews, approves or merges (no `issues`, no `pull_requests`). It has its whole hour for a call.
    - GitHub's answer says what the token holds, and a worker is handed it only if that is `contents: write`, `metadata: read` and, where the installation holds it, `workflows: write`, and nothing else (`TokenError::TooBroad`), so the scope is checked against what GitHub granted, not what kelpie asked. Kelpie's own token asks for `issues: write, pull_requests: write` alone, so it never gains contents.
    - The App's manifest asks for `contents: write` too. An App registered earlier lacks it and GitHub answers a worker's request 422, which `doctor` reports as MISSING with the fix (set Contents to Read and write in the App's settings, accept it on the installation, or `github setup --replace`); the call does not start, since a covered repo never falls back to the maintainer's login (as for kelpie's posts).
    - A worker's token asks for `workflows: write` too where the installation holds it, since without it a worker's push of a workflow file, `ci.yml`, was refused even after the maintainer gave the App the permission, and a ruling asked what to do (#462). Kelpie reads the installation afresh for each worker token (`GET /repos/{owner}/{repo}/installation` lists the permissions the installation accepted), so a permission accepted later takes effect on the next call, and an App without it gets the token it got before.
    - `pushes_only` accepts `contents`, `metadata` and `workflows: write`, and still refuses any other permission. The manifest asks for `workflows: write`, so a new App has it. This lets a worker change CI, which runs with the repo's secrets, so the maintainer reviews a workflow change as such; `doctor`'s `workers` line says whether workers can change workflow files.
  - The token reaches the worker in a file, not a variable.
    - Kelpie writes a `gh` config folder in the worker's build folder for each call (`gh/hosts.yml`, 0600, and a `config.yml` saying `version: "1"`), and `GH_CONFIG_DIR` points `gh` at it. A variable named for a key, a secret or a token is dropped from the commands Codex runs, and shows in every process's environment, so none carries it.
    - Git's credential helpers are emptied through `GIT_CONFIG_PARAMETERS`, which git reads after every config file and which drops the keychain's helper, and github.com's helper is `gh auth git-credential`, which answers from that folder. A call whose login cannot be written does not start.
    - Kelpie writes it as the maintainer, outside the sandbox, into a folder the worker can write, so it never follows a link there: the files are opened with `O_NOFOLLOW` and `gh/` is opened with `O_NOFOLLOW | O_DIRECTORY` and written by descriptor (`crates/worker_folder/src/worker_folder.rs`). A worker that swaps `gh/` or `hosts.yml.tmp` for a link to `~/.config/gh` or another file would otherwise have kelpie overwrite the maintainer's own login (shep-pm/shep-kelpie#439).
    - The fence then read-denies `~/.config/gh/**` and `~/Library/Keychains/**` and denies the commands `security`, `git credential`, `git credential-*` and `git -c credential*`, which it does not do for a project with no App, whose worker runs as the maintainer. These are guardrails against a mistake, not the boundary: the keychain itself is closed by shep-pm/shep-kelpie#429, which blocks it inside a covered call's sandbox.
    - `gh auth token` in a covered worker prints its own token. `crates/core/src/profile/mod.rs` pins the env and fence a call gets (`on_a_repo_the_app_covers_a_worker_holds_the_apps_token_and_never_the_maintainers_login`).
  - A token that cannot open a pull request means kelpie opens it, as the login `gh` acts as, the one the worker opened it with before.
    - A worker on a covered repo is told to write its title and body in `pull-request.md` in its build folder (first line the title, the rest the body, ending `Resolves #<issue>`), not to run `gh pr create`.
    - When a turn ends with the branch pushed and no pull request, kelpie opens a draft from the file (`Forge::create_pull_request`, `gh api`); when a later turn changes the file, it sets the title and body (`Forge::edit_pull_request`), compared with a copy it keeps in the build folder, so an edit made on GitHub meanwhile is not undone by a turn that left the file alone. A file with no title opens nothing and is told in the log.
    - Kelpie never follows a link in a worker's folder (shep-pm/shep-kelpie#439): the worker can write the build folder and kelpie reads it as the maintainer, so a `pull-request.md` linked to the App's key or `~/.ssh/id_ed25519` would be posted as the pull request, where the worker can read it back.
    - The file is opened with `O_NOFOLLOW`, then the open file is checked to be a regular file the user owns, with no other hard link, of 1 MiB or less (a FIFO is opened without blocking and refused), and a refusal is a note naming the file that never quotes it.
    - The copy kelpie keeps, the findings file for a fix turn and the other files it writes there are written to a new file made with `O_EXCL` and `O_NOFOLLOW` and renamed into place, so a link there is replaced and what it named is untouched. The deferred and disputed findings files are read the same way. All of it is in `crates/worker_folder/src/worker_folder.rs`.
    - With no App nothing changes: the worker opens its own pull request.
  - A token can push any branch of the repo. A push to `main` is refused by GitHub only where `main` is protected (a branch protection rule or ruleset), so `doctor` says to protect it, and the profile's `git push` rules and the guard still refuse one as a guardrail.
  - A covered worker's token reads nothing else, so kelpie reads CI for it. `gh pr checks` and `gh run view` need `pull_requests`, `checks` and `actions` read, which the token lacks, and the red-CI and merge-queue prompts told the worker to run them. On a covered repo kelpie reads the end of the failed runs' logs (`Forge::failed_run_logs`: `gh run list --json`, then `gh run view --log-failed`, 3 runs and 6000 bytes of each at most) as the login `gh` acts as and puts them in the prompt, and says so when it finds none or cannot read them. Any other worker is pointed at the commands as before. Reading more would widen the token past pushing, so it is not done.
  - A red run is rerun once before it costs a fix turn (shep-pm/shep-kelpie#648). Retros named a flaky test outside the branch eleven times, each costing the worker a turn to push nothing or call it a flake, and the worker's credential cannot rerun a job. `ci_failed` reads the failed runs' logs with `failed_run_logs` whether or not the App covers the repo, and the changed files with `git diff --name-only origin/main...<head>`. When the log names none of them (a plain substring test of each path), `Forge::rerun_failed` runs `gh run rerun <id> --failed` for each failed run of the head as the maintainer's login, `reran` records the head (state file version 36), the phase's `since` restarts so the rollup, which reads red for a moment, is waited out, and `status` shows `rerunning` while the item waits on it. An empty log, a read or git error, a refused rerun and a head already rerun send the fix turn, which says the failure repeated after a rerun. The rerun counts toward no `ci.fix_attempts`, and runs before the cap check, so a cap of `0` still reruns once.
  - A still-red ruling remembers the review round a red run interrupted (shep-pm/shep-kelpie#689). A red run while a round waited for green CI sent the worker's fix turn back to that round, but a yes to the still-red ruling that followed went to `Phase::Ci`, so green CI reached the gate with no round having read the head. `Stuck::StillRed` now carries that round as `review` (state file version 37), `ci_failed` fills it from its `review` argument, and a yes returns to it. A still-red ruling raised from CI, after the rounds finished, has none and goes to CI as before. A hand-pushed fix still changes the head, so the yes adopts it and starts the review from its first round.
  - A token lasts an hour from its mint and a call can run longer (`worker.turn_timeout` has no upper bound, and time on the test lease counts against it). While a covered worker's call runs, a second thread writes a fresh login over the file every 30 minutes (`crates/runner/src/runner/login_refresh.rs`), renamed into place so a `gh` never reads half of it: with no token in the file it would look in the keychain. A mint that fails is tried at the next time round.
  - A token GitHub will not give for a reason that passes (out of reach, busy or rate limited) holds the worker's turn back and does not park the work item on a `turn-failed` ruling: the turn is tried again after 30 seconds, and the log says so once. A reason that does not pass (an App without Contents, a token broader than asked) still fails the turn and asks the maintainer.
  - With no App covering the repo a project runs as before and `doctor` says its workers hold the maintainer's login (`unsure`: the App is optional).
- `shep kelpie github setup [--org <org>] [--name <name>] [--replace]` registers an App through GitHub's manifest flow.
  - It listens on a free port of 127.0.0.1 and serves one page that posts the manifest to `https://github.com/settings/apps/new`, or `/organizations/<org>/settings/apps/new`, with a random 128-bit `state`, opening the browser with `open` on macOS and `xdg-open` elsewhere and printing the URL either way.
  - The manifest names the App (`kelpie-<owner>` by default; App names are global on GitHub, so on a name GitHub refuses the user runs again with `--name`), its homepage, the callback as `redirect_url`, `public: false`, `hook_attributes.active: false` and the three permissions.
  - A request whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>`, and a callback whose `state` is not the run's or whose code is not plain letters and digits, are refused with HTTP 400 and never converted. The right one is converted with `POST /app-manifests/{code}/conversions`, which needs no login. An App owned by anyone but the asked owner is not kept, and the message names both owners.
  - A conversion that fails or is not kept leaves the page waiting for another try; one that is kept ends the run, and kelpie opens `https://github.com/apps/<slug>/installations/new` for the user to pick the repos. The owner is `--org`, or the login `gh` answers for.
  - Setup for an owner kelpie has an App for says so, names the App's install page and stops, unless `--replace`. A replacement keeps the default name only once the old App is deleted on GitHub, since names are unique, so the message says to delete it first or give `--name`; an old App kelpie cannot use, such as one with an exposed key, is replaced after a warning.
- Kelpie keeps each App the way it keeps the authenticator secret: under `<kelpie home>/github/<owner>/`, the owner's login in lower case. Never a project's settings or the state file.
  - `app.json` holds the App's id, slug, client id and owner; `key.pem` holds its private key, 0600, written beside its name, synced and renamed into place, before `app.json`, so an App on record always has its key. Saving sets the `github` folder and the owner's folder to 0700 and refuses either when it is a link or another user's. The client secret and webhook secret the conversion also returns are not kept, since nothing uses them.
  - Before anything is signed, the key and both folders must be the user's own, not links, and closed to others. A key or `app.json` that is not a regular file, such as a FIFO a read would wait on, is refused.
  - A worker's sandbox denies kelpie's home around the worker's own folders, so no worker call reads the key, and Claude Code's Read rules name the `github` folder among the entries around them.
  - `github` is one of kelpie's own names, which no project may take in any case, since a case-insensitive volume reads `Github` as `github`; a runner by that name in the dog's book file is dropped from it on load, with a line in the dog's log, and the rest of the book kept.
  - Kelpie holds the key in memory during setup, from the conversion's answer to its file, never passes it in a process argument or an environment variable, and the signer reads it from the file.
- Tokens come from the `GithubApp` port, which #397 and #398 call.
  - For a repo it reads its owner's App (a repo owner that is not a GitHub login is refused before any file is read), signs a JWT (RS256, `iss` the client id, issued 60 seconds back, lapsing nine minutes on), asks `GET /repos/{owner}/{repo}/installation`, then `POST /app/installations/{id}/access_tokens` with `{"repositories": [<name>]}`, so each token reaches its one repo, and keeps it per installation and repo until five minutes before its `expires_at`.
  - A mint answered 401 or 404 drops the installation kept for the repo, so the next asks for it again. A repo GitHub answers 301 for has moved; the redirect is never followed, so a JWT reaches nothing but GitHub's API, and the error says to update `git.remote`.
  - The calls run on `curl` with a config on stdin, as the webhook's do, so no process listing shows a JWT; the JWT is signed by `openssl dgst -sha256 -sign <key file>`, which reads the key itself, so no crate is added for RSA.
  - `doctor` asks the port for a token for each project's repo: an App not installed on the repo is `MISSING` naming its install page, and a refusal such as 401 is `MISSING`. An owner with no App is `unsure` naming `shep kelpie github setup`, because the App is optional: without one kelpie falls back to posting from the user's own `gh` login, so its absence must not fail `doctor`. GitHub out of reach, a 5xx, or a spent rate limit (429, or 403 saying so) is `unsure`.
  - A token is minted with one flight per App and repo (#397, from #400's review), since a lock held across both curl calls of a mint, up to 30 s each, stalled every repo's token behind one slow answer: only askers for the same repo wait on each other, and two of them mint once.
- Kelpie's posts go through the App (#397), by the `Voice` port beside `Forge`. `Voice` holds what kelpie writes for the maintainer to read: a comment on an issue or pull request, an issue, a label, and an issue's label.
  - Its real adapter, `AppVoice`, makes each with the repo's installation token over the REST API (`POST /repos/{o}/{r}/issues/{n}/comments`, `/issues`, `/labels`, `/issues/{n}/labels`, and `DELETE /issues/{n}/labels/{name}` with the name percent-encoded; a label the issue lacks counts as taken off, as `gh issue edit` does).
  - A repo is *covered* when the owner has an App installed on it: no App, an owner that is no login, and an App not installed there are not covered, and kelpie writes there through `gh` as before, so with no App behaviour is unchanged.
  - An App that is set but cannot mint a token now (GitHub out of reach, a refused JWT) still covers the repo: its writes fail and are told, and nothing is posted as the maintainer in its place, which would be the post the maintainer is never notified of. Every write goes through the local-path guard first, as a `gh` post does.
  - A summon (`@codex review`, `@cubic-dev-ai review`, a full-review comment), the `review please` label and every label on a pull request stay on the maintainer's own `gh` login: a review bot answers a person's comment or label, and nothing measured says it answers an App's. Merging, marking ready and closing a parent issue stay there too. A refusal comment on an adoption or a rework, and the comment on a parent issue kelpie closes, go through the App where one covers the repo, since the maintainer's login should carry only what the maintainer wrote. `shep kelpie add` makes its labels from the terminal, with no runner, so those stay on `gh`.
  - A ruling is posted whatever its kind, on the work item's pull request or, while it has none, on its issue. Under `gh` the merge ruling and the follow-up ruling post no comment (the `ready-for-human` label says it, and the pull request is merged); through the App they do, since the thread is where the maintainer is notified and answers.
    - It starts with the maintainer's login as a mention, from `git.maintainer`, else the login `gh` acts as (`gh api user`, asked once a run and kept; the repo's owner is not guessed from, since every `shep-pm` repo is an organization's and its owner is no one to notify).
    - The text is the public-safe one the `gh` comment has, never the forge's or a reviewer's own words, and it ends with how to answer: the grammar of #398 with the ruling's id first (`99 yes`, `99 no <note>`, `99 rework <note>`, or for a question the answer in free text), whose reply counts (only the login mentioned), and the terminal's `shep kelpie rule <id> <answer>`, which still works. A ruling that mentions no one says it is answered at the terminal only.
  - A notice is a comment on the thread of the work item it is about: the automatic merge's on its pull request, a work item closed with no change on its issue, and a withdrawn merge ruling on the pull request, or the issue while it has none. They are posted once, when the notice is made, and a failed post is told once in the log and not retried; the webhook's post and its retry are unchanged and still happen. The runner's `finished` line is on no thread, since no work item is left by then, so it goes to the webhook and the log alone.
  - A review round of kelpie's own reviewers (a session, a command or an endpoint) is posted on the pull request as it ends: the reviewer, the round, the head its start found checked out, and each finding with its severity, file, line, what and why, or that it found nothing (#376, on the App). A round that read nothing (every file unreviewed, a reviewer skipped) and a first look that a second look follows post nothing. Bots post their own reviews, so only these were missing.
  - A failed post never fails its step: a ruling's step reports it in `comment_failed` as before, a notice or a round tells it once in the runner's log. The ruling kelpie raises again when it finds a foreign change on a pull request (`ask_again`), the one place a failed ruling comment was dropped silently, tells it in the log too, with or without an App.
  - When `git.maintainer` is unset the mention is the login `gh` acts as. `doctor` shows it for a project whose App covers its repo as `ok`, `a ruling mentions @<login> (from gh)`, and says a ruling mentions no one and notifies no one (`MISSING`, with the fix, set `git.maintainer`) only when `gh` cannot say who it acts as. In that case a ruling still goes up unmentioned as the record on the thread: the step's `comment_failed` says so, and the runner notes it once a run, after the first such ruling that went up (a post that failed is not one, and does not use the note up). The next ruling asks `gh` again.
  - `AppTokens` believes one refusal for a while: an App found not installed on a repo is believed for 10 minutes per App and repo, since a `covers` before each label, comment and ruling otherwise signed a JWT and called `GET /installation` each time before falling back to `gh`. Nothing else is held. A mint that fails for GitHub being down, busy or rate limited is not remembered, because a failed post is not retried and remembering it would drop every ruling and notice for that repo until it lapsed; a post while GitHub is down costs a failed mint for `covers` and one for the write, and the post fails and is told. The price is that an App newly installed on a repo is noticed up to 10 minutes later, by the runner and by `doctor`; a fresh `doctor` run in a new process asks at once.
  - A ruling is answered by replying in its thread (#398), on a repo an App covers.
    - The runner asks the forge once per `BOARD_POLL` for the repo's comments since the last it read (`GET /repos/{o}/{r}/issues/comments?since=` through `gh api --paginate --slurp`, one call for every thread however many rulings wait, oldest first), gated by time, never by wakes, so a drain's 500ms polls cost nothing.
    - The call is made with the runner's lock let go, as the board's git is (`thread_job` decides a read is due and copies what it needs, `ThreadJob::run` asks the forge, `apply_threads` locks again and acts), so a slow GitHub never holds a trigger. A failed read waits a poll too and is told once in the log while it keeps failing. `Forge` is `Send + Sync` and the runner's port an `Arc` for this.
  - Who may answer, and with what.
    - **Only the login the ruling's comment mentions** (`git.maintainer`, else the login `gh` acts as) answers it in the thread, and it must also have write access (`GET /repos/{o}/{r}/collaborators/{login}/permission`, `admin` or `write`, asked once per author per read). **A ruling that mentions no one is answered at the terminal only**: it is not read at all, and its comment says so. A bot or an App never answers (`user.type` is not `User`).
    - **A comment kelpie posted as the login `gh` acts as is never an answer**: that login is the one that answers, so each id `Forge::comment` returns (a summons, and without an App a refusal on an adoption or a rework, a ruling comment and the comment on a parent issue kelpie closes) is recorded in the state file (`posted`, the last 500) the moment it is posted, not at the next save, and skipped.
    - The window left is a crash between GitHub taking the comment and the file taking its id, or a write that fails, which is told in the log; a summons so lost could be read as an answer only by a ruling that mentions the login `gh` acts as and waits on the same thread, and only if it came after that ruling's own comment. `Forge::close_issue` takes no comment: a `--comment` on `gh issue close` would be a post with no id, so the parent's closing comment goes through `Forge::comment` first, on the first try only, and the issue is closed without it.
    - **A merge ruling's answer names its id, as the terminal does**: `99 yes`, `99 no <note>`, `99 rework <note>`. A bare `yes` is unreadable, so a conversational one never merges; the same goes for a `stuck`, `agent-files`, `foreign-change` or `follow-up` ruling's yes or no. A worker's question keeps free text from the mentioned login, with the id first only when several rulings wait on one thread. The ruling's comment says exactly what to type and whose reply counts.
    - Anyone else's reply gets no answer and no reaction, so a stranger on a public repo cannot make kelpie speak. A permission that cannot be read ends the read at that comment, to be tried again at the next poll.
    - A reply taken as the answer gets a thumbs up as the App (`POST .../issues/comments/{id}/reactions`, covered by the App's issue permission); one that cannot be read gets one reply saying what to type, and the ruling stays open. Every comment by the mentioned login on a thread with a pending ruling is read as an answer, so an ordinary remark there is told what to type too; that is the cost of having no marker on a reply.
  - The place read to is in the state file, `heard`, by ruling id: the login mentioned, and the time and id of a comment.
    - It starts at the ruling's own comment, **its `created_at` and id as GitHub's answer to the post gave them**, not the local clock, so a comment from before the ruling never answers it and clock skew cannot let one through.
    - It moves to a comment before that comment is acted on, so a reply is answered once and a crash loses an answer rather than doubling it, and **only for the rulings on that comment's thread**: a reply acted on one thread never moves the place on another, and no other comment moves it at all, so a reply the forge lists late is still read.
    - The forge's `since` counts a comment from its last edit, so the read keeps the comments' own `created_at`. A read asks from five minutes before the last read, and never from before the oldest place read to; a bot's or a stranger's comment is remembered in memory until a read no longer reaches it.
  - An answer given in the thread and one given at the terminal, on ntfy or by the project manager: the first wins. A ruling that leaves the list, however it was answered, is watched for an hour more, and a reply there that names it is told it is already answered; the terminal told second hears `ruling <id> is already answered, or was never raised` where it heard `no ruling <id> is pending`. The ntfy path is unchanged and still reads its topic where ntfy is set.
  - A ruling that is settled other than by the maintainer in its thread (#472) has its posted comment edited through the App: a first line says it is settled and nothing waits on the maintainer, and who settled it and how (the project manager with its answer and why, `shep kelpie rule`, a reply to the alert, or the withdrawal and its reason), and the options and reply lines go. A ruling answered in its own thread keeps its comment. A refused edit is tried again at each poll for an hour. The comment is found from `heard.ruling_comment`, or, for a ruling posted with no mention, from `unmentioned` (state version 27), the ruling id and its comment id. A ruling dropped because its work item finished or closed is not edited.
  - A ruling's comment through the App is one short format (#464, slice 1 of #461), whatever its kind: a `###` title, a line of what happened, a table of the options and what each does, a **Panel** list, and the ways to answer, with the mention on the line that opens them.
    - The Panel holds the project manager's words where it gave any (the `PM says:` and `PM recommends:` lines kelpie already writes into a ruling's question) and is left out when it gave none. From #465 the Panel lists the panel's votes once they are in, and the recommendation line, which the panel writes once it has voted (#466, below). A ruling that mentions no one drops the ways to answer and says the terminal answers it.
    - `crates/runner/src/runner/voice/card/mod.rs` renders it, and the same options are what a reaction or a tick is read against, so the two cannot drift apart. The expected comments, `fixtures/rulings/*.md`, are written by hand from the format in #461, not recorded: kelpie has not posted one yet.
  - Answering from the ruling's own comment (#464).
    - A yes/no ruling (`stuck`, `agent-files`, `foreign-change`, `follow-up`) takes the mentioned login's 👍 or 👎. A merge ruling takes them as its first two options. A merge ruling and a worker's question list their options as task-list boxes; a question's options are the `- ` lines it ends on, plus an `Other` row with no box.
    - Each `BOARD_POLL` the thread read also asks `Forge::comment_marks` for every waiting ruling whose comment id is saved (`heard.ruling_comment`, state version 26; a ruling from an older file reads no reaction): the comment's body, its 👍 and 👎, and who made each edit, from REST for the node id and GraphQL for `reactions` and `userContentEdits`.
    - A thumb counts only from the login the ruling mentions. Both thumbs from it, or two ticked boxes, answer nothing, and a thumb wins over a tick.
    - **A tick counts only when every edit of the comment was by the mentioned login or by the App that wrote it.** The forge says who edited a comment, not which edit ticked which box, so one edit by anyone else with write access leaves the boxes dead for that ruling, and a reaction or a reply answers instead.
    - A reaction or a tick carries no note, so a 👎, a ticked `Send back` or a ticked `Rework` gives the worker `NO_NOTE`, which says the maintainer gave none; a note takes a reply. The answer goes through `Runner::rule` as any other, so the board's events tell the project manager the ruling was answered. A refusal from `rule` is noted once per ruling, since the reaction stays and is read again.
    - The write-access check a reply needs is not made for a reaction: the login is the one `git.maintainer` or `gh` names. Every page of `userContentEdits` is read, since a tick is trusted only over the whole edit history; a page that says more follow without a cursor makes the read fail. The GraphQL shape (`IssueComment.reactions`, `userContentEdits { editor }`) is from GitHub's schema, not a recording, since a worker's sandbox cannot run `gh api`.
  - The panel (#465, slice 2 of #461). Four experts vote on each ruling, each blind to the others: the worker, the project manager, the advisor and the researcher.
    - A project has a panel once it names an advisor or a researcher (`agents.advisor`, `agents.researcher`, off while absent as `agents.pm` is), and a ruling gets one when it lists two options or more. A worker's question that lists fewer than two options gets its options from the project manager first (#709): its one wake on the question may carry `candidates` beside `escalate` (or alone), two or three one-line answers, kept as `- ` lines after the question and dropped when the question already lists two options or the project has no panel. `Ask the maintainer` is the one candidate that is no answer for the worker: a panel pick of it, or a tick on it, decides nothing and the maintainer answers, in their own words or with another option.
    - Under `shadow` nothing decides by the votes (#466, below): they are kept on the ruling (`panel`, state file version 28) and listed in its comment under **Panel**, in the table's order (worker, project manager, researcher, advisor), a vote as `- **Advisor** (B): <why>` and an abstention as `- **Advisor**: abstained`.
    - Until a ruling's panel has voted its comment is held back from the maintainer, as a question is for the project manager's one wake, for 20 minutes at most (`panel::HOLD`), counted from when its experts are asked, since one ruling's experts run at a time; then it lists the votes that are in and the rest abstain. A question the project manager may answer is held for it first, and its panel starts once that hold ends, so a question it settles costs no vote.
    - A ruling raised while the runner drains waits for the panel like any other (shep-pm/shep-kelpie#711): the restart or `undrain` takes it up, and one still waiting after the hold goes to the maintainer with `skipped` set to `draining` (`posted` when its comment had gone out before the panel took it up), kept in `rulings.jsonl` and counted in `status`'s `panel.skipped`. A held comment is kept on its ruling (`unposted`), so a runner that restarts mid-hold still posts it, and each expert's 15-minute ceiling counts from when it has the lease it waited for. A ruling is offered a panel only while its comment is held, so a restart does not ask again for one already posted.
    - The worker's vote runs in its work item's own session, so the item takes no turn while it flies (a ruling answered meanwhile ends it), and the item keeps where the session's cost stands without counting the vote, which is in no item's tally. An answer by the project manager is kept in `rulings.jsonl` as its own, not the maintainer's.
  - What each reads, and what kelpie writes there. They never run git, `gh` or a command, and write nothing: the reply is the vote. Both folders are emptied and written before each call, and each is read-denied to the other.
    - The **advisor** (`role: advisor`, kelpie's own is Opus 5.5 at high) reads the codebase, in `<project>/advisor`: `ruling.md` (the title, what happened, the options), `diff.patch` (the work item's branch from main, as the board's last git read has it, cut at 64 KiB; the board reads each branch's diff while a panel is set, not only a project manager) and `where.md`, with the worktrees and the checkout beside, read only, under the project manager's fence and its list of secret-shaped files (`fenced_reach`, the project manager's fence made a function). It reaches no host but the model's and has no web.
    - The **researcher** (`role: researcher`, Sonnet 5.5 at high) reads what is outside the codebase, in `<project>/researcher`, and reads nothing else: `ruling.md`, `rulings.md` (the latest 60 rulings answered and how, from `<project>/rulings.jsonl`, which kelpie appends as each answer is saved, since the state file keeps only the rulings that wait; it holds the rulings answered from this build on), `threads/issue-<n>.md` and `threads/pull-request-<n>.md` (the title, the body and the last 80 comments of the last 14 days, from the forge), `worker.md` (the worker's session as its harness wrote it, prompts, replies and one line a tool call, the last 128 KiB) and `maintainer/<n>-<harness>.md` (below).
  - The researcher's web is `WebFetch` and `WebSearch` on Claude Code and Codex's live web search, read only; pi has none. Behind the sandbox's strict allowlist a fetch reaches only `researcher.allowed_domains` (empty when absent), where a search goes through the model's own host. A page can try to steer it, so its vote is one of four, its prompt says a page is data, and a vote's `why` is posted with its `@` broken (`@` and a zero-width space), so a page cannot make a comment mention anyone.
  - `researcher.transcripts` names folders of the maintainer's own agent sessions (`~` is the home folder, a relative path is taken from the project's folder in kelpie's home). It is off while empty.
    - `crates/core/src/transcripts/mod.rs` holds one small table of the harnesses (`KEPT`): Claude Code's sessions are `~/.claude/projects/<folder>/<session>.jsonl`, Codex's `~/.codex/sessions/<year>/<month>/<day>/rollout-*.jsonl` and pi's `~/.pi/agent/sessions/<folder>/<time>_<session>.jsonl`, how far down a named folder a session file lies at most (3), and which top-level `type` a harness's lines start with, to tell a file's harness from its content. #456's harness facts can absorb the table.
    - Reading a session is `watch`'s (`said_in`), which `shep kelpie watch` reads the same files with. A session is read only if the folder it ran in, from the `cwd` in its first lines, is the project's checkout or under it, so a root holding every project's sessions can be named. They are read newest first, at most 12, the last 96 KiB of each and 512 KiB in all, and only what was asked and said: no tool call, result or thinking.
  - The worker votes by resuming its own session once, with the tools of a retro (reading its worktree, no file written, no command), and abstains when its work item has no worker turn on record or no worktree left. The call is no turn: it is in the ledger as a `vote` call of the worker's role and in no work item's tally.
    - The project manager is woken as for anything else with a new reason, a ruling before the panel, and answers in a new `votes` key, a list of `{"ruling", "choice", "why", "design"}`; a ruling it gives no vote on, or a wake it was down for, is an abstention.
    - The three others run at once in one flight (`flight/panel.rs`): a thread each inside one, one ruling's experts at a time, 15 minutes each. Their prompts and folders hold the ruling alone: a test pins that no prompt or folder carries another's vote.
  - Every vote is #461's object, `{"choice": "<option key>", "why": "<at most 350 characters>", "design": true|false}`, the last object in the reply with a `choice`. A reply with none, a choice that is no option's key, or a missing `why` or `design` is no vote, and the expert abstains with the reason in the log (`ruling 1: the advisor abstains, since ...`). A `why` is cut to 350 characters on one line. The tally, `design`'s effect, `rulings.decide` and the shadow streak are built (#466), described below.
  - Deciding (#466, slice 3 of #461). Three experts on one option decide a ruling, unless one flagged `design`; anything less is a split. `rulings.decide` is `shadow` (the default) or `panel`.
    - Under `shadow` every expert votes on every ruling, the panel's votes and its recommendation are posted, and the maintainer answers.
    - Under `panel` the ruling is applied at once as the maintainer's yes, no or rework would be (`Settler::Panel`, `crates/runner/src/runner/panel/decided.rs`): a no's note is "Decided by the panel:" and the first agreeing vote's reason, and the ruling's own comment, which was held for the votes, is never posted. A comment of its own is posted instead through the App, headed `Decided by the panel: <key>, <option>`, with the votes beneath and no way to answer but `<id> no <note>`.
    - The maintainer gets a split, a merge under `git.merging = "ask"` and any `design` flag, each with every vote, and the last two with `**Recommendation: A** (3 of 4)` under the Panel. A split gets no recommendation: three agreeing is what makes one.
    - Its figures are kept on the ruling as `verdict` (state version 30): the work item's type, the panel it set, and the `advice` (choice, how many chose it, how many were asked).
  - `no <note>` reopens a decided ruling (#466).
    - The runner keeps the ruling as it was decided, in memory, for 24 hours (`DECIDED`, longer than the hour an answered ruling is watched, since the maintainer reads it later), and watches its decision comment for the login `git.maintainer` names.
    - A reply `<id> no <note>` there puts the ruling back, parks the work item on it again and answers it with the note, so the worker takes it as any `no`. It does so only for a work item that is open, not running a call and not parked on another ruling; otherwise the reply is answered with why, and a decision whose work item has finished cannot be undone. A worker's question takes the note as its answer.
    - Anything else in the thread (`yes`, or a `no` that names no ruling) gets "was not reopened", with how to reopen it; other chat is left alone. A runner that restarts forgets what it watched, so a decision older than the restart cannot be reopened from its thread.
  - Who votes (#466). The work item's type comes from its pull request's conventional title, read from the forge when the panel is taken up (`crates/panel/src/panel/tally/mod.rs`, `work_of`): `docs` asks the project manager, `fix`, `refactor`, `perf`, `test`, `ci`, `chore` and `style` the project manager and the advisor, and `feat`, any type marked `!`, any other word and a title that cannot be read all four.
    - Under `panel` the panel is asked a stage at a time, the smallest first. A smaller panel decides only when everyone it asked picked one option with no `design` flag, and an expert missing from it, or that abstained, is not agreement; otherwise the next panel up is asked, and a vote already given stays, so the project manager, who has voted, is not woken again. The full panel decides on three of four.
    - An advisor or researcher the project does not name is never asked and counts as an abstention, so a project without a researcher decides a `feat` on three of three.
    - A merge under `ask` is asked the type's panel as any ruling is, and goes to the maintainer whatever it comes to, with the recommendation if it came to one. The hold on a ruling's comment (20 minutes) counts from each stage's turn.
  - Two rules only raise the panel, and policies for who votes are scored from shadow votes (#536).
    - Reason: the type is what the worker wrote in the pull request's title, so the label that sets how much scrutiny a change gets was chosen by the agent under scrutiny: a `ci` or `fix` change to the guard or the workflows asked the project manager and the advisor, and a worker's question asked whatever the item's type said.
    - A `question` ruling starts at the full panel (`first_tier`, `crates/panel/src/panel/policy/mod.rs`), and a `design` flag in a smaller panel asks the full panel at once in place of the next one up (`settle`, `tally/mod.rs`).
    - A ruling on a work item whose diff from its merge base touches a glob on `rulings.full_panel_paths` starts at the full panel (empty by default; the diff is read with the `changed_files` the reviewer lineup uses, in the work item's worktree against `origin/main`, not the review base, so the commits an adopted pull request arrived with count, and one that cannot be read counts as touching, since the safe side is more scrutiny). Neither rule lowers anything.
    - Which table should replace the type's is not settled by argument. Under `shadow` every expert votes blind on every ruling, so any policy can be played over the same ballots afterwards with no extra call, and the decision is to score a fixed list of candidates from those votes and the ledger in place of making the tiers configurable: `Policy` in `crates/panel/src/panel/policy/mod.rs` (`type`, `type+risk`, `kind+risk`, `kind+risk-researcher`, `pm+advisor`, `pm+researcher`, `all`), reported as `whatif` in `status`.
    - A configurable table would have been one more setting to get wrong and could not say what a choice would have cost. The list is code, not a setting; once the data picks one, a later change makes it what `panel` means and removes the rest.
    - For that, a `Verdict` also keeps `risky` (whether the diff touched a path on the list) and `shadow` (whether the votes were a shadow run, with nothing decided), both left out while false (state version 32). A line from before has neither, so `whatif` scores only rulings answered from this build on.
    - The pairs have no one above them: a split or a `design` flag in one goes to the maintainer, which is what the score for them says.
    - A policy's cost per ruling is the cost of the ledger lines of the votes it asks, each voter once however many panels it was in, over the rulings scored; a project manager's wake shares its cost between the rulings it voted on, and a call with no reported cost adds nothing; a ledger that cannot be read leaves `cost` null, not zero.
  - `rulings.pm_alone` (#466) lists kinds of ruling the project manager decides with its own vote on any type of work, by the kebab-case name of the kind (`merge`, `question`, `agent-files`, `foreign-change`, `follow-up` and the stuck reasons: `rebase`, `still-red`, `merge-refused`, `closed`, `fix-not-pushed`, `unpushed`, `turn-timeout`, `turn-failed`, `unlabelled`; `RulingName` in `settings/rulings.rs`). It is empty by default.
    - Only `merge` is refused, since a merge ruling must not be decided by one voice: the runner does not start, with `rulings.pm_alone` named, and a change that adds it to a running runner is refused as any setting that does not hold is, keeping the settings it has. `merge-refused` is a stuck ruling about a refused merge, not a merge ruling, and is allowed.
    - Under `panel` the project manager alone is the first stage for a listed kind; a question and a ruling on a risky path are never alone (the rules that raise the panel win over `pm_alone`, #536), and `question` listed here only fills its `pm_alone` run; a `design` flag goes to the full panel and an abstention to the panel the type sets, all four for a question or a risky path (the project manager's vote stays in it), and an agreeing vote with no flag decides with no other call.
    - Under `shadow` the project manager is not alone: all four vote, so that what each smaller panel would have decided can be told afterwards.
  - Measuring (#466). Each vote is one `votes` entry on the ledger line of the call that cast it (`CallLine.votes`, `usage/mod.rs`): `ruling`, `ruling_kind`, `voter`, `panel` (the type's, `docs`, `fix` or `full`, which `status` calls `pm`, `pm+advisor` and `all`), `work` (the type) and `choice`, left out for an abstention. The cost, tokens and seconds are the line's own.
    - The project manager's wake carries an entry for each ruling it was asked to vote on, found from the wake in flight when its line is written, and counts its whole cost shared among them and its whole wall time for each; a wake that served another reason too (a pick, a stuck item) counts in full, since its cost cannot be split by reason.
    - `shep kelpie usage` prints, after the project manager's and the retros' totals, `panel votes on N rulings, $X a ruling, split by:` and three tables (`expert`, `kind`, `type`) of calls, cost, median wall time, abstentions and cost per ruling (`crates/core/src/usage/panel.rs`). The panel's cost per ruling is the cost of the votes over the rulings they were cast on.
  - `status` reports the panel from `rulings.jsonl` (`crates/runner/src/runner/panel/measure/mod.rs`), which already held each answered ruling for the researcher and also holds its kind, the option it chose, the verdict and the ballots, and whether the maintainer, the project manager or the panel answered it. Only the maintainer's answers count.
    - `streak` is the run of answered rulings where the panel's recommendation was the answer; a ruling with none, a split, leaves it as it is, since it asked nothing the panel got wrong and the maintainer would have been asked anyway, and an answer that differs, or that is none of the options (the reply of a worker's question in the maintainer's own words), ends it.
    - `pm_alone` is the same run for the project manager's own vote by kind of ruling, a vote that flagged `design` or abstained leaving it; it is counted for every kind, listed or not, since it is how a kind is earned.
    - `experts` has each expert's `votes`, `abstained`, `agreed` and `lone` (the votes that were the answer, and the ones that were the only one), and the same two by kind of ruling as `by_kind` (#536). `panels` has, for each panel asked alone, how many rulings it would have decided and how many it decided as the maintainer answered. `facts_due` is set once the panel has voted on 30 rulings.
    - The file holds the rulings answered from this build on, and a project that has the panel from before holds none of the earlier ones.
  - A worker posts no comment (`crates/core/src/guard/gh.rs`). Its `gh` is the maintainer's login, so a comment on a pull request from it would read as the maintainer's answer, and `100 yes` typed there would merge it, from the pull request's own worker or another.
    - `gh pr comment` and `gh issue comment` are refused outright. For the `pr`, `issue` and `discussion` groups it is an allow-list: only `create` and `edit` may carry text, and any other verb carrying `--comment`, `-c`, `--body`, `-b`, `--body-file` or `-F` in any spelling (`--comment=x`, `-cx`, `-dc x`) is refused, so `close` and `reopen` with a comment, `review` with a body, and the next verb gh adds are covered.
    - The read verbs (`view`, `list`, `status`, `diff`, `checks`) are exempt, since `-c` there is `--comments`. A `-b` that means a branch or a base (`gh pr checkout -b`, `gh pr list -b`) is refused on a verb that is not a read, which a worker can do without.
  - The guard reads a worker's `gh` as gh does (`crates/core/src/guard/gh.rs`).
    - **The only flag before the group or the verb is `-R`/`--repo` with its value** (`--repo=x` and `-Rx` too): gh takes any other flag there with the next word as its value, so `gh pr --comment="101 yes" close 418` and `gh pr -b x comment 418` were `close` and `comment` to gh while the guard read the word after the flag. Any other flag there is refused (`gh --version` alone stays).
    - **A gh call whose words hold shell expansion is refused**: a word with `$`, a backtick, `{`, `~`, `*`, `?` or `[` (`$'--comment'`, `--comment$IFS`, `F=--comment; gh pr close 3 $F x`, `gh pr $'merge' 3`), as `wrap/mod.rs`'s `built()` refuses an expanded program name.
    - The words come with their quotes removed, so a quoted one cannot be told from a bare one; the one exemption is the value of `--body`/`-b` and `--title`/`-t`, which is text and may hold them. The price is that a `--jq` or `--search` value with a bracket or a brace is refused too.
## Budget

- Kelpie paces against each account's weekly window. The daily allowance is what is left of the week divided by the days until reset (100/7 on a fresh week), one figure for the day, not spread by the hour (decided 2026-09-27 on #15), given the gates already in place: the 5-hour window and the board's own screening.
  - A day is 24 hours counted from the weekly reset, so the days until reset are always whole. The allowance is fixed when the day begins and kept in the state file, so a restart keeps it.
  - Today's spend is the week's utilization now minus its utilization at that read, the maintainer's own sessions included. Once spend reaches the allowance, no work item is dispatched and those in flight continue.
  - `pacing.kickoff_hours` (8 by default, about 1.8% an hour) only divides the allowance into the per-hour figure `status` shows.
- The 5-hour window is a local limiter: at 50% no turn starts, dispatch included, until the window resets. Usage is read only before a dispatch and before a turn that has not begun, never mid-turn, and a turn resumed after a restart is not held. A hold is trusted for at most 10 minutes, since reset times are printed to the minute and a window can reset mid-read.
- A maintainer's `add <issue>` is not held by the daily allowance, the way it already skips the board's screening. The 5-hour window still holds its turns.
- `pacing.enabled` (on when absent) turns both limits off for a stretch when usage does not matter, such as a free reset coming (decided 2026-09-28 on #67). Nothing is held, including on an unreadable reading, but usage is still read before each dispatch and turn, so `status` shows `pacer.enabled: false` beside the live numbers.
- When usage cannot be read, the pacer holds both limits and says so in `status`. A pacer that guessed would spend the account it exists to protect.
- Per account since #129. Each account keeps its own day start, allowance, 5-hour stop and holds; Codex's day start is `codex_pacing` in the state file, written only once one exists.
  - A new work item is paced on every account the project's calls spend (each listed implementer's and each session reviewer's), and holds on the first one over its allowance or past its 5-hour mark: a local implementer with a Claude reviewer still spends Claude's week. The worker's turns are paced on its agent's account, and a reviewer's session on its own agent's account with the same 5-hour stop.
  - `status.pacer` lists each account the project spends, and any other read this run, under its name (`pacer.claude`, `pacer.codex`), with what holds a new work item on it. Hold reasons name Codex ("Codex's 5-hour window is at 55%") and keep Claude's wording.
- A work item has a spending cap, `budget.per_item_usd` ($10 when absent, kept in whole cents; shep-pm/shep-kelpie#492).
  - It is compared with the priced calls of the worker and the reviewers together, a call whose harness reports no dollars counting nothing, and only before a worker turn or a review round starts (a local round, a reviewer's session, a review bot's round), beside the pacer's check, so a call in flight is never cut off. Past it the work item parks on a `stuck` ruling for `over-budget`.
  - A yes doubles its cap and the worker carries on from the phase it was in, or the review round that was due starts. A no with a note sends the worker the note and doubles the cap too, so one answer buys one more stretch; parked in a review, the note is a fix turn and the pull request is reviewed again from the first round.
  - The state keeps how many times the cap was doubled (`budget_raises`) and not the cap, so a changed `budget.per_item_usd` applies to a doubled item too. The project manager never unsticks it, though `over-budget` may be listed in `rulings.pm_alone`.

## Where the time goes

- Phase timings (shep-pm/shep-kelpie#141, six phases since shep-pm/shep-kelpie#331, ADR 0006). Each work item records the seconds it spent in each of six timing phases: `worker`, `review`, `ci`, `ruling`, `merge` and `other`. Every second since the work item was created lands in exactly one.
  - `review` is every listed reviewer's round, a local round's wait for the GPU, a session's or an endpoint's run and whichever review bot's lease, window and review the work item waits on.
  - `ci` is the wait at the gate and a review round's wait for the run on the head its reviewer would read (ADR 0008).
  - `other` is between steps, a work item's wait for a slot (shep-pm/shep-kelpie#355) and the time the runner is down, a stop with `pause` included. A worker turn that waits for a local agent's lease is `worker`.
- Time is charged at the state's save, to the phase the work item was in before it, so no step that changes a work item has to know about timings. The phase is read off the work item's state, in this order: a turn this process runs, then a running call, then a wait for a slot, then a ruling, then the gate it waits at. A stopped runner's time is `other`, a parked item's included, as the maintainer decided on 2026-10-01 for a paused project, since nothing steps it.
- A turn marked running in the state file does not count as the worker's unless this process runs it. The runner keeps the turns it runs in memory, from the step that begins the call until the save that ends it, so no restart inherits one. A turn stopped with the runner is saved to the worker as it stops, and the downtime after it is `other`.
- The runner saves the charge at the start of a step once a work item has gone half a minute without one, so about every minute while the loop idles (it sleeps 60 seconds between steps), and once as it stops. Calls run in flight, so the loop beats while a long turn runs, and a crash or a kill costs only about the last interval to `other`. A beat that cannot save is told and let go, since the next save charges the same time. The save as the runner stops waits for the loop's pass to let go first, and is skipped when it does not, so a shutdown never waits on a pass.
- A local round's wait for the GPU is reported by the reviewer adapter, since it happens inside the call, and counts as `review` like the round after it. Only an endpoint round behind a gateway reports one, from paddock's wait for a turn (`RoundStage::Queued`). A command that queues on a lock itself, as the qwen script does, is no longer watched (#502), so all of it counts as the round.
- The state file keeps a record per finished work item in `history`, merged or dropped, with its wall time and every phase, and the last 100 of them (Facts). The oldest record goes in the same write that removes the work item. `status` shows each open item's `timings` and the ten most recent records, and `timings [n]` totals the last `n` (10 when left out) as JSON with a plain-text table.

## Where the usage goes

- Every model call is recorded in the control room's units (shep-pm/shep-kelpie#347), so kelpie's cost can be held against what it replaces (Why kelpie exists). The record is the usage ledger, `<kelpie home>/<project>/usage.jsonl`: one JSON object per line, appended and never rewritten.
  - A `call` line is written where the runner hears a call end, so no kind is missed: the worker's turns, every reviewer's sessions and local rounds, the project manager's wakes and `/compact`, and, from `shep kelpie issue`, the issue writer's headless runs. `issue --interactive` is the maintainer's own `claude` session in their terminal, which kelpie starts and does not read back, so it gets no line.
  - It carries the time, the issue (null for the project manager and the issue writer), the pull request once there is one, the role, the kind of call, the agent, harness, model and effort as the call started, the session, the four token counts (with `cache_write_5m`, the part of the cache writes kept for five minutes, where Claude Code reports it), the units, `cost_usd` (the change in the session's cost) or `unpriced`, the session's cost so far, the seconds it took, how it ended (`answered`, `unreadable`, `failed`, `timed-out`, `stopped`), a local round's `gpu_seconds` (from when it began to run, past its queue), and each account's last pacer reading (when it was read, the 5-hour and weekly percent, and when each window resets), where the runner has one: the issue writer's and imported lines have none.
  - A call that never reached a model (its settings could not be written, its harness could not start, its session had never begun) get no line, the stop's lines included. A Codex call whose thread could not be recorded after it ran is a `failed` call, not a setup failure, since the model ran.
  - A call that was stopped, ended past its ceiling, failed, or came back `unreadable` from its harness reports no usage, so its line carries no tokens and the units undercount it (a reviewer's reply that came back but read as no review keeps its tokens); its dollars are not lost, since the next call in the same session costs the change in the session's cost, which takes them in.
  - A call still in flight when the runner stops is told to stop and never heard from, so the stop writes its `stopped` line from the draft it launched with, one append per call inside the stop's bound. The drafts are kept outside the runner's lock, so a pass that has not let go by then holds none of this up, and whichever of the stop and the runner takes a draft first writes its line.
  - A call whose thread panicked is written as `failed` before the panic goes on. A call's line goes in only once its end is saved, since one not saved runs again and its session's cost by then takes in the first call's.
- Units are `input + 2 × one-hour cache writes + 1.25 × five-minute cache writes + 0.1 × cache_read + 5 × output`, rounded to the nearest whole unit: the weights the control room was measured in, with a five-minute write at its price against the hour's. Claude Code reports the split as `usage.cache_creation.ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`; a harness that reports no split counts every write as an hour's. The four counts are kept beside them, so another weighting can be worked out from the same lines. Dollars are kept only where the harness reports them, as for `status`.
- The project manager's session is no work item's, so its call's cost is worked out from the ledger itself: the change from the session's cost on its last written line, read from the file once per runner (again on the next call, if the read failed), so a restart costs nothing twice. A worker's or reviewer's call's cost comes from its work item's record, as `status` has it.
- A finished work item adds a `finished` line: issue, title, pull request, merged, wall time, units and dollars by role and in all, its local rounds and their seconds, review rounds (reviewers' rounds that answered, a second look counted with its first), fix turns (turns sent to fix a round's held findings) and rulings raised.
  - Review rounds count a review bot's read too. Units are each call's own rounded units summed, so the finished line agrees with its call lines.
  - A worker's or reviewer's call that reached its model and reported no usage has no call record, so its work item counts it in `counts` (`worker_unreported`, `reviewer_unreported`), and the finished tally adds those to the role's calls and unpriced calls. The state file's `history` record keeps the same as `spend`, and an open work item counts its rounds, fix turns, rulings and unreported calls in `counts`, which made the state file version 10.
- A runner keeps two logs of what it does (shep-pm/shep-kelpie#491). The shepherd's out log, `$SHEP_HOME/logs/<project>-0-out.log`, is for a person: one plain line per event, such as `#303 dispatched to claude-sonnet-5 (medium)`, and `up: koji, 0 work items open, 0 rulings waiting` as the runner starts. It never holds a JSON object. The machine-read steps are `<kelpie home>/<project>/steps.jsonl`, beside the usage ledger.
  - `steps.jsonl` is one JSON object per line, appended and never rewritten, the same `StepReport` the log used to carry plus an `at` field first: the time it was logged, RFC 3339 in UTC to the millisecond, from the system's clock (the runner's own clock counts whole seconds, and `watch` lays steps among transcript lines stamped to the millisecond). A line torn by a crash is ended before the next is added, as in the ledger. A file that cannot be written fails no step: the runner says so on stderr once, and again only after a write has worked.
  - The plain line is the step's work item, its name and its fields (`#7 finished merged=true`); a dispatch names the model and effort of its agent while the project still lists it, otherwise its agent.
  - `watch` and `usage --import` read `steps.jsonl` and no longer parse the out log. A runner from before this change left its steps in the out log with shep's time stamp; they are not read, so `--import` of an old out log adds nothing.
- A ledger that cannot be written fails no call and no step: the runner logs it once, and again only after a write has worked. A line torn by a crash is ended before the next is added, and a reader passes it over, a character cut in half included.
- `shep kelpie usage [<project>] [--since <date>]` reads the ledgers, not the shepherd.
  - It prints, per merged pull request, units, dollars, wall time, rulings and the worker's and reviewers' shares of the units, with their medians, each item's unpriced calls beside its dollars, the dropped work items' total, the project manager's and the issue writer's totals, and the calls of work items with no `finished` line (open, or from before the ledger). It prints plain text only: the verbs that run here rather than as a runner's trigger take no `--json`.
  - `--import <steps file>` reads a runner's `ended` and `asked` lines in `steps.jsonl`, the only calls runners logged with their usage before the ledger, into it as `imported` worker turns with no agent, model or duration, matching each line the ledger held before the import began to at most one logged call of the same session within 10 seconds of it, and skipping a line logged twice; two turns of one session that end seconds apart both go in, and one a partial ledger lost is recovered. A log is read lossily, so a bad byte costs only its line.
- To compare with the control room, take units per merged pull request. A baseline is a mean over a window: every unit spent in it, divided by the pull requests merged in it.
  - So `usage` prints a loaded figure the same way, every call's units in its window (the project manager's, the issue writer's and dropped work items' included) over the merged count, and holds each baseline against that first. The median of merged items' own calls is printed too, as the cost of a typical item. Each ratio is kelpie over the baseline, so below 1 is cheaper.
  - Every dollar figure the report prints says how many unpriced calls it leaves out (`$4.20 + 3 unpriced calls`), since a Codex or pi call reports no cost and the sum would otherwise read as complete.
  - The pacer's readings on each line give the week's percent spent between two merges, so allowance per merged pull request can be worked out the same way, within one weekly window: each reading carries when its week resets, and two readings with different resets span a reset, so their percents do not subtract.
  - Baselines such as the control room's are kept on the maintainer's machine only, in `<kelpie home>/baselines/baselines.json`, never in the repo, and `usage` prints each one's units per merged pull request with kelpie's loaded and median figures over it; a missing or unreadable file is skipped.

## Windows

Parent #241. The shell-outs and the tests' command fakes (#1149).

- Windows has no `sh`. Git for Windows ships `sh.exe` and `env.exe` under `usr/bin`, off `PATH` unless the installer put them there. `spawn::sh()` and `spawn::env()` return the Unix path on Unix. On Windows they find the Git for Windows that a `git.exe` on `PATH` belongs to, then its default install folders, and fall back to the bare name. The lookup is a pure function over injected `var` and `exists`, so it is tested on every platform.
- Per call site: a hook (`core/hooks`), the test-runner (`adapters/test_runner`), the dev server's install (`runner/dev_server/bump/install`) and the Claude sandbox's `env` (`adapters/claude/sandbox.rs`) run a command line the maintainer wrote in POSIX shell, so they require Git for Windows and use `spawn::sh()`. Porting them to Rust would give a different language to the same setting.
- `tar` and `shasum` in `upgrade` are reached only for a release asset, and no Windows asset exists, so they stay Unix. `cp -R` in `test_support` became Rust (`copy_dir`). `kill` and `ps` belong to #1148, sockets to #1147.
- Windows workers run through crabpot like the others (#1217, see Fence): the wrap is kelpie's own binary with `--crabpot` on every platform, `@anthropic-ai/sandbox-runtime` is off `tools install`, and the machine needs a one-time `crabpot windows-install`. The install fixes one loopback mode for every session after it, srt-win refuses a session that asks for the other, and `doctor` names each state of the install it reads from `crabpot::windows_status`.
- `test_support::write_fake(dir, name, &Fake)` writes a stand-in command from a small description (print, write to stderr, exit, sleep, record its arguments) as an `sh` script on Unix and a `.cmd` file on Windows, and returns the path to start. `write_script` stays for a script that needs real shell, which Windows runs only through `spawn::sh()`. A plain `true`, `false` or `sleep` stand-in, and the `upgrade` and `home` build fixtures, moved to `Fake`.
- A FIFO is a Unix file, so the tests that make one are `#[cfg_attr(windows, ignore = "a FIFO is a Unix file")]`.
- The tests Windows cannot run are in `docs/agents/sandbox-red-tests.md`, read from the source because the Windows job runs `cargo check` only. `core` and every crate above it do not compile for Windows yet (`std::os::unix`, `tokio::signal::unix`, `rustix::process`, `UnixStream`, mode bits), so the shell-outs there are checked on the host only.

- `board`, `board move` and `board top` order the list (shep-pm/shep-kelpie#495, slice of #294). One trigger action, `board`, takes no params to list, `move <issue> <position>` or `top <issue>`, and always answers the list under `board`: place from 1, issue, title, priority, `blocked` and `held`. It reads the ready issues the runner last read, the way `board.md` does, so a move works on what the maintainer sees and an issue not in that list is refused as not ready. A move puts the issue at the place and shifts the others by one, and the listed issues refill the places they held in `order`, so an open issue the list leaves out keeps its own place between them; a place before the first or past the last is refused, and a refused move saves nothing. It writes `order` and leaves `ranked` alone, so a move survives the next read until the issue's priority label changes. A move wakes the loop like any trigger that is not `status`, `timings` or `drain`.

## Decided, not built

- Overlapping items are bundled when the combined pull request stays small, and chained otherwise, the next worker in a chain starting from `--fork-session` of the previous worker's last session. Today the board's catch-up with `main` is where an overlap shows, as a conflict that is the worker's next turn, and the project manager may hold an issue whose paths overlap an open branch.
- One work item, one pull request, and every pull request boundary is a reset point. A worker that finds more than one pull request's worth of work would split the rest into chained work items, because a shep refactor issue became four pull requests in one session with a huge context, though the pieces barely overlapped. Today the issue writer scopes and splits before a work item exists.
- Conflicts nobody predicted: the item that reaches the gate later rebases after the first merges, and the footprint miss is logged. Serializing instead would be a project setting for small codebases.
- A calculator that reads every call's usage and acts at a phase boundary or a threshold, with an in-turn hook that hands a worker a decision ("delegate the next chunk"), never a cost figure. Which reset is cheaper, and when, is for the work-split tests.
- The pacer setting concurrency and logging utilization per unit by hour of day, so a peak-hour effect, if one returns, shows up in the data. "Do n work items today" once per-item costs are measured.
- The split of a GPU wait into the GPU busy with another round and the GPU idle (shep-pm/shep-kelpie#251), which needs a sample during the wait and new timing phases.
- Shots and the preview (shep-pm/shep-kelpie#54, #131), parked by ADR 0006: removed, recoverable from git history, not designed out.

## Watching

- `shep kelpie watch [<issue> | pm] [--back <n>] [--full]` (shep-pm/shep-kelpie#408) is one live stream of a project: its runner steps and the transcripts of the sessions kelpie runs, merged by time. It reads files only, the project's `steps.jsonl` and the transcripts it names, and asks the shepherd only to find the project from the folder. Polling every 250 ms keeps a line within a second of its write.
- A session is attributed by id, not by guessing its folder. The runner logs a `session-started` step as each call starts, from the three places that launch one (a worker's or reviewer's turn, the project manager's wake, the issue writer's label call), carrying the work item's issue (none for the project manager), role, agent, harness, session id and `transcript`, where the harness writes it. The step is logged by the runner's loop as it starts the call, not as a pass's result, since a call starts in the middle of a pass. `ended` and `asked` name a session only once its call is over, which is too late to follow it. A local review round has no session and no step.
- `Agents::transcript` says where a call's transcript is, so the adapter that knows the layout is the one that says: Claude Code's `~/.claude/projects/<cwd, non-alphanumerics as dashes>/<session>.jsonl`, pi's `<call home>/sessions/<time>_<session>.jsonl`, and Codex's `<call home>/sessions/<year>/<month>/<day>/rollout-<time>-<thread>.jsonl`. Codex names its own threads and kelpie learns which only as a call ends, so until then `watch` takes the newest rollout no known session claims that was written since the call began.
- It starts at the end: the whole log is read to learn the sessions, none of their old lines are shown, and each transcript is followed from its end. `--back <n>` reads the most recently written transcripts first and stops once the n-th newest line is newer than the next file's last write. A session that is resumed shows only the lines written since its new `session-started` step, half a second before it.
- Scope: `watch <issue>` keeps steps whose `issue` is that issue and sessions started for it, reviewers' and the issue writer's included. `watch pm` keeps the `pm-*` steps and the project manager's sessions.
- A steps file that predates the step shows its runner steps and none of its sessions, since the older steps name a session after its call and not where it is.

## V1 directions

Not built and not decided: where the maintainer wants kelpie to go after the MVP, noted 2026-09-28.

- Names and shape, per the maintainer: `shep-kelpie` stays the shep adapter (the runner, the dog and a library), published as crates. `kelpie` becomes the Tauri app on top of shep and those crates, shipped as an app, never as a crate.
- A kelpie GitHub App. Pull requests would come from its own identity instead of the maintainer's account, so the maintainer can request changes and approve like any reviewer. GitHub refuses both from a pull request's author, which is why #53 reworks on a `ready-for-agent` label. Installation tokens, scoped per repo, replace the maintainer's `gh` token, and the gates show as check runs. Webhooks would replace polling, but kelpie runs on the maintainer's machine, so they need a tunnel. Identity and check runs come first, on polling.
- Any CLI agent, through adapters. Claude Code, pi and Codex are behind the agent port, each inside kelpie's own sandbox, and pacing is per account. What is still Claude-shaped: the issue writer and the project manager run on Claude Code alone, `attach` on Claude Code, pi, Codex and goose, and only Claude Code runs a project's `worker.guard_hooks`. A project's `hooks` run on every harness and role.
- A spike on Restate (restatedev/restate), a durable-execution engine: journaled steps that resume after a crash, exactly-once calls, durable timers and promises, and single-writer keyed state.
  - The runner hand-rolls that today in its state file and resume logic, and the bugs fixed on 2026-09-28 were that class: a crash between the label call and the save that could summon twice, a review round cut short by a restart recorded as a failure (#46), a lease book lost on restart (#19). A ruling is a durable promise, and the turn ceiling and pacing are durable timers.
  - The spike models one work item's loop as a Restate workflow and measures whether the resume code shrinks and those bugs go away.
  - The costs: `restate-server` is one more process (it could run as a sheep), the tests change shape, and the server is under the Business Source License 1.1, which allows this use (it bars offering Restate as a hosted service). Its Rust SDK is MIT.
- Prior art, checked against each vendor's docs on 2026-09-28. GitHub's Copilot coding agent, Codex, Jules, Cursor's cloud agents and claude-code-action all ship issue to pull request, rework from review comments, and UI screenshots on the pull request. Copilot's Playwright defaults (on by default, localhost only) were the shape #54 followed, now parked. None of them has an ordered gate chain, pacing against a subscription's usage windows, or leases on a shared resource across repos. That is where kelpie's design effort goes.

## Test series

In order: transport, model calibration, work split, then code. Each series gets its own spec when it starts.

### Transport

- T1: `claude -p --resume`, one process per turn. The measured baseline.
- T2: a long-lived `claude --input-format stream-json --output-format stream-json` worker, held by a project runner.
- T3: `claude --bg` plus socket messages, attached with `claude attach`. Needs a permission rule for reading the target's peer token.
- T4: kelpie-served tools. In-process MCP over the stream-json control protocol, against a small stdio MCP binary that relays to kelpie over shep.
- T5: MCP channel push, if the account has channels.
- Lease round trip, runner to dog: a "wants" metric, then `status` and `grant` triggers, against a direct `shep trigger` to the dog if that reaches one. Latency, a dropped metric, and reclaim when a runner dies holding a lease.
- Rate limits: whether stream-json carries the utilization windows.

Measure each: cache write and read per turn, wake latency on an idle worker, a 100 KB output line through the runner, recovery after a crash, subscription auth, and whether the maintainer can take a worker over.

### Model calibration

Extend the maintainer's local model-calibration harness, which has only scored local models, to Opus, Sonnet, Haiku and Fable at two or three effort levels each. Reviewer and checker roles reuse its frozen sets: planted bugs, real false findings, and clean diffs for false alarms. A new implementer set of small shep specs with hidden tests scores tests passing, review findings, units and wall clock.

### Work split

Run the same real work items as inline, inline with compaction, a phased chain with handoffs, a crew of subagents working from an implementation doc, and agent teams (only if a long-lived transport wins, since teams do not spawn under `-p`). Run each with and without codebase-memory-mcp.

The model to fit: one session's cache reads grow with the square of its length. Splitting it into k pieces cuts reads about k times and adds a fixed cost per piece, so the best k is about √(0.025 × calls × growth ÷ per-piece cost). Worked example with guessed inputs (150 calls, a 41k floor, 500 output tokens a call): inline to 650k is about 6.9M units, three quarters of it cache reads; five phases, each with a 10k handoff and 30k of re-reading, is about 4.6M. The tests measure the real inputs.

### The e2e run (shep-pm/shep-kelpie#521)

- What a run does once the dog grants the host: `rsync -a --delete -e ssh` of the worktree to `kelpie-e2e/<project>` (excluding `.git`, with `--filter=':- .gitignore'`), `ssh -tt <host> "cd 'kelpie-e2e/<project>' && './<command>'"`, then `rsync -rt --no-links --no-perms --no-owner --no-group` of the results folder back. The code is `crates/dog/src/dog/e2e/run/mod.rs`; the lease, the wait and the hangup are `crates/dog/src/dog/e2e/mod.rs`.
- The host's lease is a `CountedLease` of capacity 1 named `e2e:<host>`, made at the host's first ask and kept in `Desk` beside `cargo-test`'s. Holders are not saved. The ceiling of 30 minutes counts from the grant, not from the ask, so a long queue does not eat it.
- What the local side starts is `ssh` and `rsync`, from argument lists. A test with scripts standing in for both records every start with its parent's process, and sees the dog's own process as the parent of each and no other program.
- What a run will not do: it never follows a link on the host (`--no-links`), never copies more than the results folder back, and refuses a link in the worktree wherever the copy meets one.
  - rsync writes into `e2e-back-<n>` in the project's folder (outside the worktree, cleared before and after), and `src/dog/e2e/run/deliver.rs` then opens the worktree's results path folder by folder with `O_NOFOLLOW` and creates each file through the folder it is in, so a link swapped in while the copy goes is refused, not followed.
  - A file already in the results folder is unlinked and made again with `O_EXCL`, never opened: opening would write through a hard link to a file outside the worktree, and block the dog on a FIFO.
  - A refused or failed copy-back is reported as a line of output and the command's own exit code stays the answer.
- `command` and `results` may hold only letters, digits, `.`, `_`, `-` and `/`, because they reach a remote shell. `shell_quote` quotes them as well, so the limit is a second guard.
- Exit codes: the command's own; `128 + n` when a signal ended it; 255 when ssh gave no code; 124 when the 30-minute ceiling ended the run (`Done` after a line saying so). `-tt` gives the command a terminal, so its stderr arrives merged with its stdout and with `\r\n` line ends, which the dog trims. Stdin to ssh is held open and never written, so the command does not see end of input.
- A worker that hangs up is heard because the dog keeps reading the connection while the run goes: end of input, or any input, ends the run. Dropping the run's future kills ssh (`kill_on_drop`), which closes the terminal and so hangs up the command on the host. A command that detaches from the terminal is not ended by that.
- The tests use stand-ins, not a real ssh and rsync: `src/dog/e2e/stand_in.rs`. The stand-in rsync honours only `--exclude=.git` and `--no-links`, so a run that drops one of them copies what it would have held back. No test here ran the real programs. The flags are as their manuals document, and the dog needs an rsync that has them (3.x): the openrsync that macOS ships may not.
- A test with the clock paused (`start_paused`) cannot wait on a child process with a virtual sleep: the runtime advances the clock as soon as nothing else is ready, so a timeout fires while the process is still working. The hangup and ceiling tests poll in real time (`spawn_blocking`) for what the process does, and use virtual time only for the ceiling.
- On the worker's own Mac, inside kelpie's sandbox, the tests that bind the dog's socket (`dog::door` and `lease::cli`) could not run, the same refusal as in the suite on macOS above. The `dog::e2e` tests, which start no socket, passed. The door tests also passed there through a temporary `UnixStream::pair` in place of the listener, which is not in the branch. CI runs them as written.
