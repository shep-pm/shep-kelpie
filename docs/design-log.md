# Design log

Decisions from the design sessions starting 2026-09-24, and the facts behind them. The hard-to-reverse ones are also ADRs in `docs/adr/`. The vocabulary is in `CONTEXT.md`.

## Why kelpie exists

Before kelpie, one long-running Claude session per project acted as a control room. It held the board, rationed reviews, relayed messages between the sessions that owned pull requests, and merged. Measured 2026-09-24 over shep's transcripts, in units weighted by cache pricing (cache read 0.1, one-hour cache write 2, output 5, uncached input 1):

- 2,352 transcripts, 6,020M units. The control room was 7% of that, and subagents were 54%.
- Transcripts that peaked above 500k context were 43% of all spend.
- The control room itself: 7,883 calls, median context 349k, 41 compactions, 80% of its cost in cache reads. 62% of its cost was calls that followed a Bash result (git 20%, gh 17%, the review driver 13%, the GPU queue 12%). Relaying messages was about 15%.

So kelpie moves the control room's rules (gates, locks, rate windows) into code, calls Claude only for the work and for judgement, and controls the other big cost: how large each agent's context grows.

## The shape

- Kelpie is a dog under its own pinned shepherd. Each project is a sheep, kelpie's project runner, and the project's workers are its lambs. See ADR 0001 and ADR 0002.
- Since shep-pm/shep-kelpie#110 the runners and the dog are sheep of the maintainer's own shepherd (ADR 0003). Kelpie is adopted there and left disabled, and `shep kelpie <command>` runs it in the caller's folder with `SHEP_HOME` set. `add`, in a checkout, reads the forge from `origin` and refuses a default branch other than `main`, which every branch is cut from. It makes the three labels the repo lacks, and registers two sheep, both stopped: the runner, named for the repo unless named on the command line, holding its settings as its `[app.dogs.kelpie]` table, and `kelpie-dog`, which runs the dog. The table is the defaults plus what the checkout and forge say: `repo`, `forge`, `ci` from whether `.github/workflows` exists, CodeRabbit on only for a public repo, and the local round off unless the maintainer's qwen script is installed. Lookout shows each key's description from kelpie's schema, which stands in for a comment per key, since shep keeps a table without comments. A project that still has its settings file from before the tables gets that file as its table instead, when it names this checkout. Everything is read before anything is written, so a refusal changes nothing, and each piece is made only when missing, so a second `add` changes nothing. A sheep of the same name that is not kelpie's, an enabled dog included, is refused. `start` and `pause` take a project's name, or find the one whose `repo` is this checkout. `start` first starts the dog's sheep and the runner's when they are down, and waits up to 30 seconds for the runner's own answer: a runner opens its channel before it takes its actions, and shep-channel answers `unknown action` in plain text meanwhile, so any reply that is not JSON means it is still starting. `status` asks every sheep with a kelpie table. A runner's state file now makes its own folder, since a project from `add` has none. From the control session's review: `add` refuses a checkout or repo another project's table already names, since two runners would take the same issues. `start` and `pause` act only on a sheep with a kelpie table that kelpie started as `runner <project>`, so a sheep of the maintainer's stopped on purpose is never started. Replacing a Flockfile dog deletes the old sheep first, so a failure leaves at most one, and reports the deletion before anything else can fail. The new dog keeps every variable the old entry set: shep withholds their values, so each comes from the environment `add` runs in, and one missing there stops `add` before anything changes. An adopted `kelpie` left enabled only restarts, so `add` says to disable it. After the re-review: `TMPDIR` and `PATH` are never taken from the shell, since a shell always has both and a moved dog locking the GPU under another `TMPDIR` than the runners' would let two rounds hold it, so an old entry setting either is refused until they come out of it, and `add` names every variable it did take. The one-runner check reads each other sheep's raw `repo` and `forge`, from its table or a Flockfile runner's old file, so a table that no longer parses still counts. `start` with kelpie adopted and enabled and no `kelpie-dog` says to disable it.
- Rust for all business code. A Tauri GUI comes after the MVP. Until then kelpie is run and watched from a Claude session.
- One kelpie serves every project, because the GPU lease, the CodeRabbit window and the usage pacer are machine-wide or account-wide. Realistically two projects at once. shep comes first.
- Kelpie and its runners talk through shep: triggers down, `channel.metric` up on the bus. Runners report running totals, because metrics drop under backpressure. A private socket only if the MVP shows the round trips do not hold up.
- Book leases (CodeRabbit first) live in the dog, and only runners and the maintainer ask for them. Workers and crew never touch the GPU or CodeRabbit. The GPU lease is the lock the maintainer's qwen scripts already take, and the dog stays out of it (decided 2026-09-26 on #5, option A): a qwen round takes the lock itself, and so does `kelpie lease run|take gpu`, in the same format, for the maintainer's own by-hand use. A project runner's own qwen-review loop (shep-pm/shep-kelpie#11) follows the same rule: it never takes or holds that lock either, leaving it entirely to the round it spawns, unless the project's local round asks it to (shep-pm/shep-kelpie#107).
- A runner asks for a book lease by raising running totals, `lease.<kind>.want.<epoch>` and `lease.<kind>.return.<epoch>`, and the dog grants with `grant <kind> <epoch>`. The epoch is the runner's pid, which shep's process events also carry, so the dog reclaims an old run's leases on `restart` without racing the new run's first metric.
- The dog saves its book to `<kelpie home>/dog/book.json` after every change, with the same atomic write as a runner's state file, and loads it on start (decided on #19, the ticket's first option). The file keeps holders and queues with their epochs, each review window's quota, summons and quoted refusal, and each runner run's totals, so a restart grants no second summon inside a window. On start the dog checks every runner in the book against the live flock: a holder whose sheep now has a different pid, or none, is reclaimed. A missing file, or one another build wrote, loads as an empty book. One that claims this format and cannot be read also starts empty, but with the CodeRabbit window closed for an hour, as if a summon had just been accepted.
- MVP: a thin vertical slice. One project, one worker at a time, merge on `ask`, no GUI. shep-pm/shep-kelpie#5 is its spec.
- A project's settings are its runner sheep's `[app.dogs.kelpie]` table, and kelpie's own are its `[kelpie]` section of `dogs.toml` (shep-pm/shep-kelpie#114, on shep 0.11). Lookout edits both from kelpie's `--schema` answer once kelpie is adopted, and draws the webhook's URL `<set>`. Every project setting is required except those added after the first build, so a missing or malformed one stops the runner with a message naming it as a dotted key, `review.loop_guard = 0`. The project's state file stays at `~/.kelpie/projects/<project>/state.json`, written atomically.
- A runner reads its own table through the shep client, with `DogSheepSettings` and `DogConfig` on the name `kelpie`, not from the dog (decided on #114). shep answers both to any client, a runner is a sheep with no `DogRuntime`, and reading it itself keeps a runner's start independent of the dog being up. It finds its table by `SHEP_NAME`, else the project's name. A table goes through the settings file's own parser, rendered as TOML, so a table and a file take the same keys, defaults and checks.
- A settings change takes effect live, at the runner's next wake (within a minute when idle) and then at the next step or call that reads it. `repo` and `forge` wait for the next start, since a work item's worktree and pull request belong to them. A work item in flight keeps the worker model it was added with. A change is checked as a start checks it, and one that fails keeps the settings in effect and is offered again at each wake, so it lands once what refused it is fixed. Reading on each wake was chosen over subscribing to `config.sheep.kelpie`: no second connection to carry across a shepherd's reload, and a minute is soon enough.
- The files kelpie used before the tables, `~/.kelpie/projects/<project>/settings.toml` and `~/.kelpie/settings.toml`, still load while a table is unset, with a notice naming `kelpie settings move <project>`. That command writes an equal table and the file's own text as the section, refuses to overwrite a table that is set, and deletes nothing.

## Work

- GitHub Issues stay the tracker for the work kelpie does, with the `ready-for-agent` family of triage labels. The board of work items lives inside kelpie.
- Priority orders the board (shep-pm/shep-kelpie#144). Ready issues labelled `priority: P0` go first, then `P1`, `P2`, `P3`, then those with no priority label, the labels shep uses. Within a priority the oldest issue goes first, as before, and an issue with several priority labels ranks by the highest. Adoptions and reworks still go before any issue. A blocked, assigned or otherwise passed-over issue does not hold up the next one, whatever its priority.
- A planning session forms work items: the maintainer with an Opus agent, interactive, fed mechanical footprints. Kelpie adds the results to the board and dispatches.
- Overlapping items are bundled when the combined PR stays small, and chained otherwise. The next worker in a chain starts from `--fork-session` of the previous worker's last session.
- One work item, one PR, and every PR boundary is a reset point. A worker that finds more than one PR's worth of work splits the rest into chained work items and divides its remaining budget among them. The motivating case: a shep refactor issue became four PRs in one session with a huge context, though the pieces barely overlapped.
- Conflicts nobody predicted: the item that reaches the gate later rebases after the first merges, and the footprint miss is logged. Serializing instead is a project setting for small codebases.
- Several work items per project (shep-pm/shep-kelpie#103). A pull request waiting on CodeRabbit's hourly window, CI or a merge ruling held the whole project: overnight on shep that was about one pull request an hour with the GPU idle between rounds, and the playground sat all night on one merge ruling. A project's `max_items` (1 when absent) sets how many work items are open at once, each with its own branch, worktree, build folder, phase and rulings. The board opens one whenever a slot is free, adoptions and reworks first as before, and never an issue or pull request whose work item is open. A step tries each open item, and the board while a slot is free, starting after the one that last acted, and an item waiting on a lease, CI, CodeRabbit or a ruling yields to the next. An item parked on a ruling keeps its slot, so raising `max_items` is how work moves past it. Items merge independently, and one merging sends the others through the existing catch-up with `main` at their gate. A ruling names its work item, and its answer moves the item parked on it. `gate` and `drop` take the item's issue when more than one is open. `status` lists every open item under `work_items`, keeping `work_item` as the oldest. The state file is version 2, and a version 1 file loads as a list of one.
- What `max_items` does not change: one worker, review or shots call at a time per project, since the steps run on one thread, and every gate per item. The CodeRabbit lease is still one grant, one summon: the runner records which item took it, and another item waits for a grant of its own rather than inheriting it, which would summon twice in a window the dog counted once. The GPU stays the qwen script's own lock. `max_items = 1` behaves exactly as before.
- What a worker finds along the way: fixed now if small and in a file it already touches, otherwise filed by the worker itself as a `needs-triage` issue.

## Workers

- A worker outlives its sessions. A reset, by compact or by clear with a handoff, keeps the same worker. Which reset is cheaper, and when, is for the work-split tests.
- The worker picks the work split: inline, phased, or a crew. The project manager never does, so it keeps a minimal context for merges, git and gates.
- The calculator runs as needed. Kelpie code reads every call's usage, which is free, and acts only at a phase boundary or a threshold. Inside a turn, a skill plus a hook that fires before an agent spawn or past a context threshold.
- Agents never see budget numbers. Budget talk makes models stop after every task. Budgets live in kelpie's code, and the in-turn hook hands a worker a decision ("delegate the next chunk"), never a cost figure.
- Workers start with `--setting-sources project` plus a settings file kelpie writes for each one. They get the project's CLAUDE.md and project skills, and none of the maintainer's hooks, plugins or skills. Kelpie's own guard goes into every worker's file (shep-pm/shep-kelpie#108), and the guard hooks the project settings name follow it. `worker.guard_hooks` is optional and the example leaves it empty, since its old entry was a file on the maintainer's machine and a beta tester's copy would fail every Bash call. A hook command that does not resolve (its program on `PATH` or at its path, and every absolute or `~/` path in it) stops the runner at start, naming it. `local` was dropped on shep-pm/shep-kelpie#98: it adds only the worktree's `.claude/settings.local.json`, a file no repo commits and nothing kelpie runs needs, and it was the door the #55 review walked through. The review round and the judge start the same way.
- Claude Code's own files in a worktree (any `.claude` folder, and `.mcp.json` at the root) are the maintainer's (shep-pm/shep-kelpie#98). Every Claude call in the worktree loads them, and a hook there runs outside the sandbox. The #55 review wrote a SessionStart hook into `.claude/settings.local.json` with the Write tool, and the next `claude -p` ran it unsandboxed. Four fences now: the sandbox denies writes to them, `kelpie confine` refuses the file tools there (as written and as resolved, in any case), each Claude call first checks the root's `.claude` folder and `.mcp.json` against a trusted commit, and a pull request that changes them parks on a ruling. The check before a call passes when every one of those files matches `origin/main`, the commit the branch left `main` at, or a head the maintainer accepted; a difference fails the turn, and the ruling carries the files. Kelpie asks before a worker turn on a branch with a pull request (a rework starts on one), before the qwen-review loop's steps, before CodeRabbit's, and before CI, naming the files the branch changes from `main`. A yes accepts them at that head, so later heads that leave them alone pass, and a no stops the work item: the worker cannot write those files, so a note would not help it.
- Permissions: `bypassPermissions` with three layers under it. The project's `main` ruleset (shep's already blocks direct pushes, force-pushes and deletion, and requires a PR and passing checks). Claude Code's sandbox, confining Bash writes to the worktree (`sandbox.filesystem.allowWrite`, `failIfUnavailable`, `allowUnsandboxedCommands: false`), with kelpie's `confine` hook holding the file tools to the same folders. A short denylist of what only the project manager does: `gh pr merge`, `gh pr ready`, adding the `review please` label, reading credential paths. Kelpie flags any label or ready change it did not make and parks that worker. No auto mode: classifier outages have blocked work before.
- Model defaults, settled 2026-09-26 and kept as project settings: workers on Sonnet 5 at medium effort, implementing inline. Claude review rounds on Sonnet 5 at medium effort. Judging findings on Opus 5.5 at low effort. The relay on Haiku 4.5 at low effort. A `worker:<model>-<effort>` label on an issue overrides the worker's defaults for that item. Planning stays on Opus.
- A worker turn has a ceiling, `turn_timeout` in project settings, 60 minutes by default: decided 2026-09-27 on #16, over having no ceiling. The implementation series' 152 turns ran a median of 70s and at most 18 minutes, so a turn still going at 60 minutes is more likely stuck than busy. Kelpie stops it with the stop ladder, keeps its session, parks it and raises a ruling; a yes resumes the same session for another turn, a no stops the work item.
- A worker fills the repo's pull request template, and a project can add worker instructions (shep-pm/shep-kelpie#87). Seen on kelpie's first shep pull request, shep-pm/shep#639: the worker wrote its own body with `gh pr create --body`, which skips the template, and the body carried an em dash the maintainer never uses. When the worker's worktree has a template in any place GitHub reads one (`pull_request_template.md` in the root, `.github/` or `docs/`, in any case, or a `PULL_REQUEST_TEMPLATE` folder), each turn's instructions gain a line telling it to fill that template, still ending with `Resolves #<issue>`. A repo without one gets the `pr` step's skill instead (below). A project's optional `worker.instructions_file` is read once when the runner starts and appended to the instructions for rules the repo's docs don't carry; a missing file stops the runner naming it.
- Every step kelpie drives an agent through runs a skill, mattpocock/skills by default, each overridable (shep-pm/shep-kelpie#147). The maintainer wants kelpie to follow that process, with kelpie's own prompts as the fallback rather than the process. Kelpie vendors the skills its steps use in `skills/`, pinned to one upstream commit with its MIT licence and the pin's `git ls-tree` in `blobs.txt`, which a test checks the copies against. The binary carries them and each runner writes them out as a plugin, `mattpocock`, under `~/.kelpie/projects/<project>/skills/`, passed with `--plugin-dir`, so a project installs nothing and an override is just another folder. A step's prompt starts with the skill's slash command and carries kelpie's own prompt as its arguments: `implement` on the worker's first turn on an issue, `code-review` on each Claude round, `diagnosing-bugs` on a red CI turn. `tdd` and `pr` happen inside a turn, so the worker's instructions name them, and a repo's pull request template still wins over `pr`. `triage`, `to-tickets` (#139), `to-spec`, `handoff` and `retro` (#104) are vendored and overridable but no step drives them yet. A project's `[skills]` table points a step at a skill folder (copied into a plugin of its own, `kelpie-<step>`), a skill in a plugin folder, or `none`. A skill that cannot load runs kelpie's own prompt, and the runner logs why and `status` shows it, since Claude Code itself passes an unknown slash command through as text (Facts). Rework first turns, fix turns and the judge run no skill. An adoption's first turn runs none of its own, but when the gate hands it a red CI run, that run's `diagnosing-bugs` command leads the prompt, since a command only runs from the very start. The vendored files stay byte-identical to upstream, and kelpie wraps every skill call in headless rules that win over the skill, decided by the maintainer on the #170 review: there is no one to ask or wait for, so the agent decides and records the decision (the worker in its pull request's body, keeping `<kelpie-question>` for what only the maintainer can decide); no sub-agents or Task; the reply format is kelpie's wherever a skill names another; the Claude round runs no commands; and the worker runs no `/code-review` of its own, since kelpie's rounds review the pull request. The Claude round's settings deny `Agent`, `Task` and `Bash`, because `code-review` otherwise spawns two sub-agents and answers under `## Standards` and `## Spec` headings, which `read_review` would refuse. A project's own skill folder or plugin inside `~/.kelpie/projects/<project>/skills/` stops the runner, since kelpie rewrites that folder, and a project plugin named `mattpocock` or `kelpie-<step>` does not load. For #139 and #104: `to-spec`, `to-tickets`, `triage` and `handoff` publish to the issue tracker or write outside the worktree, which the worker's GitHub denies and the confine hook refuse, so those steps need their own settings rather than the worker's.
- A turn that fails, because its worktree cannot be prepared or its call errors, raises a ruling carrying the reason, alerted like the rest (shep-pm/shep-kelpie#57): found on the playground's first live rework, where a leftover local branch failed the turn and left the work item idle with no ruling. A yes retries the step that failed and a no stops the work item as a no on a turn timeout does. A rework reuses a local branch left behind when it matches its branch on `origin` exactly; a fresh work item's branch is still cut new from `origin/main`, and a local branch holding a commit `origin` lacks stays a refusal.

## Review and merge

- Kelpie runs the qwen round itself and hands the findings file straight to the worker's next turn. No model reads the findings and rewrites them.
- The qwen queue: critical first, then closest to merge, then arrival. A running round is never preempted, since a kill takes 20 to 70 seconds and throws the partial round away.
- The Claude round is a fresh review session each time, never the worker's, on Sonnet 5 at medium effort, with findings delivered as a file like qwen's.
- Opus 5.5 at low effort judges every qwen, Claude and CodeRabbit finding before the worker sees it: whether it holds, and its severity, which it may regrade. The worker fixes only the findings that hold.
- CodeRabbit is in the first build's gates. Its free plan reviews public repos only, so the gate is a per-project setting, and the runner refuses to start with it on for a repo the forge reports as private. With it off, a work item goes from the qwen-review loop and CI straight to the merge ruling.
- The worker opens its own draft PR with its own title and body. Only the project manager summons CodeRabbit (adds `review please`) or marks a PR ready. With CodeRabbit on it marks the PR ready as the first round starts, since CodeRabbit skips drafts (shep-pm/shep-kelpie#65); with it off, at the merge, after a yes or under `auto`. shep's `.coderabbit.yaml` gates auto-review on that label, so opening a PR spends nothing.
- Merge authority is a project setting: `auto`, `ask`, or `ask-surface` (ask only when a PR touches operator-facing surface). The default is `ask`. `ask-surface` is still refused.
- `auto` (shep-pm/shep-kelpie#83), chosen over running shep's merges from a Claude control room so the merge rules stay in kelpie's code. It replaces the merge ruling and nothing else. Where `ask` would raise it, `auto` merges by the path a yes takes: the head the gate passed, CI green on it, the latest `main`, CodeRabbit satisfied where it is on, and a merge commit. Every other ruling still asks, and the tests raise each one under `auto`. Kelpie never puts `ready-for-human` on for the merge. A merge that no longer holds, because the head moved, CI stopped being green or `main` moved, goes back to CI as a withdrawn yes does, and CI catches the branch up. A merge the forge refuses takes that path once; a second refusal on the same work item parks it on a `merge-refused` ruling, and any answer to it gives the next refusal its catch-up again. Its pull request comment names the head and leaves the forge's reason out, since that text is not written for strangers. After an automatic merge kelpie posts a notice to the webhook naming the project, the pull request, its issue and the merged head. A notice is not a ruling: it has no id, takes no answer, goes to the relay only where the webhook is off (shep-pm/shep-kelpie#118), and is saved with the merge so it goes out once, retried like a ruling's post and never ahead of one. A merge at the gated head that a restart or a lost answer hid, found merged on the next look, still gets its notice, and so does one that lands after kelpie read its error, since kelpie records the head it tried. A merge the gate started under `auto` goes ahead only while the project is still `auto`: a project switched back to `ask` goes back to CI and gets the merge ruling. Under `ask` a yes on a `rebase` or still-red ruling vouches for whatever head the gate sees next, because the merge ruling follows; under `auto` nothing follows, so the yes reads the branch's tip, and a tip the gates never saw is adopted and goes back through the qwen-review loop and, where it is on, a CodeRabbit round. The same holds for a head the gate finds with none known, such as one a yes under `ask` vouched for before a restart onto `auto`. The switch back to `ask` is read after the pull request's state, so a merge that landed before the switch still gets its notice. `status` shows the project's merge authority.
- The relay, a stopgap for the first build: a background Claude Code session that kelpie sends each ruling to over the session's messaging socket. It pushes the question to the maintainer's phone and passes the reply back verbatim through `shep trigger`. A merge yes through it needs the maintainer's tap on a permission prompt. It rides an undocumented protocol and costs tokens per ruling, so every ruling is also posted once to a webhook (Discord or ntfy), and the relay is best-effort beside it. The webhook becomes the only path when the relay goes.
- The qwen-review loop (shep-pm/shep-kelpie#11). Once the worker's draft pull request is open, `Phase::Review` runs before CI: rounds alternate qwen and Claude, qwen first, each round's raw findings judged one at a time by Opus before the worker ever sees them. A round with no findings is clean at once; one with findings, once every finding is judged, sends only the held ones to the worker's next turn as a file, using the judge's own (possibly regraded) severity for the nit rule. The loop ends once two rounds in a row hold nothing above a nit, which a strict alternation makes one of each reviewer without a special case. Past the round guard (`review.loop_guard`, default 8), the worker parks for a ruling; a yes clears the guard for the rest of that work item, rather than asking again every following round. Kelpie never takes or holds the qwen GPU lock itself: the script does, waiting up to an hour, which is normal, not a hang. A round's findings and its completion marker both come from disk (`QWEN_REVIEW_OUT`, redirected per work item rather than the script's own path slug, so a test rig never touches the maintainer's real `~/.claude`), never from stdout. A file the script skips as too large is cut into a `-U25` hunk against `origin/main` and reviewed again on its own, with its findings folded back in against the original path. The Claude round and the judge run with no sandbox and no bypassed permissions, since neither writes anything; the Claude round may read the worktree with Read, Grep or Glob to check its work, the same as `pi` mode in the maintainer's own qwen-review skill.
- The local round is a per-project choice (shep-pm/shep-kelpie#107), since a beta tester has neither the maintainer's script nor the same GPU. `review.local` picks `off`, `endpoint` or `command`, and a table or file without it runs `~/.claude/scripts/qwen-review.sh` as before, so the live projects load unchanged. With it off, every round is the Claude round, and one round that holds nothing above a nit ends the loop: with no second reviewer to alternate with, a second clean round would only ask the same model again. The round guard and the fix-turn rule are unchanged. `endpoint` is kelpie's own reviewer for any OpenAI-compatible server: it diffs from the round's base with ten lines of context, numbers each line by its place in the new file so the model can name one, cuts the diff into chunks sized from the settings' `context` (three bytes a token, a quarter of the context kept for the reply), and sends each with a fixed prompt in kelpie's code, reading findings back in the same `SEVERITY|file:line|what|why` format. A thinking model's `<think>` block is dropped before the findings are read, and a reply that ends inside one fails the round, since it reviewed nothing. A reply with no finding counts as clean only when it is exactly `CLEAN`, for the endpoint and the Claude round alike: an empty or prose reply reviewed nothing, and with the local round off the Claude round is the only review before CI. A command's `round-N.txt` and its marker are removed before each run, since the folder is the issue's and a rework or a retried round would otherwise read the last run's. `command` keeps the qwen script's own contract, which the README now sets out, and adds `KELPIE_REVIEW_HEAD`. Kelpie still never takes the GPU lock for a command that takes it itself. `gpu_lease = true`, on either kind, has kelpie take it around the round in the scripts' format and on their schedule, and let it go after. The runner checks at start that a command is an executable file and that an endpoint answers `GET /models`, and refuses to start otherwise, naming it. A live change to `review.local` gets the same check before it takes effect, and one that fails is refused and offered again at each wake. It is not held for the next start, as `repo` and `forge` are: nothing in flight belongs to it, since each round reads it when the round begins. It does not check the model is listed, since llama.cpp's server answers to any model name.
- A fix turn for held findings counts only if it moves the branch's head on `origin` (shep-pm/shep-kelpie#40), in a qwen-review round and a CodeRabbit round alike (shep-pm/shep-kelpie#49). Kelpie fetches the head when it sends the findings and again when the turn ends, from git rather than the forge, whose head lags a push. An unmoved head parks the worker on a ruling, and a yes sends the same findings again.
- Built in shep-pm/shep-kelpie#14. Kelpie starts the relay with `claude --bg --remote-control kelpie-relay --name kelpie-relay --setting-sources ""`, its own settings and appended instructions, in the maintainer's home folder (already trusted). The fixed `--name` is how kelpie avoids a second one: every send looks the session up again in `claude agents --json --all` by that name, never keeping a handle across restarts, and starts one only when none is found. A merge yes needs a tap because `kelpie relay-yes <project> <id>` is the only trigger the relay's settings gate behind `ask`; `kelpie relay-answer <project> '<id> no <note>'` and `'<id> answer <text>'` are pre-allowed. Both subcommands send `rule <params>` to the project's sheep, as `shep trigger <project> rule <params>` would; naming them precisely, rather than gating a pattern over `shep trigger` itself, keeps a free-text note that happens to contain "yes" from tripping the merge gate. The relay's send is best-effort and untried again on failure: the webhook beside it is what a ruling actually depends on, per the decision on #13 above. The relay is cleared (its process killed by pid, found the same way) once a day, only when a ruling is about to be sent, never for a notice, since a clear would end a question still up. No live push reached the maintainer's phone in this build: that check is the maintainer's own, on the playground.
- The relay runs nothing but its two commands (shep-pm/shep-kelpie#80). It runs them by kelpie's absolute path, the runner's own binary, in its instructions and both permission rules, since its `PATH` need not hold kelpie. Every other tool call, `shep` above all, is refused outright by `kelpie relay-gate`, a PreToolUse hook in its settings, and never asked: the default permission mode would ask on the phone, and `dontAsk` would refuse the tap on `relay-yes` too. The gate passes `ToolSearch`, `PushNotification`, and each command alone with its arguments in the shape the instructions write. Each message's header line says whether the ruling `wants` an answer or a yes or no, so the relay picks its command from that rather than from the question. A failed command is reported to the maintainer word for word, never worked around. The hook line ends in `|| exit 2`, since Claude Code blocks only on a hook's exit 2 and a kelpie that cannot run would otherwise fall through to a prompt. A send that changes the relay's settings or instructions clears the running relay first, since a session reads both only when it starts. A runner's refusal (a reply with an `error`) fails `relay-yes` and `relay-answer`, and `rule`'s refusals describe what a ruling takes rather than naming a command to run.
- A ruling the relay was sent and that is settled some other way is told to the relay (shep-pm/shep-kelpie#90). The relay answers through a `relay-rule` action, the same as `rule`, so the runner knows which answers it gave; every other answer, by `rule` or by `drop`, queues a notice for each relayed ruling it settled, and the next step tells a running relay, never starting one. The notice carries `settled=<how>` where a question carries `wants=`, and a line saying how. A ruling counts as relayed once the relay's send succeeds, saved with the ruling so a restart keeps it, and also while that send is out, since the send runs outside the runner's lock and an answer can land first; a notice queued only because of that window is dropped if the send then fails. A webhook retry for a ruling the relay already holds does not send it the question again. A clear of the relay, the daily one or the one a changed settings or instructions file makes, forgets which rulings it holds and marks each for a resend (shep-pm/shep-kelpie#150). The next steps send each to the relay again, oldest first, before the ruling that was about to go: to the relay alone, since the webhook already has it, and retried like any relay send. A fresh relay is told of a ruling only once it has been asked it. A resend still in its retry wait never holds back a newer ruling or a notice. A crash between the clear and the save that marks the resend loses it: the next start finds the files unchanged and no daily clear due. A clear by another project's runner is not seen, and that relay may still get a notice. Queued notices are kept in memory only: one lost to a restart leaves a late tap to `rule`'s own refusal, as before. `relay-yes` and `relay-answer` fall back to `rule` when shep-channel answers `unknown action: relay-rule` in plain text, as it does for a runner started on an older kelpie, which never registered the action. Since a runner always replies JSON, any other reply that is not JSON fails the command. The relay cannot take back a question it asked, so its instructions have it check for a notice before running anything for a reply, and answer a reply about a settled ruling with one plain line and nothing run.
- The merge gate (shep-pm/shep-kelpie#9). After the qwen-review loop settles, kelpie waits for CI. A red run is the worker's next turn, naming the failed checks; a second red run on a head the worker left alone parks it on a ruling. A green run on a branch that has the latest `main` raises the merge ruling, and a branch without it is rebased and pushed by the project manager first. A conflict is the worker's next turn too (shep-pm/shep-kelpie#61), naming the files: it merges `origin/main` in and pushes, so nothing is force-pushed. A turn that leaves the same head, or a conflict on the same `main` again, parks it on the `rebase` ruling.
- A ruling is a log line, a status entry and a webhook post, all carrying the same question and the triggers that answer it. Ruling ids never repeat. A no with a note is the worker's next turn. The pull request gets a comment for every ruling but a merge (shep-pm/shep-kelpie#89). It says what happened and that it waits on the maintainer, and names no command: `ready-for-human` already says the pull request waits, and the webhook and relay carry the question.
- Worker questions (shep-pm/shep-kelpie#13). A worker ends its final message with its question between `<kelpie-question>` and `</kelpie-question>`, and only a block that ends the message counts. Kelpie parks the worker on a ruling that carries the question verbatim, and `shep trigger <project> rule '<id> answer <text>'` makes the answer the worker's next turn. A question takes only an answer, and a gate ruling only a yes or a no. A question asked before the pull request exists has no comment, and goes with its work item on a drop.
- Every ruling, whatever raised it, is also posted once to one webhook, not only when the relay cannot be reached (decided on #13). It is named in kelpie's own settings, its `[kelpie]` section of `dogs.toml`, which every project shares: a `[webhook]` table with `kind` (`discord` or `ntfy`) and `url`, both required. A failed post is logged and tried again after a minute, doubling to at most half an hour, and a ruling counts as alerted only once a post lands, so a restart between the post and the save can post it twice. The URL is a credential: it reaches `curl` on stdin, never in its arguments, curl's own messages are dropped, and no error, log line, status or comment carries it. Plain `http` is accepted only for a stand-in on the same machine.
- Rulings reach the maintainer by the webhook, the relay or both (shep-pm/shep-kelpie#109), so a tester with only ntfy or only the Claude app can run kelpie. `ruling_channels` is a list of `webhook` and `relay`, in a project's settings or in kelpie's own, the project's winning, and both when neither names any, so a live project keeps both with no edit. An empty list is refused at start. A channel that is off is never touched: with the relay off no relay is started, cleared or told anything, and with the webhook off kelpie's settings need no `webhook` table, or none at all. A ruling counts as alerted once the webhook post lands, or once the relay's send lands where the webhook is off, and is retried the same way. The notice of an automatic merge follows the same channels (shep-pm/shep-kelpie#118): the webhook where it is on, else the relay, as a push notification with no question, so it leaves nothing waiting to block the next ruling. It never clears the relay, since a clear would end a question still up, and where both channels are on the relay is sent nothing, as before. The choice is a set of channels, so a further way to reach the maintainer is one more variant.
- Rulings are answered from ntfy (shep-pm/shep-kelpie#111), so ntfy alone is a full alternative to the Claude app. An answer that acts proves itself with the maintainer's authenticator code, decided by the maintainer over a first build that posted a one-time code on the alert: that code sat on the topic it guarded, so anyone who could read the topic could merge. The code is RFC 6238 TOTP (HMAC-SHA-1, 30-second steps, six digits). `shep kelpie totp` draws the 160-bit secret once into `<kelpie home>/totp/secret` (the folder 0700, the file 0600) and prints it as an `otpauth://` URI and a terminal QR code to scan; `shep kelpie totp --rotate` draws a new one, written beside the old and renamed over it, the folder synced after so a crash cannot bring the old one back (a first `shep kelpie totp` links its file into place instead, so two at once keep one secret), and every runner reads the file afresh for each reply, so the old secret's codes stop at once. A secret file, or a totp folder, anyone but its owner may read or write stops the runner. Workers and the shots' dev server are denied `~/.kelpie/totp/**` like the other credentials. A reply names the project, since every project reads the one topic and ruling ids are per project: `<project> <id> yes <code>`, `<project> <id> no <note> <code>` or `<project> <id> answer <text> <code>`, the code always last. The part after the project is read by `rule`'s own parser, so a change to `rule`'s grammar reaches ntfy replies too. The code is checked against the time ntfy took the reply, which no sender can set, and taken in that step and the one before. Every code the maintainer sends is on the topic afterwards, so every right code anywhere in a post is claimed before anything else about it is read: whether answers are on, whether it is kelpie's own, which project it names, how old it is, or how the code was typed. Every text the post carries counts, its title, tags and attachment name included, and in each every decimal digit of any script is taken in order with whatever stands between dropped, so `123-456`, `123 456`, full-width, Arabic-Indic or math-bold digits all spend the code. A post spends the codes of three steps: the one before and its own, which `verify` takes, and the one after, from a phone whose clock runs ahead, which a replay could send once that step comes. Their codes are computed once a post and compared to every six digits in a row. A secret that cannot be read, or a claim that cannot be written, holds the post at the head of the queue, with the read position behind it, and backs off; it never passes the post by with its code unspent, and nothing on the topic says a code is still live. Only the exact shape, six ASCII digits last, can act. Review probes showed that a reply that answered nothing (a no with no note, a code followed by a phone's stray period, a code in the title, or a reply read in the same poll as the wrong code that turned answers off) left its code for a reader to reuse. A claim is `<kelpie home>/totp/used/<step>`, holding the id of the ntfy message that first sent the step's code, written beside its name, synced and hard-linked into place, so it is whole or absent. Every runner reads every reply, so a runner that finds the step claimed by the same message counts it as that message's, and one claimed by another message is a replay: it runs nothing, and the named project's runner tells the topic to send the next code. A wrong six-digit code is counted once by message id under `<kelpie home>/totp/failed`, and the fifth turns answers from the topic off for every project (RFC 4226 section 7.3), with one line on the topic that also suggests moving to a new topic, until `shep kelpie totp --unlock` on the terminal; a right answer forgives the count. Only a wrong code in the exact shape counts. While they are off, alerts say nothing of replies and the topic is not read. A reply with a valid code for a ruling already settled runs nothing and gets a line saying so, and a refusal from `rule` goes to the topic as a line too. Anything else is ignored and logged without its text. The alert ends with the replies that answer it and carries no code and no buttons, since a button cannot carry a code the maintainer has not typed yet. The runner reads the topic's cached messages (`/json?poll=1`) after the last one it read, saved in the state file, every 15 seconds while an alerted ruling waits, and for an hour after an alert lands, backing off to five minutes while reads fail. A read reaches back ten minutes and three steps at most, since a replay of the next step's code, which a post spends, can still verify up to three steps after the post, so a saved position ntfy no longer holds never returns its whole cache. A reply older than ten minutes is read only to spend its code, so a replay just inside the window finds it used. Claims are let go an hour behind the older of the claimed step and this machine's step, since the step is ntfy's clock, so a local clock running ahead never lets go of a claim in use. With no secret yet, alerts say nothing of replies and the topic is never read. An answer from ntfy tells the relay, the same as `rule` does. So a reader of the topic can read every ruling and every code already sent, and answer nothing, and a writer who is not the maintainer gets five guesses at a one-in-a-million code before answers stop. Once ruling ids are global, the project in a reply can go. Four limits are accepted. Anyone who can write the topic can turn answers off with five guesses; that fails closed, `rule` and the relay still answer, and only the terminal turns them back on. And an alert's text is not authenticated: a code proves who answered, not what they were shown, so a writer who posts a fake alert could get a real answer to a question kelpie never asked, though only for a ruling id that is pending. And a topic writer who posts every code can burn steps without tripping the lockout, since a right code is never a wrong one: that only delays the maintainer's answer, and ntfy rate-limits the posts. And a post kelpie cannot read in full, such as a message over 4,095 bytes that ntfy turns into `attachment.txt`, is not fetched: it spends every step a code sent with it could name, answers nothing, and gets one line on the topic saying it was too long to read and to send a shorter reply with a new code.
- A yes merges only the head it was asked about, while CI on it is green and it has the latest `main`. Otherwise kelpie withdraws the yes, reruns CI, and asks again. The merge is `gh pr merge --merge --match-head-commit`, never a squash, and kelpie then removes the worktree, both branches and the build folder.
- A pull request the maintainer merges by hand ends its work item with no merge by kelpie. One closed without merging parks the worker.
- CodeRabbit rounds (shep-pm/shep-kelpie#12). On a project with the gate on, green CI starts a round while CodeRabbit is not yet satisfied, and the merge ruling waits for it. The dog's CodeRabbit lease is one window per account: its quota is the newest footer's by when it was posted, whichever project reports it, one an hour until one is read, the hour runs from each accepted summon, and a refusal's quoted opening overrides the book's count until a later summon is accepted. A runner reports these as `window.<kind>.<summoned|opens|quota-<n>>.<epoch>` metrics, each carrying a Unix time: the summon, the opening, or the footer. A round records its own label changes as kelpie's, so a restart after the label went on records that summon instead of making a second one. A grant to the maintainer counts as a summon at once, since the dog cannot see what they do with it.
- A round first marks a draft ready, in a pass of its own before the summon, then waits until the forge reads it ready or two minutes pass (the checks settle), since the forge can show the old state for a few seconds. It never marks again inside that wait. It records that in `known` so the foreign-change check never reads it as someone else's. A rework on a ready pull request leaves it ready. A round then takes the lease, takes `review please` off if it is already on and puts it back on, and gives the lease back as soon as CodeRabbit answers: a review running or landed (accepted at the moment of the summon), or a refusal (the label comes off and the round asks again). A head a review already covers is never summoned. A summon with no answer in ten minutes is counted as spent (once it has had its re-send, below), and two hours with no review parks the worker on a ruling. Once a review covers the head, the label comes off and the judge rules on every open thread: rejected ones are resolved, held ones go to the worker, and its fix goes through CI to the next round. Satisfied means no thread open and nothing held; a worker's turn clears it. At the cap with findings held, a yes sends the worker the findings and lifts the cap for the rest of the item, the same meaning a yes has on the qwen loop's guard.
- Kelpie records each issue whose work item it finished, merged or dropped, and the board never takes one again: GitHub closes an issue from `Resolves` a moment after the merge, and the playground's board re-picked #22 in that moment. `shep trigger <project> drop [<issue>]` ends a work item without merging, paused or not, naming its issue when more than one is open, keeping its pull request and branch on the forge.
- Reworks (shep-pm/shep-kelpie#53). A rework makes a work item of an open pull request from a `kelpie/<issue>` branch on the repo itself, opened by the account kelpie acts as (`gh api user`, read once a run), dropped or finished alike. A collaborator's or a fork's pull request on such a branch is not kelpie's, and the poll leaves it alone. A rework that asks but cannot start, because the forge failed or a label would not come off, is passed over for that poll like a ready issue that could not be taken, and the next pull request and then the board get their turn. The pull request asks for one: `ready-for-agent` on it, since kelpie opens pull requests under the maintainer's account and GitHub won't let an author request changes, or a review requesting changes from anyone else with a hand in the repo (its owner, a member or a collaborator, since anyone can review a public repo's pull requests). The runner checks its open pull requests on the board's poll, before any ready issue, and `shep trigger <project> rework <pr>` asks by hand. Each review that started or was refused a rework is recorded and never asks again. It is refused while the project has `max_items` open or one for its issue, and when the latest review has no body and no unresolved comment; a refusal the pull request asked for goes to it as a comment, with the label off.
- The triage labels say whose turn a pull request is. A rework takes `ready-for-agent` and `ready-for-human` off as it starts. Kelpie puts `ready-for-human` on, and takes `ready-for-agent` off, at the merge ruling and whenever a work item ends unmerged, and takes `ready-for-human` off when an answer sends the worker back to work. The gate ignores `ready-for-agent` added while a work item is in flight, so a second ask waits for that item to end. The board's `gh issue list` never lists a pull request. `shep kelpie add` makes both, and `review please`, where the repo lacks them (shep-pm/shep-kelpie#110); nothing else in kelpie creates a label. The worker starts a new session on the branch as `origin` holds it, so commits the maintainer pushed stay, and it pushes without force. Its first turn names a file in its build folder that holds the review's body and its unresolved comments verbatim, each with its file and line. The turn goes to the qwen-review loop and then every other gate. Its issue stays finished, so only the trigger brings a rework, never the board.
- Adoptions (shep-pm/shep-kelpie#84). An adoption makes a work item of an open pull request kelpie didn't open, so the maintainer's other sessions can hand theirs over. The maintainer adopts one with `shep trigger <project> adopt <pr>`, or with `ready-for-agent` on one whose branch isn't `kelpie/N`, seen on the board's poll. Kelpie refuses, with a comment, one that is closed or merged, comes from a fork, merges into a branch other than `main`, has another author than the account kelpie acts as, or names no issue it closes; a refusal from the label takes the label off. The lowest issue it closes becomes the work item's issue. Adopted pull requests wait in the state file for a free slot, one at a time, and one closing an issue whose work item is open waits for it to end, and go before reworks and the board; `status` lists them as `adopted`. One the label adopted leaves the queue when the label comes off, and one merged or closed while it waits leaves without a comment. One starts on a fresh worktree of its branch as `origin` holds it, with its labels, ready state and head taken as kelpie's own, so nothing already there reads as a foreign change, and `ready-for-agent`, `ready-for-human` and `review please` come off, so no push summons CodeRabbit outside the lease. It goes straight to CI and then CodeRabbit rounds, whose cap counts the commits CodeRabbit already reviewed, a clean review included and a reply in a thread (an empty review) not. A review of the head it arrived with counts once, when the gate finds it. Reviews from before the adoption count toward the cap but never satisfy a round, under `ask` and `auto` alike: the maintainer adopts a pull request so kelpie runs its CodeRabbit rounds, so it needs one review CodeRabbit posts after a summon of kelpie's, on a head at or after the adoption. One from before with threads still open lands as a round, so its findings reach the judge. A round that would end satisfied summons instead, and only a review posted after that summon answers it, even on a head CodeRabbit already reviewed. The worker's first turn is whatever the gate first sends it, behind a file in its build folder holding the pull request's title and body and its issue. A latest review requesting changes from its owner, a member or a collaborator goes in that file too and is the first turn at once, followed by the qwen-review loop. That loop, and its judge, diff from the head the pull request arrived with, so only the worker's own commits are reviewed. A branch behind `main` is merged, never rebased, and nothing on it is force-pushed. The branch's owner may still be pushing, so a push counts as the worker's only when the worker's worktree holds it, and one found before a worker's turn sends the work item to the gate instead of the turn. Either way a push from anyone else parks it as on kelpie's own branches. The merge follows the project's `merge_authority`.
- Full reviews (shep-pm/shep-kelpie#100). The label asks CodeRabbit only for what is new since it last read the pull request, and a branch kelpie caught up with `main` holds nothing new to it. So on a pull request CodeRabbit has reviewed before, an adopted pull request's owed summon, and any summon after kelpie's own catch-up push, asks with a `@coderabbitai full review` comment instead, with the label taken off so no push summons outside the lease. A pull request CodeRabbit never read keeps the label alone. The comment is a summon like the label: it waits for the dog's lease, is counted from when it was made, and is saved as made before it is posted, so a restart never posts it twice (a comment the forge refuses leaves the round waiting for the lease again). CodeRabbit marking the head "Review completed" with nothing posted since the summon is an answer: after a minute's settle, since a review posts a few seconds before that status, kelpie reads it as a clean read, unless a summon is owed. An owed summon answered that way asks once for a full review, and then waits for it as for any summon, so two hours with nothing is still the `coderabbit-silent` ruling. The control room measured about six real findings from a full review to one from an incremental review on shep.
- A confirmed finding left unfixed at merge becomes a follow-up issue (shep-pm/shep-kelpie#142). The judge holds a finding and the worker fixes it; one the worker leaves as out of scope goes, in the findings file's own format, into `deferred-findings.md` beside the findings file in its build folder, which the findings file's header names. Once the pull request merges, kelpie reads that file once, before it removes the build folder, and files each finding as an issue on the project labelled `ready-for-agent`, linking the pull request. An open issue whose body names the file, and whose title matches or whose body says the same thing, gets a comment instead of a second issue. Under `ask` a `follow-up` ruling comes first, raised after the merge: a yes files them and a no drops them. Under `auto` they are filed with no ruling. Only what kelpie itself sent the worker is filed: each round's held findings are kept on the work item, and a line in the file counts only when it names one of them by file, line and what, and the issue carries kelpie's text, not the worker's, so a worker cannot put its own words on the tracker. A refuted finding never reaches the worker, so it is never held. If the forge keeps refusing for six hours from its first refusal (issues off, a missing label, a rejected body), a `follow-up` ruling lists the findings and the reason: a yes tries again for another window, a no drops them. Passes do not count, only time, so a short outage of the forge's own costs nothing. A finding fixed or refuted in a later round stays in the held union, since it is only ever filed when the worker also names it in the deferred file. An open issue counts as already holding a finding only when its body names the file. A crash between opening an issue and saving that leaves a redundant "confirmed this too" comment on the new issue at the retry, which is accepted. A finding whose text names a folder on this machine is not posted (the forge guard refuses it), so it is left out and counted in the step's report rather than retried. Not built: a reviewer that answers after the merge, since nothing watches a pull request once its work item is gone, and a worker that defers every finding, whose fix turn pushes nothing and raises the not-pushed ruling.
- A summon CodeRabbit never acknowledged is sent once more (shep-pm/shep-kelpie#122). A sign within fifteen minutes of the summon counts as hearing it: the "Review in progress" status on the head, a change to any of its comments (the walkthrough is edited in place), a review or any other status on the head, or a rate-limit notice. With none, the runner sends the summon again through the same choice between the label and `@coderabbitai full review` that made the first one, says so in the log (`SummonedAgain`), and waits as before. The re-send is the same round: it keeps the lease the first summon took, opens no window of its own, and the hour still runs from the first summon. A label summon goes off and on again, since a label already on sends CodeRabbit no event. It is saved before the comment goes out and made at most once per summon, so a second silence falls to the two-hour `coderabbit-silent` ruling, counted from the first summon. It is sent only under a lease row of the work item's own, so after a restart, which clears the rows, it is not sent under a grant another item took. A review that stays "Review in progress" still falls to the two-hour ruling, and only the newest status on the head says whether it is running. The ten-minute spent count now applies only after the re-send, since the lease has to be held for it.
- A clean catch-up goes back to CI only, with no new CodeRabbit round (decided 2026-09-29 on shep-pm/shep-kelpie#106). With several work items open, one merging sends the others through a catch-up with `main`, so this comes up often. Kelpie's own rebase or merge of `main` with no conflict leaves the pull request's own diff unchanged, so there is nothing new for CodeRabbit to read, and CI checks the combined code. A catch-up the worker resolves is a new push of its own, so its turn clears CodeRabbit's satisfaction and the next green CI starts a round, as a fix for red CI does. A summon owed for another reason after a catch-up still asks for a full review, as above.
- Two kinds of reviewer, behind two interfaces (shep-pm/shep-kelpie#123, shape chosen 2026-09-29). A local reviewer runs on this machine against a diff and hands its findings back when the call ends: qwen, the Claude round, or #107's endpoint or command. A pull request reviewer is summoned on the pull request and answers there, later, within a rate window of its own: CodeRabbit now, cubic and Codex next. They share their output, a finding with a severity, file, line and text, and from there the judge and the worker's fix are one path. They are two interfaces because the rest is different: a pull request reviewer needs a lease on its window, a sign that it heard, a re-send when it did not, threads to resolve, and a head its review covers, and a local reviewer needs none of that. CodeRabbit and cubic follow the same script on GitHub, so the pull request side is one review bot provider, the runner's round, with a profile per bot for what differs: its login, its label and full-review comment, how its answers read (heard, reviewed, refused, done), how a thread's severity reads, its quota and the lease it spends. Profiles and their parsers are code, tested against the bot's recorded output. CodeRabbit is the first profile, and nothing it does changed in the move. The saved names stay CodeRabbit's (the `coderabbit` phase, lease row, ruling kinds and tally, and the `coderabbit` settings), since the state file and live settings carry them. Settings do not override a profile's simple fields yet.
- cubic is the second review bot profile, and the outside round goes to whichever listed bot is free (shep-pm/shep-kelpie#124, shape chosen 2026-09-29). Kelpie's `[kelpie.reviewers]` defines each bot by its window, `reviews` in `hours`; CodeRabbit is defined with one an hour when absent, and cubic only once defined. A project's `pull_request_reviewers` lists defined bots in preference order, `coderabbit` alone when absent, and a start refuses a bot kelpie does not define. A round waiting to summon asks the dog for every listed bot's lease and summons the first listed it was granted, giving the other asks back unless a sibling work item waits on them, so a pull request waiting on CodeRabbit's hour takes a cubic round and one with both busy waits for whichever frees first. The phase records the bot holding the round (`bot`, left out for CodeRabbit), and so does the silent ruling. cubic has no label, so it is always summoned by its comment. A refusal parks the bot until its window opens: CodeRabbit quotes when, and a refusal that quotes nothing, such as cubic's, parks it for its window's span. The round cap, a fixed `coderabbit.rounds`, an adoption's count and a rework's count all add every listed bot's reviews, and one review from any listed bot settles an adopted pull request's owed summon. The dog reads the definitions from kelpie's section when it starts, so a changed window reaches it on its next start; the runner takes a changed list or definition at once. Until a bot's definition reaches the dog, the dog never grants it, since a lease with no window would be granted freely and a refusal would have no window to close. A round that lands judges every listed bot's open threads, not only those of the bot that answered, and a work item that ends gives back the lease of the bot its round holds even if the list has dropped it. CodeRabbit's private-repo check applies only when it is listed, so a private repo can list cubic alone. The profile's `P1`..`P3` level is the finding's severity (P0 and P1 high, P2 medium, P3 low) and goes to the judge with cubic's confidence as the finding's why.
- A fixed review budget (shep-pm/shep-kelpie#158). The review loop cost hours on a fast-moving project for mostly nits: the divisor cap gives CodeRabbit at least two rounds at one review an hour, and the local and Claude rounds alternate until one of each in a row is clean. `coderabbit.rounds` sets a fixed number of rounds per work item in place of the divisor's cap. The last round's held findings go to the worker as any round's do, with the `review please` label taken off first, and its fix push goes to CI and the merge ruling with no further summon. Once the rounds are spent no later turn summons again, a CI fix or a merge ruling's no included, though an adopted pull request still gets the one review owed to it. The count is per pull request, so a rework, which stays on its pull request, starts from the reviews CodeRabbit already gave it and spends no second round. `review.local_rounds` caps the local rounds per work item, counted across every pass of the loop, so a merge ruling's no or an accepted foreign change does not start the count again; once they are spent every round is Claude's, and one clean Claude round ends the loop. Unset, both keep the behaviour above. shep's table sets `coderabbit.rounds = 1`.
- The foreign-change check covers the head too (shep-pm/shep-kelpie#69). Kelpie records the branch's head on `origin` as each worker turn ends, and the head its own catch-up push leaves, so a worker's merge of `main` and kelpie's rebase are never foreign. At the gate, once the forge's head matches `origin`, any other head parks the worker on a ruling that names the commit. A yes moves the worktree to that head, refusing if it holds work not pushed, and sends it through the qwen-review loop and, where it is on, a CodeRabbit round before the merge ruling. A yes on a `rebase` or still-red ruling asks the maintainer to fix the branch, so it vouches for whatever head the gate sees next. Under `auto` it vouches for no head the gates did not see. A commit pushed while the worker's turn runs is read as the worker's, and gets the gates that turn's code gets.
- A work item saved before the gate existed stays with its worker until `shep trigger <project> gate` sends it in. The trigger takes only an item whose turn has ended with a known pull request.
- Seeing the UI (shep-pm/shep-kelpie#54). A repo opts in by carrying `.claude/launch.json` on `main`, the file Claude Desktop's preview reads; without it nothing changes. Kelpie reads it from `origin/main`, both whether it exists and the configuration it starts, so a worker cannot widen its own sandbox by adding one or pick the shots' dev server command by editing it. That dev server cannot write the shots folder. Kelpie's shots start the file's configuration (`preview.configuration`, else the first) under the sandbox runtime `srt`, capture each route at 390 by 844 and 1280 by 800, light and dark, in headless Chromium from kelpie's own Playwright, and stop the server. Routes are `preview.routes` (default `/`) plus every route the worker named through `mcp__kelpie__shots`. Kelpie takes shots of the head before each Claude review round, which gets the PNG paths and the folder in `additionalDirectories`, and before the merge ruling, whose run goes on one pull request comment that later runs edit in place. The PNGs are committed to `kelpie-shots/<number>` on `origin`, never the work item's branch, and the comment links them by commit. Kelpie deletes that branch when the work item finishes, merged or not, so the comment's images stop showing then. A failed or partial run is reported and kept, and holds no gate. Every worker with a launch file gets the Playwright MCP server and kelpie's shots tool through `--mcp-config`. `preview.domains` reaches the worker's sandbox, the shots' dev server sandbox and both browsers alike. `kelpie tools install` puts the pinned `@playwright/mcp`, `@anthropic-ai/sandbox-runtime` and Playwright's headless Chromium under `~/.kelpie/tools`.
- Chosen over driving Chromium over the DevTools protocol from a crate: measured on the playground, raw CDP's own network-idle event never fired with Vite's dev server open (30s timeout on every shot), where Playwright's `networkidle` settled each shot in about 1.1s. Playwright also brings request routing and colour-scheme emulation, which raw CDP would rebuild.
- The preview's switch is `enabled = true` under `[app.dogs.kelpie.preview]` in the project's settings (shep-pm/shep-kelpie#131). The launch file on `main` is still needed, and still read from there, but it turns nothing on alone: shep carries one for the maintainer's own Claude preview of `web/`, and kelpie took shots of every shep pull request anyway.
- The project manager is kelpie code plus one-shot judgement calls (reading commits that landed after a review, auditing a docs PR's claims, checking new plans for overlapping intent) and a state file workers read. Coordination needs footprints, not a codebase map: planned files from the plan, actual files from the branch diff, `git merge-tree` for conflicts, and GitHub issue dependencies for order.

## Budget

- Kelpie paces against the account's weekly window. The daily allowance is what is left of the week divided by the days until reset (100/7 on a fresh week), one figure for the day, not spread by the hour. The hours set at kickoff (default 8, about 1.8% an hour) only produce the per-hour figure `status` shows. It covers all account usage, the maintainer's own sessions included.
- The 5-hour window is a local limiter: pause near 50% until it resets.
- Built in #15. A day is 24 hours counted from the weekly reset, so the days until reset are always whole. The allowance is fixed when the day begins (what the week had left, over the days left) and kept in the state file, so a restart keeps it. Today's spend is the week's utilization now minus its utilization at that read, the maintainer's own sessions included. Once spend reaches the allowance, no work item is dispatched and those in flight continue. The kickoff hours only divide the allowance into the per-hour figure `status` shows.
- A maintainer's `add` is not held by the daily allowance, the way it already skips the board's screening. The 5-hour window still holds its turns.
- Decided 2026-09-27 on #15: the allowance is one figure for the day, not spread by the hour. The kickoff hours only produce the per-hour figure `status` shows, given the gates already in place: the 5-hour window and the board's own screening.
- The 50% mark stops a turn from starting, dispatch included, until the window resets. Usage is read only before a dispatch and before a turn that has not begun, never mid-turn, and a turn resumed after a restart is not held. A hold is trusted for at most 10 minutes, since reset times are printed to the minute and a window can reset mid-read.
- Decided 2026-09-28 on #67: `pacing.enabled` (on when absent) turns both limits off for a stretch when usage does not matter, such as a free reset coming. Nothing is held, including on an unreadable reading, but usage is still read before each dispatch and turn, so `status` shows `pacer.enabled: false` beside the live numbers.
- When usage cannot be read, the pacer holds both limits and says so in `status`. A pacer that guessed would spend the account it exists to protect.
- The pacer sets concurrency, and logs utilization per unit by hour of day. A peak-hour effect, if one returns, shows up in the data rather than being hard-coded.
- "Do n work items today" comes later, once per-item costs are measured.

## V1 directions

Not built and not decided: where the maintainer wants kelpie to go after the MVP, noted 2026-09-28.

- Names and shape, per the maintainer: `shep-kelpie` stays the shep adapter (the runner, the dog and a library), published as crates. `kelpie` becomes the Tauri app on top of shep and those crates, shipped as an app, never as a crate.
- A kelpie GitHub App. Pull requests would come from its own identity instead of the maintainer's account, so the maintainer can request changes and approve like any reviewer. GitHub refuses both from a pull request's author, which is why #53 reworks on a `ready-for-agent` label. Installation tokens, scoped per repo, replace the maintainer's `gh` token, and the gates show as check runs. Webhooks would replace polling, but kelpie runs on the maintainer's machine, so they need a tunnel. Identity and check runs come first, on polling.
- Any CLI agent, through adapters. The worker, reviewer and judge are already ports. Three things are Claude-shaped today. The worker adapter leans on Claude Code's session resume, usage output and settings file. The guardrails are Claude Code's own sandbox, deny rules and hooks, so another CLI needs kelpie to supply its own sandbox, the largest piece. Pacing reads Anthropic's weekly and 5-hour windows, which becomes a budget per provider.
- A spike on Restate (restatedev/restate), a durable-execution engine: journaled steps that resume after a crash, exactly-once calls, durable timers and promises, and single-writer keyed state. The runner hand-rolls that today in its state file and resume logic, and the bugs fixed on 2026-09-28 were that class: a crash between the label call and the save that could summon twice, a review round cut short by a restart recorded as a failure (#46), a lease book lost on restart (#19). A ruling is a durable promise, and the turn ceiling and pacing are durable timers. The spike models one work item's loop as a Restate workflow and measures whether the resume code shrinks and those bugs go away. The costs: `restate-server` is one more process (it could run as a sheep), the tests change shape, and the server is under the Business Source License 1.1, which allows this use (it bars offering Restate as a hosted service). Its Rust SDK is MIT.
- Prior art, checked against each vendor's docs on 2026-09-28. GitHub's Copilot coding agent, Codex, Jules, Cursor's cloud agents and claude-code-action all ship issue to pull request, rework from review comments, and UI screenshots on the pull request. Copilot's Playwright defaults (on by default, localhost only) are the shape #54 follows. None of them has an ordered gate chain, pacing against a subscription's usage windows, or leases on a shared resource across repos. That is where kelpie's design effort goes.

### How messages reach sessions

Read from the desktop app's bundle and the CLI binary, 2026-09-25.

- Desktop app sessions run through the Agent SDK: the app spawns `claude --input-format stream-json --output-format stream-json` and holds its stdin. Its session tools are an in-process SDK MCP server with no socket or port. Sending a message writes a user turn into the target's stdin. An outside program cannot reach a desktop session.
- CLI sessions each register `~/.claude/sessions/<pid>.json` with a messaging socket (`/tmp/cc-socks/<pid>.sock`) and a 0600 peer token file. `SendMessage` is JSON lines over that socket, with an auth line first. The protocol is undocumented.
- `claude agents --json` lists live sessions, interactive and background, with their status. It is meant for scripting and needs no TTY.
- Background sessions: `claude --bg` prints an id that `claude attach`, `logs`, `stop` and `rm` take. `--bg --resume <id>` continues a session in the background.
- An MCP server can push `notifications/claude/channel` into a session, which would wake it. It is gated per organisation and off on Bedrock and Vertex.
- A socket message wakes an idle background session, about 5 seconds, 3 times out of 3. It arrives framed as a message from another Claude session.

### Usage limits

- Weekly limits were never tied to time of day. Anthropic announced in March 2026 that 5-hour limits drain faster on weekdays between 5 and 11am PT. Secondary sources report that was removed for Claude Code on Pro and Max on 2026-05-06.
- `/usage` reports the share of usage spent while four or more sessions ran in parallel, and says queueing uses the shared limit more evenly. Parallelism is about timing against the 5-hour window, not a surcharge.
- Headless `/usage`, measured 2026-09-26 on Claude Code 2.1.283 (recorded in `fixtures/usage-result.json`): `total_cost_usd` 0, `num_turns` 0, `local_command: "usage"`, about 1.5 to 3 seconds. The `result` text has one line per window, `Current session: 2% used · resets Sep 27 at 3:40am (America/New_York)`, and a `Current week (all models)` line beside per-model ones (`Current week (Fable)`). Percentages are whole numbers.
- Reset times carry no year and are rounded to the minute. The same weekly reset printed as `Sep 25 at 10:59pm` on two reads and `Sep 25 at 11pm` on a third, so a weekly reset that moves by under an hour is the same week. A reset later today may print as time only.
- `--setting-sources ""` and `--no-session-persistence` both leave `/usage` working, so the read runs none of the maintainer's hooks and writes no transcript.

### Worker profile and sandbox

Measured 2026-09-26 on Claude Code 2.1.283.

- `--setting-sources ""` also drops the project's CLAUDE.md and project skills, so workers do not use it.
- `--setting-sources project,local` keeps both and drops the maintainer's hooks, plugins and skills. It brought the floor from 29.2k to 24.8k. It also loaded the maintainer's global CLAUDE.md in one probe.
- A hook passed through `--settings` still runs under `project,local`.
- The sandbox keys exist as named: `sandbox.enabled`, `sandbox.failIfUnavailable`, `sandbox.filesystem.allowWrite` and `sandbox.network.allowedDomains`. With only the worktree and the build folder writable, a warm-cache `cargo check` passed and a write to the home folder was refused.
- The build folder must exist before the worker starts.
- The sandbox confines Bash and its children only. Claude's Edit and Write tools go through permissions, and under `bypassPermissions` only deny rules and hooks stop them. So kelpie adds a PreToolUse hook, `kelpie confine`, that holds the file tools to the worktree and the build folder. Live, it refused a Write to the home folder under `bypassPermissions`.
- When the working folder is a git worktree, Claude Code opens the repo's whole common git dir to sandboxed writes, `config` and `hooks` included, whatever `allowWrite` says. A worker could plant a hook that kelpie later runs unsandboxed.
- `denyWrite` beats `allowWrite`, so the git dir cannot be narrowed by allowing less. Denying `config`, `hooks`, `info`, `HEAD`, `index`, `packed-refs`, `refs/remotes` and `refs/tags` still lets a commit from the worktree land, and refuses writes to all of them. A wildcard deny spans `/`: denying `refs/heads/*` also refused the work item's own `refs/heads/kelpie/7`.
- The worker's settings file still lists what a commit writes (`objects`, the worktree's own git dir, and its branch's ref, lock and reflog), in case a later Claude Code stops opening the git dir itself. On this version that list cannot be shown minimal, since the whole dir is open anyway.
- Measured 2026-09-27 on 2.1.283, on a private playground repo (issue 37): the `Read(~/.kelpie/projects/**)` deny refused the held findings file to the Read tool ("File is in a directory that is denied by your permission settings"), and the sandbox refused it to Bash. The worker said so, pushed nothing and ended its turn, in both rounds. The findings file now lives in the work item's build folder, which the worker reads and no commit carries.
- Live on the pinned worker repo's commit (#7's demo), two workers committed on their branches inside the sandbox. One ran cargo into a cold build folder with a warm registry, 2.4 GB of it. Writes outside were refused through Bash and through Write, and so were `.git/config`, `~/.ssh` and `gh pr merge`.
- Measured 2026-09-29 on Claude Code 2.1.284, in scratch repos, with sandboxed Bash under `bypassPermissions` and `allowWrite` holding the worktree. With no `denyWrite` of kelpie's, the sandbox already refused writes into an existing `.claude` folder and to `.mcp.json`, in any case, by redirect, `cp`, `mv` and `ln -s`, and refused `mkdir .claude`. It let `mkdir other && mv other .claude` create the folder at the root, and let any nested `.claude` be created. So kelpie's own `denyWrite` of `<worktree>/.claude`, `<worktree>/**/.claude` and `<worktree>/.mcp.json` is what holds: with it, every one of those writes was refused, `mv` into place and nested `.CLAUDE` included, and ordinary files in the worktree and the build folder were still written. `**` in a `denyWrite` path matches folders at any depth.
- Same day: `--setting-sources project` keeps the project's CLAUDE.md and project skills, and drops `.claude/settings.local.json`, whose SessionStart hook ran under `project,local` and not under `project`.
- Same day, with this branch's `kelpie confine` as the PreToolUse hook: Write to `.claude/settings.local.json` and `.mcp.json`, and Edit of `.claude/settings.json`, were refused with "is Claude Code's own configuration, which only the maintainer changes", and Write to an ordinary file went ahead. Claude Code's own settings validation refuses an Edit that makes a settings file invalid before any hook runs.
- Same day: APFS folds Unicode case, so a file created as `.mcp.jſon` (U+017F, long s) opens as `.mcp.json`. The sandbox refused writing it, since it judges the path the file system resolves, but kelpie's own checks matched names by ASCII case only and missed it (found in the security review of shep-pm/shep-kelpie#99). Kelpie now folds names the Unicode way and refuses what is still not ASCII, and the per-call check opens `.claude` and `.mcp.json` by name so the file system folds them itself. Git matches a pathspec by exact case even with `core.ignorecase`, so the trusted side lists the root tree and folds it the same way.
- With the sandbox on, Claude Code makes an empty `.claude/.cc-writes` folder in the working folder itself. The check before a call compares files only, so an empty folder passes.
- `kelpie guard` (shep-pm/shep-kelpie#108) is the PreToolUse hook on every worker's Bash calls, after `confine` and `browse-guard`. It carries over what a worker needs from the maintainer's own git and gh guard, in Rust: the home folder's absolute path is refused in a commit's or tag's message, in the lines a commit adds, in the commits a push sends, and in a `gh` title, body or notes; and `gh pr create` needs a `--title` that is a conventional commit, as does `gh pr edit --title`. The hook runs outside the sandbox, so it runs git only through the same trusted call kelpie's own worktree steps use (the worktree's git dirs named, its `commondir` checked, hooks off), and only for a folder in the worktree with no repo of the worker's own inside it: git run in a repo the worker made starts whatever program its config names as `core.fsmonitor`, which a test shows with plain `git status`. The rest of that guard is the maintainer's own (their name and email, private repo names, production figures, voice reminders, file-size limits for repos they own) and stays out. Measured 2026-09-29 on Claude Code 2.1.284, in a scratch repo and a worktree cut from it the way kelpie cuts one, with this branch's build as the only hook: a worker that wrote a file holding its working folder's path and committed it in one Bash call got the commit through, since nothing was staged when the hook ran; the push that followed was refused naming the file, and `origin` did not move. `gh pr create --title 'Add notes'` was refused with the conventional commit shape.
- Measured 2026-09-29 on Claude Code 2.1.284, in the same scratch worktree, headless like a worker (shep-pm/shep-kelpie#117's review): a committed `.claude/settings.json` holding `"disableAllHooks": true` switched off a PreToolUse hook passed through `--settings`, and the Bash call it should have refused ran. With `"disableAllHooks": false` in the `--settings` file, the hook ran again, so kelpie's file sets it. The worker's tool list holds `Monitor`, which runs a shell command or opens a WebSocket that no Bash hook sees; a `Monitor` deny rule took it out of the list (47 tools to 46). The guard's first command reader re-read every nested body at each `)`, doubling per level (22 levels of `$( )` took 3.87s); a hook that hangs or crashes does not block the call.
- The pinned worker repo, `~/.kelpie/repos/shep`, has no `origin` remote, so kelpie cannot cut branches in it. A runner now refuses to start on a repo without one. The demo ran on a clone whose origin held the pinned commit as `main`.

### A worker's push, `gh` and package installs

Measured 2026-09-26 on Claude Code 2.1.283, gh 2.96 and bun 1.4.0, from a sandboxed worker on a private bun, Vite and TypeScript project, the playground.

- `git push origin <branch>` reaches GitHub through the system's osxkeychain credential helper. With `refs/remotes` denied, the push lands but the tracking ref fails to write. So `refs/remotes` is no longer denied: kelpie fetches `origin/main` before cutting a branch, and a fetch forces tracking refs.
- `git push -u` cannot write `config`, which stays denied. Workers push with `git push origin HEAD`.
- `gh` will not start without `~/.config/gh/config.yml`, so that folder is no longer read-denied. It holds no token on the maintainer's machine; the token is in the keychain. Writes there are still refused. `gh` will not start without `hosts.yml` either, so it cannot be denied alone. On a machine where `gh` keeps its token in a file rather than the keychain, `hosts.yml` holds the token, and the folder must stay denied.
- `gh auth` is denied, since `gh auth token` prints the maintainer's token.
- Inside the sandbox, `gh` fails TLS verification with `x509: OSStatus -26276`. Claude Code's docs name this for Go tools on macOS. `sandbox.enableWeakerNetworkIsolation` fixes it and keeps `gh` inside the write fence and the domain allowlist. `excludedCommands` would have run `gh` unsandboxed.
- A cold `bun install` reaches only `registry.npmjs.org`. Inside the sandbox it fails with "unable to write files to tempdir: EPERM", because bun stages downloads in `~/.bun/install/cache`. With `BUN_INSTALL_CACHE_DIR` in the build folder it installed 733 packages in 9.7 seconds, and the project's tests and typecheck passed.
- The sandbox refused deleting `.idea` folders that a bun install outside it had left in `node_modules`. Installing them from inside worked.
- Final fence, for every worker. Writable: the worktree, the build folder, the common git dir's `objects`, the worktree's own git dir, and the branch's ref, lock and reflog under both `refs/heads` and `refs/remotes/origin`. Denied inside the git dir: `config`, `hooks`, `info`, `modules`, `HEAD`, `index`, `packed-refs` and `refs/tags`. Domains: `github.com` and `api.github.com`. Also denied: the clone's `refs/heads/main`. Denied commands, besides merge, ready and the `review please` label: `gh api`, `gh auth`, a push naming `main` as `origin main`, `HEAD:main` or `refs/heads/main`, and a push carrying `--mirror`, `--all`, `--delete`, `-d`, `--force`, `-f` or a `+` refspec. Those are pattern rules over the command text, so a script can get past them; a token scoped to a worker's needs would be a real fence.
- Measured 2026-09-28 on Claude Code 2.1.284: under `bypassPermissions`, a sandboxed `curl` to a host outside `allowedDomains` got its 200. Claude Code's settings reference says so: without `sandbox.network.strictAllowlist`, bypass mode allows a host outside the list rather than asking. With `strictAllowlist: true` in the worker's `--settings` file, the same `curl` was refused ("host is not on the allow list"), so every worker's settings carry it.
- Per project, `worker.allowed_domains` adds domains (shep: `crates.io`, `index.crates.io`, `static.crates.io`; the playground: `registry.npmjs.org`), and `worker.build_env` points tool caches into the build folder (the playground: `BUN_INSTALL_CACHE_DIR`).

### Seeing the UI

Measured 2026-09-28 on Claude Code 2.1.284, Node 26.8, bun 1.4, Playwright 1.64 (the alpha `@playwright/mcp` 0.0.82 pins) and `@anthropic-ai/sandbox-runtime` 0.0.77, on a copy of the playground outside any project repo.

- Chromium cannot start inside Claude Code's sandbox on macOS. The cached Playwright headless shell, with or without `--no-sandbox`, died on `bootstrap_check_in ... MachPortRendezvousServer: Permission denied`, even with `sandbox.network.allowMachLookup: ["*"]`: the check-in registers a service, and the key only opens lookups. System Chrome failed on its profile and crashpad folders first. So the browser runs outside the worker's sandbox: as the Playwright MCP server's child, which Claude Code starts unsandboxed, and as kelpie's own child for its shots.
- A dev server inside the worker's sandbox needs two allowances, and a worker with a launch file gets only these: `sandbox.network.allowLocalBinding: true` (without it, `listen EPERM 127.0.0.1`) and `allowMachLookup: ["com.apple.FSEvents"]` (without it, Vite's watcher died on `EMFILE: too many open files, watch`). With both, the playground's Vite answered on its port in about a second.
- Node's `fetch` ignores the sandbox's proxy, so a server-side call from inside either sandbox failed with `ENOTFOUND`. `NODE_USE_ENV_PROXY=1` makes it use `HTTPS_PROXY`, in the main thread and in worker threads alike; workers with a launch file, and kelpie's own dev server, start with it. ### The local model's placement

Built in shep-pm/shep-kelpie#145, after a model loaded on the CPU instead of the GPU ran review-sized prompts at a twentieth of normal speed on 2026-09-29 and nothing noticed for 14 minutes.

- Ollama's `GET /api/ps` lists each loaded model with its `size` and `size_vram` in bytes, its `context_length` and its `expires_at`. A model is on the GPU when `size_vram` equals `size`, and `size_vram / size` is the share on it. Recorded shape: `fixtures/ollama-ps.json`, written by hand from Ollama's documented response, since the maintainer's host did not answer from the worker's sandbox.
- It cannot say how busy the GPU is: there is no utilization, so a model on the GPU that another round is using looks the same as an idle one. That is the GPU metrics ticket's job, not this check's.
- It lists only loaded models. A model not loaded yet is not checked, and the check cannot say where it will go when the round's first request loads it. A model that loads spilled in the middle of a round is not caught until the next round.
- Kelpie reads `/api/ps` only where it holds the GPU lock around the round (`gpu_lease = true`), after taking it and before the round. Without the lock the read races whoever holds it: it would rule on another session's spill that a round would have queued behind, and could pass just before the holder reloads the model spilled. The default command round, `qwen-review.sh`, takes the lock itself, so it is not checked, and `ollama` on a command without `gpu_lease = true` is refused when the settings load, with that reason. An endpoint with no `gpu_lease` is skipped the same way. The host is the endpoint's `url` without `/v1`, or the command's `ollama`. A command names its model with `ollama_model`, and only that model is checked. Without it every model the host has loaded is looked at, and one spilled for another reason fails the round, and each yes runs into it again until it unloads (two hours by default). Model names match without regard to case. A model partly or wholly on the CPU fails the round without running it, and raises a ruling that says which model and how much is on the GPU, so it reaches the maintainer's webhook. A yes runs the same round again. A 404, or a reply that is not `/api/ps`'s, means the server is not Ollama and skips the check. A reply that lists models with no readable `size` is Ollama-shaped, so the runner logs how many were left unchecked. A host that cannot be reached fails the round, and the runner retries it as any failed round.
- `status` shows `local_model` from the last read: the name, the percent on the GPU, the context length and when it unloads. It is absent until a round has read one, and it is the last round's view, not live.

### The shep surface kelpie leans on

- `Request::Trigger` becomes an `action` message on a sheep's shepherd channel (fd 3), answered with an `action-reply`. `ready`, `metric` and `action-reply` are all republished on the bus as `channel.*`.
- `SendLine` (`shep whisper`) writes one line to a sheep's stdin.
- A lamb is a pid and an executable name, found by walking the process tree, never argv. The stop ladder kills the process group.
- A sheep with `shutdown_with_message` that exits on the message never reaches the stop ladder, so its lambs are orphaned. Seen 2026-09-26: `shep restart` left the worker running beside the resumed one. The runner now stops its `claude` children itself before it exits: SIGTERM, then SIGKILL after 3 seconds. Before that it asks the worker's thread to stop and waits up to 2 seconds for its step to end, so a step that finishes in time is saved before its calls are ended.
- Shep has two stop caps. `kill_timeout` (1.6s by default) covers `stop`, `restart`, `delete`, the daemon's own automatic restarts and the engine-wide shutdown. `graceful_timeout` (8s) covers only a reload's drain. Read from shep's source (`LadderCap` in the supervisor's reload module and the defaults in the app behavior config) on 2026-09-28, not measured. A runner's stop needs about 7s: 2s to join the worker, 3s of child grace, 2s to flush. So every runner's Flockfile entry needs `kill_timeout = "10s"` or more, and the playground's has it. A runner cannot check its own: no `SHEP_*` variable carries the value, so a warning at start would take a describe call to the shepherd, and none is built.
- A dog is an ordinary sheep with a marker. Wildcard selectors never touch a dog. A dog's `--schema` feeds lookout's settings pane.
- A sheep under the pinned shep 0.10.1 starts with only `HOME`, `LANG`, `PATH`, `USER` and its `SHEP_*` variables, read with `ps eww` on 2026-09-26. `TMPDIR` and `SHEP_HOME` are not among them, though the shepherd itself has both. So `${TMPDIR:-/tmp}` names `/tmp` under the shepherd and macOS's per-user temporary folder in the maintainer's shell: two different GPU locks. ### `shep kelpie upgrade`

Built for shep-pm/shep-kelpie#143. Before it, an upgrade was a sequence of hand steps (build, copy, sign, relink, restart the runners between steps and, for a new shep minor, save, kill and muster the shepherd), and on 2026-09-29 one of them deleted the dog's sheep until it was restarted by hand.

- `shep kelpie upgrade --ref <git ref>`, `--release <version>` or `--binary <path>` installs a build as `<kelpie home>/bin/shep-kelpie`, the binary every kelpie sheep runs, and keeps the one it replaces beside it as `shep-kelpie.previous`. `--rollback` puts that one back and keeps the one it replaced in its place, so a second rollback undoes the first. Running the same build again changes no file, so finishing an upgrade that stopped part way does not push the real previous build out.
- The installed and the previous build are put in place by renames, and the previous one is a hard link to the inode the installed build had, never a copy. A sheep that restarts on its own mid-upgrade finds a whole build. On macOS a Mach-O binary is signed ad hoc (`codesign --force --sign -`) once it is copied; a script (the tests' stand-in builds) is not signed. Not measured: whether an unsigned copy is killed on this machine's macOS, which is why the signing is kept.
- A build says which shep it is made with through `shep-kelpie version --json` (`{ "kelpie": ..., "shep": ... }`, the second being `SHEP_VERSION`). The upgrade runs it on the new build and compares its minor with the shepherd's, read through a connection that does not apply the running kelpie's own pin, since a kelpie on the old minor must be able to install a build for the new one after the shepherd moved. A difference stops the upgrade before a file changes or a sheep restarts, and the message says which side to move: a build for a newer shep than the shepherd's means save the flock, stop the shepherd, install the new shep, muster, then upgrade again; an older one means install a kelpie built for the shepherd's line. The same check gates `--rollback`. A previous build from before `version --json` cannot answer it: the rollback goes ahead and says the minor is unchecked.
- Restarts go dog first, since every runner asks it for leases, then each runner in name order, one at a time. A sheep restarts only when its `status` shows no work item in `merge`, or in `done` with its pull request merged, and the dog only when no runner has one. The upgrade asks again every 500ms for up to an hour, saying what it waits on, then fails naming the runner and restarts nothing for it. A restarted sheep must answer `status` in 60s before the next goes down. A merge can still begin between a `status` and the restart that follows; the runner's own stop lets the step in flight finish first. A sheep that is stopped stays stopped and starts on the new build. One whose entry runs another binary is restarted and named, since the restart cannot move it: run `shep kelpie add`, which registers the installed build once there is one.
- `--ref` keeps a clone of the repo in `<kelpie home>/upgrade/source` (`KELPIE_SOURCE` names another repo than shep-pm/shep-kelpie), checks out the remote's branch, tag or commit detached, and runs `cargo build --release --locked` with its own `CARGO_TARGET_DIR`. Measured 2026-09-30: a nested cargo that inherits the maintainer's `CARGO_TARGET_DIR` puts the binary there, not in the clone's `target`, and the build reported success with no file where kelpie looked.
- `--release <version>` runs `gh release download v<version>` for the asset `shep-kelpie-<arch>-<os>.tar.gz` (`aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`) and unpacks `shep-kelpie` from it. This repo has no release workflow yet, so the asset name is a decision and not a measurement; the build inside must say it is that version or nothing is installed.

In order: transport, model calibration, work split, then code. Each series gets its own spec when it starts.

### Transport

- T1: `claude -p --resume`, one process per turn. The measured baseline.
- T2: a long-lived `claude --input-format stream-json --output-format stream-json` worker, held by a project runner.
- T3: `claude --bg` plus socket messages, attached with `claude attach`. Needs a permission rule for reading the target's peer token.
- T4: kelpie-served tools. In-process MCP over the stream-json control protocol, against a small stdio MCP binary that relays to kelpie over shep.
- T5: MCP channel push, if the account has channels.
- Lease round trip, runner to dog: a "wants" metric, then `status` and `grant` triggers, against a direct `shep trigger` to the dog if that reaches one. Latency, a dropped metric, and reclaim when a runner dies holding a lease.
- Rate limits: whether stream-json carries the utilization windows.

Measure each: cache write and read per turn, wake latency on an idle worker, a 100 KB output line through the runner, recovery after a crash, subscription auth, and whether the maintainer can take a worker over.

### Model calibration

Extend the maintainer's local model-calibration harness, which has only scored local models, to Opus, Sonnet, Haiku and Fable at two or three effort levels each. Reviewer and checker roles reuse its frozen sets: planted bugs, real false findings, and clean diffs for false alarms. A new implementer set of small shep specs with hidden tests scores tests passing, review findings, units and wall clock.

### Work split

Run the same real work items as inline, inline with compaction, a phased chain with handoffs, a crew of subagents working from an implementation doc, and agent teams (only if a long-lived transport wins, since teams do not spawn under `-p`). Run each with and without codebase-memory-mcp.

The model to fit: one session's cache reads grow with the square of its length. Splitting it into k pieces cuts reads about k times and adds a fixed cost per piece, so the best k is about √(0.025 × calls × growth ÷ per-piece cost). Worked example with guessed inputs (150 calls, a 41k floor, 500 output tokens a call): inline to 650k is about 6.9M units, three quarters of it cache reads; five phases, each with a 10k handoff and 30k of re-reading, is about 4.6M. The tests measure the real inputs.
