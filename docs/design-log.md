# Design log

Decisions from the design sessions starting 2026-09-24, and the facts behind them. The hard-to-reverse ones are also ADRs in `docs/adr/`. The vocabulary is in `CONTEXT.md`.

The cleanup of 2026-10-05: ADR 0005 hands every stop to shep, and ADR 0006 cuts the flow to one builder and a serial list of reviewers that each run once. The sections below still describe the code as it stands. Each phase of the cleanup rewrites the sections for what it removes, in the same pull request.

## Why kelpie exists

Before kelpie, one long-running Claude session per project acted as a control room. It held the board, rationed reviews, relayed messages between the sessions that owned pull requests, and merged. Measured 2026-09-24 over shep's transcripts, in units weighted by cache pricing (cache read 0.1, one-hour cache write 2, output 5, uncached input 1):

- 2,352 transcripts, 6,020M units. The control room was 7% of that, and subagents were 54%.
- Transcripts that peaked above 500k context were 43% of all spend.
- The control room itself: 7,883 calls, median context 349k, 41 compactions, 80% of its cost in cache reads. 62% of its cost was calls that followed a Bash result (git 20%, gh 17%, the review driver 13%, the GPU queue 12%). Relaying messages was about 15%.

So kelpie moves the control room's rules (gates, locks, rate windows) into code, calls Claude only for the work and for judgement, and controls the other big cost: how large each agent's context grows.

## The shape

- Kelpie is a dog under its own pinned shepherd. Each project is a sheep, kelpie's project runner, and the project's workers are its lambs. See ADR 0001 and ADR 0002.
- Since shep-pm/shep-kelpie#110 the runners and the dog are sheep of the maintainer's own shepherd (ADR 0003; the dog's half is superseded by #180 below). Kelpie is adopted there and left disabled, and `shep kelpie <command>` runs it in the caller's folder with `SHEP_HOME` set. `add`, in a checkout, reads the forge from `origin` and refuses a default branch other than `main`, which every branch is cut from. It makes the three labels the repo lacks, and registers two sheep, both stopped: the runner, named for the repo unless named on the command line, holding its settings as its `[app.dogs.kelpie]` table, and `kelpie-dog`, which runs the dog. The table is the defaults plus what the checkout and forge say: `repo`, `forge`, `ci` from whether `.github/workflows` exists, CodeRabbit on only for a public repo, and the local round off unless the maintainer's qwen script is installed. Lookout shows each key's description from kelpie's schema, which stands in for a comment per key, since shep keeps a table without comments. A project that still has its settings file from before the tables gets that file as its table instead, when it names this checkout. Everything is read before anything is written, so a refusal changes nothing, and each piece is made only when missing, so a second `add` changes nothing. A sheep of the same name that is not kelpie's, an enabled dog included, is refused. `start` and `pause` take a project's name, or find the one whose `repo` is this checkout. `start` first starts the dog's sheep and the runner's when they are down, and waits up to 30 seconds for the runner's own answer: a runner opens its channel before it takes its actions, and shep-channel answers `unknown action` in plain text meanwhile, so any reply that is not JSON means it is still starting. `status` asks every sheep with a kelpie table. A runner's state file now makes its own folder, since a project from `add` has none. From the control session's review: `add` refuses a checkout or repo another project's table already names, since two runners would take the same issues. `start` and `pause` act only on a sheep with a kelpie table that kelpie started as `runner <project>`, so a sheep of the maintainer's stopped on purpose is never started. Replacing a Flockfile dog deletes the old sheep first, so a failure leaves at most one, and reports the deletion before anything else can fail. The new dog keeps every variable the old entry set: shep withholds their values, so each comes from the environment `add` runs in, and one missing there stops `add` before anything changes. An adopted `kelpie` left enabled only restarts, so `add` says to disable it. After the re-review: `TMPDIR` and `PATH` are never taken from the shell, since a shell always has both and a moved dog locking the GPU under another `TMPDIR` than the runners' would let two rounds hold it, so an old entry setting either is refused until they come out of it, and `add` names every variable it did take. The one-runner check reads each other sheep's raw `repo` and `forge`, from its table or a Flockfile runner's old file, so a table that no longer parses still counts. `start` with kelpie adopted and enabled and no `kelpie-dog` says to disable it.
- Since shep-pm/shep-kelpie#180 the adopted `kelpie` is the lease dog, and the `kelpie-dog` sheep goes (ADR 0004). Kelpie's `--version` answer asks for the shepherd channel, which shep 0.12 records at `shep adopt`, so a start with no arguments under `SHEP_DOG_NAME` runs the dog. It checks for the channel first: an adoption from before the ask has none, and the dog exits naming `shep adopt` again, then `shep disable kelpie` and `shep enable kelpie`. Then it removes a left-over `kelpie-dog` sheep of kelpie's (started as `dog`, not a dog), waiting for shep's answer, which comes once the sheep has exited, and opens the book after, never writing it for the move. A left-over whose entry sets `KELPIE_HOME` or `HOME` is refused and kept, since its book is not where the adopted dog's was (Facts). From the control session's review: the dog runs only when `SHEP_NAME` is set too, since `shep kelpie` with no verb sets `SHEP_DOG_NAME` alone, and `add` and `start` count the adopted dog as up only while it is online. `add` registers the runner alone and says when the adopted kelpie is not enabled or has no channel; `start` refuses then, since its runner would never be granted a lease. `shep kelpie lease` triggers `kelpie` only. The Flockfile dog named `kelpie` and `add`'s move from it go with `kelpie-dog`.
- Since shep-pm/shep-kelpie#253 kelpie's home is `$SHEP_HOME/kelpie`, since kelpie is a plugin of shep (decided by the maintainer on 2026-10-01). `KELPIE_HOME` still overrides it, and with neither `SHEP_HOME` nor `KELPIE_HOME` set it is under shep's own default, `~/.shep`. Kelpie's shared files sit at the top (`settings.toml`, `totp`, `tools`, `rulings`, `builds`, `upgrade.lock`), and each project has a folder named for it holding `state.json`, its worker files, `worktrees`, `builds`, `shots` and `playwright`. So a project may not be named for one of kelpie's own entries. The dog's book and door are always under `$SHEP_HOME/kelpie/dog`, since shep hands the adopted dog `SHEP_HOME` and not `KELPIE_HOME`. `add` registers the checkout it runs in as `repo`, as before. A runner refuses to start when its door or the longest socket a call opens (a 128-bit name in its worker folder) is over 103 bytes, naming the path, since macOS caps a socket's path at 104.
- The move from `~/.kelpie` (#253) runs only in the dog and the runners, which always know their shepherd: a bare `kelpie totp` with no `SHEP_HOME` would otherwise move files into `~/.shep/kelpie` and split the home (found in the control session's review). It moves by an explicit list, by rename, so files kelpie does not own stay. The dog moves `dog/book.json`. Every runner moves the shared files, each leaving a link at its old place so a runner still on the old build keeps working through an upgrade, and its own project's `wt/<project>`, `targets/<project>`, `shots/<project>`, `playwright/<project>` and then `projects/<project>/*`, with `state.json` last. Each move is done once: it leaves `.moved-from` in its new place. The old home keeps `.moved-to` naming the new home, and a runner whose home works out elsewhere is refused only while the old home still holds files of kelpie's for it, so a separate shepherd's runners (the GUI's, on `SHEP_HOME=~/.kelpie`) start, and a runner that would start empty beside its unmoved state does not (the control session's re-review). The runner checks its socket lengths before anything moves, so a home it refuses is never filled. Nothing moves from, or into a project folder holding, `flock.json`, `shep.toml` or `run/`, since that is a shepherd's home (the maintainer means `~/.kelpie` for the GUI's shepherd). A new home inside the old one, such as `~/.kelpie/shep/kelpie`, is refused, since every path the move writes would break when the shepherd leaves. A shared file already in the new home is kept and its old copy left, since `tools install` or `totp` before the first runner start makes one, and `totp` and `doctor` read the old home's files until then. Any project item that cannot move, or whose new place is taken, stops the start and is named, so a runner never opens on a fresh state beside its old one. The state file then has every path under an old folder rewritten, since a work item keeps its worktree's and build folder's paths. Moving the worktrees rewrites git's `gitdir` file for each, and every runner runs `git worktree repair` on its worktrees as it opens, before a later removal's `git worktree prune` can drop one git lost track of. Each project moves only when its own runner starts, after the old runner has stopped its workers. A worker in flight may still start its next turn in a new session, since Claude Code finds a session by its folder: the runner already starts over on `No conversation found`.
- The links in `~/.kelpie` are removed by the first runner start that finds every other running kelpie runner (a sheep started as `runner <project>`) up for less time than the newest link has existed, along with the old `dog/lease.sock` when no dog answers there. The runner that made them is left out by the pid it wrote to `.linked-by`: shep counts a sheep's uptime from its spawn, so that runner always looks older than its own links and alone would block the sweep until it restarted (found in the re-review). `shep kelpie upgrade` removes any left before it restarts anything, since the build running it already moved the home, and `doctor` names any that remain. A rollback to a build from before the move needs the files moved back by hand. `codex` is not moved: no kelpie code reads it yet.
- Rust for all business code. A Tauri GUI comes after the MVP. Until then kelpie is run and watched from a Claude session.
- One kelpie serves every project, because the GPU lease, the CodeRabbit window and the usage pacer are machine-wide or account-wide. Realistically two projects at once. shep comes first.
- Kelpie and its runners talk through shep: triggers down, `channel.metric` up on the bus. Runners report running totals, because metrics drop under backpressure. A private socket only if the MVP shows the round trips do not hold up.
- Book leases (CodeRabbit first) live in the dog, and only runners and the maintainer ask for them. Workers and crew never touch the GPU or CodeRabbit. The one lease a worker takes is `cargo-test` (shep-pm/shep-kelpie#218): a counted lease on the dog, three holders at once by default (`[kelpie.leases] cargo-test`), so test runs across workers queue. A command asks for it at the dog's door, its own socket at `$SHEP_HOME/kelpie/dog/lease.sock` (never under `KELPIE_HOME`, which shep does not hand the adopted dog), and holds it while the connection stays open, so nothing has to poll a pid. The command run under it inherits the connection, so its whole process tree holds the lease however the asking process ends, and the asking process shuts the connection when the command ends, which ends it for every copy, so a process left behind does not keep it. If the asking process is killed outright, a process the command left running, such as a build server, holds the lease until it exits; `status` shows each holder's `since`, and nothing yet bounds a hold. It goes through a socket of the dog's, not shep's trigger: a worker's sandbox may connect to that socket alone, and shep's home stays unreadable to it, since its socket would let a worker trigger anything. The runner passes the same path to the sandbox's allowlist and to the worker as `KELPIE_LEASE_SOCKET`. The same `shep kelpie lease run cargo-test -- <command>` works from any shell on the machine, and exits 75 when it cannot have the lease and 127 when the command cannot start. Holders are never saved, as a dog restart closes every connection: a run that loses its dog mid-run knocks every second with `running`, and the next dog seats it at once, over capacity if need be. For three seconds after its door opens the dog grants nothing new, so those runs are counted before anyone fresh. A run still waiting when its dog goes away asks again, fresh, every second for a minute before it exits 75. A restart longer than a minute, or a run started by a kelpie from before `running`, can still let more than the capacity run. Workers build outside the lease (`cargo test --no-run`) and run the suite inside it, as their instructions say, naming the kelpie binary by its path, since the guard refuses a command whose program comes from a variable. The GPU lease is the lock the maintainer's qwen scripts already take, and the dog stays out of it (decided 2026-09-26 on #5, option A): a qwen round takes the lock itself, and so does `kelpie lease run|take gpu`, in the same format, for the maintainer's own by-hand use. A project runner's own local round (shep-pm/shep-kelpie#11) follows the same rule: it never takes or holds that lock either, leaving it entirely to the round it spawns, unless the project's local round asks it to (shep-pm/shep-kelpie#107).
- A runner asks for a book lease by raising running totals, `lease.<kind>.want.<epoch>` and `lease.<kind>.return.<epoch>`, and the dog grants with `grant <kind> <epoch>`. The epoch is the runner's pid, which shep's process events also carry, so the dog reclaims an old run's leases on `restart` without racing the new run's first metric.
- The dog saves its book to `<kelpie home>/dog/book.json` after every change, with the same atomic write as a runner's state file, and loads it on start (decided on #19, the ticket's first option). The file keeps holders and queues with their epochs, each review window's quota, summons and quoted refusal, and each runner run's totals, so a restart grants no second summon inside a window. On start the dog checks every runner in the book against the live flock: a holder whose sheep now has a different pid, or none, is reclaimed. A missing file, or one another build wrote, loads as an empty book. One that claims this format and cannot be read also starts empty, but with the CodeRabbit window closed for an hour, as if a summon had just been accepted.
- MVP: a thin vertical slice. One project, one worker at a time, merge on `ask`, no GUI. shep-pm/shep-kelpie#5 is its spec.
- A project's settings are its runner sheep's `[app.dogs.kelpie]` table, and kelpie's own are its `[kelpie]` section of `dogs.toml` (shep-pm/shep-kelpie#114, on shep 0.11). Lookout edits both from kelpie's `--schema` answer once kelpie is adopted, and draws the webhook's URL `<set>`. Every project setting is required except those added after the first build, so a missing or malformed one stops the runner with a message naming it as a dotted key, `coderabbit.divisor = 0`. The project's state file is `<kelpie home>/<project>/state.json`, written atomically.
- A runner reads its own table through the shep client, with `DogSheepSettings` and `DogConfig` on the name `kelpie`, not from the dog (decided on #114). shep answers both to any client, a runner is a sheep with no `DogRuntime`, and reading it itself keeps a runner's start independent of the dog being up. It finds its table by `SHEP_NAME`, else the project's name. A table goes through the settings file's own parser, rendered as TOML, so a table and a file take the same keys, defaults and checks.
- A settings change takes effect live, at the runner's next wake (within a minute when idle) and then at the next step or call that reads it. `repo` and `forge` wait for the next start, since a work item's worktree and pull request belong to them. A work item in flight keeps the worker model it was added with. A change is checked as a start checks it, and one that fails keeps the settings in effect and is offered again at each wake, so it lands once what refused it is fixed. Reading on each wake was chosen over subscribing to `config.sheep.kelpie`: no second connection to carry across a shepherd's reload, and a minute is soon enough.
- The files kelpie used before the tables, `~/.kelpie/projects/<project>/settings.toml` and `~/.kelpie/settings.toml`, still load while a table is unset, with a notice naming `kelpie settings move <project>`. That command writes an equal table and the file's own text as the section, refuses to overwrite a table that is set, and deletes nothing.

## Work

- GitHub Issues stay the tracker for the work kelpie does, with the `ready-for-agent` family of triage labels. The board of work items lives inside kelpie.
- Priority orders the board (shep-pm/shep-kelpie#144). Ready issues labelled `priority: P0` go first, then `P1`, `P2`, `P3`, then those with no priority label, the labels shep uses. Within a priority the oldest issue goes first, as before, and an issue with several priority labels ranks by the highest. Adoptions and reworks still go before any issue. A blocked, assigned or otherwise passed-over issue does not hold up the next one, whatever its priority.
- An issue a work item holds carries `in-progress` (shep-pm/shep-kelpie#199), so a reader of GitHub sees a worker has it while it still carries `ready-for-agent`. It goes on as the work item opens, by the board, `add`, a rework or an adoption, and comes off as it ends, merged, handed back or dropped. The name is the one the maintainer's control session already puts on this repo's issues by hand. `shep kelpie add` makes it with the other labels, and `doctor` checks it. A runner that starts puts it on each issue it holds, and takes it off each finished issue whose removal a refusal once missed. The label is a courtesy: a forge that refuses it leaves a line in the runner's log and the work item runs on.
- An issue writer forms work items (docs/adr/0006-one-agent-builds-reviewers-run-once.md): an agent that runs before kelpie sees an issue, researches the request, scopes it to one pull request's worth or splits it into sub-issues, and labels the worker that should build it. It is not built yet, so until it is the maintainer writes, splits and labels issues by hand. Kelpie adds the results to the board and dispatches.
- The board never works an issue with sub-issues, since they are worked in its place, and closes one whose sub-issues are all closed, whoever made them. A close the forge refuses three times in a row is passed over until the runner restarts, so one refusal that never clears does not hold every poll; each refusal is a line in the runner's log.
- No planning call (docs/adr/0006-one-agent-builds-reviewers-run-once.md). Kelpie used to plan the board's pick on Opus before opening its work item, splitting it into sub-issues and picking its worker as a `worker:` label (shep-pm/shep-kelpie#139, #266, #276). The experiments found no plan-then-implement arm beat one agent with no plan, and a shared plan spread its bugs into every build made from it, so the call is removed and splitting and the worker pick move to the issue writer. A project table that still sets `planning`, `models.planner`, `agents.planner` or `skills.planning` is refused at load, naming the key and saying to delete it. A state file's `plans` are dropped as it loads, and one holding a pending ruling on a split, a stuck split or a stuck close is refused, naming the ruling, to be answered or dropped on the old build first.
- Overlapping items are bundled when the combined PR stays small, and chained otherwise. The next worker in a chain starts from `--fork-session` of the previous worker's last session.
- One work item, one PR, and every PR boundary is a reset point. A worker that finds more than one PR's worth of work splits the rest into chained work items and divides its remaining budget among them. The motivating case: a shep refactor issue became four PRs in one session with a huge context, though the pieces barely overlapped.
- Conflicts nobody predicted: the item that reaches the gate later rebases after the first merges, and the footprint miss is logged. Serializing instead is a project setting for small codebases.
- Several work items per project (shep-pm/shep-kelpie#103). A pull request waiting on CodeRabbit's hourly window, CI or a merge ruling held the whole project: overnight on shep that was about one pull request an hour with the GPU idle between rounds, and the playground sat all night on one merge ruling. A project's `max_items` (1 when absent) sets how many work items are open at once, each with its own branch, worktree, build folder, phase and rulings. The board opens one whenever a slot is free, adoptions and reworks first as before, and never an issue or pull request whose work item is open. A step tries each open item, and the board while a slot is free, starting after the one that last acted, and an item waiting on a lease, CI, CodeRabbit or a ruling yields to the next. An item parked on a ruling keeps its slot, so raising `max_items` is how work moves past it. Items merge independently, and one merging sends the others through the existing catch-up with `main` at their gate. A ruling names its work item, and its answer moves the item parked on it. `gate` and `drop` take the item's issue when more than one is open. `status` lists every open item under `work_items`, keeping `work_item` as the oldest. The state file is version 2, and a version 1 file loads as a list of one.
- What `max_items` does not change: one worker, review or shots call at a time per project, since the steps run on one thread, and every gate per item. The CodeRabbit lease is still one grant, one summon: the runner records which item took it, and another item waits for a grant of its own rather than inheriting it, which would summon twice in a window the dog counted once. The GPU stays the qwen script's own lock. `max_items = 1` behaves exactly as before.
- What a worker finds along the way: fixed now if small and in a file it already touches, otherwise filed by the worker itself as a `needs-triage` issue.
- Kelpie works on its own repo (shep-pm/shep-kelpie#140). Until then a control session worked it by hand: a dispatcher, run as a sheep, started a background session per issue once its blockers closed, each with a handwritten note and a shared set of rules; the control session ran an Opus review when a pull request left draft, relayed the fixes to the session, merged at the reviewed head and cleaned up. Each of those is now a setting or a feature kelpie already has. The repo is a project on the maintainer's shepherd, added with `shep kelpie add` in a clone of its own under `~/.kelpie/repos`, never the checkout sessions work in, and worked by the board like shep with `max_items` above one. The dispatcher's blocker check is the board's own, its model per issue is the `worker:<model>-<effort>` label, its priority the priority labels, and an issue it held or kept for the maintainer is one without `ready-for-agent`. The note per issue goes in the issue's body. The shared rules that hold for any worker on this repo are in `CLAUDE.md`, which every worker reads, and those that name this machine's paths go in the project's `worker.instructions_file`, which stays under `~/.kelpie`. The Opus review is a local reviewer of kind `claude` on Opus with `paths` over the code (#125), listed after `qwen` and `claude` in `review.reviewers`; the relayed fixes are the findings each reviewer sends the worker; the merge is the gate's, under `ask`, at the head it passed. CodeRabbit stays off for this repo (`coderabbit.enabled = false`), as it was for the control session, since its hourly window is the one shep's runner waits on. One thing the dispatcher did has no setting: it held an issue while a refactor in the same area was open. Kelpie leaves that to the gate's catch-up with `main`, where a conflict is the worker's next turn. A merged change reaches the runner only when the maintainer builds `main` and restarts it, as before. The cutover is the maintainer's: this build tried first on the scratch repo shep-pm/kelpie-scratch, then `add` on this repo, and the dispatcher's sheep stopped and deleted. That retires the dispatcher.

## Workers

- A worker outlives its sessions. A reset, by compact or by clear with a handoff, keeps the same worker. Which reset is cheaper, and when, is for the work-split tests.
- The worker picks the work split: inline, phased, or a crew. The project manager never does, so it keeps a minimal context for merges, git and gates.
- The calculator runs as needed. Kelpie code reads every call's usage, which is free, and acts only at a phase boundary or a threshold. Inside a turn, a skill plus a hook that fires before an agent spawn or past a context threshold.
- Agents never see budget numbers. Budget talk makes models stop after every task. Budgets live in kelpie's code, and the in-turn hook hands a worker a decision ("delegate the next chunk"), never a cost figure.
- Workers start with `--setting-sources project` plus a settings file kelpie writes for each one. They get the project's CLAUDE.md and project skills, and none of the maintainer's hooks, plugins or skills. Kelpie's own guard goes into every worker's file (shep-pm/shep-kelpie#108), and the guard hooks the project settings name follow it. `worker.guard_hooks` is optional and the example leaves it empty, since its old entry was a file on the maintainer's machine and a beta tester's copy would fail every Bash call. A hook command that does not resolve (its program on `PATH` or at its path, and every absolute or `~/` path in it) stops the runner at start, naming it. `local` was dropped on shep-pm/shep-kelpie#98: it adds only the worktree's `.claude/settings.local.json`, a file no repo commits and nothing kelpie runs needs, and it was the door the #55 review walked through. The review round starts the same way.
- Claude Code's own files in a worktree (any `.claude` folder, and `.mcp.json` at the root) are the maintainer's (shep-pm/shep-kelpie#98). Every Claude call in the worktree loads them, and a hook there runs outside the sandbox. The #55 review wrote a SessionStart hook into `.claude/settings.local.json` with the Write tool, and the next `claude -p` ran it unsandboxed. Four fences now: the sandbox denies writes to them, `kelpie confine` refuses the file tools there (as written and as resolved, in any case), each Claude call first checks the root's `.claude` folder and `.mcp.json` against a trusted commit, and a pull request that changes them parks on a ruling. The check before a call passes when every one of those files matches `origin/main`, the commit the branch left `main` at, or a head the maintainer accepted; a difference fails the turn, and the ruling carries the files. Kelpie asks before a worker turn on a branch with a pull request (a rework starts on one), before the review's steps, before CodeRabbit's, and before CI, naming the files the branch changes from `main`. A yes accepts them at that head, so later heads that leave them alone pass, and a no stops the work item: the worker cannot write those files, so a note would not help it.
- Permissions: `bypassPermissions` with three layers under it. The project's `main` ruleset (shep's already blocks direct pushes, force-pushes and deletion, and requires a PR and passing checks). Claude Code's sandbox, confining Bash writes to the worktree (`sandbox.filesystem.allowWrite`, `failIfUnavailable`, `allowUnsandboxedCommands: false`), with kelpie's `confine` hook holding the file tools to the same folders. A short denylist of what only the project manager does: `gh pr merge`, `gh pr ready`, adding the `review please` label, reading credential paths. Kelpie flags any label or ready change it did not make and parks that worker. No auto mode: classifier outages have blocked work before.
- Model defaults, kept as project settings: workers on Sonnet 5.5 at high effort, implementing inline with no plan to follow. The maintainer's experiments, 2026-09-29 to 10-01 (40 builds of two real tickets, scored on hidden tests, blind panels and mutation testing), found Sonnet 5.5 at high even with Opus 5.5 at 0.6 to 0.8 of its cost, `xhigh` no better at 1.7 to 1.8 times the cost, and every plan or spec workflow no better at 1.1 to 4.9 times the cost. Claude review rounds stay on Sonnet 5 at medium effort until that role is measured. A `worker:<model>-<effort>` label overrides the worker for that item, and `models.labels` maps each name to the model id it runs.
- A worker turn has a ceiling, `turn_timeout` in project settings, 60 minutes by default: decided 2026-09-27 on #16, over having no ceiling. The implementation series' 152 turns ran a median of 70s and at most 18 minutes, so a turn still going at 60 minutes is more likely stuck than busy. Kelpie stops it with the stop ladder, keeps its session, parks it and raises a ruling; a yes resumes the same session for another turn, a no stops the work item.
- A worker fills the repo's pull request template, and a project can add worker instructions (shep-pm/shep-kelpie#87). Seen on kelpie's first shep pull request, shep-pm/shep#639: the worker wrote its own body with `gh pr create --body`, which skips the template, and the body carried an em dash the maintainer never uses. When the worker's worktree has a template in any place GitHub reads one (`pull_request_template.md` in the root, `.github/` or `docs/`, in any case, or a `PULL_REQUEST_TEMPLATE` folder), each turn's instructions gain a line telling it to fill that template, still ending with `Resolves #<issue>`. A repo without one gets the `pr` step's skill instead (below). A project's optional `worker.instructions_file` is read once when the runner starts and appended to the instructions for rules the repo's docs don't carry; a missing file stops the runner naming it.
- Every step kelpie drives an agent through runs a skill, mattpocock/skills by default, each overridable (shep-pm/shep-kelpie#147). The maintainer wants kelpie to follow that process, with kelpie's own prompts as the fallback rather than the process. Kelpie vendors the skills its steps use in `skills/`, pinned to one upstream commit with its MIT licence and the pin's `git ls-tree` in `blobs.txt`, which a test checks the copies against. The binary carries them and each runner writes them out as a plugin, `mattpocock`, under `~/.kelpie/projects/<project>/skills/`, passed with `--plugin-dir`, so a project installs nothing and an override is just another folder. A step's prompt starts with the skill's slash command and carries kelpie's own prompt as its arguments: `implement` on the worker's first turn on an issue, `code-review` on each Claude round, `diagnosing-bugs` on a red CI turn. `tdd` and `pr` happen inside a turn, so the worker's instructions name them, and a repo's pull request template still wins over `pr`. `triage`, `to-spec`, `handoff` and `retro` (#104) are vendored and overridable but no step drives them yet, and `to-tickets` is vendored with no step at all. A project's `[skills]` table points a step at a skill folder (copied into a plugin of its own, `kelpie-<step>`), a skill in a plugin folder, or `none`. A skill that cannot load runs kelpie's own prompt, and the runner logs why and `status` shows it, since Claude Code itself passes an unknown slash command through as text (Facts). Rework first turns and fix turns run no skill. An adoption's first turn runs none of its own, but when the gate hands it a red CI run, that run's `diagnosing-bugs` command leads the prompt, since a command only runs from the very start. The vendored files stay byte-identical to upstream, and kelpie wraps every skill call in headless rules that win over the skill, decided by the maintainer on the #170 review: there is no one to ask or wait for, so the agent decides and records the decision (the worker in its pull request's body, keeping `<kelpie-question>` for what only the maintainer can decide); no sub-agents or Task; the reply format is kelpie's wherever a skill names another; the Claude round runs no commands; and the worker runs no `/code-review` of its own, since kelpie's rounds review the pull request. The Claude round's settings deny `Agent`, `Task` and `Bash`, because `code-review` otherwise spawns two sub-agents and answers under `## Standards` and `## Spec` headings, which `read_review` would refuse. A project's own skill folder or plugin inside `~/.kelpie/projects/<project>/skills/` stops the runner, since kelpie rewrites that folder, and a project plugin named `mattpocock` or `kelpie-<step>` does not load. For #104: `to-spec`, `to-tickets`, `triage` and `handoff` publish to the issue tracker or write outside the worktree, which the worker's GitHub denies and the confine hook refuse, so those steps need their own settings rather than the worker's.
- A turn that fails, because its worktree cannot be prepared or its call errors, raises a ruling carrying the reason, alerted like the rest (shep-pm/shep-kelpie#57): found on the playground's first live rework, where a leftover local branch failed the turn and left the work item idle with no ruling. A yes retries the step that failed and a no stops the work item as a no on a turn timeout does. A rework reuses a local branch left behind when it matches its branch on `origin` exactly; a fresh work item's branch is still cut new from `origin/main`, and a local branch holding a commit `origin` lacks stays a refusal.
- A first turn that ends with no pull request and no question stopped short, often on a tool that failed, and is never left idle (shep-pm/shep-kelpie#140). The control session saw dispatched sessions stop on a failed tool and sit until someone looked. Kelpie asks the forge again for the branch's pull request, since the turn's end may have missed one, and goes to the review if one is open. With none, it resumes the worker's session once with a prompt saying the turn ended with no pull request, to try again or another way, and to ask with a `<kelpie-question>` block if only the maintainer can unblock it. The next turn that stops short parks the work item on the failed-turn ruling: a yes sends the worker back the same way, and a no stops the work item. A forge that cannot be asked is tried again at the next step. The work item saves `sent_back` only once it is set, so a state file from before still loads, and one with it set is refused by the build before, which denies unknown fields.

## Agents

- An agent is a harness plus the model and effort it runs on (shep-pm/shep-kelpie#127, the first of #127 to #130). Claude Code is the one harness today; #130 adds a local model such as qwen through a second one. The goal is any harness, not one shaped like Codex, so everything Claude-specific stays in the Claude adapter: the settings file and its hooks, `--setting-sources project`, `--effort`, `bypassPermissions`, `--plugin-dir`, and `/usage` for pacing.
- Kelpie's own settings define agents by name, `[kelpie.agents.<name>]` with `harness`, `model` and `effort`. A project names one per role in its `[agents]` table: the worker, the project's own Claude round (`reviewer`) and the deep round (`deep_reviewer`). A role it leaves out keeps its `models` entry on Claude Code, so a project that names none keeps the defaults above. A local reviewer of kind `session` names an agent from the same list, and `kind = "claude"` stays as a Claude session defined in place. An agent nobody defines stops the runner, naming the setting.
- One interface for every role: start or resume a session by id in a folder, with kelpie's instructions, a prompt, the kinds of tool it may use (`Work`, `Review` or `Answer`), its MCP servers and skill plugins, a timeout, and a sandbox that names no harness. The sandbox lists folders the session may read and, for a fenced session, the folders it may write, the paths it may not write or read, the hosts it may reach, the commands it may not run (as prefixes with `*`), its environment, the preview's browser domains, and what kelpie's own checks run with. The answer is the session id, the final text, the tokens the call used, and the session's cost only where the harness reports one. A call with no cost leaves the work item's record of that session unchanged.
- Claude Code builds its settings file from that sandbox in the interface's `prepare`, which the runner calls before it marks a turn or review call running, so a file that cannot be written fails the step and a yes retries the turn it was for. The file turns Claude Code's own sandbox off and holds the deny rules and the `confine`, `browse-guard` and `guard` hooks. `confine` is there because Claude Code's sandbox never covered its own file tools, which is the adapter's knowledge, not the profile's; under kelpie's sandbox it is the second layer. Built both ways for a worker with and without the preview, every key of the file matched `main`'s and the deny list held the same rules in a different order. The project's `worker.guard_hooks` are Claude Code hook events, so the profile carries them as they are, for a harness that can run them.
- Every agent call runs whole inside kelpie's OS sandbox (shep-pm/shep-kelpie#128): the harness, its tools, its hooks and the MCP servers it starts, not only its commands. The sandbox is a port, `Sandbox`, with Anthropic's sandbox runtime (`srt`, pinned at 0.0.77 under `~/.kelpie/tools`) behind it, so a later build, a compiled single binary or a Rust port, changes no caller. The policy is the call's fence plus what the harness itself needs, which its adapter knows: for Claude Code, its transcript folder, a scratch folder and `api.anthropic.com`. A call without a fence, such as a review round, writes nothing but those and reads no credential path. A missing runtime fails the call and stops a runner at start. Claude Code's own sandbox is off under it, since on macOS a sandbox cannot start inside another (Facts); its deny rules and kelpie's hooks stay on as the second layer. The preview's Playwright server and kelpie's shots tool cannot run inside it, so kelpie runs them outside and bridges each over a Unix socket, reading every message on its way and passing only what `browse-guard` would. The model's endpoint is open to the whole process, since the harness itself calls it, so the worker's commands reach it too: an agent CLI started from them (`claude`, `codex`, `pi`) would run a session with none of kelpie's hooks or deny rules, and `kelpie guard` refuses one wherever it reads a program. The list is each harness's `program` in the fence's own table, so a new harness cannot be left off it. After `cd`, `ls`, `mkdir`, `rmdir`, `rm`, `cp`, `mv`, `touch`, `echo`, `printf`, `git` or `cargo`, an agent's name is a file or a word, so `git add src/adapters/pi` and `cargo test pi` pass (found by the control session's second review). The check is by name: `node` on pi's own script, or `npx` on a harness's package, still starts one, and the OS sandbox is the boundary.
- Each harness declares the files in a worktree that make it run code: Claude Code its `.claude` folders and `.mcp.json`, Codex its `.codex` and `.agents` folders (Codex lists a repo's `.agents/skills` whether or not it trusts the repo). The fence holds every harness's files whichever harness a call runs on, so a worker on one cannot plant files for the next call on another. Rulings call them agents' own files. Each harness also declares the files in the home folder that hold its login (Claude Code's `~/.claude/.credentials.json` on Linux and `~/.claude.json`, which holds MCP servers' secrets; Codex's `~/.codex`), and a call on one harness cannot read another's. A harness reads its own to run, so those stay readable to its own calls, apart from Codex: kelpie runs it on a login of its own, and the maintainer's `~/.codex` is read by no call (#233).
- What each role needs from a harness. The worker: a session it can resume by id across turns, instructions appended to the system prompt, skills a prompt can invoke, MCP servers, no permission prompts, a fence that confines its writes and hosts and fails closed, a check kelpie runs before every command and every file write, a turn the adapter can kill at its ceiling, and each call's tokens. The Claude round: a fresh session each time that reads and searches the worktree and the shots folder, runs no command, starts no crew, and answers in kelpie's finding format. Any harness that can do those fills the role; one that cannot fence the worker cannot be the worker.
- The second harness is pi (shep-pm/shep-kelpie#130), chosen over the Codex CLI by one run of each on the same issue (Facts). Each call carries its harness, and for pi the server its model is on, and a port, `Routed`, sends it to that harness's adapter. An agent error names the harness's program, so a Claude Code turn still reads `claude failed: ...` and a pi one `pi failed: ...`. A pi agent takes `url` and `context` as an endpoint reviewer does, and its usage is `none`, so it holds the GPU lease for each whole call.
- pi runs every role inside kelpie's sandbox with a home kelpie writes beside the call's settings: one provider, `kelpie`, with the one model, and the sessions folder, the only part pi may write besides two lock folders. It loads none of the maintainer's or the repo's extensions, skills, prompt templates or project files, and reads the repo's AGENTS.md and CLAUDE.md. The settings trim (#228) is Claude Code's own keys and tool names, so nothing in it applies to pi: its tools are already an allowlist, `--tools`, and the rest is off by flag. The cargo-test lease (#231) reaches a pi worker the way it reaches a Claude one: the dog's door is in the fence's sockets, so pi's sandbox may connect to it, `KELPIE_LEASE_SOCKET` is in the fence's variables, which pi's commands get, and the instructions that say to run tests under `kelpie lease run cargo-test` are the ones pi gets with `--append-system-prompt`. A pi call's sandbox allows no host of the model server's: the call's model traffic goes to a forwarder kelpie runs outside it, which passes only the chat completions call (#235, and the Facts below). A fenced call loads one extension, kelpie's, that runs `kelpie confine` on each write and edit and `kelpie guard` on each command, as Claude Code's hooks do, and refuses any other tool that is not a read. Any failure of the check refuses. It resolves a path the way pi's write and edit do (odd spaces folded, a leading `@` stripped, `~` expanded) and refuses a `file:` URL, which pi would open as the path it names and `confine` would read as a file in the worktree (found by the control session's review). pi takes kelpie's session id as its own (`--session-id`), so a resume is the same call shape as a new session, and a resume onto an id with no session file is `NoSession`. Kelpie's instructions are passed on every call, since pi builds its system prompt afresh each time. A step's `/<plugin>:<skill>` becomes pi's `/skill:<skill>` with that skill's folder. pi starts no MCP servers and runs no Claude Code hooks, so a project whose worker agent is on pi and that turns on `preview.enabled` or names `worker.guard_hooks` stops when its settings load, and a turn checks again before it runs. The prefix deny rules Claude Code also gets have no pi equivalent; `kelpie guard` covers the same commands.
- Codex is the third harness (shep-pm/shep-kelpie#233), on the ChatGPT plan, for the worker, Claude round and session reviewer roles. A review round's session on a Codex agent is the local Codex CLI reviewer #126 left. A project opts in per role by naming a `harness = "codex"` agent, which takes no `url` or `context` and reads its usage with `codex`, so the plan's 5-hour and weekly windows pace it beside Claude's. Each call is one `codex exec --json`, a resume `codex exec resume <thread>`, since Codex names its own sessions: kelpie keeps which thread each of its session ids is, and the thread's tokens so far, beside the call's settings and out of the call's reach. A turn reports the thread's running total, so kelpie counts the difference (Facts).
- Kelpie has its own Codex login, signed in by the maintainer with device auth, in `codex_home` (`<kelpie home>/codex` by default), decided 2026-10-01. A runner's start moves a login left at `~/.kelpie/codex` by #254's home move into it, modes kept, in a move of its own that still runs where #254's shared move already finished. Run on `~/.codex`, Codex copied the maintainer's whole session history into each call's database. Each call runs with `CODEX_HOME` set to a home of its own beside its settings, which holds its sessions, database and logs, with the login's `auth.json` linked in; the maintainer chose that over one home every call shares, where one project's worker could read and edit another's Codex transcripts. Kelpie never reads the login. The sandbox lets a call read `auth.json` and nothing else under `codex_home`, read nothing under `~/.codex` or `~/.agents`, and reach `chatgpt.com` only. In its own home it writes only `sessions`, `archived_sessions`, `db` (Codex's databases, by `sqlite_home`), `log`, `thread-writer-locks` and `installation_id`. Not `tmp`, which Codex puts on every hook's PATH (Facts). Everything else there is Codex's to load, not the call's to write: the login, `config.toml`, `hooks.json`, `.env` (whose variables reach every hook's shell), `AGENTS.md` and `AGENTS.override.md`, rules, skills and the model catalog. It was a list of those until the control session's review of #255 found `.env` and `AGENTS.override.md` missing from it: a worker could have set `ZDOTDIR` to a `.zshenv` that made `confine` and `guard` exit 0 on its next turn. `codex_home` may not be the home folder, a folder above it or anything in `~/.codex`, and a runner reads it when it starts. `auth.openai.com` stays out: a refresh could not be saved through the read-only link, and a lost refresh token signs kelpie out. The usage read runs outside the sandbox on `codex_home` before each dispatch and refreshes a login near its expiry there. `ports::Unreadable` adds `codex_home` to every call's unreadable paths, so Claude Code and pi calls leave it alone wherever the setting puts it.
- A Codex call runs with Codex's own sandbox and approvals off under kelpie's, loads no user config or rules, searches no web, and turns off Codex's features that reach past its tools: its own crew, apps, plugins, browser and computer use, image generation, memories, shell snapshots and the rest of `FEATURES_OFF` in the adapter. `unified_exec` cannot be turned off from a call (Facts). A fenced call runs kelpie's checks as Codex's `PreToolUse` hooks, trusted for the call with `--dangerously-bypass-hook-trust`: `kelpie confine` on `apply_patch`, the tool Codex writes files with on ChatGPT's models, and `kelpie guard` on `Bash`, every command. This answers #130's finding that Codex wrote files through its shell, where `confine` saw no path: on the plan's models it writes through `apply_patch`, whose hook payload carries the patch, and confine judges every file the patch names. A patch typed as a command, `apply_patch <<EOF`, Codex applies in its own process past that hook, so `guard` refuses `apply_patch` and `applypatch` as programs. A step's `/<plugin>:<skill>` becomes a line telling a worker to follow that skill's `SKILL.md`, which its shell reads. A call with no shell has no tool that reads a file, so kelpie reads the `SKILL.md` itself and puts its text in the prompt; files the skill points to beside it stay out of that call's reach (found by the control session's re-review of #255). Only a worker runs commands: every other Codex call, such as a review round, has no shell (`shell_tool` off), as Claude Code's review round has no Bash, since a pull request under review could otherwise talk the round into running commands no `kelpie guard` sees. Codex has no tool that only reads, so such a call reads only what its prompt holds: a review round its diff and the issue's criteria. Its model's `apply_patch` cannot be turned off from a call, so a call with no fence runs one hook that refuses every patch. A fenced worker's `kelpie guard` answers an allowed command with a check that it runs where it was judged, judges it again in a `workdir` inside the worktree, and refuses one outside it (Facts). Codex starts no MCP servers kelpie bridges and runs no Claude Code hooks, so a project whose worker is on Codex and that turns on the preview or names `worker.guard_hooks` stops when its settings load, as with pi. Codex reads the repo's AGENTS.md, not CLAUDE.md.
- Codex writes its stdout and stderr to files kelpie opens for it, beside the call's settings where the sandbox cannot open them, since a shared pipe the sandbox's Node makes non-blocking killed it on its first large output (Facts). Kelpie removes them once read.
- A local worker takes only the issues the maintainer labels `worker:local`, until the design log has numbers for it. A project opts in per role by naming a local agent in `[agents]`. With a local worker, an unlabelled issue runs on `models.worker` on Claude Code, and so does an issue with a `worker:<model>-<effort>` label, each paced on Claude's account; `worker:local` on a project whose worker is not local is a label error. A new work item is then paced on Claude's account too, since it may run there. The choice is recorded on the work item (`worker.local` in the state file), so a later edit to the local agent keeps the item on it, and each turn runs the agent's model and effort as they are then, since the label asks for the local worker rather than a model, and an item whose project no longer names a local worker fails its turn saying so rather than going to Claude Code with a local model's name. A `worker:local` issue on a project with no local worker is skipped by the board as a label error. The field is written only for such an item, and a state file holding one does not load in an older binary.
- Pacing and spend per agent, built in #129. Each agent names how its usage is read with `usage`: `claude` (`/usage`, the default on Claude Code), `codex` (the Codex account's own 5-hour and weekly windows), or `none` for a local model. The reader must be the harness's own, since an agent spends its harness's account whatever its `usage` says: on Claude Code only `claude` is taken and on pi only `none`, so `codex` waits on a Codex harness, and the runner's tests reach it through a test-only `stand-in` harness. An account is its reader, so the model is one login per harness; a second Claude login would need its own config folder and is not modelled. A `none` agent is never paced. Its limit is its `lease` (the GPU lock, `gpu`, by default), which `ports::Leased` takes for the whole of each call on it, worker turn, round or verdict alike, so a qwen round on the same lock waits behind a local worker's turn. `status.local_leases` shows who holds each such lease.
- Spend is tokens per role for every agent. Dollars are kept only for calls whose harness reports them: `by_role.<role>.cost_usd` covers those, is null when there are none, and `unpriced_calls` counts the rest. A turn's log line carries `cost_usd: null` when its harness reported none. The state file marks such a call `unpriced`, so its zero cost is not read as free. `work_item.cost_usd` sums the priced calls only, and `work_item.unpriced_calls` says how many it leaves out.
- The state file change is one way. `ProjectState` and `CallRecord` refuse unknown fields, so a file holding a `codex_pacing` day start or a call marked `unpriced` does not load in a binary from before #129, and going back means deleting those fields by hand. Neither is written until a project spends the Codex account or runs a harness that reports no dollars, which no release build can do before #130.
- `shep kelpie doctor` reads Codex's usage for each project whose roles spend the Codex account and adds a `<project>: codex usage` line: missing when `codex` cannot run or the backend refuses the read, unsure otherwise.

## Review and merge

- Kelpie runs the qwen round itself and hands the findings file straight to the worker's next turn. No model reads the findings and rewrites them.
- The qwen queue: critical first, then closest to merge, then arrival. A running round is never preempted, since a kill takes 20 to 70 seconds and throws the partial round away.
- The Claude round is a fresh review session each time, never the worker's, on Sonnet 5 at medium effort, with findings delivered as a file like qwen's.
- No judge (ADR 0006). Measured against 52 known bugs, kelpie's review gate caught none and its Opus 5.5 low-effort judge kept 69% of the findings that were not real, so no model rules on a finding between its reviewer and the worker. A round that finds anything above a nit sends the worker all of its findings, nits included, at the reviewer's own severity, and every thread a review bot leaves open goes to the worker as a finding.
- CodeRabbit is in the first build's gates. Its free plan reviews public repos only, so the gate is a per-project setting, and the runner refuses to start with it on for a repo the forge reports as private. With it off, a work item goes from the review and CI straight to the merge ruling.
- The worker opens its own draft PR with its own title and body. Only the project manager summons CodeRabbit (adds `review please`) or marks a PR ready. With CodeRabbit on it marks the PR ready as the first round starts, since CodeRabbit skips drafts (shep-pm/shep-kelpie#65); with it off, at the merge, after a yes or under `auto`. shep's `.coderabbit.yaml` gates auto-review on that label, so opening a PR spends nothing.
- Merge authority is a project setting: `auto`, `ask`, or `ask-surface` (ask only when a PR touches operator-facing surface). The default is `ask`. `ask-surface` is still refused.
- `auto` (shep-pm/shep-kelpie#83), chosen over running shep's merges from a Claude control room so the merge rules stay in kelpie's code. It replaces the merge ruling and nothing else. Where `ask` would raise it, `auto` merges by the path a yes takes: the head the gate passed, CI green on it, the latest `main`, CodeRabbit satisfied where it is on, and a merge commit. Every other ruling still asks, and the tests raise each one under `auto`. Kelpie never puts `ready-for-human` on for the merge. A merge that no longer holds, because the head moved, CI stopped being green or `main` moved, goes back to CI as a withdrawn yes does, and CI catches the branch up. A merge the forge refuses takes that path once; a second refusal on the same work item parks it on a `merge-refused` ruling, and any answer to it gives the next refusal its catch-up again. Its pull request comment names the head and leaves the forge's reason out, since that text is not written for strangers. After an automatic merge kelpie posts a notice to the webhook naming the project, the pull request, its issue and the merged head. A notice is not a ruling: it has no id, takes no answer, goes to the webhook alone, and is only logged where there is none (shep-pm/shep-kelpie#118), and is saved with the merge so it goes out once, retried like a ruling's post and never ahead of one. A merge at the gated head that a restart or a lost answer hid, found merged on the next look, still gets its notice, and so does one that lands after kelpie read its error, since kelpie records the head it tried. A merge the gate started under `auto` goes ahead only while the project is still `auto`: a project switched back to `ask` goes back to CI and gets the merge ruling. Under `ask` a yes on a `rebase` or still-red ruling vouches for whatever head the gate sees next, because the merge ruling follows; under `auto` nothing follows, so the yes reads the branch's tip, and a tip the gates never saw is adopted and goes back through a pass of the review and, where it is on, a CodeRabbit round. The same holds for a head the gate finds with none known, such as one a yes under `ask` vouched for before a restart onto `auto`. The switch back to `ask` is read after the pull request's state, so a merge that landed before the switch still gets its notice. `status` shows the project's merge authority.
- The review (shep-pm/shep-kelpie#11, made serial by ADR 0006). Once the worker's draft pull request is open, `Phase::Review` runs before CI: one pass down the project's reviewers, each run once, in order. A round with no findings, or only nits (LOW), goes straight to the next reviewer. One with anything above a nit sends all of that reviewer's findings, at its own severity, to the worker's next turn as a file, and the next reviewer reads the fix. After the last reviewer the work item goes to CI, and whatever the last fix leaves is what CI and the merge see. There is no end rule and no round guard: the maintainer's ruling is that reviewers are not a loop, they go in series and whatever the pass ends on is what it ends on, and the experiments repo found the gain in the first two reads while the old loop's "two clean rounds in a row" spent its rounds on nits. A pass starts again from the top only on a new head that needs it: the fix a merge ruling's no asks for, an accepted foreign change, or a rework. Kelpie never takes or holds the qwen GPU lock itself: the script does, waiting up to an hour, which is normal, not a hang. A round's findings and its completion marker both come from disk (`QWEN_REVIEW_OUT`, redirected per work item rather than the script's own path slug, so a test rig never touches the maintainer's real `~/.claude`), never from stdout. A file the script skips as too large is cut into a `-U25` hunk against `origin/main` and reviewed again on its own, with its findings folded back in against the original path. The Claude round runs with no fence and no bypassed permissions, since it writes nothing; it may read the worktree with Read, Grep or Glob to check its work, the same as `pi` mode in the maintainer's own qwen-review skill.
- The local round is a per-project choice (shep-pm/shep-kelpie#107), since a beta tester has neither the maintainer's script nor the same GPU. `review.local` picks `off`, `endpoint` or `command`, and a table or file without it runs `~/.claude/scripts/qwen-review.sh` as before, so the live projects load unchanged. With it off, the review is the Claude round alone. `endpoint` is kelpie's own reviewer for any OpenAI-compatible server: it diffs from the round's base with ten lines of context, numbers each line by its place in the new file so the model can name one, cuts the diff into chunks sized from the settings' `context` (three bytes a token, a quarter of the context kept for the reply), and sends each with a fixed prompt in kelpie's code, reading findings back in the same `SEVERITY|file:line|what|why` format. A thinking model's `<think>` block is dropped before the findings are read, and a reply that ends inside one fails the round, since it reviewed nothing. A reply with no finding counts as clean only when it is exactly `CLEAN`, for the endpoint and the Claude round alike: an empty or prose reply reviewed nothing, and with the local round off the Claude round is the only review before CI. A command's `round-N.txt` and its marker are removed before each run, since the folder is the issue's and a rework or a retried round would otherwise read the last run's. `command` keeps the qwen script's own contract, which the README now sets out, and adds `KELPIE_REVIEW_HEAD`. Kelpie still never takes the GPU lock for a command that takes it itself. `gpu_lease = true`, on either kind, has kelpie take it around the round in the scripts' format and on their schedule, and let it go after. The runner checks at start that a command is an executable file and that an endpoint answers `GET /models`, and refuses to start otherwise, naming it. A live change to `review.local` gets the same check before it takes effect, and one that fails is refused and offered again at each wake. It is not held for the next start, as `repo` and `forge` are: nothing in flight belongs to it, since each round reads it when the round begins. It does not check the model is listed, since llama.cpp's server answers to any model name.
- A project lists its local reviewers (shep-pm/shep-kelpie#125). Kelpie's `[local_reviewers.<name>]` define each one: `command`, `endpoint`, or `claude` with its own model and effort. `claude` is always defined as the project's own Claude round on `models.reviewer`, and defining it is refused. A project lists names in `review.reviewers`, and each pass runs them once each in that order: every round goes to the first listed reviewer the pass has not run (`ran` in the review's state), skipping any that cannot run, one whose `paths` the pull request does not touch or a local one marked down, so a reviewer taken off the list or a list reordered mid-pass leaves the rest to run. The pass ends once none is left; one in which none can run gets the project's Claude round. The round's reviewer is kept in its state once it starts, so a round cut short resumes with the same one. A reviewer whose call fails three times in a row (a reply that is neither findings nor `CLEAN`, a crash) is passed over for the rest of its pass, with a `ReviewerSkipped` report, and `status` lists it under `reviewers_skipped`. An empty or absent list with `review.local` set is that round then `claude`. `review.local` still loads, with a notice at start naming the new form, and cannot be set beside a list. A reviewer's `paths` limit it to pull requests changing a matching file, by the glob matcher `generated` uses, read with `git diff --name-only` against the round's base. Each definition names its `lease`: `gpu` is the qwen scripts' lock and any other name a lock of the same format under `$TMPDIR/kelpie-leases/`, taken the way the GPU lock is, so option A of 2026-09-26 holds and the dog's book stays out of it. `gpu_lease = true` stays as the older spelling of `lease = "gpu"`. Every round's prompt carries the issue's title and acceptance criteria, the section under an "Acceptance criteria" heading or the whole body, cut at 4,000 bytes so a small model keeps room for the diff: appended to a Claude round's prompt, to an endpoint's system prompt, and written to a file a command finds in `KELPIE_REVIEW_CRITERIA`. `shep kelpie add` writes `reviewers = ["deep"]` where the maintainer's script is missing. A round now keeps `reviewer` and `last` in the state file even for a project with no list, and the build before this one reads a review phase with `deny_unknown_fields`, so a state file from this build is not readable by the one before: rolling a runner back needs its work items out of review first. Accepted as one-way at the control session's review.
- A fix turn for findings sent to the worker counts only if it moves the branch's head on `origin` (shep-pm/shep-kelpie#40), in a review round and a CodeRabbit round alike (shep-pm/shep-kelpie#49). - The merge gate (shep-pm/shep-kelpie#9). After the review's last reviewer, kelpie waits for CI. A red run is the worker's next turn, naming the failed checks; a second red run on a head the worker left alone parks it on a ruling. A green run on a branch that has the latest `main` raises the merge ruling, and a branch without it is rebased and pushed by the project manager first. A conflict is the worker's next turn too (shep-pm/shep-kelpie#61), naming the files: it merges `origin/main` in and pushes, so nothing is force-pushed. A turn that leaves the same head, or a conflict on the same `main` again, parks it on the `rebase` ruling.
- A ruling is a log line, a status entry and a webhook post, all carrying the same question and the triggers that answer it. Ruling ids never repeat. A no with a note is the worker's next turn. The pull request gets a comment for every ruling but a merge (shep-pm/shep-kelpie#89). It says what happened and that it waits on the maintainer, and names no command: `ready-for-human` already says the pull request waits, and the webhook carries the question.
- Worker questions (shep-pm/shep-kelpie#13). A worker ends its final message with its question between `<kelpie-question>` and `</kelpie-question>`, and only a block that ends the message counts. Kelpie parks the worker on a ruling that carries the question verbatim, and `shep kelpie rule <id> <text>` makes the answer the worker's next turn. A question takes only an answer, and a gate ruling only a yes or a no. A question asked before the pull request exists has no comment, and goes with its work item on a drop.
- Every ruling, whatever raised it, is posted once to one webhook (decided on #13). It is named in kelpie's own settings, its `[kelpie]` section of `dogs.toml`, which every project shares: a `[webhook]` table with `kind` (`discord` or `ntfy`) and `url`, both required. A failed post is logged and tried again after a minute, doubling to at most half an hour, and a ruling counts as alerted only once a post lands, so a restart between the post and the save can post it twice. The URL is a credential: it reaches `curl` on stdin, never in its arguments, curl's own messages are dropped, and no error, log line, status or comment carries it. Plain `http` is accepted only for a stand-in on the same machine.
- Rulings reach the maintainer by the webhook (shep-pm/shep-kelpie#109, ADR 0005), the one channel since the relay went. The webhook is on exactly when kelpie's own `[webhook]` table is set, and `ruling_channels` is a setting no more: a project table or kelpie section that still carries it is refused at load, naming the key and saying to delete it, as `models.relay` is. With no webhook a ruling reaches the maintainer in the log, `status` and `shep kelpie rule` only, and the runner logs one line at start saying so. A ruling counts as alerted once the webhook post lands and is retried the same way; with no webhook nothing is posted, so no ruling waits on an alert and none holds back the next. The notice of an automatic merge (shep-pm/shep-kelpie#118) goes to the webhook, and is only logged where there is none, so it leaves nothing waiting to block the next ruling.
- Rulings are answered from ntfy (shep-pm/shep-kelpie#111). An answer that acts proves itself with the maintainer's authenticator code, decided by the maintainer over a first build that posted a one-time code on the alert: that code sat on the topic it guarded, so anyone who could read the topic could merge. The code is RFC 6238 TOTP (HMAC-SHA-1, 30-second steps, six digits). `shep kelpie totp` draws the 160-bit secret once into `<kelpie home>/totp/secret` (the folder 0700, the file 0600) and prints it as an `otpauth://` URI and a terminal QR code to scan; `shep kelpie totp --rotate` draws a new one, written beside the old and renamed over it, the folder synced after so a crash cannot bring the old one back (a first `shep kelpie totp` links its file into place instead, so two at once keep one secret), and every runner reads the file afresh for each reply, so the old secret's codes stop at once. A secret file, or a totp folder, anyone but its owner may read or write stops the runner. Workers and the shots' dev server are denied `~/.kelpie/totp/**` like the other credentials. A reply names the project, since every project reads the one topic and ruling ids are per project: `<project> <id> yes <code>`, `<project> <id> no <note> <code>` or `<project> <id> answer <text> <code>`, the code always last. The part after the project is read by `rule`'s own parser, so a change to `rule`'s grammar reaches ntfy replies too. The code is checked against the time ntfy took the reply, which no sender can set, and taken in that step and the one before. Every code the maintainer sends is on the topic afterwards, so every right code anywhere in a post is claimed before anything else about it is read: whether answers are on, whether it is kelpie's own, which project it names, how old it is, or how the code was typed. Every text the post carries counts, its title, tags and attachment name included, and in each every decimal digit of any script is taken in order with whatever stands between dropped, so `123-456`, `123 456`, full-width, Arabic-Indic or math-bold digits all spend the code. A post spends the codes of three steps: the one before and its own, which `verify` takes, and the one after, from a phone whose clock runs ahead, which a replay could send once that step comes. Their codes are computed once a post and compared to every six digits in a row. A secret that cannot be read, or a claim that cannot be written, holds the post at the head of the queue, with the read position behind it, and backs off; it never passes the post by with its code unspent, and nothing on the topic says a code is still live. Only the exact shape, six ASCII digits last, can act. Review probes showed that a reply that answered nothing (a no with no note, a code followed by a phone's stray period, a code in the title, or a reply read in the same poll as the wrong code that turned answers off) left its code for a reader to reuse. A claim is `<kelpie home>/totp/used/<step>`, holding the id of the ntfy message that first sent the step's code, written beside its name, synced and hard-linked into place, so it is whole or absent. Every runner reads every reply, so a runner that finds the step claimed by the same message counts it as that message's, and one claimed by another message is a replay: it runs nothing, and the named project's runner tells the topic to send the next code. A wrong six-digit code is counted once by message id under `<kelpie home>/totp/failed`, and the fifth turns answers from the topic off for every project (RFC 4226 section 7.3), with one line on the topic that also suggests moving to a new topic, until `shep kelpie totp --unlock` on the terminal; a right answer forgives the count. Only a wrong code in the exact shape counts. While they are off, alerts say nothing of replies and the topic is not read. A reply with a valid code for a ruling already settled runs nothing and gets a line saying so, and a refusal from `rule` goes to the topic as a line too. Anything else is ignored and logged without its text. The alert ends with the replies that answer it and carries no code and no buttons, since a button cannot carry a code the maintainer has not typed yet. The runner reads the topic's cached messages (`/json?poll=1`) after the last one it read, saved in the state file, every 15 seconds while an alerted ruling waits, and for an hour after an alert lands, backing off to five minutes while reads fail. A read reaches back ten minutes and three steps at most, since a replay of the next step's code, which a post spends, can still verify up to three steps after the post, so a saved position ntfy no longer holds never returns its whole cache. A reply older than ten minutes is read only to spend its code, so a replay just inside the window finds it used. Claims are let go an hour behind the older of the claimed step and this machine's step, since the step is ntfy's clock, so a local clock running ahead never lets go of a claim in use. With no secret yet, alerts say nothing of replies and the topic is never read. So a reader of the topic can read every ruling and every code already sent, and answer nothing, and a writer who is not the maintainer gets five guesses at a one-in-a-million code before answers stop. Once ruling ids are global, the project in a reply can go. Four limits are accepted. Anyone who can write the topic can turn answers off with five guesses; that fails closed, `rule` still answers, and only the terminal turns them back on. And an alert's text is not authenticated: a code proves who answered, not what they were shown, so a writer who posts a fake alert could get a real answer to a question kelpie never asked, though only for a ruling id that is pending. And a topic writer who posts every code can burn steps without tripping the lockout, since a right code is never a wrong one: that only delays the maintainer's answer, and ntfy rate-limits the posts. And a post kelpie cannot read in full, such as a message over 4,095 bytes that ntfy turns into `attachment.txt`, is not fetched: it spends every step a code sent with it could name, answers nothing, and gets one line on the topic saying it was too long to read and to send a shorter reply with a new code.
- `shep kelpie <verb>` (shep-pm/shep-kelpie#119). Every trigger a runner takes is also a verb of the adopted kelpie, sending the trigger `shep trigger` sends, which keeps working. `-p <project>` goes anywhere before a `--`, before the verb included, and for `rule` before the answer's second word, so a note can carry a `-p`. - One deep review round instead of many shallow ones (shep-pm/shep-kelpie#284). #272 took ten rounds and nine worker turns, $18.53 of its $31, and still merged a feature that could not work, while one review that ran the code against its criteria found the same HIGH in one pass. The round is a state machine in `Review.stage` (`deep`, with a `step`), saved at every step: (1) a fresh session on the `deep_reviewer` role (`[models.deep_reviewer]`, Opus 5.5 at high effort when absent, `agents.deep_reviewer` over it, which is refused at load on Codex or pi while `worker.guard_hooks` is set, as `agents.worker` is, since the sessions that run commands run under the worker's fence and its hooks, and a pi deep reviewer is refused an `allowed_domains` entry that reaches its model server, as a pi worker is: one check serves both roles) reads the diff with Read, Grep and Glob and no command, under the maintainer's defect prompt word for word (a test pins it) and the reply format kelpie already reads, with the issue's acceptance criteria after it as every round's prompt carries them, and kelpie's shots when the project shows its UI; (2) a second fresh session on the same role is given the first's findings and the same prompt and asked only for what the first missed, and an empty second list is as good as a first one; (3) each HIGH of both lists, worst first, is confirmed by a session that may run commands in the worktree under the worker's fence narrowed to writing the worktree and its build folder, so it can write and run a test but commit and push nothing, and it answers `CONFIRMED|<test file>|<command>` or `UNCONFIRMED|<why>`: a test file that is not in the worktree, a reply that is neither, and a call that failed all leave the HIGH unconfirmed rather than stalling the round, and an unconfirmed HIGH still goes to the worker, marked so; (4) one worker turn gets every finding of both lists, with each backed HIGH's test (left uncommitted in its worktree, for the worker to make pass and commit) and each unconfirmed HIGH marked, in the same findings file and with the same deferred-findings copy-a-line rule as any round, and a turn that pushes nothing parks on the same ruling a fix turn always does; (5) a re-check session that may run commands, which writes only the build folder and never the source it verifies, is shown only the diff since the head the findings were sent from, and only once the worktree is the pushed head with nothing in it changed or new and uncommitted, and the pushed head still holds, in order, the lines each confirming session added (kelpie takes the worktree's differing files, with their blob ids, before each confirming call, and records after it the lines it added to each file against that, so two sessions' tests may go in one file and a fix may change the file elsewhere; a line a later session takes out of an earlier session's leaves that session's pin; a session whose changes git cannot read, or that added nothing to the file it named, leaves the HIGH unconfirmed; a session that does not confirm, however it ended, has the worktree put back as it was before it, new files removed and edits reverted to what the snapshot held, so no half-written or still-failing test is left for the worker to commit nor counted for the next session, and a session stopped with the runner keeps the snapshot of its first try through the retry, which restores to it), since a fix left uncommitted or unpushed, or a test edited to pass, would be verified here and never reach the branch as it was verified; any of these parks on the fix-not-pushed ruling, whose question says the fix was ended but names the cause (which test, or which files are uncommitted), and calls it the deep review, and replies `FIXED|<n>|<evidence>` or `UNFIXED|<n>|<why>` for each finding, running each failing test, because the experiments found a fixer's "fixed" wrong for one in four bugs it was handed. A finding the reply leaves out, calls fixed with no evidence or calls unfixed is unfixed, and a reply with no such line is a failed gate that asks again. A finding the worker deferred, by copying its line to the deferred-findings file, is resolved and not unfixed (matched by file, line and what, as filing the issue matches it, so a reworded why still defers it), and it is not asked about at the re-check (which counts it apart from the fixed, as `deferred`) since kelpie files it as an issue once the pull request merges; a deferred finding's failing test is dropped from the pin, and the worker is told to remove it from its worktree and not commit it, since a failing test must not be committed. A worker that defers every finding has nothing to push, so an unmoved head is no fix-not-pushed: the worktree need only be clean, and the review goes on as a re-check with nothing to ask. Unfixed findings go to the worker once more and are re-checked once more, and still unfixed after that is a `deep-review` ruling whose yes sends the worker them once more, and whose no is a note to the worker, which restarts the review as any no does. There is no judge: the experiments' reader precision with this prompt was 80% to 95%, and a HIGH is confirmed by a test rather than by opinion. Every call of the round is one timing phase, `deep_round`, and one spend role, `deep_reviewer`. The state file writes `deep_round` only once it holds time, so a work item that never ran the round is read by a build from before it (an older build refuses a timing key it does not know); `status` and `timings` always show it. The role is not hidden the same way: a work item's call records keep their role in the state file, so a build from before `deep_reviewer` cannot read the state of an item that has completed a deep call (a spend by role is the point of the round's cost, and a record under another role's name would lose it). Rolling back means finishing or dropping such an item first; the refusal names the role. Decided on the issue, against its own opening text: the readers run no command (the first draft of the issue had them break the lines the new tests cover), since the experiments found a reviewer that runs tests found fewer bugs and only confirms what it finds.

- Adoptions (shep-pm/shep-kelpie#84). An adoption makes a work item of an open pull request kelpie didn't open, so the maintainer's other sessions can hand theirs over. The worker's first turn is whatever the gate first sends it, behind a file in its build folder holding the pull request's title and body and its issue. A latest review requesting changes from its owner, a member or a collaborator goes in that file too and is the first turn at once, followed by a pass of the review. The branch's owner may still be pushing, so a push counts as the worker's only when the worker's worktree holds it, and one found before a worker's turn sends the work item to the gate instead of the turn. Either way a push from anyone else parks it as on kelpie's own branches. The merge follows the project's `merge_authority`.
- Full reviews (shep-pm/shep-kelpie#100). The label asks CodeRabbit only for what is new since it last read the pull request, and a branch kelpie caught up with `main` holds nothing new to it. So on a pull request CodeRabbit has reviewed before, an adopted pull request's owed summon, and any summon after kelpie's own catch-up push, asks with a `@coderabbitai full review` comment instead, with the label taken off so no push summons outside the lease. A pull request CodeRabbit never read keeps the label alone. The comment is a summon like the label: it waits for the dog's lease, is counted from when it was made, and is saved as made before it is posted, so a restart never posts it twice (a comment the forge refuses leaves the round waiting for the lease again). CodeRabbit marking the head "Review completed" with nothing posted since the summon is an answer: after a minute's settle, since a review posts a few seconds before that status, kelpie reads it as a clean read, unless a summon is owed. An owed summon answered that way asks once for a full review, and then waits for it as for any summon, so two hours with nothing is still the `coderabbit-silent` ruling. The control room measured about six real findings from a full review to one from an incremental review on shep.
- A confirmed finding left unfixed at merge becomes a follow-up issue (shep-pm/shep-kelpie#142). A reviewer's finding goes to the worker, which fixes it; one the worker leaves as out of scope goes, in the findings file's own format, into `deferred-findings.md` beside the findings file in its build folder, which the findings file's header names. Once the pull request merges, kelpie reads that file once, before it removes the build folder, and files each finding as an issue on the project labelled `ready-for-agent`, linking the pull request. An open issue whose body names the file, and whose title matches or whose body says the same thing, gets a comment instead of a second issue. Under `ask` a `follow-up` ruling comes first, raised after the merge: a yes files them and a no drops them. Under `auto` they are filed with no ruling. Only what kelpie itself sent the worker is filed: each finding sent to the worker is kept on the work item, and a line in the file counts only when it names one of them by file, line and what, and the issue carries kelpie's text, not the worker's, so a worker cannot put its own words on the tracker. A round of nits never reaches the worker, so its nits are never held. If the forge keeps refusing for six hours from its first refusal (issues off, a missing label, a rejected body), a `follow-up` ruling lists the findings and the reason: a yes tries again for another window, a no drops them. Passes do not count, only time, so a short outage of the forge's own costs nothing. A finding fixed in a later round stays in the held union, since it is only ever filed when the worker also names it in the deferred file. An open issue counts as already holding a finding only when its body names the file. A crash between opening an issue and saving that leaves a redundant "confirmed this too" comment on the new issue at the retry, which is accepted. A finding whose text names a folder on this machine is not posted (the forge guard refuses it), so it is left out and counted in the step's report rather than retried. Not built: a reviewer that answers after the merge, since nothing watches a pull request once its work item is gone, and a worker that defers every finding, whose fix turn pushes nothing and raises the not-pushed ruling.
- A summon CodeRabbit never acknowledged is sent once more (shep-pm/shep-kelpie#122). A sign within fifteen minutes of the summon counts as hearing it: the "Review in progress" status on the head, a change to any of its comments (the walkthrough is edited in place), a review or any other status on the head, or a rate-limit notice. With none, the runner sends the summon again through the same choice between the label and `@coderabbitai full review` that made the first one, says so in the log (`SummonedAgain`), and waits as before. The re-send is the same round: it keeps the lease the first summon took, opens no window of its own, and the hour still runs from the first summon. A label summon goes off and on again, since a label already on sends CodeRabbit no event. It is saved before the comment goes out and made at most once per summon, so a second silence falls to the two-hour `coderabbit-silent` ruling, counted from the first summon. It is sent only under a lease row of the work item's own, so after a restart, which clears the rows, it is not sent under a grant another item took. A review that stays "Review in progress" still falls to the two-hour ruling, and only the newest status on the head says whether it is running. The ten-minute spent count now applies only after the re-send, since the lease has to be held for it.
- A clean catch-up goes back to CI only, with no new CodeRabbit round (decided 2026-09-29 on shep-pm/shep-kelpie#106). With several work items open, one merging sends the others through a catch-up with `main`, so this comes up often. Kelpie's own rebase or merge of `main` with no conflict leaves the pull request's own diff unchanged, so there is nothing new for CodeRabbit to read, and CI checks the combined code. A catch-up the worker resolves is a new push of its own, so its turn clears CodeRabbit's satisfaction and the next green CI starts a round, as a fix for red CI does. A summon owed for another reason after a catch-up still asks for a full review, as above.
- Two kinds of reviewer, behind two interfaces (shep-pm/shep-kelpie#123, shape chosen 2026-09-29). A local reviewer runs on this machine against a diff and hands its findings back when the call ends: qwen, the Claude round, or #107's endpoint or command. A pull request reviewer is summoned on the pull request and answers there, later, within a rate window of its own: CodeRabbit now, cubic and Codex next. They share their output, a finding with a severity, file, line and text, and from there the worker's fix is one path. They are two interfaces because the rest is different: a pull request reviewer needs a lease on its window, a sign that it heard, a re-send when it did not, threads to resolve, and a head its review covers, and a local reviewer needs none of that. CodeRabbit and cubic follow the same script on GitHub, so the pull request side is one review bot provider, the runner's round, with a profile per bot for what differs: its login, its label and full-review comment, how its answers read (heard, reviewed, refused, done), how a thread's severity reads, its quota and the lease it spends. Profiles and their parsers are code, tested against the bot's recorded output. CodeRabbit is the first profile, and nothing it does changed in the move. The saved names stay CodeRabbit's (the `coderabbit` phase, lease row, ruling kinds and tally, and the `coderabbit` settings), since the state file and live settings carry them. Settings do not override a profile's simple fields yet.
- cubic is the second review bot profile, and the outside round goes to whichever listed bot is free (shep-pm/shep-kelpie#124, shape chosen 2026-09-29). Kelpie's `[kelpie.reviewers]` defines each bot by its window, `reviews` in `hours`; CodeRabbit is defined with one an hour when absent, and cubic only once defined. A project's `pull_request_reviewers` lists defined bots in preference order, `coderabbit` alone when absent, and a start refuses a bot kelpie does not define. A round waiting to summon asks the dog for every listed bot's lease and summons the first listed it was granted, giving the other asks back unless a sibling work item waits on them, so a pull request waiting on CodeRabbit's hour takes a cubic round and one with both busy waits for whichever frees first. The phase records the bot holding the round (`bot`, left out for CodeRabbit), and so does the silent ruling. cubic has no label, so it is always summoned by its comment. A refusal parks the bot until its window opens: CodeRabbit quotes when, and a refusal that quotes nothing, such as cubic's, parks it for its window's span. The round cap, a fixed `coderabbit.rounds`, an adoption's count and a rework's count all add every listed bot's reviews, and one review from any listed bot settles an adopted pull request's owed summon. The dog reads the definitions from kelpie's section when it starts, so a changed window reaches it on its next start; the runner takes a changed list or definition at once. Until a bot's definition reaches the dog, the dog never grants it, since a lease with no window would be granted freely and a refusal would have no window to close. A round that lands sends the worker every listed bot's open threads, not only those of the bot that answered, and a work item that ends gives back the lease of the bot its round holds even if the list has dropped it. CodeRabbit's private-repo check applies only when it is listed, so a repo GitHub marks private can list cubic alone. The profile's `P1`..`P3` level is the finding's severity (P0 and P1 high, P2 medium, P3 low) and goes to the worker with cubic's confidence as the finding's why.
- Codex is the third review bot profile (shep-pm/shep-kelpie#126). `@codex review` summons it, and it is defined in `[kelpie.reviewers.codex]` as the plan's weekly allowance for code reviews, such as 10 reviews in 168 hours, and listed in `pull_request_reviewers` like the others. Its first comment after a summon is a notice and not a refusal, so any comment of its since the summon is the sign it heard. A review covers the commit it names, by prefix, since its comments give ten characters. A comment naming a usage limit is a refusal that quotes no reopening, so it parks the bot for its window's span, as cubic's does. A thumbs up it leaves on the pull request after the summon is a review with nothing in it. Whether marking ready is its summon is the definition's `reviews_on_ready` (see Facts). The badge on a finding, `P0` to `P3`, is its severity as cubic's level is. The local Codex CLI reviewer is not part of it; that moved to #233 with Codex as an agent.
- A fixed review budget (shep-pm/shep-kelpie#158). The review cost hours on a fast-moving project for mostly nits: the divisor cap gives CodeRabbit at least two rounds at one review an hour. `coderabbit.rounds` sets a fixed number of rounds per pull request in place of the divisor's cap. The last round's open threads go to the worker as any round's do, with the `review please` label taken off first, and its fix push goes to CI and the merge ruling with no further summon. Once the rounds are spent no later turn summons again, a CI fix or a merge ruling's no included, though an adopted pull request still gets the one review owed to it. The count is per pull request, so a rework, which stays on its pull request, starts from the reviews CodeRabbit already gave it and spends no second round. A rework counts as an adoption does (shep-pm/shep-kelpie#162): a review of the pull request's current head is left out, and the gate counts it once when it finds it, so a rework that pushes nothing does not spend that round twice. Unset, the divisor's cap holds. shep's table sets `coderabbit.rounds = 1`.
- The foreign-change check covers the head too (shep-pm/shep-kelpie#69). Kelpie records the branch's head on `origin` as each worker turn ends, and the head its own catch-up push leaves, so a worker's merge of `main` and kelpie's rebase are never foreign. At the gate, once the forge's head matches `origin`, any other head parks the worker on a ruling that names the commit. A yes moves the worktree to that head, refusing if it holds work not pushed, and sends it through a pass of the review and, where it is on, a CodeRabbit round before the merge ruling. A yes on a `rebase` or still-red ruling asks the maintainer to fix the branch, so it vouches for whatever head the gate sees next. Under `auto` it vouches for no head the gates did not see. A commit pushed while the worker's turn runs is read as the worker's, and gets the gates that turn's code gets.
- A work item saved before the gate existed stays with its worker until `shep kelpie gate` sends it in. The trigger takes only an item whose turn has ended with a known pull request.
- Seeing the UI (shep-pm/shep-kelpie#54). A repo opts in by carrying `.claude/launch.json` on `main`, the file Claude Desktop's preview reads; without it nothing changes. Kelpie reads it from `origin/main`, both whether it exists and the configuration it starts, so a worker cannot widen its own sandbox by adding one or pick the shots' dev server command by editing it. That dev server cannot write the shots folder. Kelpie's shots start the file's configuration (`preview.configuration`, else the first) under the sandbox runtime `srt`, capture each route at 390 by 844 and 1280 by 800, light and dark, in headless Chromium from kelpie's own Playwright, and stop the server. Routes are `preview.routes` (default `/`) plus every route the worker named through `mcp__kelpie__shots`. Kelpie takes shots of the head before each Claude review round, which gets the PNG paths and the folder in `additionalDirectories`, and before the merge ruling, whose run goes on one pull request comment that later runs edit in place. The PNGs are committed to `kelpie-shots/<number>` on `origin`, never the work item's branch, and the comment links them by commit. Kelpie deletes that branch when the work item finishes, merged or not, so the comment's images stop showing then. A failed run never posts: the merge ruling or notice says it failed, and an earlier head's comment, if there is one, stays as it was. It holds no gate. Every worker on a project with the preview on (see the switch below) gets the Playwright MCP server and kelpie's shots tool through `--mcp-config`. Its instructions name the launch configuration's command, port and folder, the folder being `cwd` resolved against the worker's worktree exactly as the shots tool resolves it, so the worker and kelpie start the dev server in the same place (shep's is `web/`, not the root). A `cwd` that leaves the worktree, through `..`, an absolute path or a link, is refused, and a run that cannot find it fails. `preview.domains` reaches the worker's sandbox, the shots' dev server sandbox and both browsers alike. `kelpie tools install` puts the pinned `@playwright/mcp`, `@anthropic-ai/sandbox-runtime` and Playwright's headless Chromium under `~/.kelpie/tools`.
- Chosen over driving Chromium over the DevTools protocol from a crate: measured on the playground, raw CDP's own network-idle event never fired with Vite's dev server open (30s timeout on every shot), where Playwright's `networkidle` settled each shot in about 1.1s. Playwright also brings request routing and colour-scheme emulation, which raw CDP would rebuild.
- The preview's switch is `enabled = true` under `[app.dogs.kelpie.preview]` in the project's settings (shep-pm/shep-kelpie#131). The launch file on `main` is still needed, and still read from there, but it turns nothing on alone: shep carries one for the maintainer's own Claude preview of `web/`, and kelpie took shots of every shep pull request anyway.
- The project manager is kelpie code plus one-shot judgement calls (reading commits that landed after a review, auditing a docs PR's claims, checking new plans for overlapping intent) and a state file workers read. Coordination needs footprints, not a codebase map: planned files from the plan, actual files from the branch diff, `git merge-tree` for conflicts, and GitHub issue dependencies for order.

## Budget

- Kelpie paces against the account's weekly window. The daily allowance is what is left of the week divided by the days until reset (100/7 on a fresh week), one figure for the day, not spread by the hour. The hours set at kickoff (default 8, about 1.8% an hour) only produce the per-hour figure `status` shows. It covers all account usage, the maintainer's own sessions included.
- The 5-hour window is a local limiter: pause near 50% until it resets.
- Built in #15. A day is 24 hours counted from the weekly reset, so the days until reset are always whole. The allowance is fixed when the day begins (what the week had left, over the days left) and kept in the state file, so a restart keeps it. Today's spend is the week's utilization now minus its utilization at that read, the maintainer's own sessions included. Once spend reaches the allowance, no work item is dispatched and those in flight continue. The kickoff hours only divide the allowance into the per-hour figure `status` shows.
- A maintainer's `add` is not held by the daily allowance, the way it already skips the board's screening. The 5-hour window still holds its turns.
- Decided 2026-09-27 on #15: the allowance is one figure for the day, not spread by the hour. The kickoff hours only produce the per-hour figure `status` shows, given the gates already in place: the 5-hour window and the board's own screening.
- The 50% mark stops a turn from starting, dispatch included, until the window resets. Usage is read only before a dispatch and before a turn that has not begun, never mid-turn, and a turn resumed after a restart is not held. A hold is trusted for at most 10 minutes, since reset times are printed to the minute and a window can reset mid-read.
- Decided 2026-09-28 on #67: `pacing.enabled` (on when absent) turns both limits off for a stretch when usage does not matter, such as a free reset coming. Nothing is held, including on an unreadable reading, but usage is still read before each dispatch and turn, so `status` shows `pacer.enabled: false` beside the live numbers.
- When usage cannot be read, the pacer holds both limits and says so in `status`. A pacer that guessed would spend the account it exists to protect.
- The pacer sets concurrency, and logs utilization per unit by hour of day. A peak-hour effect, if one returns, shows up in the data rather than being hard-coded.
- "Do n work items today" comes later, once per-item costs are measured.
- Per account since #129. Each account keeps its own day start, allowance, 5-hour stop and holds; Codex's day start is `codex_pacing` in the state file, written only once one exists. A new work item is paced on every account the project's calls spend (the worker's, the reviewer's and each session reviewer's), and holds on the first one over its allowance or past its 5-hour mark: a local worker with a Claude reviewer still spends Claude's week. Decided on the control session's review of #210. The worker's turns are paced on the worker's account. A review round run as a session is paced on its own agent's account with the same 5-hour stop: with one account the worker's turns throttled the rounds between them, and with two nothing else would. `status.pacer` lists each account the project spends, and any other read this run, under its name (`pacer.claude`, `pacer.codex`), with what holds a new work item on it. Hold reasons name Codex ("Codex's 5-hour window is at 55%") and keep Claude's wording.

## Where the time goes

- Phase timings (shep-pm/shep-kelpie#141). Each work item records the seconds it spent in each of thirteen timing phases: `worker`, `gpu_wait`, `local_round`, `claude_round`, `deep_round` (added by shep-pm/shep-kelpie#284), `ci`, `coderabbit_window`, `coderabbit_review`, `ruling`, `merge`, `shots`, `paused` and `other`. Every second since the work item was created lands in exactly one, and a work item already open when a kelpie with timings first loads counts from that load. The `coderabbit_*` phases cover whichever listed review bot's lease and review the work item waits on. A worker turn that waits for a local agent's lease is `worker`: only a local review round splits its wait for the GPU out.
- Time is charged at the state's save, to the phase the work item was in before it, so no step that changes a work item has to know about timings. The phase is read off the work item's state, in this order: a turn this process runs, then a running call by its kind, then a paused project, then a ruling, then the gate it waits at. A paused project beats a ruling: an item parked on a ruling while the project is paused is `paused`, decided by the maintainer on 2026-10-01 since nothing steps a paused project and the answer is the maintainer's to give when it resumes. `other` is between steps, and the time kelpie is down.
- A turn marked running in the state file does not count as the worker's unless this process runs it. A stop leaves a cut short turn marked, a restart finds it marked until a step resumes it, and a session that dies unborn while the project pauses leaves it marked with nothing running it. The runner keeps the turns it runs in memory, from the step that begins the call until the save that ends it, so nothing about it is written to the state file and no restart inherits one. A turn stopped with the runner is saved to the worker as it stops, and the downtime after it is `other`.
- The runner saves the charge at the start of a step once a work item has gone half a minute without one, so about every minute while the loop idles (it sleeps 60 seconds between steps), and once as it stops. A crash usually costs about the last interval to `other`. A beat that cannot save is told and let go, since the next save charges the same time. A long turn or call is the exception: it blocks the step loop, so no beat runs, and a kill during one charges all of it since its start to `other` (shep-pm/shep-kelpie#240). The save as the runner stops waits for the worker to let go first, and is skipped when it does not, so a shutdown never waits on a step in flight.
- A local round's wait for the GPU is reported by the reviewer adapter, since it happens inside the call. Kelpie's own hold reports when its first try finds the lock held and when it gets it. A command that queues on the lock itself, as the qwen script does, is watched by polling the lock: a live holder outside the command's own process group is a queue, and the round runs only once its own group holds the lock, so the moment the lock is free and another process takes it first is still waiting. The watch ends once the command's group holds the lock, so a later holder cannot put the round back in the queue. Only a command with no lease is watched, on the assumption that it queues on the `gpu` lock as the qwen script does; one under a lease of kelpie's own is never watched, since the lock the watcher reads says nothing about it. An endpoint round with no lease has a queue kelpie cannot see, so all of it is `local_round`.
- The state file keeps a record per finished work item in `history`, merged or dropped, with its wall time and every phase, and the last 100 of them: the file is written whole at every save and every heartbeat. The oldest record goes in the same write that removes the work item. `status` shows each open item's `timings` and the ten most recent records, and `shep trigger <project> timings [n]` totals the last `n` (10 when left out) as JSON with a plain-text table. The state file stays version 2: every new field has a default. The change is one way, though: a kelpie from before it refuses a state file with a `history` or a work item's `timings`, and no runner opens. To roll back, stop the runners and remove both from each project's `state.json`, for example `jq 'del(.history) | .work_items |= map(del(.timings))' state.json > state.new && mv state.new state.json`, then start the older build. The time counted so far is lost.

## V1 directions

Not built and not decided: where the maintainer wants kelpie to go after the MVP, noted 2026-09-28.

- Names and shape, per the maintainer: `shep-kelpie` stays the shep adapter (the runner, the dog and a library), published as crates. `kelpie` becomes the Tauri app on top of shep and those crates, shipped as an app, never as a crate.
- A kelpie GitHub App. Pull requests would come from its own identity instead of the maintainer's account, so the maintainer can request changes and approve like any reviewer. GitHub refuses both from a pull request's author, which is why #53 reworks on a `ready-for-agent` label. Installation tokens, scoped per repo, replace the maintainer's `gh` token, and the gates show as check runs. Webhooks would replace polling, but kelpie runs on the maintainer's machine, so they need a tunnel. Identity and check runs come first, on polling.
- Any CLI agent, through adapters. The worker and reviewers are already ports. Three things are Claude-shaped today. The worker adapter leans on Claude Code's session resume, usage output and settings file. The guardrails are Claude Code's own sandbox, deny rules and hooks, so another CLI needs kelpie to supply its own sandbox, the largest piece. Pacing reads Anthropic's weekly and 5-hour windows, which becomes a budget per provider.
- A spike on Restate (restatedev/restate), a durable-execution engine: journaled steps that resume after a crash, exactly-once calls, durable timers and promises, and single-writer keyed state. The runner hand-rolls that today in its state file and resume logic, and the bugs fixed on 2026-09-28 were that class: a crash between the label call and the save that could summon twice, a review round cut short by a restart recorded as a failure (#46), a lease book lost on restart (#19). A ruling is a durable promise, and the turn ceiling and pacing are durable timers. The spike models one work item's loop as a Restate workflow and measures whether the resume code shrinks and those bugs go away. The costs: `restate-server` is one more process (it could run as a sheep), the tests change shape, and the server is under the Business Source License 1.1, which allows this use (it bars offering Restate as a hosted service). Its Rust SDK is MIT.
- Prior art, checked against each vendor's docs on 2026-09-28. GitHub's Copilot coding agent, Codex, Jules, Cursor's cloud agents and claude-code-action all ship issue to pull request, rework from review comments, and UI screenshots on the pull request. Copilot's Playwright defaults (on by default, localhost only) are the shape #54 follows. None of them has an ordered gate chain, pacing against a subscription's usage windows, or leases on a shared resource across repos. That is where kelpie's design effort goes.

### Headless Claude Code

Measured 2026-09-24 on Claude Code 2.1.282, `--model sonnet`, one sample each. Floor means input plus cache write plus cache read on a trivial prompt.

- Baseline floor 41,012. `--setting-sources ""` gives 22,927, and also drops hooks and plugins. `--strict-mcp-config` with an empty `--mcp-config` gives 36,935. `--disable-slash-commands` gives 36,482. All three together give 26,273. `--tools ""` grows the floor to 91,744.
- `--bare` refuses subscription login. It reads only an API key.
- Two identical fresh calls share the whole prefix: the second reads 41,010 from cache. A different working directory shares only about 10k.
- The first `--resume` onto a fresh session rewrote about 29k of cache in one early probe. Seven runs in the transport series wrote only the new turn (about 5.3k), so it did not reproduce.
- `total_cost_usd` is cumulative across a resumed session. `usage` is per call. Measured again 2026-09-26 on 2.1.283: `modelUsage` is cumulative too, and the top-level `usage` sums every request inside one call. The recorded pair is in `fixtures/`.
- A call killed within its first second leaves no transcript. `--resume` onto it prints "No conversation found with session ID" and exits 1 with no JSON, and `--session-id` can take the same id again. Once a transcript exists, `--session-id` refuses the id as already in use.
- `/compact` works under `-p`. The result carries `local_command: "compact"` and `num_turns: 0`. Context went from 125,122 to 54,484 on the next turn, which wrote a fresh 42.6k cache. `/compact <instructions>` is accepted.
- Plugin skills under `-p`, measured 2026-09-29 on Claude Code 2.1.285 with Haiku 4.5, one sample each. A `--plugin-dir` plugin loads under `--setting-sources project`, and `-p "/<plugin>:<skill> <args>"` runs the skill even with `disable-model-invocation: true`, on a fresh session and on `--resume` alike. Multi-line arguments reach it whole. An unknown skill, or a `--plugin-dir` that doesn't exist, is no error: the call succeeds and the model answers that the command "isn't available". A plugin manifest's `skills` list does not load an absolute path outside the plugin's folder. A copied skill answers to both its folder's name and its `SKILL.md` name.
- Trimming unused features, measured 2026-10-01 on Claude Code 2.1.286 with Sonnet, floor as above, two samples each, identical. A reviewer's settings file (`deny` of `Agent`, `Task` and `Bash`) gives 16,093. The same file with `disableBundledSkills`, `disableWorkflows`, `disableClaudeAiConnectors` and `disableArtifact` set, and the plan-mode, cron, design and worktree tools added to `deny`, gives 9,011: 7,082 fewer on every turn. A bare tool name in `deny` removes the tool's definition, where a scoped rule only blocks the call.
- Two concurrent `--resume` calls on one session both succeed and run one after the other. `--fork-session` gives a new session id and a separate transcript.
- Flags missing from `--help` but present in the binary: `--max-budget-usd`, `--task-budget`, `--autocompact`, `--session-id`, `--resume-session-at`, `--channels`, `--dangerously-load-development-channels`.
- The CLI parses rate-limit data into `five_hour` and `seven_day` windows (plus `seven_day_opus` and `seven_day_sonnet`), each with a utilization and a reset time. `-p --output-format json` does not carry it, stream-json does as `rate_limit_event`, and headless `claude -p "/usage"` reads it for free.

### How messages reach sessions

Read from the desktop app's bundle and the CLI binary, 2026-09-25.

- Desktop app sessions run through the Agent SDK: the app spawns `claude --input-format stream-json --output-format stream-json` and holds its stdin. Its session tools are an in-process SDK MCP server with no socket or port. Sending a message writes a user turn into the target's stdin. An outside program cannot reach a desktop session.
- CLI sessions each register `~/.claude/sessions/<pid>.json` with a messaging socket (`/tmp/cc-socks/<pid>.sock`) and a 0600 peer token file. `SendMessage` is JSON lines over that socket, with an auth line first. The protocol is undocumented.
- `claude agents --json` lists live sessions, interactive and background, with their status. It is meant for scripting and needs no TTY.
- Background sessions: `claude --bg` prints an id that `claude attach`, `logs`, `stop` and `rm` take. `--bg --resume <id>` continues a session in the background.
- An MCP server can push `notifications/claude/channel` into a session, which would wake it. It is gated per organisation and off on Bedrock and Vertex.
- A socket message wakes an idle background session, about 5 seconds, 3 times out of 3. It arrives framed as a message from another Claude session.

### Usage limits

- Weekly limits were never tied to time of day. Anthropic announced in March 2026 that 5-hour limits drain faster on weekdays between 5 and 11am PT. Secondary sources report that was removed for Claude Code on Pro and Max on 2026-05-06.

- Headless `/usage`, measured 2026-09-26 on Claude Code 2.1.283 (recorded in `fixtures/usage-result.json`): `total_cost_usd` 0, `num_turns` 0, `local_command: "usage"`, about 1.5 to 3 seconds. A model is on the GPU when `size_vram` equals `size`, and `size_vram / size` is the share on it. Recorded shape: `fixtures/ollama-ps.json`, written by hand from Ollama's documented response, since the maintainer's host did not answer from the worker's sandbox.
- It cannot say how busy the GPU is: there is no utilization, so a model on the GPU that another round is using looks the same as an idle one. That is the GPU metrics ticket's job, not this check's.
- It lists only loaded models. A model not loaded yet is not checked, and the check cannot say where it will go when the round's first request loads it. A model that loads spilled in the middle of a round is not caught until the next round.
- Kelpie reads `/api/ps` only where it holds the GPU lock around the round (`gpu_lease = true`), after taking it and before the round. Without the lock the read races whoever holds it: it would rule on another session's spill that a round would have queued behind, and could pass just before the holder reloads the model spilled. The default command round, `qwen-review.sh`, takes the lock itself, so it is not checked, and `ollama` on a command without `gpu_lease = true` is refused when the settings load, with that reason. An endpoint with no `gpu_lease` is skipped the same way. The host is the endpoint's `url` without `/v1`, or the command's `ollama`. A command names its model with `ollama_model`, and only that model is checked. Without it every model the host has loaded is looked at, and one spilled for another reason fails the round, and each yes runs into it again until it unloads (two hours by default). Model names match without regard to case. A model partly or wholly on the CPU fails the round without running it, and raises a ruling that says which model and how much is on the GPU, so it reaches the maintainer's webhook. A yes runs the same round again. A 404, or a reply that is not `/api/ps`'s, means the server is not Ollama and skips the check. A reply that lists models with no readable `size` is Ollama-shaped, so the runner logs how many were left unchecked. A host that cannot be reached fails the round, and the runner retries it as any failed round.
- `status` shows `local_model` from the last read: the name, the percent on the GPU, the context length and when it unloads. It is absent until a round has read one, and it is the last round's view, not live.

### The GPU's metrics

Built in shep-pm/shep-kelpie#146, for the load `/api/ps` cannot give (above).

- `nvidia_gpu_exporter` serves Prometheus text on port 9835. Kelpie reads five of its series, each labelled by the GPU's `uuid`: `nvidia_smi_utilization_gpu_ratio` (0 to 1), `nvidia_smi_memory_used_bytes`, `nvidia_smi_memory_total_bytes`, `nvidia_smi_power_draw_watts` and `nvidia_smi_temperature_gpu`. Recorded shape: `fixtures/gpu-exporter.txt`, written by hand from the exporter's documented output, since the maintainer's box did not answer from the worker's sandbox (a 5 second connect timeout, as for `/api/ps`).
- `gpu_metrics_url` in kelpie's own settings names the page, since the GPU is the machine's and not one project's. Without it nothing is read and `status` has no `gpu`. It takes the same `http://` or `https://` URL as an endpoint, and is read again at the runner's next wake like the rest of kelpie's settings.
- A thread reads the page every 15 seconds with `curl` (3 seconds to connect, 5 in all, 1 MiB at most, cut off mid-transfer), and `status` shows the last reading: each GPU's `utilization_percent`, `memory_used_bytes`, `memory_total_bytes`, `power_watts` and `temperature_celsius`, and `age_seconds` since the read ended. A series the page lacks is left out of that GPU. A page with none of the five, or one that cannot be fetched, leaves `status` as it was and puts the reason in `gpu.error`. Until the first read, `gpu.error` says it has not been read yet. The reason never names the URL, because the host is the maintainer's, and `EndpointUrl` prints as `EndpointUrl(..)` in `Debug` for the same reason.
- The read is off the request path because shep gives an action 3 seconds (`action_timeout`, which kelpie leaves at its default) and a box that is off or hung takes 5 to fail. Measured against a listener that accepts and never replies: `curl` gave up after 5.01 seconds. A `status` that waited on it would time out at the shepherd, and `kelpie upgrade` counts a timed out `status` as a runner still busy. Every trigger that answers with the status shows the same cached reading, and none waits on the box. Changing `gpu_metrics_url` takes effect at the next reread and reads the new page at once.
- Not done (shep-pm/shep-kelpie#251): the split of a `gpu_wait` into the GPU busy with another round and the GPU idle. It needs a sample during the wait and two new timing phases, which changes the state file's `timings` and the rollback above.

### CI and the merge

Read 2026-09-26 with gh 2.96.

- `gh pr view --json statusCheckRollup` lists two kinds of check: a `CheckRun` (GitHub Actions, with `status` and `conclusion`) and a `StatusContext` (a commit status such as CodeRabbit's, with `state`). shep's checks include `SKIPPED` runs, which count as passing.
- The playground's pull requests carry no checks at all: an empty rollup. GitHub cannot tell that from CI not registered yet, so a project says whether it runs CI with `ci` in its settings. With it on, an empty rollup is pending, never green; with it off, kelpie reads no checks. The playground's settings have `ci = false`, set 2026-09-27.
- Upgrading the playground's runner past #34 crash-looped it on 2026-09-27: its settings file predated `worker.turn_timeout` and the parser required every key. A key added after a project was created now loads with its documented default: `worker.turn_timeout` 60, `worker.allowed_domains` and `worker.build_env` empty. `ci` stays required, since the design log documents no default for it and a wrong guess either hangs a repo with no CI or merges past checks that never registered.
- A check set registers a check at a time, so kelpie reads a verdict from a head's rollup only two minutes after it first saw that head, and merges two minutes after marking a draft ready, which can start a fresh run on the same head.
- A conflict is one turn for the worker. Seen live on the playground's rework of #38: the gate raised a `rebase` ruling, the maintainer sent a note, and the worker resolved it in one turn.
- `gh pr view` lags a push. Seen live 2026-09-27 on the playground: two seconds after kelpie pushed a rebase, it still reported the old head. Kelpie now reads the branch on `origin` after each fetch and waits while the forge's head differs.
- A commit pushed by hand after a CodeRabbit round reached the merge ruling unreviewed. Seen live 2026-09-28 on the scratch repo's PR #5: CodeRabbit satisfied at `0119b4d`, `4887ecf` pushed by hand four minutes later, and the merge ruling followed at `4887ecf` two minutes after that. The foreign-change check then compared only labels and the ready state.
- `gh pr merge --delete-branch` also deletes and switches branches in the checkout gh runs from, so kelpie leaves it out and removes the branch with `git push origin --delete`.
- A forge with "delete head branches on merge" set removes the worker's branch itself, so kelpie's `git push origin --delete` can find it gone. Seen 2026-09-29 after merging shep-pm/shep#639: the push was rejected with `cannot lock ref ... unable to resolve reference`, the runner logged `gate-failed` and finished on the retry. The text varies by git version and host, so kelpie does not match it: after a failed delete it asks `git ls-remote` whether the ref is still on `origin`, and a ref that is gone counts as deleted.
- The runner's own `gh` and `git` calls are plain child processes. The worker's settings file, its sandbox and its denylist apply only to `claude` sessions started with it, so they never reach the project manager's merge, rebase or `--force-with-lease` push.
- A merge queue on `main` (shep-pm/shep-kelpie#213). With one on, `gh pr merge --merge --match-head-commit` queues the pull request and exits 0. GitHub tests it on top of the pull requests ahead of it, then merges it or removes it, and it stays `OPEN` the whole time. `gh pr view --json` has no queue field, so kelpie asks GraphQL for `isInMergeQueue` and the `RemovedFromMergeQueueEvent` timeline items, whose `reason` is free text. Read 2026-09-30 with gh 2.96: with the event filter on, `totalCount` still counts every timeline item (6 on a merged pull request with no removal), so kelpie counts the returned nodes.
- A queued pull request is waited on. Its work item records how many removals it had when kelpie queued it, and skips every gate while the queue holds it, since `main` moves under it. A pull request open and out of the queue with more removals on record went unmerged, and one with none on record gets two minutes' grace before it counts the same. Either goes back to the worker like red CI, with the forge's reason in the prompt, and a second one at the same head raises the `merge-refused` ruling. The workflows run `on: merge_group` so every required check reports in the queue. Turning the queue on is the maintainer's step, and `main` had no ruleset or branch protection when it was written, so "Require merge queue" alone would merge with nothing to wait for. The ruleset on `main` needs: Require merge queue with the merge method Merge commit, and Require status checks to pass with `lint`, `test`, `docs`, `msrv`, `private-names`, `real-shepherd` and `file-size / file-size`. cubic and CodeRabbit never report on `merge_group`, so they stay out of the required checks.
- With a queue required, `gh pr merge` arms auto-merge instead when the pull request cannot be queued yet, and auto-merge queues whatever head the branch has later. Kelpie reads `autoMergeRequest` with the queue and waits on an armed one as it does on a queued one, unless the head moved or CI on it went red: then it runs `gh pr merge --disable-auto` and the work item goes back to CI.
- A work item with a pull request in the queue saves `merge_queued`, which a runner from before this change refuses to load. The state file is one-way while a pull request is queued: roll a runner back only once none is.

### The shep surface kelpie leans on

- `Request::Trigger` becomes an `action` message on a sheep's shepherd channel (fd 3), answered with an `action-reply`. `ready`, `metric` and `action-reply` are all republished on the bus as `channel.*`.
- `SendLine` (`shep whisper`) writes one line to a sheep's stdin.
- A lamb is a pid and an executable name, found by walking the process tree, never argv. The stop ladder kills the process group.
- A sheep with `shutdown_with_message` that exits on the message never reaches the stop ladder, so its lambs are orphaned. Seen 2026-09-26: `shep restart` left the worker running beside the resumed one. The runner now stops its `claude` children itself before it exits: SIGTERM, then SIGKILL after 3 seconds. Before that it asks the worker's thread to stop and waits up to 2 seconds for its step to end, so a step that finishes in time is saved before its calls are ended.
- Shep has two stop caps. `kill_timeout` (1.6s by default) covers `stop`, `restart`, `delete`, the daemon's own automatic restarts and the engine-wide shutdown. `graceful_timeout` (8s) covers only a reload's drain. Read from shep's source (`LadderCap` in the supervisor's reload module and the defaults in the app behavior config) on 2026-09-28, not measured. A runner's stop needs about 7s: 2s to join the worker, 3s of child grace, 2s to flush. So every runner's Flockfile entry needs `kill_timeout = "10s"` or more, and the playground's has it. A runner cannot check its own: no `SHEP_*` variable carries the value, so a warning at start would take a describe call to the shepherd, and none is built.
- A dog is an ordinary sheep with a marker. Wildcard selectors never touch a dog. A dog's `--schema` feeds lookout's settings pane.
- A sheep under the pinned shep 0.10.1 starts with only `HOME`, `LANG`, `PATH`, `USER` and its `SHEP_*` variables, read with `ps eww` on 2026-09-26. `TMPDIR` and `SHEP_HOME` are not among them, though the shepherd itself has both. ### `shep kelpie upgrade`

Built for shep-pm/shep-kelpie#143. Before it, an upgrade was a sequence of hand steps (build, copy, sign, relink, restart the runners between steps and, for a new shep minor, save, kill and muster the shepherd), and on 2026-09-29 one of them deleted the dog's sheep until it was restarted by hand.

- The maintainer's install-layout call (2026-10-01) is to do it the way shep upgrades itself, with no link and no re-adopt. The installed kelpie is whatever program the adopted dog runs, read from the shepherd (`~/.cargo/bin/shep-kelpie` for the README's install), and a runner started by `shep kelpie add` runs the same path. `shep kelpie upgrade --ref <git ref>`, `--release <version>` or `--binary <path>` writes the new build beside that file and renames it over, so the running file's bytes are never edited in place and the fresh inode needs no re-signing by the system. On macOS a Mach-O copy is still signed ad hoc (`codesign --force --sign -`) before the rename; a script (the tests' stand-in builds) is not.
- Before the swap the file it replaces is copied into `<kelpie home>/builds/shep-kelpie.previous`, resolved if the installed path is a symlink: the link stays a link, its target gets the new build, and the copy is a regular file of the old bytes. `--rollback` stages that copy beside the installed file and renames it over the same way, keeping the build it replaced as the previous, so a second rollback undoes the first. Running the same build again changes no file, so finishing an upgrade that stopped part way does not push the real previous build out.
- Measured 2026-10-01 on the maintainer's macOS: a cargo-built binary (`Signature=adhoc`, linker-signed) copied with a plain `cp` to a new path ran `version --json` with no `codesign` run on the copy. The signing step stays for a release build that is not linker-signed; this run did not measure one.
- Every sheep the upgrade restarts must run the dog's path, since a restart cannot move a sheep onto another binary. One that does not stops the upgrade before a file changes or a sheep restarts, naming the sheep and its path. A stopped sheep on another path does not block it, and is said to stay behind.
- A build says which shep it is made with through `shep-kelpie version --json` (`{ "kelpie": ..., "shep": ... }`, the second being `SHEP_VERSION`). The upgrade runs it on a staged copy of the new build, with a 20s limit that kills a build that hangs and a refusal of a non-zero exit, and compares its minor with the shepherd's, read through a connection that does not apply the running kelpie's own pin, since a kelpie on the old minor must be able to install a build for the new one after the shepherd moved. A difference stops the upgrade before a file changes or a sheep restarts, and the message says which side to move: a build for a newer shep than the shepherd's means upgrade shep and reload its shepherd, then run the new build's own `upgrade` (printed with the build's path, since the old installed kelpie refuses the new shepherd); an older one means install a kelpie built for the shepherd's line. The same check gates `--rollback`. A previous build from before `version --json` cannot answer it: the rollback goes ahead and says the minor is unchecked.
- `--binary` given a file without its executable bits is refused, naming the `chmod +x` that fixes it. Two upgrades at once are refused by a lock file, `<kelpie home>/upgrade.lock`, holding the pid of the upgrade that took it. A lock left by a process that is gone is taken over.
- Restarts go dog first, since every runner asks it for leases, then each runner in name order, one at a time. A sheep restarts only when its `status` shows no work item in `merge`, or in `done` with its pull request merged, and the dog only when no runner has one. A `status` that shep delivered and that timed out is not an answer of no merge: shep reports it as `TimedOut`, apart from a sheep that is not running, and the upgrade waits on it like a merge. It asks again every 500ms for up to an hour, saying what it waits on, then fails naming the runner and restarts nothing for it. A restarted sheep must answer `status` in 60s before the next goes down. A merge can still begin between a `status` and the restart that follows; the runner's own stop lets the step in flight finish first. A sheep that is stopped stays stopped and starts on the new build. The flock is read again after the build and right before each restart, because the wait can last an hour: a runner stopped meanwhile stays stopped (reproduced with a probe in review before the fix). A `Starting` sheep counts as running; an `Errored` or `WaitingRestart` one is left alone and named.
- A failure after the swap leaves the new build installed, and the error says so with the command that finishes the restarts, `upgrade --binary <installed path>`, which finds the bytes equal, moves no file and restarts. A `--rollback` run again would swap the builds back instead. The same line prints before the restarts, so a Ctrl-C leaves it on screen. `--rollback` goes ahead without a minor check only for a previous build that ran and exited 2 on `version`; one that cannot start, hangs or dies is refused.
- Not done: the runner's stop can still cut a merge that begins between the idle `status` and the restart (`JOIN_BOUND` is 2s), and the lock's stale take-over checks and then acts.
- `--ref` keeps a clone of the repo in `<kelpie home>/upgrade/source` (`KELPIE_SOURCE` names another repo than shep-pm/shep-kelpie), checks out the remote's branch, tag or commit detached, and runs `cargo build --release --locked` with its own `CARGO_TARGET_DIR`. Measured 2026-09-30: a nested cargo that inherits the maintainer's `CARGO_TARGET_DIR` puts the binary there, not in the clone's `target`, and the build reported success with no file where kelpie looked.
- `--release <version>` runs `gh release download v<version>` for the asset `shep-kelpie-<arch>-<os>.tar.gz` (`aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`) and unpacks `shep-kelpie` from it. This repo has no release workflow yet, so the asset name is a decision and not a measurement; the build inside must say it is that version or nothing is installed.

### The state file

- A finished work item's record in `history` is about 500 bytes in the pretty-printed state file, 572 with five-digit seconds in every phase and a 50-character title. The cap of 100 keeps the records under about 57 KB, and under about 80 KB with GitHub's longest title, 256 characters. They are written whole at every save and every beat.

### codebase-memory-mcp

DeusData/codebase-memory-mcp, MIT per its badge, written in C. Indexing is local CPU and costs no tokens ("average repo in milliseconds", the Linux kernel in 3 minutes), stored in SQLite under `~/.cache/codebase-memory-mcp/`, and a background watcher reindexes on git changes. It has 17 MCP tools, including `detect_changes` (git diff to affected symbols) and `trace_path`. Its installer writes to agent config files, so load it through `--mcp-config` instead. Claude Code lists its tools as deferred behind a tool search: in the implementation series no worker looked them up unprompted, in 12 runs out of 12.

## Test series

In order: transport, model calibration, work split, then code. Each series gets its own spec when it starts.

### Transport

- T1: `claude -p --resume`, one process per turn. The measured baseline.
- T2: a long-lived `claude --input-format stream-json --output-format stream-json` worker, held by a project runner.
- T3: `claude --bg` plus socket messages, attached with `claude attach`. Needs a permission rule for reading the target's peer token.
- T4: kelpie-served tools. In-process MCP over the stream-json control protocol, against a small stdio MCP binary that relays to kelpie over shep.
- T5: MCP channel push, if the account has channels.
- Lease round trip, runner to dog: a "wants" metric, then `status` and `grant` triggers, against a direct `shep trigger` to the dog if that reaches one. Latency, a dropped metric, and reclaim when a runner dies holding a lease.
- Rate limits: whether stream-json carries the utilization windows.

Measure each: cache write and read per turn, wake latency on an idle worker, a 100 KB output line through the runner, recovery after a crash, subscription auth, and whether the maintainer can take a worker over.

### Model calibration

Extend the maintainer's local model-calibration harness, which has only scored local models, to Opus, Sonnet, Haiku and Fable at two or three effort levels each. Reviewer and checker roles reuse its frozen sets: planted bugs, real false findings, and clean diffs for false alarms. A new implementer set of small shep specs with hidden tests scores tests passing, review findings, units and wall clock.

### Work split

Run the same real work items as inline, inline with compaction, a phased chain with handoffs, a crew of subagents working from an implementation doc, and agent teams (only if a long-lived transport wins, since teams do not spawn under `-p`). Run each with and without codebase-memory-mcp.

The model to fit: one session's cache reads grow with the square of its length. Splitting it into k pieces cuts reads about k times and adds a fixed cost per piece, so the best k is about √(0.025 × calls × growth ÷ per-piece cost). Worked example with guessed inputs (150 calls, a 41k floor, 500 output tokens a call): inline to 650k is about 6.9M units, three quarters of it cache reads; five phases, each with a 10k handoff and 30k of re-reading, is about 4.6M. The tests measure the real inputs.
