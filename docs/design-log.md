# Design log

Decisions from the design sessions starting 2026-09-24, and the facts behind them. The hard-to-reverse ones are also ADRs in `docs/adr/`. The vocabulary is in `CONTEXT.md`.

The sections below describe the code as it stands. What was built and later changed or removed is in History, one dated line each, and how a file saved by an older kelpie loads is in Old files. What was decided and never built is in Decided, not built.

## Why kelpie exists

Before kelpie, one long-running Claude session per project acted as a control room. It held the board, rationed reviews, relayed messages between the sessions that owned pull requests, and merged. Measured 2026-09-24 over shep's transcripts, in units weighted by cache pricing (cache read 0.1, one-hour cache write 2, output 5, uncached input 1):

- 2,352 transcripts, 6,020M units. The control room was 7% of that, and subagents were 54%.
- Transcripts that peaked above 500k context were 43% of all spend.
- The control room itself: 7,883 calls, median context 349k, 41 compactions, 80% of its cost in cache reads. 62% of its cost was calls that followed a Bash result (git 20%, gh 17%, the review driver 13%, the GPU queue 12%). Relaying messages was about 15%.

So kelpie moves the control room's rules (gates, locks, rate windows) into code, calls Claude only for the work and for judgement, and controls the other big cost: how large each agent's context grows.

## The shape

- Kelpie is a dog of the maintainer's own shepherd (ADR 0001, ADR 0003). The adopted `kelpie` is the lease dog (ADR 0004): its `--version` answer asks for the shepherd channel, which shep 0.12 records at `shep adopt` (shep-pm/shep#656), so shep starts it with `channel` and `shutdown_with_message`. It runs the dog only when shep starts it with no arguments and both `SHEP_DOG_NAME` and `SHEP_NAME` set; `shep kelpie <verb>` sets `SHEP_DOG_NAME` alone and runs the verb in the caller's folder. An adoption from before the ask has no channel, and the dog exits naming `shep adopt` again, then `shep disable kelpie` and `shep enable kelpie`. The dog names itself in shep's handshake (`connect_as` with `SHEP_DOG_NAME`), so shep never lists it `silent`, and `add`, `start` and `doctor` count it up only while it is online and has named itself.
- Each project is a sheep, kelpie's runner (`runner <project>`), and every agent call the runner starts is that sheep's lamb, labelled with its issue and role (ADR 0002, shep-pm/shep#624). One kelpie serves every project, because the GPU lock, the review bots' windows and the usage pacer are machine-wide or account-wide. Realistically two projects at once. shep comes first.
- `shep kelpie add`, in a checkout, reads the forge from `origin` and refuses a default branch other than `main`, which every branch is cut from. It makes the four labels the repo lacks (`ready-for-agent`, `ready-for-human`, `in-progress`, `review please`), writes kelpie's own agent files where they are missing, and registers the runner, stopped, holding its settings as its `[app.dogs.kelpie]` table: the defaults plus what the checkout and forge say (`repo`, `forge`, `ci` from whether `.github/workflows` exists, and `qwen` before `defect-hunter` where the maintainer's qwen script is installed). Lookout shows each key's description from kelpie's schema, which stands in for a comment per key, since shep keeps a table without comments. Everything is read before anything is written, so a refusal changes nothing, and each piece is made only when missing, so a second `add` changes nothing. A sheep of the same name that is not kelpie's is refused, and so is a checkout or repo another project's table already names, since two runners would take the same issues: that check reads each other sheep's raw `repo` and `forge`, so a table that no longer parses still counts. `add` says when the adopted kelpie is not enabled, not running or has no channel, and `start` refuses then, since its runner would never be granted a lease.
- A project runs while its runner's sheep runs, and only then (shep-pm/shep-kelpie#268): shep's own state is the run state, so `shep ls` and lookout show it, and `shep start <project>` runs a project as `shep kelpie start` does. A runner has no paused state and never comes up paused. Before, the state file kept a `run` of its own, so a runner shep showed online could sit paused, picking up nothing, with nothing in `shep ls` or lookout saying so.
- `start` and `pause` take a project's name, or find the one whose `repo` is this checkout, and act only on a sheep with a kelpie table that kelpie started as `runner <project>`, so a sheep of the maintainer's stopped on purpose is never started. `start` starts the runner when it is down and waits up to 30 seconds for it to answer `status`: a runner opens its channel before it takes its actions, and shep-channel answers `unknown action` in plain text meanwhile, so any reply that is not JSON means it is still starting. `status` asks every sheep with a kelpie table.
- `pause` lets the runner finish what it has running, then stops its sheep, so `shep ls` shows it stopped. It drains the runner as `upgrade` does before a restart, waits until no call runs, bounded the same way (the ceiling the runner gives plus 5 minutes), then waits out a merge in flight for up to an hour, as the upgrade's merge wait does, since a stop mid-merge can leave a merged pull request with its work item open. A drain does not hold back a merge, so a merge that starts after that wait's last `status`, from a yes on a merge ruling or a gate the pass reaches, can still be cut short by the stop; the window is two `status` reads (the merge wait's last, and the one that looks for attached sessions) and the stop request wide, and the work item resumes as after any stop. A runner that goes down while it is waited on is reported stopped, with no stop or `undrain` sent. A runner on a build from before the run state went still answers `status` with `run`; when that says `paused`, `start` sends it that build's own `start` too. A runner still starting is waited on until it answers `status`, for up to 60 seconds, since it takes no `drain` yet. It says what it waits on as it waits. Then shep stops the sheep. A wait that runs out, a Ctrl-C or SIGTERM during the waits, or a refused stop sends the runner `undrain` and leaves it running; once the stop is asked for, a Ctrl-C no longer undoes it. A session the maintainer attached (`shep kelpie attach`) is their own process, started in their terminal, so the stop does not end it: `pause` names each attached work item, which stays held until its session ends, as across any restart. Pausing a runner that is not running changes nothing and says how to start it.
- `shep kelpie rule` answers a stopped runner's ruling too. The ruling and its answer are read from the state file as before; a runner that is down gets the answer as a file, `<kelpie home>/<project>/answers/<id>`, holding `rule`'s params, written atomically and named by the id's number (`007` is `7`, and `0` is no id), the last answer to a ruling standing. A file that cannot be read, or whose answer cannot be saved, stays for the next pass; a write's temporary file a minute old is removed, and anything else in the folder is logged once. Each pass reads that folder first, so the runner acts on the answer at its start: it answers each as the `rule` trigger would, oldest id first, removes the file, and logs what came of it, a refusal included (a ruling answered meanwhile from ntfy, say). A running runner still gets the trigger, so its refusal reaches the terminal.
- The runner's loop never waits on an agent call (shep-pm/shep-kelpie#318, ADR 0005). It starts each call, a worker's turn, a reviewer's session or local round, or the project manager's wake, on a thread of its own and goes on, and the call's end comes back on a channel that wakes the loop, whose next pass records it. A work item has at most one call in flight, and the open work items' calls run at once, beside the project manager's one. Pacing, leases and the fence are checked at each call's start. Triggers, `status` and a settings reread answer while calls run. git and gh calls stay short children of the pass that makes them, and a usage read stays one too. Each work item's calls write their harness files under names of their own in the worker folder (`settings-<issue>.json`, `instructions-<issue>.md`, `review-settings-<issue>.json`, with each harness's files beside them), so two items' calls never share one. The runner's git on the project's repo waits up to 2s for a ref lock and 5s for `packed-refs` (`core.filesRefLockTimeout`, `core.packedRefsTimeout`), since several items' calls and passes use its refs at once.
- The stop is shep's (shep-pm/shep-kelpie#319, ADR 0005). Kelpie needs a shepherd from shep 0.12.4, the first whose stop sweeps a sheep's whole lamb tree (shep-pm/shep#688), and refuses an earlier patch of the 0.12 line as it refuses another minor, naming the version it needs; `upgrade` refuses to install a build onto a shepherd that build would refuse. A stop reaches the runner as a message: it asks the loop's thread to stop and waits up to 1 second for its pass, then refuses new calls, sends each call's process group SIGTERM without waiting, saves the work items' time, flushes for up to half a second and exits. shep then ends every lamb the runner left, whatever group or session it is in: SIGTERM, then SIGKILL after the entry's `kill_timeout`. The group SIGTERM is for what shep's sweep cannot find: a member of a call's group already reparented to init. The runner fits inside shep's default `kill_timeout` (1.6 seconds), so `add` writes none, and an entry that still sets one works as before. A pre-release of 0.12.4 is refused too, since it may predate the sweep; one of a later patch is taken. A restart resumes each work item from its session. Kelpie keeps a process group per call to end that one call at a turn's ceiling.
- Kelpie's home is `$SHEP_HOME/kelpie`, since kelpie is a plugin of shep (shep-pm/shep-kelpie#253, decided by the maintainer on 2026-10-01). `KELPIE_HOME` overrides it, and with neither set it is under shep's own default, `~/.shep`. Kelpie's shared entries sit at the top (`agents`, `builds`, `codex`, `dog`, `rulings`, `tools`, `totp`, `upgrade` and `upgrade.lock`), and each project has a folder named for it holding `state.json`, `board.md`, its worker files, `worktrees`, `builds`, `issues` and `pm`. So a project may not be named for one of kelpie's own entries. The dog's book and door are always under `$SHEP_HOME/kelpie/dog`, since shep hands the adopted dog `SHEP_HOME` and not `KELPIE_HOME`. A runner refuses to start when its door or the longest socket a call opens (a 128-bit name in its worker folder) is over 103 bytes, naming the path, since macOS caps a socket's path at 104.
- A home that never moved from `~/.kelpie` must not start empty beside its old state (shep-pm/shep-kelpie#311). A runner refuses to start while `~/.kelpie` holds its project's old folders (`projects`, `wt`, `targets`, `shots` or `playwright`, each `/<project>`), or kelpie's shared files with no `.moved-to`, and the dog refuses while `~/.kelpie/dog/book.json` is there. Each names the old home and the file or folder it holds, and says what to do with it by folder. `projects/<project>`, the project's state, is moved to `<kelpie home>/<project>/` (the home is `$SHEP_HOME/kelpie`). `wt/<project>` and `targets/<project>` are deleted once the project has no open work item, since kelpie makes its worktrees and builds again; `shots/<project>` and `playwright/<project>` are deleted, since kelpie no longer uses them. They are not moved, because a work item's state keeps the absolute path of its worktree and build folder, and the runner reads the new `worktrees` and `builds` folders only for work items it opens after the move. The shared files (`totp` and the rest) and the dog's book are moved or deleted. A project with an open work item whose worktree is still under `wt` has no supported way through: the guard refuses the runner while `wt/<project>` exists, and no release moves the paths in its state, so the message says so and does not invent a procedure. No release moves it any more (#322). `doctor` reports a project's leftover as missing, per project, and `add` warns when it registers a runner whose name has one. A runner that refuses this way exits with 78 (`EX_CONFIG`), and its flock entry lists 78 in `stop_exit_codes`, so shep leaves it stopped instead of restarting it into the same refusal (shep-pm/shep-kelpie#345, Facts). A runner registered before that keeps its entry, and so still restarts under shep's backoff until `shep kelpie add` is run again in its checkout, which adds 78 to the entry's `stop_exit_codes` and keeps the codes it has. A runner with `KELPIE_HOME` set is never refused, since its home never came from `~/.kelpie`, and neither is anything beside a `~/.kelpie` holding `flock.json`, `shep.toml` or `run/`, which is a shepherd's home.
- Rust for all business code. A Tauri GUI comes after the MVP. Until then kelpie is run and watched from a Claude session. MVP: a thin vertical slice, one project, one worker at a time, merge on `ask`, no GUI; shep-pm/shep-kelpie#5 is its spec.
- Kelpie and its runners talk through shep: triggers down, `channel.metric` up on the bus. Runners report running totals, because metrics drop under backpressure. A private socket only if the round trips do not hold up.
- The dog's book holds the leases a review bot's window and `cargo-test` need, and only runners and the maintainer ask for a window. A runner asks for a book lease by raising running totals, `lease.<kind>.want.<epoch>` and `lease.<kind>.return.<epoch>`, and the dog grants with `grant <kind> <epoch>`. The epoch is the runner's pid, which shep's process events also carry, so the dog reclaims an old run's leases on `restart` without racing the new run's first metric. A bot's window is `reviews` in `hours` from its agent file, which the dog reads when it starts, and a footer's quota or a refusal's quoted opening overrides the book's count until a later summon is accepted.
- The dog saves its book to `<kelpie home>/dog/book.json` after every change, with the same atomic write as a runner's state file, and loads it on start (decided on #19). The file keeps holders and queues with their epochs, each window's quota, summons and quoted refusal, and each runner run's totals, so a restart grants no second summon inside a window. On start the dog checks every runner in the book against the live flock: a holder whose sheep now has a different pid, or none, is reclaimed. A missing file, or one another build wrote, loads as an empty book. One that claims this format and cannot be read also starts empty, but with CodeRabbit's window closed for an hour, as if a summon had just been accepted.
- `cargo-test` is the one lease a worker takes (shep-pm/shep-kelpie#218): a counted lease on the dog, three holders at once by default (`[kelpie.leases] cargo-test`), so test runs across workers queue. A command asks for it at the dog's door, its own socket at `$SHEP_HOME/kelpie/dog/lease.sock`, and holds it while the connection stays open, so nothing has to poll a pid. The command run under it inherits the connection, so its whole process tree holds the lease however the asking process ends, and the asking process shuts the connection when the command ends, which ends it for every copy. If the asking process is killed outright, a process the command left running, such as a build server, holds the lease until it exits; `status` shows each holder's `since`, and nothing yet bounds a hold. It goes through a socket of the dog's, not shep's trigger: a worker's sandbox may connect to that socket alone, and shep's home stays unreadable to it, since its socket would let a worker trigger anything. The runner passes the same path to the sandbox's allowlist and to the worker as `KELPIE_LEASE_SOCKET`. The same `shep kelpie lease run cargo-test -- <command>` works from any shell on the machine, and exits 75 when it cannot have the lease and 127 when the command cannot start. Holders are never saved, as a dog restart closes every connection: a run that loses its dog mid-run knocks every second with `running`, and the next dog seats it at once, over capacity if need be. For three seconds after its door opens the dog grants nothing new, so those runs are counted before anyone fresh. A run still waiting when its dog goes away asks again, fresh, every second for a minute before it exits 75. A restart longer than a minute can still let more than the capacity run. Workers build outside the lease (`cargo test --no-run`) and run the suite inside it, naming the kelpie binary by its path, since the guard refuses a command whose program comes from a variable.
- The GPU lease is the lock the maintainer's qwen scripts already take, and the dog stays out of it (decided 2026-09-26 on #5, option A). A qwen round takes the lock itself, and so do `kelpie lease run|take gpu`, in the same format, for the maintainer's own by-hand use. A runner never takes or holds that lock around a command that takes it itself; a reviewer or a local agent whose file names a `lease` has kelpie take that lock around each round or call.
- A project's settings are its runner sheep's `[app.dogs.kelpie]` table, and kelpie's own are its `[kelpie]` section of `dogs.toml` (shep-pm/shep-kelpie#114, on shep 0.11). Lookout edits both from kelpie's `--schema` answer once kelpie is adopted, and draws the webhook's URL `<set>`. Every project setting is required except those added after the first build, so a missing or malformed one stops the runner with a message naming it as a dotted key, `worker.turn_timeout = 0`. Nothing else is read (shep-pm/shep-kelpie#332): with no table the runner stops, saying so, and with no section kelpie's own settings are empty.
- A runner reads its own table through the shep client, with `DogSheepSettings` and `DogConfig` on the name `kelpie`, not from the dog (decided on #114). shep answers both to any client, a runner is a sheep with no `DogRuntime`, and reading it itself keeps a runner's start independent of the dog being up. It finds its table by `SHEP_NAME`, else the project's name. A table goes through the settings' own parser, rendered as TOML.
- A settings change takes effect live, at the runner's next wake (within a minute when idle) and then at the next step or call that reads it. `repo` and `forge` wait for the next start, since a work item's worktree and pull request belong to them. A work item in flight keeps the agent it opened on. A change is checked as a start checks it, and one that fails keeps the settings in effect and is offered again at each wake, so it lands once what refused it is fixed. Reading on each wake was chosen over subscribing to `config.sheep.kelpie`: no second connection to carry across a shepherd's reload, and a minute is soon enough. The agent files are looked at on each wake too.

## Work

- GitHub Issues stay the tracker for the work kelpie does, with the `ready-for-agent` family of triage labels. The board of work items lives inside kelpie.
- An issue writer forms work items (ADR 0006, shep-pm/shep-kelpie#324): an agent that runs before kelpie sees an issue, researches the request, scopes it to one pull request's worth or splits it into sub-issues, and labels the implementer that should build it, as `agent:<name>`. Kelpie adds the results to the board and dispatches. There is no planning call: no plan-then-implement arm beat one agent with no plan, and a shared plan spread its bugs into every build made from it (Facts).
  - It is an agent file with `role: issue-writer`, which takes `harness`, `model` and `effort` and no other key, runs on `claude-code` alone (`--interactive` starts `claude`, and its guard is a Claude Code hook), and must have a body, its prompt. Kelpie ships `issue-writer`, Opus 5.5 at medium, the measured planner default. Its body is the maintainer's rule: split only where each piece works, tests and ships on its own, never cut a piece short to keep it small, most requests stay whole; acceptance criteria in every issue; one `agent:` label per issue, the default implementer for features and anything with state or concurrency, a smaller one for mechanical work, the strongest only where a bad first build is hard to undo. It says nothing of what a model costs. Kelpie adds the project's implementers, the default first, the commands its guard runs, and how the run ends.
  - `shep kelpie issue "<request>"` runs it on its own from the maintainer's command line, not from the runner: the command waits on its answer, so the session is not a lamb and is not paced. It is one fresh session in a detached worktree at `origin/main`, just fetched, under the project's `issues` folder, in the sandbox with nothing to write and only GitHub to reach, Read, Grep and Glob, and Bash held by its guard. It files `ready-for-human` and ends with `{"filed": [...], "note": "..."}`. Kelpie reads each filed issue back and prints it, and names one without acceptance criteria, its status label or exactly one listed `agent:` label (read as the board reads it), exiting non-zero. A session that fails, or a reply that is not that list, keeps its worktree and prints `cd <worktree> && claude --resume <id>`; otherwise the worktree is removed.
  - `--interactive` starts `claude` in the foreground in the project's checkout, inheriting the terminal, with the prompt appended by `--append-system-prompt`, the request as the first message, and a settings file of the same deny rules and guard but no `allow` rule, so Claude Code asks the maintainer before each command the guard lets through: an outsider's issue the session reads could otherwise talk it into a command the maintainer never sees. It files `ready-for-agent`. It is not a lamb and not in kelpie's sandbox, and kelpie does nothing once it starts.
  - Its guard is `kelpie guard` with `--issues=<status label>`, an `--agent=<name>` per listed implementer and `--ledger=<file>`, and it runs only what it lists, the reverse of a worker's: `gh issue create`, `gh issue view <n>` and `gh issue list` read against an allow-list of their flags (no `-R`, `--repo`, `--web` or URL, in any spelling or short-flag cluster), and, for the issues the session filed, `gh issue edit` with `--add-label` or `--remove-label` and `gh api` POSTs on `repos/{owner}/{repo}/issues/<n>/sub_issues` and `/dependencies/blocked_by`, plus GETs on `repos/{owner}/{repo}/issues/<n>` for an issue's database id. Each is plain words with no `$`, backticks, pipes, redirects or `cd`, and a heredoc only behind a quoted delimiter, since the shell expands a bare one's body. gh fills `{owner}/{repo}` from the checkout, so it works on the project's repo alone. A filed issue must carry the status label and no other kelpie status, exactly one `agent:` label naming a listed implementer, an acceptance criteria heading with a list item under it, and no path on this machine. `gh issue view` and `list` let it find an open issue that already covers a request.
  - It runs no git. A security review of the first build found git's options too wide for a deny-list to hold: `git grep --open-files-in-pa=<program>` (git takes any unambiguous abbreviation) ran a program, and `--no-index`, `blame --contents`, `-C <dir>` and `ls-files --exclude-from` read any file. The session reads the repo with Read, Grep and Glob, and the headless worktree is already at `origin/main`.
  - The ledger is a PostToolUse hook, the same guard with `--record`, which after each command keeps the number from a line that is one lone `gh issue create` (with at most the `cat` its `--body "$(cat <<'EOF' ...)"` reads) and printed one issue URL and nothing else, and the id a lone `gh api 'repos/{owner}/{repo}/issues/<n>' --jq .id` printed. The guard refuses a `cat` of its own, one for each such body at most, since it could print a forged URL for the ledger to take. The guard allows an edit, or a link's issue, only on a number the session filed, a `sub_issue_id` only of an issue it filed, and an `issue_id` (a blocker) only of an issue of this repo whose id it read. A missing or unreadable ledger holds nothing, so an edit or a link fails closed. On its own it lives in the call's scratch folder, which Claude Code empties as the call starts and the sandbox lets it write; interactively it is a file of the run's own under `issues`, removed when `claude` ends. That the PostToolUse input carries the command's output as `tool_response.stdout` has not been checked against a live session; if it does not, edits and links are refused, not allowed.
  - Its file tools read only its checkout (and, on its own, its scratch folder): every other entry from `/` down is a Read deny rule, worked out entry by entry around the checkout as the worker's are, plus `~/.config/gh`, `~/.claude.json`, `~/.claude` and the shell's history by name. On its own the sandbox also denies the history and the usual credentials. gh's config and Claude Code's files stay readable to the sandbox, since gh and the harness read them themselves; the session's commands cannot read a file, so the Read rules are its whole reach.
  - Each listed implementer's `agent:` label, and the status label, is made on the repo before the session when the repo lacks it, since the forge refuses a label the repo lacks.
- Priority orders the board (shep-pm/shep-kelpie#144). Ready issues labelled `priority: P0` go first, then `P1`, `P2`, `P3`, then those with no priority label, the labels shep uses. Within a priority the oldest issue goes first, and an issue with several priority labels ranks by the highest. Adoptions and reworks go before any issue. A blocked, assigned or otherwise passed-over issue does not hold up the next one, whatever its priority. A blocker's state is its issue's, never its pull request's.
- An issue's `agent:<name>` label picks its implementer from the project's list, the prefix read in any case. A label naming no listed implementer, or two `agent:` labels, is a label error, which the board skips and `add <issue>` refuses. A `worker:` label is no longer read: an issue still carrying one runs on the default implementer, and the runner's log says so as its work item opens.
- The board never works an issue with sub-issues, since they are worked in its place, and closes one whose sub-issues are all closed, whoever made them. A close the forge refuses three times in a row is passed over until the runner restarts, so one refusal that never clears does not hold every poll; each refusal is a line in the runner's log.
- An issue a work item holds carries `in-progress` (shep-pm/shep-kelpie#199), so a reader of GitHub sees a worker has it while it still carries `ready-for-agent`. It goes on as the work item opens, by the board, `add`, a rework or an adoption, and comes off as it ends, merged, handed back or dropped. A runner that starts puts it on each issue it holds, and takes it off each finished issue whose removal a refusal once missed. The label is a courtesy: a forge that refuses it leaves a line in the runner's log and the work item runs on.
- Several work items per project (shep-pm/shep-kelpie#103). A pull request waiting on a review bot's window, CI or a merge ruling held the whole project: overnight on shep that was about one pull request an hour with the GPU idle between rounds, and the playground sat all night on one merge ruling. A project's `max_items` (1 when absent) sets how many work items are open at once, each with its own branch, worktree, build folder, phase and rulings. The board opens one whenever a slot is free, and never an issue or pull request whose work item is open. An item waiting on a lease, CI, a bot or a ruling yields to the next, and an item parked on a ruling keeps its slot, so raising `max_items` is how work moves past it. Items merge independently, and one merging sends the others through the catch-up with `main` at their gate. A ruling names its work item, and its answer moves the item parked on it. `gate` and `drop` take the item's issue when more than one is open. `status` lists every open item under `work_items`, keeping `work_item` as the oldest. What `max_items` does not change: every gate per item, one call in flight per item, and one summon per grant of a bot's window: the runner records which item took a grant, and another item waits for a grant of its own rather than inheriting it, which would summon twice in a window the dog counted once.
- Kelpie records each issue whose work item it finished, merged or dropped, and the board never takes one again: GitHub closes an issue from `Resolves` a moment after the merge, and the playground's board re-picked #22 in that moment. An entry goes once its issue reads closed (shep-pm/shep-kelpie#172): each dispatch step asks the forge for every finished issue the board does not list as ready, and one it cannot answer for stays. `shep kelpie drop [<issue>]` ends a work item without merging, paused or not, keeping its pull request and branch on the forge.
- Kelpie works on its own repo (shep-pm/shep-kelpie#140), as a project on the maintainer's shepherd added with `shep kelpie add` in a clone of its own, never the checkout sessions work in, and worked by the board like shep with `max_items` above one. Its model per issue is an `agent:<name>` label, its order the priority labels, and an issue kept for the maintainer is one without `ready-for-agent`. The rules that hold for any worker on this repo are in `CLAUDE.md`, which every worker reads, and those that name this machine's paths go in the project's `worker.instructions_file`. A merged change reaches the runner only when the maintainer upgrades it.
- The board briefing (shep-pm/shep-kelpie#326). The runner writes `<kelpie home>/<project>/board.md` for the project manager's agent, so that agent never runs git or gh: measured, a PM briefed from a code-written board decided as well as one that looked for itself (Facts) at about half the units a wake. It is written atomically at start and at the end of any pass whose saves changed the board, and refreshed once a minute. Every save diffs the state before and after it into board events (a turn starting, ending or failing, a review call starting or ending, a pull request found, a phase change, a work item opened or closed, a ruling raised or answered), and the ready queue's reads and a worker going idle or active add their own. The state file keeps the newest 50 events with ids that only grow, and `pm_seen`, the PM's cursor: the board shows the events after it, or the last 20 while there is none. The board quotes each ready issue's first 600 characters, as the measured boards did, every line behind `> ` so no heading, rule or fence in a body reads as the board's own, and titles and failures go on one line with no backticks. A failure, a skip's error, a ruling's question or a worker's closing message that names this machine or one of the project's `private_names` is withheld from the board, by the same check the forge's posts get. A worker's activity is when its transcript was last written (a Codex call's output file, a pi session's file), which the runner reads with a `stat` on each pass, never a model. A worker silent for 10 minutes reads as idle and records an event, counted from the turn's start while its transcript is not written yet or is older than the turn: the measured PM missed a worker hung on a prompt in 7 of 8 tries, because the board said only "busy". Overlap comes from git: each branch's files are `git diff origin/main...<head>` of its local branch, which has the worker's commits before any push, each pair of branches gets `git merge-tree`, and each ready issue's paths are the backticked spans in its body that name files on `main` (by whole path or last parts, at most 3 matches) or a new path with a folder. Each answer is kept by the commits it read, so a write runs only what moved, and git runs with the runner's lock let go, so a trigger never waits on git for the board. `merge-tree --write-tree` needs git 2.38 or later; with an older git, or a commit git cannot find, the pair reads "conflict check unavailable" and is asked again on the next write.
- The project manager's agent (shep-pm/shep-kelpie#327). A project opts in with `agents.pm`, naming an agent file whose role is `pm`; kelpie ships `pm`, Opus 5.5 at medium, which `add` writes. Absent, the board's rule picks and every ruling waits on the maintainer. Code wakes it, never a timer, on four things: a free slot with two or more ready issues the board could take, a pair of open branches newly in conflict per `git merge-tree`, a stuck work item (parked on a ruling for a failed turn, a turn that stopped twice with no pull request, a turn past its ceiling, or CI still red with no fix pushed, or with a call the board reads as idle), and the maintainer's `shep kelpie tell "<note>"`. The reasons gathered since its last wake go in one call, through `flight` as a lamb labelled `pm`, at most one in flight per project, on a pass that started nothing else and after the board is written, so the loop never waits on it; a dispatch that wants its pick waits for it while other items go on.
  - Its folder, `<kelpie home>/<project>/pm`, holds a copy of `board.md` taken as it wakes, so the board holds still while it reads, and its `pm-notes.md`. Of kelpie's and the shepherd's homes its fence reads that folder alone, and it never reads the checkout, `~/.config/gh` (`gh`'s token) or the credential paths no worker reads; the rest of the machine stays readable, as for a reviewer, since Claude Code reads its own files wherever they are installed. It reaches only the model's host. Its tools are an allow-list, `--tools Read,Glob,Grep,Edit,Write` with `--strict-mcp-config`, and its settings deny Bash, sub-agents, skills, messages, the web, `MultiEdit` and `NotebookEdit` besides; they allow `Edit` and `Write` on its notes alone, and a PreToolUse hook, `kelpie confine --append <notes>`, refuses any write that does not leave the notes starting with all they held, adds more than 64 KiB, or goes through a symlink. Two writes racing could each pass the check, which reads the file before the write lands; one call runs at a time, so none do.
  - The prompt names each reason and quotes each `tell` in full; the first wake of a session, and the first after a compaction, spells out the answer: `pick`, `hold` (every ready issue to keep waiting until an open work item closes, each answer replacing the last), `unstick` (`item`, `retry` / `re-scope` / `ask` / `none`, `why`), `reply` and `why`. Kelpie reads the last top-level object with an answer's key, field by field, skipping past each whole JSON value so braces inside a string never count, and checks it against the board before acting: a pick or hold must name a ready issue the board shows, an unstick a work item stuck now. Anything else, an unknown field included, is dropped and logged in the `pm-answered` report with why. A `retry` answers the item's ruling yes, or for CI still red no with a note sending the worker back, and on an idle worker ends its call, whose ceiling ruling it then answers yes. `re-scope` and `ask` add its words to the item's ruling, on one line behind `PM says:` and cut at 300 characters, and the ruling posts again; no ruling kind is added. A reply loses its control characters and is cut at 2,000. A pick that it also holds is dropped. A pick of none starts nothing until its next wake, or, with no work item open, for 30 minutes, after which the board rule picks. A hold lasts until a work item closes, and with no work item open a hold over every issue the board could start goes at once, so neither can stall a project with nothing in flight. A pick goes stale when a work item opens or closes. A stuck item or a conflict given up while it was unavailable is woken for again once it is back, if the item is still stuck or the branches still conflict, and each reason is queued once.
  - One session per project is resumed on each wake and kept in the state file, with the notes told since its last answered wake and the terminal holding it. A wake whose context, the last model request's input, passes 100k is followed by `/compact` on the session before the next wake. A session that cannot be resumed starts fresh from the board at once, and two failed wakes in a row start the next one fresh. Each answered wake advances `pm_seen` to the last event before it woke. A failed call or an unreadable answer passes it over for 10 minutes, and a call is ended past 10 minutes. While it is not set up, down, over Claude's 5-hour pace, held in the maintainer's terminal, or its pick is dropped, the board rule picks and a stuck item keeps its ruling; a `tell` waits for the next wake.
  - `shep kelpie pm` hands its session to the maintainer's terminal the way `attach` hands a worker's, on the same holder: the runner holds the project manager for the command's process and then the session's, each known by its pid and its `ps` start time, so a reused pid is not taken for it and a `ps` that cannot answer keeps the hold; one process holds it at a time, a wake in flight is waited out, and the hold goes at `detach` or at the first look after both have ended. The session runs in its folder, on its settings and inside its sandbox, through `terminal::run`, not as a lamb: an interrupt is the session's and a SIGTERM or SIGHUP is passed on to it. With no session yet, `pm` starts the one later wakes resume.

## Workers

- A worker owns one work item and outlives its sessions. It builds inline, with no plan to follow and no crew: its instructions say to implement the issue itself, and every skill call's headless rules forbid sub-agents and the Agent and Task tools. A reset, by compact or by clear with a handoff, would keep the same worker; no step drives one yet.
- Agents never see budget numbers. Budget talk makes models stop after every task. Budgets live in kelpie's code.
- Model defaults, kept in kelpie's own agent files (shep-pm/shep-kelpie#313): implementers on Sonnet 5.5 at high effort, `sonnet-high`, the default a new project lists, and `opus-high`, Opus 5.5 at high, for work that is hard to undo. Measured, Sonnet 5.5 at high built as well as Opus 5.5 for less, `xhigh` was no better for more, and every plan or spec workflow was no better for more (Facts). An `agent:<name>` label runs that item on another implementer the project lists.
- Workers start with `--setting-sources project` plus a settings file kelpie writes for each one. They get the project's CLAUDE.md and project skills, and none of the maintainer's hooks, plugins or skills. `local` was dropped on shep-pm/shep-kelpie#98: it adds only the worktree's `.claude/settings.local.json`, a file no repo commits and nothing kelpie runs needs, and it was the door the #55 review walked through. Kelpie's own guard goes into every worker's file (shep-pm/shep-kelpie#108), and the guard hooks the project settings name follow it. `worker.guard_hooks` is optional and the example leaves it empty, since its old entry was a file on the maintainer's machine and a beta tester's copy would fail every Bash call. A hook command that does not resolve (its program on `PATH` or at its path, and every absolute or `~/` path in it) stops the runner at start, naming it.
- Permissions: `bypassPermissions` with three layers under it. The project's `main` ruleset (shep's already blocks direct pushes, force-pushes and deletion, and requires a PR and passing checks). Kelpie's OS sandbox around the whole call, confining writes to the worktree and build folder and hosts to GitHub, the model's API and `worker.allowed_domains`, with kelpie's `confine` hook holding the file tools to the same folders. A short denylist of what only kelpie's code does, which `kelpie guard` enforces in any shape it reads: `gh pr merge`, `gh pr ready`, adding the `review please` label, `gh api`, `gh auth`, a push to `main`, reading credential paths. Kelpie flags any label or ready change it did not make and parks that worker. No auto mode: classifier outages have blocked work before.
- Agents' own files in a worktree (any `.claude` folder, `.mcp.json` at the root, Codex's `.codex` and `.agents` folders) are the maintainer's (shep-pm/shep-kelpie#98). Every call in the worktree loads them, and a hook there runs outside the sandbox. The #55 review wrote a SessionStart hook into `.claude/settings.local.json` with the Write tool, and the next `claude -p` ran it unsandboxed. Four fences: the sandbox denies writes to them, `kelpie confine` refuses the file tools there (as written and as resolved, in any case), each call first checks them against a trusted commit, and a pull request that changes them parks on an `agent-files` ruling. The check before a call passes when every one of those files matches `origin/main`, the commit the branch left `main` at, or a head the maintainer accepted; a difference fails the turn, and the ruling carries the files. Kelpie asks before a worker turn on a branch with a pull request (a rework starts on one), before the review's steps, and before CI, naming the files the branch changes from `main`. A yes accepts them at that head, so later heads that leave them alone pass, and a no stops the work item: the worker cannot write those files, so a note would not help it.
- A worker turn has a ceiling, `turn_timeout` in project settings, 60 minutes by default: decided 2026-09-27 on #16, over having no ceiling. The implementation series' 152 turns ran a median of 70s and at most 18 minutes, so a turn still going at 60 minutes is more likely stuck than busy. The ceiling is a deadline the runner's loop checks on each pass, waking for it, and counts from the turn's start, so a restart buys no fresh hour. A local agent's turn queued for its lease gets what it had of the ceiling again from the grant, so two items on one GPU do not time out the second while it waits, and one still queued when its ceiling passes leaves the queue without starting. Kelpie ends a turn past it through the call's own process group with the stop ladder, keeps its session, and parks it on a `stuck` ruling for `turn-timeout`; a yes resumes the same session for another turn, a no stops the work item.
- A worker fills the repo's pull request template, and a project can add worker instructions (shep-pm/shep-kelpie#87). Seen on kelpie's first shep pull request, shep-pm/shep#639: the worker wrote its own body with `gh pr create --body`, which skips the template, and the body carried an em dash the maintainer never uses. When the worker's worktree has a template in any place GitHub reads one (`pull_request_template.md` in the root, `.github/` or `docs/`, in any case, or a `PULL_REQUEST_TEMPLATE` folder), each turn's instructions gain a line telling it to fill that template, still ending with `Resolves #<issue>`. A repo without one gets the `pr` step's skill instead. A project's optional `worker.instructions_file` is read once when the runner starts and appended to the instructions for rules the repo's docs don't carry; a missing file stops the runner naming it. An implementer's agent file body goes after the skills' lines and before that file.
- What a worker finds outside its work item it leaves, and names in its final message. A reviewer's finding it leaves as out of scope goes into its deferred findings file, which the merge files as follow-ups.
- Every step kelpie drives an agent through runs a skill, mattpocock/skills by default, each overridable (shep-pm/shep-kelpie#147). The maintainer wants kelpie to follow that process, with kelpie's own prompts as the fallback rather than the process. Kelpie vendors the skills its steps use in `skills/`, pinned to one upstream commit with its MIT licence and the pin's `git ls-tree` in `blobs.txt`, which a test checks the copies against. The binary carries them and each runner writes them out as a plugin, `mattpocock`, under the project's `skills` folder in kelpie's home, passed with `--plugin-dir`, so a project installs nothing and an override is just another folder. A step's prompt starts with the skill's slash command and carries kelpie's own prompt as its arguments: `implement` on the worker's first turn on an issue, `diagnosing-bugs` on a red CI turn. `tdd` and `pr` happen inside a turn, so the worker's instructions name them, and a repo's pull request template still wins over `pr`. `triage`, `to-spec`, `handoff` and `retro` (#104) are vendored and overridable but no step drives them yet; `code-review` and `to-tickets` are vendored with no step at all. A project's `[skills]` table points a step at a skill folder (copied into a plugin of its own, `kelpie-<step>`), a skill in a plugin folder, or `none`. A skill that cannot load runs kelpie's own prompt, and the runner logs why and `status` shows it, since Claude Code itself passes an unknown slash command through as text (Facts). Rework first turns and fix turns run no skill. An adoption's first turn runs none of its own, but when the gate hands it a red CI run, that run's `diagnosing-bugs` command leads the prompt, since a command only runs from the very start. The vendored files stay byte-identical to upstream, and kelpie wraps every skill call in headless rules that win over the skill, decided by the maintainer on the #170 review: there is no one to ask or wait for, so the agent decides and records the decision (the worker in its pull request's body, keeping `<kelpie-question>` for what only the maintainer can decide); no sub-agents or Task; the reply format is kelpie's wherever a skill names another; and the worker runs no `/code-review` of its own, since kelpie's reviewers review the pull request. A project's own skill folder or plugin inside its `skills` folder stops the runner, since kelpie rewrites that folder, and a project plugin named `mattpocock` or `kelpie-<step>` does not load. For #104: `to-spec`, `to-tickets`, `triage` and `handoff` publish to the issue tracker or write outside the worktree, which the worker's GitHub denies and the confine hook refuse, so those steps need their own settings rather than the worker's.
- A turn that fails, because its worktree cannot be prepared or its call errors, parks on a `stuck` ruling for `turn-failed` carrying the reason (shep-pm/shep-kelpie#57): found on the playground's first live rework, where a leftover local branch failed the turn and left the work item idle with no ruling. A yes retries the step that failed and a no stops the work item. A rework reuses a local branch left behind when it matches its branch on `origin` exactly; a fresh work item's branch is still cut new from `origin/main`, and a local branch holding a commit `origin` lacks stays a refusal.
- A first turn that ends with no pull request and no question stopped short, often on a tool that failed, and is never left idle (shep-pm/shep-kelpie#140). Kelpie asks the forge again for the branch's pull request, since the turn's end may have missed one, and goes to the review if one is open. With none, it resumes the worker's session once with a prompt saying the turn ended with no pull request, to try again or another way, and to ask with a `<kelpie-question>` block if only the maintainer can unblock it. The next turn that stops short parks the work item on the `turn-failed` ruling: a yes sends the worker back the same way, and a no stops the work item. A forge that cannot be asked is tried again at the next step. A turn, a rework's or an adoption's included, that ends with uncommitted files and no new push is resumed once in the same session to commit and push in the foreground (shep-pm/shep-kelpie#275, Facts).
- Worker questions (shep-pm/shep-kelpie#13). A worker ends its final message with its question between `<kelpie-question>` and `</kelpie-question>`, and only a block that ends the message counts. Kelpie parks the worker on a `question` ruling that carries the question verbatim, and the maintainer's answer is the worker's next turn. A question takes only an answer, and every other ruling a yes or a no. A question asked before the pull request exists has no comment, and goes with its work item on a drop. A question may end with two to four `- ` lines of likely answers, which stay inside it verbatim.
- The maintainer takes over a worker with `shep kelpie attach <issue>` (shep-pm/shep-kelpie#325). The runner holds the work item for the attaching process, saved on the work item as `attached` with its pid and start time (`ps -o lstart=` in the C locale and UTC), so a pid given to a later process holds nothing, and a `ps` that cannot say keeps the hold for the next pass to ask again. No call starts for it, and a call in flight runs to its end while `attach` says it is waiting and asks again every 5 seconds. Then the runner prepares the worker's call as for a turn, writing its settings file, and answers with the session as a command: `claude --resume` inside the worker's sandbox, with `--setting-sources project` and the worker's settings file, and without `-p` or `bypassPermissions`, so Claude Code asks before each tool call as it always does. The CLI runs that in the terminal, holding off the terminal's interrupt and passing a SIGTERM or SIGHUP on to the session, so it outlives the session, then tells the runner to let go. Once the session runs, the CLI sends its pid too, and the hold stands while either process runs, so no turn starts under a session that outlived a SIGKILLed CLI. `drop` refuses an item under a live hold, since its worktree is the session's folder. Letting go records the branch's head on `origin` as the worker's own push, as a turn's end does, and a pull request the session opened as the one a turn would find, so the gate takes neither as a change kelpie did not make, and the next turn resumes the same session. A hold whose processes have both ended is let go at the runner's next pass, and a new `attach` takes it over. `attach` changes nothing and says what to do instead for a work item whose worker has no session yet, one parked on a ruling, one merging or closing, and one whose worker is not on Claude Code, since Codex and pi sessions resume another way. The session is the maintainer's, not a lamb (ADR 0005). Not yet run by hand against a live worker.

## Agents

- An agent is a definition file (shep-pm/shep-kelpie#313, ADR 0006): `<name>.md` in the `agents` folder of kelpie's home, YAML frontmatter and then a Markdown body. The name is the file's stem, lowercase letters, digits and `-`. The frontmatter is tagged by `role`: `implementer`, `reviewer`, `issue-writer` or `pm`, each with its own keys, so a reviewer's `paths` or `second_look` on an implementer is an unknown key, named with its line. A file that does not parse, has a key missing or unknown, names an unknown harness or misses a key its harness needs stops the runner, naming the file, the key and the file's line. A `.md` file whose name is no agent's, such as a `README.md`, is skipped, named in the runner's log and by `doctor` as unsure, and blocks nothing. The frontmatter is read with serde-saphyr, already in the build through shep-core, pure Rust and maintained, where serde_yaml is archived.
- Kelpie embeds its own agents from the repo's `agents/` folder with `include_str!`, so they are reviewable files: `sonnet-high`, `opus-high`, `defect-hunter`, `qwen`, `coderabbit`, `cubic`, `codex`, `issue-writer` and `pm`. A file of the same name replaces one, and a name with no file falls back to kelpie's own, so a home that never ran the newer `add` still runs. `shep kelpie add` writes each that is missing, never over one, and `qwen` only where the maintainer's qwen-review script is installed. A runner reads the folder when it starts and looks again each time it wakes, so an agent file edited, added or removed lands at the next wake as a settings change does, and a yes to a turn that failed on a missing file retries against the file written since. `doctor` adds an `implementers` line per project, naming the default or what is wrong.
- A project lists its implementers in `agents.implementers`, in order, each once, `["sonnet-high"]` when absent, its reviewers in `agents.reviewers`, and its project manager in `agents.pm`. A name with no agent file stops the runner, naming the setting and the file to write, and so does a file of the wrong role, naming both roles.
- A work item keeps the agent it opened on, as `agent` in the state file, and each turn runs that agent's file as it is then, even once the project stops listing it, so editing a file reaches the items on it. An item whose agent has no file left fails its turn on the `turn-failed` ruling, naming the file to write.
- One interface for every role: start or resume a session by id in a folder, with kelpie's instructions, a prompt, the kinds of tool it may use (`Work`, `Review`, `Answer`, or `Issues` for the issue writer), its skill plugins, a timeout, and a sandbox that names no harness. The sandbox lists folders the session may read and, for a fenced session, the folders it may write, the paths it may not write or read, the hosts it may reach, the commands it may not run (as prefixes with `*`), its environment, and what kelpie's own checks run with. The answer is the session id, the final text, the tokens the call used, and the session's cost only where the harness reports one. A call with no cost leaves the work item's record of that session unchanged. The goal is any harness, not one shaped like any one CLI, so everything harness-specific stays in its adapter.
- What each role needs from a harness. The worker: a session it can resume by id across turns, instructions appended to the system prompt, skills a prompt can invoke, MCP servers, no permission prompts, a fence that confines its writes and hosts and fails closed, a check kelpie runs before every command and every file write, a turn the adapter can kill at its ceiling, and each call's tokens. A reviewer's session: a fresh session each time that reads and searches the worktree, runs no command, starts no crew, and answers in kelpie's finding format. Any harness that can do those fills the role; one that cannot fence the worker cannot be the worker.
- Every agent call runs whole inside kelpie's OS sandbox (shep-pm/shep-kelpie#128): the harness, its tools, its hooks and the MCP servers it starts, not only its commands. The sandbox is a port, `Sandbox`, with Anthropic's sandbox runtime (`srt`, pinned at 0.0.77 under `<kelpie home>/tools`) behind it, so a later build, a compiled single binary or a Rust port, changes no caller. `kelpie tools install` installs it, and nothing else. The policy is the call's fence plus what the harness itself needs, which its adapter knows: for Claude Code, its transcript folder, a scratch folder and `api.anthropic.com`. A call without a fence, such as a reviewer's session, writes nothing but those and reads no credential path. A missing runtime fails the call and stops a runner at start. Claude Code's own sandbox is off under it, since on macOS a sandbox cannot start inside another (Facts); its deny rules and kelpie's hooks stay on as the second layer. The model's endpoint is open to the whole process, since the harness itself calls it, so the worker's commands reach it too: an agent CLI started from them (`claude`, `codex`, `pi`) would run a session with none of kelpie's hooks or deny rules, and `kelpie guard` refuses one wherever it reads a program. The list is each harness's `program` in the fence's own table, so a new harness cannot be left off it. After `cd`, `ls`, `mkdir`, `rmdir`, `rm`, `cp`, `mv`, `touch`, `echo`, `printf`, `git` or `cargo`, an agent's name is a file or a word, so `git add src/adapters/pi` and `cargo test pi` pass. The check is by name: `node` on pi's own script, or `npx` on a harness's package, still starts one, and the OS sandbox is the boundary.
- Each harness declares the files in a worktree that make it run code, and the fence holds every harness's files whichever harness a call runs on, so a worker on one cannot plant files for the next call on another. Each harness also declares the files in the home folder that hold its login (Claude Code's `~/.claude/.credentials.json` on Linux and `~/.claude.json`, which holds MCP servers' secrets; Codex's `~/.codex`), and a call on one harness cannot read another's. A harness reads its own to run, so those stay readable to its own calls, apart from Codex: kelpie runs it on a login of its own, and the maintainer's `~/.codex` is read by no call (#233).
- Claude Code builds its settings file from that sandbox in the interface's `prepare`, which the runner calls before it marks a turn or review call running, so a file that cannot be written fails the step and a yes retries the turn it was for. The file turns Claude Code's own sandbox off and holds the deny rules and the `confine` and `guard` hooks, and trims the features no role uses (#228, Facts). `confine` is there because Claude Code's sandbox never covered its own file tools, which is the adapter's knowledge, not the profile's; under kelpie's sandbox it is the second layer. The project's `worker.guard_hooks` are Claude Code hook events, so the profile carries them as they are, for a harness that can run them. A reviewer's session on Claude Code denies `Agent`, `Task` and `Bash`.
- pi is the second harness (shep-pm/shep-kelpie#130), chosen over the Codex CLI on a local model by one run of each on the same issue (Facts). Each call carries its harness, and for pi the server its model is on, and a port, `Routed`, sends it to that harness's adapter. An agent error names the harness's program, so a Claude Code turn reads `claude failed: ...` and a pi one `pi failed: ...`. A pi agent takes `url` and `context` as an endpoint reviewer does, and its usage is `none`, so it holds its lease for each whole call.
- pi runs every role inside kelpie's sandbox with a home kelpie writes beside the call's settings: one provider, `kelpie`, with the one model, and the sessions folder, the only part pi may write besides two lock folders. It loads none of the maintainer's or the repo's extensions, skills, prompt templates or project files, and reads the repo's AGENTS.md and CLAUDE.md. Its tools are an allowlist, `--tools`, and the rest is off by flag. The cargo-test lease reaches a pi worker the way it reaches a Claude one: the dog's door is in the fence's sockets, `KELPIE_LEASE_SOCKET` is in the fence's variables, and the instructions that say to run tests under `kelpie lease run cargo-test` are the ones pi gets with `--append-system-prompt`. A pi call's sandbox allows no host of the model server's: the call's model traffic goes to a forwarder kelpie runs outside it, which passes only the chat completions call (#235, Facts). A fenced call loads one extension, kelpie's, that runs `kelpie confine` on each write and edit and `kelpie guard` on each command, as Claude Code's hooks do, and refuses any other tool that is not a read. Any failure of the check refuses. It resolves a path the way pi's write and edit do (odd spaces folded, a leading `@` stripped, `~` expanded) and refuses a `file:` URL, which pi would open as the path it names and `confine` would read as a file in the worktree. pi takes kelpie's session id as its own (`--session-id`), so a resume is the same call shape as a new session, and a resume onto an id with no session file is `NoSession`. Kelpie's instructions are passed on every call, since pi builds its system prompt afresh each time. A step's `/<plugin>:<skill>` becomes pi's `/skill:<skill>` with that skill's folder. pi runs no Claude Code hooks, so a project whose implementer is on pi and that names `worker.guard_hooks` stops when its settings load, and a turn checks again before it runs. The prefix deny rules Claude Code also gets have no pi equivalent; `kelpie guard` covers the same commands.
- Codex is the third harness (shep-pm/shep-kelpie#233), on the ChatGPT plan, for the worker and reviewer sessions. A project opts in per role by naming an agent file with `harness: codex`, which takes no `url` or `context` and reads its usage with `codex`, so the plan's 5-hour and weekly windows pace it beside Claude's. Each call is one `codex exec --json`, a resume `codex exec resume <thread>`, since Codex names its own sessions: kelpie keeps which thread each of its session ids is, and the thread's tokens so far, beside the call's settings and out of the call's reach. A turn reports the thread's running total, so kelpie counts the difference (Facts).
- Kelpie has its own Codex login, signed in by the maintainer with device auth, in `codex_home` (`<kelpie home>/codex` by default), decided 2026-10-01. Run on `~/.codex`, Codex copied the maintainer's whole session history into each call's database. Each call runs with `CODEX_HOME` set to a home of its own beside its settings, which holds its sessions, database and logs, with the login's `auth.json` linked in; the maintainer chose that over one home every call shares, where one project's worker could read and edit another's Codex transcripts. Kelpie never reads the login. The sandbox lets a call read `auth.json` and nothing else under `codex_home`, read nothing under `~/.codex` or `~/.agents`, and reach `chatgpt.com` only. In its own home it writes only `sessions`, `archived_sessions`, `db` (Codex's databases, by `sqlite_home`), `log`, `thread-writer-locks` and `installation_id`. Not `tmp`, which Codex puts on every hook's PATH (Facts). Everything else there is Codex's to load, not the call's to write: the login, `config.toml`, `hooks.json`, `.env` (whose variables reach every hook's shell), `AGENTS.md` and `AGENTS.override.md`, rules, skills and the model catalog. It was a list of those until the control session's review of #255 found `.env` and `AGENTS.override.md` missing from it: a worker could have set `ZDOTDIR` to a `.zshenv` that made `confine` and `guard` exit 0 on its next turn. `codex_home` may not be the home folder, a folder above it or anything in `~/.codex`, and a runner reads it when it starts. `auth.openai.com` stays out: a refresh could not be saved through the read-only link, and a lost refresh token signs kelpie out. The usage read runs outside the sandbox on `codex_home` before each dispatch and refreshes a login near its expiry there. `ports::Unreadable` adds `codex_home` to every call's unreadable paths, so Claude Code and pi calls leave it alone wherever the setting puts it.
- A Codex call runs with Codex's own sandbox and approvals off under kelpie's, loads no user config or rules, searches no web, and turns off Codex's features that reach past its tools: its own crew, apps, plugins, browser and computer use, image generation, memories, shell snapshots and the rest of `FEATURES_OFF` in the adapter. `unified_exec` cannot be turned off from a call (Facts). A fenced call runs kelpie's checks as Codex's `PreToolUse` hooks, trusted for the call with `--dangerously-bypass-hook-trust`: `kelpie confine` on `apply_patch`, the tool Codex writes files with on ChatGPT's models, and `kelpie guard` on `Bash`, every command. On the plan's models Codex writes through `apply_patch`, whose hook payload carries the patch, and confine judges every file the patch names. A patch typed as a command, `apply_patch <<EOF`, Codex applies in its own process past that hook, so `guard` refuses `apply_patch` and `applypatch` as programs. A step's `/<plugin>:<skill>` becomes a line telling a worker to follow that skill's `SKILL.md`, which its shell reads. A call with no shell has no tool that reads a file, so kelpie reads the `SKILL.md` itself and puts its text in the prompt. Only a worker runs commands: every other Codex call, such as a reviewer's session, has no shell (`shell_tool` off), since a pull request under review could otherwise talk the session into running commands no `kelpie guard` sees. Codex has no tool that only reads, so such a call reads only what its prompt holds: a reviewer its diff and the issue's criteria. Its model's `apply_patch` cannot be turned off from a call, so a call with no fence runs one hook that refuses every patch. A fenced worker's `kelpie guard` answers an allowed command with a check that it runs where it was judged, judges it again in a `workdir` inside the worktree, and refuses one outside it (Facts). Codex runs no Claude Code hooks, so a project whose implementer is on Codex and that names `worker.guard_hooks` stops when its settings load, as with pi. Codex reads the repo's AGENTS.md, not CLAUDE.md.
- Codex writes its stdout and stderr to files kelpie opens for it, beside the call's settings where the sandbox cannot open them, since a shared pipe the sandbox's Node makes non-blocking killed it on its first large output (Facts). Kelpie removes them once read.
- A local implementer, one whose usage is `none`, takes only the issues labelled `agent:<name>` for it, and is never the default, until the design log has numbers for it. A project lists it beside an implementer that is not local, which runs every other issue: a list of only local ones is refused at load. A pi or Codex implementer beside `worker.guard_hooks`, or a pi one whose server `worker.allowed_domains` would reach, is refused at load, and a turn checks again before it runs.
- Pacing and spend per agent (#129). Each agent names how its usage is read with `usage`: `claude` (`/usage`, the default on Claude Code), `codex` (the Codex account's own 5-hour and weekly windows), or `none` for a local model. The reader must be the harness's own, since an agent spends its harness's account whatever its `usage` says: on Claude Code only `claude` is taken and on pi only `none`, so `codex` waits on a Codex harness, and the runner's tests reach it through a test-only `stand-in` harness. An account is its reader, so the model is one login per harness; a second Claude login would need its own config folder and is not modelled. A `none` agent is never paced. Its limit is its `lease` (the GPU lock, `gpu`, by default), which `ports::Leased` takes for the whole of each call on it, so a qwen round on the same lock waits behind a local worker's turn. `status.local_leases` shows who holds each such lease.
- Spend is tokens per role for every agent. Dollars are kept only for calls whose harness reports them: `by_role.<role>.cost_usd` covers those, is null when there are none, and `unpriced_calls` counts the rest. A turn's log line carries `cost_usd: null` when its harness reported none. The state file marks such a call `unpriced`, so its zero cost is not read as free. `work_item.cost_usd` sums the priced calls only, and `work_item.unpriced_calls` says how many it leaves out.
- `shep kelpie doctor` reads Codex's usage for each project whose roles spend the Codex account and adds a `<project>: codex usage` line: missing when `codex` cannot run or the backend refuses the read, unsure otherwise.
- The project manager is an agent file too (shep-pm/shep-kelpie#327): `role: pm`, on `claude-code` only, since a Claude Code hook holds its writes to its notes, with `model` and `effort` and its standing prompt as the body, which is required. Kelpie's own `pm` is Opus 5.5 at medium: measured, Sonnet 5.5 at high decided as well for less from a fresh session, but cost about the same in the session shape kelpie runs (Facts).

## Review

- The review (ADR 0006, shep-pm/shep-kelpie#314). Once the worker's draft pull request is open, `Phase::Review` runs before CI: one pass down the project's reviewers, each run once, in order. A round with no findings, or only nits (LOW), goes straight to the next reviewer. One with anything above a nit sends all of that reviewer's findings, nits included, at its own severity, to the worker's next turn as a file, and the next reviewer reads the fix. After the last reviewer the work item goes to CI, and whatever the last fix leaves is what CI and the merge see. There is no loop, no round guard and no judge: the maintainer's ruling is that reviewers go in series and whatever the pass ends on is what it ends on, and measured, the gain is in the first two reads, a judge kept most of the findings that were not real, and a loop's "two clean rounds in a row" spent its rounds on nits (Facts). A pass starts again from the top only on a new head that needs it: the fix a merge ruling's no asks for, an accepted foreign change, or a rework. Each listed reviewer's `ran` is kept in the review's state, so a reviewer taken off the list or a list reordered mid-pass leaves the rest to run, and a round cut short resumes with the same reviewer.
- A reviewer is an agent file whose `role` is `reviewer`. Its `harness` is `claude-code`, `codex` or `pi`, a fresh session on its `model` and `effort` with the `Review` tool kind on every harness (Read, Grep and Glob, no commands, no crew), or `command`, a command of the maintainer's on the qwen script's contract, or `endpoint`, kelpie's own OpenAI-compatible reviewer, each of those two with its `lease`, `ollama` and `ollama_model` and the checks a runner's start makes, or `bot` (below). An agent's file says what runs it as one enum: a session, a command, an endpoint or a bot. A session's body is its prompt, with `{{BASE}}` and `{{DIFF}}` filled and the diff after a body that has no `{{DIFF}}`, then the issue's acceptance criteria as every reviewer gets them; a session with no body, and a command, endpoint or bot with one, is refused, since a command writes its own prompt. A reviewer's `paths` limit it to pull requests changing a matching file, read with `git diff --name-only` against the round's base. A reviewer's prompt carries the issue's title and acceptance criteria, the section under an "Acceptance criteria" heading or the whole body, cut at 4,000 bytes so a small model keeps room for the diff: in a session's prompt, in an endpoint's system prompt, and in a file a command finds in `KELPIE_REVIEW_CRITERIA`. So each reviewer checks the work against the criteria in its own pass, and there is no separate whole-issue check.
- `second_look: true` runs a session twice before one fix turn, the second fresh session shown the first's findings and asked only for what it missed, in kelpie's own words; its two looks are kept in state as the round and then a `second-look` stage, so a restart resumes at the look it was on. A second look whose call keeps failing lets the first's findings go on alone. Kelpie ships `defect-hunter`, Opus 5.5 at high, the maintainer's defect prompt word for word as its body (a test pins it), with a second look: measured, the best single reader, and the second look added 11 points at 95% precision (Facts). The readers run no command, since a reviewer that runs tests was measured to find fewer bugs and only confirm what it finds.
- Kelpie ships `qwen`, a `command` reviewer on `~/.claude/scripts/qwen-review.sh`. `add` lists `agents.reviewers = ["qwen", "defect-hunter"]` where that script is installed and `["defect-hunter"]` elsewhere. A project with no list runs the same as `add` would write; an empty list reviews nothing.
- A reviewer whose call fails three times in a row (a reply that is neither findings nor `CLEAN`, a crash) is passed over for the rest of its pass, with a `ReviewerSkipped` report, and `status` lists it under `reviewers_skipped`. A pass that ends with no reviewer having read the pull request, because a listed one was down, kept failing or reviewed no file, marks the work item unreviewed with the reason: saved, shown in `status`, reported by a step of its own, named in the merge ruling's question, and under `auto` that item gets the merge ruling instead of merging, so an API outage cannot merge a `defect-hunter`-only project unread. A pass with nobody to read it by the project's own choice, an empty list or every reviewer's `paths` missing the change, is one log line and no mark, and a later pass a reviewer reads clears the mark.
- A fix turn counts only if it moves the branch's head on `origin` (shep-pm/shep-kelpie#40, #49). Kelpie fetches the head when it sends the findings and again when the turn ends, from git rather than the forge, whose head lags a push. An unmoved head parks the worker on a `stuck` ruling for `fix-not-pushed`, and a yes sends the same findings again. A fix turn that pushes nothing, having copied every finding it was sent into the deferred findings file since they were sent, goes on to the next reviewer instead; the findings sent and the file's lines as they were sent are kept on the `fixing` stage for that check, so a deferral an earlier round left counts for nothing.
- A reply with no finding counts as clean only when it is exactly `CLEAN`: an empty or prose reply reviewed nothing. A thinking model's `<think>` block is dropped before the findings are read, and a reply that ends inside one fails the round.
- Local reviewers, `command` and `endpoint`, are a per-project choice (shep-pm/shep-kelpie#107), since a beta tester has neither the maintainer's script nor the same GPU. `endpoint` is kelpie's own reviewer for any OpenAI-compatible server: it diffs from the round's base with ten lines of context, numbers each line by its place in the new file so the model can name one, cuts the diff into chunks sized from the agent's `context` (three bytes a token, a quarter of the context kept for the reply), and sends each with a fixed prompt in kelpie's code, reading findings back in the `SEVERITY|file:line|what|why` format. `command` keeps the qwen script's own contract, which the README sets out, plus `KELPIE_REVIEW_HEAD`. A round's findings and its completion marker both come from disk (`QWEN_REVIEW_OUT`, redirected per work item rather than the script's own path slug, so a test rig never touches the maintainer's real `~/.claude`), never from stdout, and a command's `round-N.txt` and its marker are removed before each run. A file the script skips as too large is cut into a `-U25` hunk against `origin/main` and reviewed again on its own, with its findings folded back in against the original path. The runner checks at start that a command is an executable file and that an endpoint answers `GET /models`, and refuses to start otherwise, naming it; a live change gets the same check before it takes effect. It does not check the model is listed, since llama.cpp's server answers to any model name. A local round that reviewed nothing, or left the same files unreviewed twice, marks its reviewer down for the work item (Facts).
- `lease` names the lock kelpie takes around a local reviewer's round: `gpu` is the qwen scripts' lock and any other name a lock of the same format under `$TMPDIR/kelpie-leases/`, taken the way the GPU lock is, so option A of 2026-09-26 holds and the dog's book stays out of it. Kelpie never takes the GPU lock for a command that takes it itself, as `qwen-review.sh` does, waiting up to an hour, which is normal, not a hang. With a lease, kelpie checks where the local model sits before the round (#145, Facts), and a model on the CPU parks on a `stuck` ruling for `local-model-spilled`. A running round is never preempted, since a kill takes 20 to 70 seconds and throws the partial round away.
- Review bots are reviewer files on a bot harness (shep-pm/shep-kelpie#315, ADR 0006). CodeRabbit, cubic and Codex are reviewer agent files with `harness: bot`, `bot` naming which, and the bot's window as `reviews` in `hours`; Codex's also takes `reviews_on_ready`, off when absent, and any bot's takes `rounds` and `paths`. A bot's file is named for its bot, `coderabbit.md`, `cubic.md` or `codex.md`, and one of another name is refused, since the window is the bot's account's and the dog books it from that file: the dog loads the agent files when it starts, and a folder it cannot read leaves kelpie's own files' windows. Kelpie embeds all three, CodeRabbit at 1 review in 1 hour, cubic at 20 in 720 and Codex at 10 in 168, and `add` writes them out and lists none. A bot takes no model, effort, lease, url, context, command, usage, second look or body. A project that lists no bot never reads a bot's activity, asks for a bot's lease or reads the repo's visibility.
- A listed bot reads in its place in the pass, once a pass, as its own round: the review phase's `summon`, `summoned` and `settling` stages. The round marks a draft ready, since CodeRabbit skips drafts (#65), waits until the forge reads it ready or two minutes pass, and records that as kelpie's own so the foreign-change check never reads it as someone else's. Then it waits for the bot's lease, summons by label or comment as its profile says, and gives the lease back once the bot answers: a review running or landed, or a refusal, after which the round asks again. A head a review already covers is never summoned. A review that covers the head does not end the round at once, since the forge can list it before the threads posted with it (Facts): the round reads the bot's open threads again, at least 20 seconds after the last read (a runner passes about once a minute), and lands once two reads agree and it first saw the review at least a minute ago, or two minutes after it first saw the review, when it takes them as they stand (shep-pm/shep-kelpie#350). A thread GitHub marks outdated, its lines changed since, is never open: it is never sent, counted or the start of a round. Those threads are then the round's findings, with their thread ids and the bot's own severity, so the nit rule, the one fix turn, the `fix-not-pushed` ruling, deferral and the unreviewed mark are any reviewer's; once the fix moves the head kelpie resolves the threads it sent (a thread the forge no longer has, or already resolved, is done), and after three steps in a row the forge refuses, the fix goes on with the rest open and the bot's next read sends them again.
- A bot is passed over for the pass when its window opens more than an hour on (unasked when the dog's book says so, which the runner reads from `dog/book.json` with the bot's file's span, and with its label off when its refusal quotes so), after two hours with no review, after two hours in which its round could not summon it (a lease never granted, or a book the runner cannot read, counted from the round's start, a refusal inside the hour keeping that clock, or from the bot marking the head done on an owed summon), when the project stops listing it mid-round, and for CodeRabbit when the forge reports the repo not public just before a summon. Each is a `ReviewerSkipped` step and a `bots_skipped` entry in `status` until the next pass starts, and a pass no other reviewer read ends unreviewed, naming why. A bot passed over that reviews the head anyway gets a round of its own at the start of the pass's next round, before the next listed reviewer, or before the pass ends: a pass with a bot in `bots_skipped` ends in a round step of its own, which reads whether it reviewed. That round takes the bot out of `bots_skipped` and settles its threads as any review's, even when the first read finds none (shep-pm/shep-kelpie#350). Once the pass has ended, its threads reach the merge ruling instead. The ruling's question names every listed bot's unaddressed threads on the pull request, by bot: open, not outdated, not sent to a fix turn still awaiting them, and above a nit, since the nit rule holds nits back on purpose. Under `auto` such threads raise the merge ruling instead of merging, as a pass no reviewer read does. CodeRabbit's check that the repo is public also runs at a start and at a live change that lists it, so a repo GitHub marks private lists cubic or Codex instead.
- A summon a bot never acknowledged is sent once more (shep-pm/shep-kelpie#122). A sign within fifteen minutes of the summon counts as hearing it: for CodeRabbit the "Review in progress" status on the head, a change to any of its comments (the walkthrough is edited in place), a review or any other status on the head, or a rate-limit notice; for Codex any comment of its since the summon. With none, the runner sends the summon again by the same choice that made the first, says so in the log (`SummonedAgain`), and waits as before. The re-send keeps the lease the first summon took, opens no window of its own, and the hour still runs from the first summon. A label summon goes off and on again, since a label already on sends CodeRabbit no event. It is saved before the comment goes out and made at most once per summon, and sent only under a lease row of the work item's own, so after a restart, which clears the rows, it is not sent under a grant another item took. A summon with no answer in ten minutes after its re-send counts as spent.
- Full reviews (shep-pm/shep-kelpie#100). The label asks CodeRabbit only for what is new since it last read the pull request, and a branch kelpie caught up with `main` holds nothing new to it. So on a pull request CodeRabbit has reviewed before, an adopted pull request's owed summon, and any summon after kelpie's own catch-up push, asks with a `@coderabbitai full review` comment instead, with the label taken off so no push summons outside the lease. A pull request CodeRabbit never read keeps the label alone. The comment is a summon like the label: it waits for the dog's lease, is counted from when it was made, and is saved as made before it is posted, so a restart never posts it twice. CodeRabbit marking the head "Review completed" with nothing posted since the summon is an answer: after a minute's settle, since a review posts a few seconds before that status, kelpie reads it as a clean read, unless a summon is owed, which then asks once for a full review. A full review finds more on shep than an incremental one (Facts).
- A clean catch-up summons no bot (decided 2026-09-29 on shep-pm/shep-kelpie#106). Kelpie's own rebase or merge of `main` with no conflict leaves the pull request's own diff unchanged, so there is nothing new for a bot to read, and CI checks the combined code. A catch-up still makes the next summon, in a later pass, ask for a full review.
- cubic has no label, so it is always summoned by its `@cubic-dev-ai review` comment. Its `P1`..`P3` level is the finding's severity (P0 and P1 high, P2 medium, P3 low) and goes to the worker with cubic's confidence as the finding's why. A refusal that quotes no opening, such as cubic's or a Codex usage limit, holds the bot for its window's span.
- Codex (shep-pm/shep-kelpie#126) is summoned by `@codex review`. Its first comment after a summon is a notice and not a refusal. A review covers the commit it names, by prefix, since its comments give ten characters. A thumbs up it leaves on the pull request after the summon is a review with nothing in it. The badge on a finding, `P0` to `P3`, is its severity as cubic's level is. Its `reviews_on_ready` says marking ready is its summon (Facts): then the round waits for its lease with the draft unmarked, marks it ready as the summon, posts no comment, and never sends that summon again by comment, so one Codex never answers is passed over at two hours. A list with another bot before one that reviews on ready is refused at load, since that bot's mark-ready would draw its review outside its lease.
- A bot's `rounds` caps its reads of a work item's pull request across passes, counting the reviews it gave before a rework or an adoption, and is unset by default. An adopted pull request with no review asking for changes starts a pass of the listed bots alone, `bots_only` in its review, and each listed bot owes it a summon of kelpie's own (`summons_owed`, per bot): until that bot answers one, which asks for a full review where it read the pull request before, no review of its from before the adoption stands for its read and its `rounds` does not pass it over; with no bot listed it goes straight to CI.
- Two kinds of reviewer share their output (shep-pm/shep-kelpie#123): a finding with a severity, file, line and text, and from there the worker's fix is one path. A local reviewer or a session hands its findings back when the call ends; a bot needs a lease on its window, a sign that it heard, a re-send when it did not, threads to resolve, and a head its review covers. The bots follow one script on GitHub, so the bot side is one provider, the runner's round, with a profile per bot for what differs: its login, its label and full-review comment, how its answers read (heard, reviewed, refused, done), how a thread's severity reads, and the lease it spends. Profiles and their parsers are code, tested against the bot's recorded output.
- A confirmed finding left unfixed at merge becomes a follow-up issue (shep-pm/shep-kelpie#142). A reviewer's finding goes to the worker, which fixes it; one the worker leaves as out of scope goes, in the findings file's own format, into `deferred-findings.md` beside the findings file in its build folder, which the findings file's header names. Once the pull request merges, kelpie reads that file once, before it removes the build folder, and files each finding as an issue on the project labelled `ready-for-agent`, linking the pull request. An open issue whose body names the file, and whose title matches or whose body says the same thing, gets a comment instead of a second issue. Under `ask` a `follow-up` ruling comes first, raised after the merge: a yes files them and a no drops them. Under `auto` they are filed with no ruling. Only what kelpie itself sent the worker is filed: each finding sent to the worker is kept on the work item, and a line in the file counts only when it names one of them by file, line and what, and the issue carries kelpie's text, not the worker's, so a worker cannot put its own words on the tracker. A round of nits never reaches the worker, so its nits are never held. If the forge keeps refusing for six hours from its first refusal (issues off, a missing label, a rejected body), a `follow-up` ruling lists the findings and the reason: a yes tries again for another window, a no drops them. Passes do not count, only time, so a short outage of the forge's own costs nothing. A crash between opening an issue and saving that leaves a redundant "confirmed this too" comment on the new issue at the retry, which is accepted. A finding whose text names a folder on this machine is not posted (the forge guard refuses it), so it is left out and counted in the step's report rather than retried. Not built: a reviewer that answers after the merge, since nothing watches a pull request once its work item is gone.

## CI and the merge

- The merge gate (shep-pm/shep-kelpie#9). After the review's last reviewer, kelpie waits for CI. A red run is the worker's next turn, naming the failed checks, led by the `ci` step's skill; a second red run on a head the worker left alone parks it on a `stuck` ruling for `still-red`. A green run on a branch that has the latest `main` raises the merge ruling, or merges under `auto`. A branch without it is caught up by kelpie first: rebased onto `main` and pushed with a lease on its head, or, where it holds a merge commit or commits that are not kelpie's to rewrite (an adoption's), merged with `main` and pushed without force. A conflict is the worker's next turn (shep-pm/shep-kelpie#61), naming the files: it merges `origin/main` in and pushes, so nothing it pushes is forced. A turn that leaves the same head, or a conflict on the same `main` again, parks it on a `stuck` ruling for `rebase`. A project says whether it runs CI with `ci`; with it off, kelpie reads no checks (Facts).
- Merge authority is a project setting: `auto` or `ask`, `ask` by default. `ask-surface` (ask only when a pull request touches operator-facing surface) is refused.
- Under `ask`, a yes merges only the head it was asked about, while CI on it is green and it has the latest `main`. Otherwise kelpie withdraws the yes, reruns CI, and asks again. The merge is `gh pr merge --merge --match-head-commit`, never a squash, and kelpie then removes the worktree, both branches and the build folder. Kelpie puts `ready-for-human` on at the merge ruling.
- `auto` (shep-pm/shep-kelpie#83), chosen over running shep's merges from a Claude control room so the merge rules stay in kelpie's code. It replaces the merge ruling and nothing else. Where `ask` would raise it, `auto` merges by the path a yes takes: the head the gate passed, CI green on it, the latest `main`, the review pass read, no listed bot's threads unaddressed (shep-pm/shep-kelpie#350), and a merge commit. Every other ruling still asks. Kelpie never puts `ready-for-human` on for the merge. A merge that no longer holds, because the head moved, CI stopped being green or `main` moved, goes back to CI as a withdrawn yes does, and CI catches the branch up. A merge the forge refuses takes that path once; a second refusal on the same work item parks it on a `stuck` ruling for `merge-refused`, and any answer to it gives the next refusal its catch-up again. Its pull request comment names the head and leaves the forge's reason out, since that text is not written for strangers. A merge the gate started under `auto` goes ahead only while the project is still `auto`: a project switched back to `ask` goes back to CI and gets the merge ruling. Under `ask` a yes on a `rebase` or `still-red` ruling vouches for whatever head the gate sees next, because the merge ruling follows; under `auto` nothing follows, so the yes reads the branch's tip, and a tip the gates never saw goes back through a pass of the review. The same holds for a head the gate finds with none known, such as one a yes under `ask` vouched for before a restart onto `auto`. The switch back to `ask` is read after the pull request's state, so a merge that landed before the switch still gets its notice. `status` shows the project's merge authority.
- After an automatic merge kelpie sends a notice naming the project, the pull request, its issue and the merged head (shep-pm/shep-kelpie#118). A notice is not a ruling: it has no id, takes no answer, goes to the webhook alone, and is only logged where there is none, and is saved with the merge so it goes out once, retried like a ruling's post and never ahead of one. A merge at the gated head that a restart or a lost answer hid, found merged on the next look, still gets its notice, and so does one that lands after kelpie read its error, since kelpie records the head it tried.
- A merge queue on `main` (shep-pm/shep-kelpie#213): kelpie queues the pull request and waits on it, skipping every gate while the queue holds it, and a removal goes back to the worker like red CI (Facts).
- The foreign-change check covers the head (shep-pm/shep-kelpie#69). Kelpie records the branch's head on `origin` as each worker turn ends, and the head its own catch-up push leaves, so a worker's merge of `main` and kelpie's rebase are never foreign. At the gate, once the forge's head matches `origin`, any other head, or a label or ready state kelpie did not set, parks the worker on a `foreign-change` ruling that names the commit. A yes moves the worktree to that head, refusing if it holds work not pushed, and sends it through a pass of the review, the listed bots included, before the merge ruling. Under `auto` a yes vouches for no head the gates did not see. A commit pushed while the worker's turn runs is read as the worker's, and gets the gates that turn's code gets.
- A pull request the maintainer merges by hand ends its work item with no merge by kelpie. One closed without merging parks the worker on a `stuck` ruling for `closed`.
- A work item saved before the gate existed stays with its worker until `shep kelpie gate` sends it in. The trigger takes only an item whose turn has ended with a known pull request.
- Reworks (shep-pm/shep-kelpie#53). A rework makes a work item of an open pull request from a `kelpie/<issue>` branch on the repo itself, opened by the account kelpie acts as (`gh api user`, read once a run), dropped or finished alike. A collaborator's or a fork's pull request on such a branch is not kelpie's, and the poll leaves it alone. The pull request asks for one: `ready-for-agent` on it, since kelpie opens pull requests under the maintainer's account and GitHub won't let an author request changes, or a review requesting changes from anyone else with a hand in the repo (its owner, a member or a collaborator, since anyone can review a public repo's pull requests). The runner checks its open pull requests on the board's poll, before any ready issue, and `shep kelpie rework <pr>` asks by hand. A rework that asks but cannot start, because the forge failed or a label would not come off, is passed over for that poll. Each review that started or was refused a rework is recorded and never asks again. It is refused while the project has `max_items` open or one for its issue, and when the latest review has no body and no unresolved comment; a refusal the pull request asked for goes to it as a comment, with the label off. The worker starts a new session on the branch as `origin` holds it, so commits the maintainer pushed stay, and it pushes without force. Its first turn names a file in its build folder that holds the review's body and its unresolved comments verbatim, each with its file and line. The turn goes to a pass of the review and then every other gate. Its issue stays finished, so only the trigger brings a rework, never the board.
- The triage labels say whose turn a pull request is. A rework takes `ready-for-agent` and `ready-for-human` off as it starts. Kelpie puts `ready-for-human` on, and takes `ready-for-agent` off, at the merge ruling and whenever a work item ends unmerged, and takes `ready-for-human` off when an answer sends the worker back to work. The gate ignores `ready-for-agent` added while a work item is in flight, so a second ask waits for that item to end. The board's `gh issue list` never lists a pull request. `shep kelpie add` and the issue writer are the only places kelpie creates a label.
- Adoptions (shep-pm/shep-kelpie#84). An adoption makes a work item of an open pull request kelpie didn't open, so the maintainer's other sessions can hand theirs over. The maintainer adopts one with `shep kelpie adopt <pr>`, or with `ready-for-agent` on one whose branch isn't `kelpie/N`, seen on the board's poll. Kelpie refuses, with a comment, one that is closed or merged, comes from a fork, merges into a branch other than `main`, has another author than the account kelpie acts as, or names no issue it closes; a refusal from the label takes the label off. The lowest issue it closes becomes the work item's issue. Adopted pull requests wait in the state file for a free slot, one at a time, and one closing an issue whose work item is open waits for it to end, and go before reworks and the board; `status` lists them as `adopted`. One the label adopted leaves the queue when the label comes off, and one merged or closed while it waits leaves without a comment. One starts on a fresh worktree of its branch as `origin` holds it, with its labels, ready state and head taken as kelpie's own, so nothing already there reads as a foreign change, and `ready-for-agent`, `ready-for-human` and `review please` come off, so no push summons a bot outside its lease. With no review asking for changes it starts a pass of the listed bots alone, or goes to CI with no bot listed. The worker's first turn is whatever the gate first sends it, behind a file in its build folder holding the pull request's title and body and its issue. A latest review requesting changes from its owner, a member or a collaborator goes in that file too and is the first turn at once, followed by a pass of the review. The review diffs from the head the pull request arrived with, so only the worker's own commits are reviewed. A branch behind `main` is merged, never rebased, and nothing on it is force-pushed. The branch's owner may still be pushing, so a push counts as the worker's only when the worker's worktree holds it, and one found before a worker's turn sends the work item to the gate instead of the turn. Either way a push from anyone else parks it as on kelpie's own branches. The merge follows the project's `merge_authority`.
- The project manager's merges, rebases and pushes are the runner's own `gh` and `git` calls, plain child processes, which the worker's settings file, sandbox and denylist never reach.

## Rulings

- Six ruling kinds (shep-pm/shep-kelpie#330, ADR 0006): `merge`, `question`, `stuck`, `agent-files`, `foreign-change` and `follow-up`. `stuck` carries its reason as a field, one of `rebase`, `still-red`, `merge-refused`, `closed`, `local-model-spilled`, `fix-not-pushed`, `turn-timeout` and `turn-failed`, each with its own question, pull request comment and effect for a yes and a no, and any further text in `why`. ADR 0006 named five kinds; `follow-up` stays its own, by the maintainer's decision, since under `ask` the findings a merged pull request left still wait for a yes before they are filed. No command takes a kind's name: `status` shows a `stuck` ruling's reason beside its kind. The project manager's stuck wakes and retries read the same reasons: `turn-failed`, `turn-timeout` and `still-red`.
- A ruling is a log line, a status entry and a webhook post, all carrying the same question and the triggers that answer it. A no with a note is the worker's next turn. The pull request gets a comment for every ruling but a merge (shep-pm/shep-kelpie#89). It says what happened and that it waits on the maintainer, and names no command: `ready-for-human` already says the pull request waits, and the webhook carries the question.
- Ruling ids never repeat and are unique across every project under one kelpie home (shep-pm/shep-kelpie#119): each id is a file `rulings/<id>` holding its project's name, linked into place so two runners never give one twice, and a new id goes past the highest claimed and every state file's `last_ruling`, so an open ruling keeps its number. `shep kelpie rule <id> <words>` reads the ruling's kind from its project's state file: `yes` and `no <note>` for a yes-or-no ruling, any text for a question, a lone `yes` included, and the older `answer <text>` still read. An id with no claim needs `-p` when two projects hold it open or any project's state file cannot be read, since the unreadable one may hold it too. `rule` alone, in a terminal, lists the rulings waiting and asks which and how; without one it lists them and exits non-zero.
- `shep kelpie <verb>` (shep-pm/shep-kelpie#119). Every trigger a runner takes is also a verb of the adopted kelpie, sending the trigger `shep trigger` sends, which keeps working. `-p <project>` goes anywhere before a `--`, before the verb included, and for `rule` before the answer's second word, so a note can carry a `-p`. Without it the project is the one whose `repo` is the folder's git top folder, or, for a worktree (kelpie's own included), the checkout its common git dir belongs to; with no match the error lists the projects. `add <issue>` puts an issue on the board and `add [<project>]` registers a checkout, told apart by an all-digit argument. `status` with no `-p` stays every project's.
- Rulings reach the maintainer by one webhook, until shep can carry a question itself (shep-pm/shep#689, shep-pm/shep-kelpie#333, ADR 0005). It is named in kelpie's own settings, its `[kelpie]` section of `dogs.toml`, which every project shares: a `[webhook]` table with `kind` (`discord` or `ntfy`) and `url`, both required. With none, a ruling reaches the maintainer in the log, `status` and `shep kelpie rule` only, and the runner logs one line at start saying so. A failed post is logged and tried again after a minute, doubling to at most half an hour, and a ruling counts as alerted only once a post lands, so a restart between the post and the save can post it twice. With no webhook nothing is posted, so no ruling waits on an alert and none holds back the next. The URL is a credential: it reaches `curl` on stdin, never in its arguments, curl's own messages are dropped, and no error, log line, status or comment carries it. Plain `http` is accepted only for a stand-in on the same machine. A long question is cut in the middle to the channel's limit, keeping its start and the triggers at its end (Facts).
- Rulings are answered from ntfy (shep-pm/shep-kelpie#111). An answer that acts proves itself with the maintainer's authenticator code, decided by the maintainer over a first build that posted a one-time code on the alert: that code sat on the topic it guarded, so anyone who could read the topic could merge. The code is RFC 6238 TOTP (HMAC-SHA-1, 30-second steps, six digits).
  - `shep kelpie totp` draws the 160-bit secret once into `<kelpie home>/totp/secret` (the folder 0700, the file 0600) and prints it as an `otpauth://` URI and a terminal QR code to scan; `shep kelpie totp --rotate` draws a new one, written beside the old and renamed over it, the folder synced after so a crash cannot bring the old one back (a first `shep kelpie totp` links its file into place instead, so two at once keep one secret), and every runner reads the file afresh for each reply, so the old secret's codes stop at once. A secret file, or a totp folder, anyone but its owner may read or write stops the runner. Workers are denied the totp folder like the other credentials.
  - A reply is `<id> yes <code>`, `<id> no <note> <code>` or `<id> <answer> <code>`, the code always last, and may still name the project first; an unnamed one goes to the runner its id was given to, and one for an id two projects hold is refused with a line asking for the project. The part after the project is read by `rule`'s own parser, so a change to `rule`'s grammar reaches ntfy replies too. The code is checked against the time ntfy took the reply, which no sender can set, and taken in that step and the one before.
  - Every code the maintainer sends is on the topic afterwards, so every right code anywhere in a post is claimed before anything else about it is read: whether answers are on, whether it is kelpie's own, which project it names, how old it is, or how the code was typed. Every text the post carries counts, its title, tags and attachment name included, and in each every decimal digit of any script is taken in order with whatever stands between dropped, so `123-456`, `123 456`, full-width, Arabic-Indic or math-bold digits all spend the code. A post spends the codes of three steps: the one before and its own, which `verify` takes, and the one after, from a phone whose clock runs ahead, which a replay could send once that step comes. A secret that cannot be read, or a claim that cannot be written, holds the post at the head of the queue and backs off; it never passes the post by with its code unspent. Only the exact shape, six ASCII digits last, can act.
  - A claim is `<kelpie home>/totp/used/<step>`, holding the id of the ntfy message that first sent the step's code, written beside its name, synced and hard-linked into place, so it is whole or absent. Every runner reads every reply, so a runner that finds the step claimed by the same message counts it as that message's, and one claimed by another message is a replay: it runs nothing, and the named project's runner tells the topic to send the next code. Claims are let go an hour behind the older of the claimed step and this machine's step, since the step is ntfy's clock.
  - A wrong six-digit code is counted once by message id under `<kelpie home>/totp/failed`, and the fifth turns answers from the topic off for every project (RFC 4226 section 7.3), with one line on the topic that also suggests moving to a new topic, until `shep kelpie totp --unlock` on the terminal; a right answer forgives the count. While they are off, alerts say nothing of replies and the topic is not read. A reply with a valid code for a ruling already settled runs nothing and gets a line saying so, and a refusal from `rule` goes to the topic as a line too. Anything else is ignored and logged without its text. The alert ends with the replies that answer it and carries no code and no buttons, since a button cannot carry a code the maintainer has not typed yet. With no secret yet, alerts say nothing of replies and the topic is never read.
  - The runner reads the topic's cached messages (`/json?poll=1`) after the last one it read, saved in the state file, every 15 seconds while an alerted ruling waits, and for an hour after an alert lands, backing off to five minutes while reads fail. A read reaches back ten minutes and three steps at most, so a saved position ntfy no longer holds never returns its whole cache. A reply older than ten minutes is read only to spend its code.
  - Four limits are accepted. Anyone who can write the topic can turn answers off with five guesses; that fails closed, `rule` still answers, and only the terminal turns them back on. An alert's text is not authenticated: a code proves who answered, not what they were shown, so a writer who posts a fake alert could get a real answer to a question kelpie never asked, though only for a ruling id that is pending. A topic writer who posts every code can burn steps without tripping the lockout, which only delays the maintainer's answer, and ntfy rate-limits the posts. A post kelpie cannot read in full, such as a message over 4,095 bytes that ntfy turns into `attachment.txt`, is not fetched: it spends every step a code sent with it could name, answers nothing, and gets one line on the topic saying it was too long to read and to send a shorter reply with a new code.

## Budget

- Kelpie paces against each account's weekly window. The daily allowance is what is left of the week divided by the days until reset (100/7 on a fresh week), one figure for the day, not spread by the hour (decided 2026-09-27 on #15), given the gates already in place: the 5-hour window and the board's own screening. A day is 24 hours counted from the weekly reset, so the days until reset are always whole. The allowance is fixed when the day begins and kept in the state file, so a restart keeps it. Today's spend is the week's utilization now minus its utilization at that read, the maintainer's own sessions included. Once spend reaches the allowance, no work item is dispatched and those in flight continue. `pacing.kickoff_hours` (8 by default, about 1.8% an hour) only divides the allowance into the per-hour figure `status` shows.
- The 5-hour window is a local limiter: at 50% no turn starts, dispatch included, until the window resets. Usage is read only before a dispatch and before a turn that has not begun, never mid-turn, and a turn resumed after a restart is not held. A hold is trusted for at most 10 minutes, since reset times are printed to the minute and a window can reset mid-read.
- A maintainer's `add <issue>` is not held by the daily allowance, the way it already skips the board's screening. The 5-hour window still holds its turns.
- `pacing.enabled` (on when absent) turns both limits off for a stretch when usage does not matter, such as a free reset coming (decided 2026-09-28 on #67). Nothing is held, including on an unreadable reading, but usage is still read before each dispatch and turn, so `status` shows `pacer.enabled: false` beside the live numbers.
- When usage cannot be read, the pacer holds both limits and says so in `status`. A pacer that guessed would spend the account it exists to protect.
- Per account since #129. Each account keeps its own day start, allowance, 5-hour stop and holds; Codex's day start is `codex_pacing` in the state file, written only once one exists. A new work item is paced on every account the project's calls spend (each listed implementer's and each session reviewer's), and holds on the first one over its allowance or past its 5-hour mark: a local implementer with a Claude reviewer still spends Claude's week. The worker's turns are paced on its agent's account, and a reviewer's session on its own agent's account with the same 5-hour stop. `status.pacer` lists each account the project spends, and any other read this run, under its name (`pacer.claude`, `pacer.codex`), with what holds a new work item on it. Hold reasons name Codex ("Codex's 5-hour window is at 55%") and keep Claude's wording.

## Where the time goes

- Phase timings (shep-pm/shep-kelpie#141, six phases since shep-pm/shep-kelpie#331, ADR 0006). Each work item records the seconds it spent in each of six timing phases: `worker`, `review`, `ci`, `ruling`, `merge` and `other`. Every second since the work item was created lands in exactly one. `review` is every listed reviewer's round, a local round's wait for the GPU, a session's or an endpoint's run and whichever review bot's lease, window and review the work item waits on. `other` is between steps and the time the runner is down, a stop with `pause` included. A worker turn that waits for a local agent's lease is `worker`.
- Time is charged at the state's save, to the phase the work item was in before it, so no step that changes a work item has to know about timings. The phase is read off the work item's state, in this order: a turn this process runs, then a running call, then a ruling, then the gate it waits at. A stopped runner's time is `other`, a parked item's included, as the maintainer decided on 2026-10-01 for a paused project, since nothing steps it.
- A turn marked running in the state file does not count as the worker's unless this process runs it. The runner keeps the turns it runs in memory, from the step that begins the call until the save that ends it, so no restart inherits one. A turn stopped with the runner is saved to the worker as it stops, and the downtime after it is `other`.
- The runner saves the charge at the start of a step once a work item has gone half a minute without one, so about every minute while the loop idles (it sleeps 60 seconds between steps), and once as it stops. Calls run in flight, so the loop beats while a long turn runs, and a crash or a kill costs only about the last interval to `other`. A beat that cannot save is told and let go, since the next save charges the same time. The save as the runner stops waits for the loop's pass to let go first, and is skipped when it does not, so a shutdown never waits on a pass.
- A local round's wait for the GPU is reported by the reviewer adapter, since it happens inside the call, and counts as `review` like the round after it. A command that queues on the lock itself, as the qwen script does, is watched by polling the lock: a live holder outside the command's own process group is a queue, and the round runs only once its own group holds the lock. Only a command with no lease is watched, on the assumption that it queues on the `gpu` lock as the qwen script does. An endpoint round with no lease has a queue kelpie cannot see, so all of it counts as the round.
- The state file keeps a record per finished work item in `history`, merged or dropped, with its wall time and every phase, and the last 100 of them (Facts). The oldest record goes in the same write that removes the work item. `status` shows each open item's `timings` and the ten most recent records, and `timings [n]` totals the last `n` (10 when left out) as JSON with a plain-text table.

## Where the usage goes

- Every model call is recorded in the control room's units (shep-pm/shep-kelpie#347), so kelpie's cost can be held against what it replaces (Why kelpie exists). The record is the usage ledger, `<kelpie home>/<project>/usage.jsonl`: one JSON object per line, appended and never rewritten. A `call` line is written where the runner hears a call end, so no kind is missed: the worker's turns, every reviewer's sessions and local rounds, the project manager's wakes and `/compact`, and, from `shep kelpie issue`, the issue writer's headless runs. `issue --interactive` is the maintainer's own `claude` session in their terminal, which kelpie starts and does not read back, so it gets no line. It carries the time, the issue (null for the project manager and the issue writer), the pull request once there is one, the role, the kind of call, the agent, harness, model and effort as the call started, the session, the four token counts (with `cache_write_5m`, the part of the cache writes kept for five minutes, where Claude Code reports it), the units, `cost_usd` (the change in the session's cost) or `unpriced`, the session's cost so far, the seconds it took, how it ended (`answered`, `unreadable`, `failed`, `timed-out`, `stopped`), a local round's `gpu_seconds` (from when it began to run, past its queue), and each account's last pacer reading (when it was read, the 5-hour and weekly percent, and when each window resets), where the runner has one: the issue writer's and imported lines have none. A call that never reached a model (its settings could not be written, its harness could not start, its session had never begun) and a local round not run because the model spilled get no line, the stop's lines included. A Codex call whose thread could not be recorded after it ran is a `failed` call, not a setup failure, since the model ran. A call that was stopped, ended past its ceiling, failed, or came back `unreadable` from its harness reports no usage, so its line carries no tokens and the units undercount it (a reviewer's reply that came back but read as no review keeps its tokens); its dollars are not lost, since the next call in the same session costs the change in the session's cost, which takes them in. A call still in flight when the runner stops is told to stop and never heard from, so the stop writes its `stopped` line from the draft it launched with, one append per call inside the stop's bound. The drafts are kept outside the runner's lock, so a pass that has not let go by then holds none of this up, and whichever of the stop and the runner takes a draft first writes its line. A call whose thread panicked is written as `failed` before the panic goes on. A call's line goes in only once its end is saved, since one not saved runs again and its session's cost by then takes in the first call's.
- Units are `input + 2 × one-hour cache writes + 1.25 × five-minute cache writes + 0.1 × cache_read + 5 × output`, rounded to the nearest whole unit: the weights the control room was measured in, with a five-minute write at its price against the hour's. Claude Code reports the split as `usage.cache_creation.ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`; a harness that reports no split counts every write as an hour's. The four counts are kept beside them, so another weighting can be worked out from the same lines. Dollars are kept only where the harness reports them, as for `status`.
- The project manager's session is no work item's, so its call's cost is worked out from the ledger itself: the change from the session's cost on its last written line, read from the file once per runner (again on the next call, if the read failed), so a restart costs nothing twice. A worker's or reviewer's call's cost comes from its work item's record, as `status` has it.
- A finished work item adds a `finished` line: issue, title, pull request, merged, wall time, units and dollars by role and in all, its local rounds and their seconds, review rounds (reviewers' rounds that answered, a second look counted with its first), fix turns (turns sent to fix a round's held findings) and rulings raised. Review rounds count a review bot's read too. Units are each call's own rounded units summed, so the finished line agrees with its call lines. A worker's or reviewer's call that reached its model and reported no usage has no call record, so its work item counts it in `counts` (`worker_unreported`, `reviewer_unreported`), and the finished tally adds those to the role's calls and unpriced calls. The state file's `history` record keeps the same as `spend`, and an open work item counts its rounds, fix turns, rulings and unreported calls in `counts`, which made the state file version 10.
- A ledger that cannot be written fails no call and no step: the runner logs it once, and again only after a write has worked. A line torn by a crash is ended before the next is added, and a reader passes it over, a character cut in half included.
- `shep kelpie usage [<project>] [--since <date>]` reads the ledgers, not the shepherd, and prints, per merged pull request, units, dollars, wall time, rulings and the worker's and reviewers' shares of the units, with their medians, each item's unpriced calls beside its dollars, the dropped work items' total, the project manager's and the issue writer's totals, and the calls of work items with no `finished` line (open, or from before the ledger). It prints plain text only: the verbs that run here rather than as a runner's trigger take no `--json`. `--import <log file>` reads a runner's `ended` and `asked` log lines, the only calls runners logged with their usage before the ledger, into it as `imported` worker turns with no agent, model or duration, matching each line the ledger held before the import began to at most one logged call of the same session within 10 seconds of it, and skipping a line logged twice; two turns of one session that end seconds apart both go in, and one a partial ledger lost is recovered. A log is read lossily, so a bad byte costs only its line.
- To compare with the control room, take units per merged pull request. A baseline is a mean over a window: every unit spent in it, divided by the pull requests merged in it. So `usage` prints a loaded figure the same way, every call's units in its window (the project manager's, the issue writer's and dropped work items' included) over the merged count, and holds each baseline against that first. The median of merged items' own calls is printed too, as the cost of a typical item. Each ratio is kelpie over the baseline, so below 1 is cheaper. Every dollar figure the report prints says how many unpriced calls it leaves out (`$4.20 + 3 unpriced calls`), since a Codex or pi call reports no cost and the sum would otherwise read as complete. The pacer's readings on each line give the week's percent spent between two merges, so allowance per merged pull request can be worked out the same way, within one weekly window: each reading carries when its week resets, and two readings with different resets span a reset, so their percents do not subtract. Baselines such as the control room's are kept on the maintainer's machine only, in `<kelpie home>/baselines/baselines.json`, never in the repo, and `usage` prints each one's units per merged pull request with kelpie's loaded and median figures over it; a missing or unreadable file is skipped.

## Old files

How a table, a state file or a home an older kelpie wrote is read now. The maintainer's own files depend on these.

- A `~/.kelpie` that still holds a project's files from before the home moved, or kelpie's shared files without its `.moved-to` mark, or the dog's old book, refuses the runner or the dog a start, naming the file (shep-pm/shep-kelpie#311): move or delete it, as the message says (shep-pm/shep-kelpie#345).
- A removed key in a project table or kelpie's section is refused at load, every removed key the table carries in one message, each saying what replaces it or to delete it: `ruling_channels` and `models.relay` (the relay); `planning`, `models.planner`, `agents.planner` and `skills.planning` (the planning call); `models.auditor` and `agents.auditor` (the whole-issue check); `models.judge`, `agents.judge`, `review.loop_guard` and `review.local_rounds` (the loop and the judge); `preview` (shots); `models.worker`, `agents.worker` and `models.labels` (now `agents.implementers` and `agent:<name>` labels); `models.reviewer`, `models.deep_reviewer`, `agents.reviewer`, `agents.deep_reviewer`, `review.reviewers`, `review.local`, and the `[models]` and `[review]` tables once nothing is left in them (now `agents.reviewers`, of agent files); `pull_request_reviewers`, `coderabbit.enabled`, `coderabbit.rounds`, `coderabbit.divisor`, `[coderabbit]` and `generated` (now a bot listed in `agents.reviewers`, with `rounds` in its file; `coderabbit.enabled`'s fix shows the project's own reviewers with `coderabbit` added); `skills.review`, which no step drove once reviewers became agent files (a reviewer's prompt is the body of its file). In kelpie's section: `[kelpie.agents.*]` (write each as a file), `[local_reviewers]` and `[reviewers]`. `shep kelpie settings move` is refused by name, saying the settings live in the tables.
- The settings files from before the tables are not read (shep-pm/shep-kelpie#332). With no table the runner stops, and when a settings file an older kelpie read is still there (`<project>/settings.toml` or kelpie's own `settings.toml`, under kelpie's home) the error names it and says kelpie no longer reads it, so its keys go into the table or the section. `doctor` names an old kelpie `settings.toml` the same way. The worker's deny rules for `~/.kelpie/projects`, `~/.kelpie/settings.toml` and `~/.kelpie/totp` stay, since the maintainer's disk still holds those files.
- The state file is version 12: version 12 added the `settling` review stage and the merge ruling's `open_threads` (shep-pm/shep-kelpie#350), and a version 11 file loads as it is. A version 9 file loads with nothing counted on its open work items and no `spend` on its `history` records. An older file loads through `src/state/removed.rs`: its `run` and `since` are dropped, so a project saved paused runs once its runner starts (shep-pm/shep-kelpie#268); a version 1 file's one work item becomes a list of one; the fields of removed features (the relay's, the planning call's `plans`, the whole-issue check's, the review loop's streak, guard, lone-reviewer mark and clean mark, the deep round's later steps, the shots' last run and comment id, a merge ruling's or notice's `shots_failed`) are dropped; the removed timing phases are summed into `review` (`audit`, `judging`, `deep_round`, `gpu_wait`, `local_round`, `claude_round`, `coderabbit_window`, `coderabbit_review`) or `other` (`paused`, `shots`), so every total holds; the `audit`, `judge` and `deep` calls, and the `auditor`, `judge` and `deep_reviewer` roles, count as a reviewer's session's.
- In an older review, `deep` and `claude` are `defect-hunter`, each once, in `reviewer`, `ran`, `last` and `reviewers_skipped`, and a round of `defect-hunter` the pass already ran is not run again; a local reviewer keeps its name; a deep round at its first or second read is `defect-hunter`'s round or second look, and one saved at a confirming or re-check step loads as finished reading (findings not yet sent go to the fix turn, a fix under way goes on, a fix already made ends the entry). A review saved mid-loop goes on as a pass that has run every listed reviewer up to and including the one it last recorded; one from before reviewers were named starts its pass from the top. A round or a bot's review that waited on the judge keeps its findings without verdicts. A state file from before the pass kept its read is taken as read.
- An older bot round is a pass of the bots alone at its stage (waiting for the lease starts that pass afresh, a summon waits on, threads found go to the fix turn with their ids, a fix under way goes on), and a question's or a ruling's bot fix is a fix in that pass. A pending `coderabbit-cap` ruling asks again, its yes sending the threads it held; a pending `coderabbit-silent` ruling becomes a pass of the bots, or is dropped, logged, when it parks no work item. An older item past its review that no bot had read clean owes the listed bots a pass, `bots_after_ci`: its next green CI starts it before the merge, under `auto` too, and a pending merge ruling is withdrawn at the runner's start so CI can, which it logs and posts once. An older adoption's owed summon is owed by each bot listed when the runner starts. The dog's book file is unchanged, so an older one loads with each window's span taken from its bot's file.
- An older work item's worker model loads as an agent name: a Claude model by its label name and effort (`sonnet-high`, `opus-high`, `opus-medium`), a model id no label named by the id itself, and the old local worker's item as `local`. Where kelpie has no agent of that name and the old worker ran a Claude model, the runner's start writes `agents/<name>.md` on Claude Code with that model and effort, never over a file, and logs it (`src/runner/kept.rs`). A local worker's item, or one on another harness's model, cannot be rebuilt from the state, so its next turn fails naming the file to write.
- A pending ruling of a kind folded into `stuck` loads as `stuck` with that kind as its reason, and a `claude-files` one as `agent-files`. In `status` JSON, `kind.reason` on a `rebase`, `merge-refused`, `local-model-spilled` or `turn-failed` ruling used to be the failure's text, and is now the stuck reason, with that text in `why`. A pending ruling of a removed kind (`split`, `split-stuck`, `close-stuck`, `audit`, `review-guard`, `deep-review`) has nothing to answer it, so the file is refused, naming the ruling, to be answered or dropped on the old build first.
- Every change is one way: an older kelpie refuses a newer file, by its version since version 5 and by an unknown field before that, so rolling back means finishing or dropping the open work items first (and clearing `history` to go back before timings). A work item with a pull request in a merge queue saves `merge_queued`, which a runner from before the queue refuses.
- Shots left files kelpie no longer touches: a repo's `kelpie-shots/<number>` branches on the forge, a project's `shots` and `playwright` folders under kelpie's home, and an older install's `tools/browsers`. Each can be deleted by hand.
- A per-item harness file left unsuffixed by an older kelpie is removed as a runner starts, removing a link and never what it points to, and a Codex or pi session in flight across that upgrade starts over with its id, as a session that died unborn does.

## Decided, not built

- Overlapping items are bundled when the combined pull request stays small, and chained otherwise, the next worker in a chain starting from `--fork-session` of the previous worker's last session. Today the board's catch-up with `main` is where an overlap shows, as a conflict that is the worker's next turn, and the project manager may hold an issue whose paths overlap an open branch.
- One work item, one pull request, and every pull request boundary is a reset point. A worker that finds more than one pull request's worth of work would split the rest into chained work items. The motivating case: a shep refactor issue became four pull requests in one session with a huge context, though the pieces barely overlapped. Today the issue writer scopes and splits before a work item exists.
- Conflicts nobody predicted: the item that reaches the gate later rebases after the first merges, and the footprint miss is logged. Serializing instead would be a project setting for small codebases.
- A calculator that reads every call's usage and acts at a phase boundary or a threshold, with an in-turn hook that hands a worker a decision ("delegate the next chunk"), never a cost figure. Which reset is cheaper, and when, is for the work-split tests.
- The pacer setting concurrency and logging utilization per unit by hour of day, so a peak-hour effect, if one returns, shows up in the data. "Do n work items today" once per-item costs are measured.
- The split of a GPU wait into the GPU busy with another round and the GPU idle (shep-pm/shep-kelpie#251), which needs a sample during the wait and new timing phases.
- A failing test a reviewer leaves, run by kelpie before and after the fix in place of a session that asks whether the fix worked (ADR 0006), alongside an execution reviewer.
- Shots and the preview (shep-pm/shep-kelpie#54, #131), parked by ADR 0006: removed, recoverable from git history, not designed out.

## V1 directions

Not built and not decided: where the maintainer wants kelpie to go after the MVP, noted 2026-09-28.

- Names and shape, per the maintainer: `shep-kelpie` stays the shep adapter (the runner, the dog and a library), published as crates. `kelpie` becomes the Tauri app on top of shep and those crates, shipped as an app, never as a crate.
- A kelpie GitHub App. Pull requests would come from its own identity instead of the maintainer's account, so the maintainer can request changes and approve like any reviewer. GitHub refuses both from a pull request's author, which is why #53 reworks on a `ready-for-agent` label. Installation tokens, scoped per repo, replace the maintainer's `gh` token, and the gates show as check runs. Webhooks would replace polling, but kelpie runs on the maintainer's machine, so they need a tunnel. Identity and check runs come first, on polling.
- Any CLI agent, through adapters. Claude Code, pi and Codex are behind the agent port, each inside kelpie's own sandbox, and pacing is per account. What is still Claude-shaped: `attach`, the issue writer and the project manager run on Claude Code alone, and only Claude Code runs a project's `worker.guard_hooks`.
- A spike on Restate (restatedev/restate), a durable-execution engine: journaled steps that resume after a crash, exactly-once calls, durable timers and promises, and single-writer keyed state. The runner hand-rolls that today in its state file and resume logic, and the bugs fixed on 2026-09-28 were that class: a crash between the label call and the save that could summon twice, a review round cut short by a restart recorded as a failure (#46), a lease book lost on restart (#19). A ruling is a durable promise, and the turn ceiling and pacing are durable timers. The spike models one work item's loop as a Restate workflow and measures whether the resume code shrinks and those bugs go away. The costs: `restate-server` is one more process (it could run as a sheep), the tests change shape, and the server is under the Business Source License 1.1, which allows this use (it bars offering Restate as a hosted service). Its Rust SDK is MIT.
- Prior art, checked against each vendor's docs on 2026-09-28. GitHub's Copilot coding agent, Codex, Jules, Cursor's cloud agents and claude-code-action all ship issue to pull request, rework from review comments, and UI screenshots on the pull request. Copilot's Playwright defaults (on by default, localhost only) were the shape #54 followed, now parked. None of them has an ordered gate chain, pacing against a subscription's usage windows, or leases on a shared resource across repos. That is where kelpie's design effort goes.

## Facts

### Headless Claude Code

Measured 2026-09-24 on Claude Code 2.1.282, `--model sonnet`, one sample each. Floor means input plus cache write plus cache read on a trivial prompt.

- Baseline floor 41,012. `--setting-sources ""` gives 22,927, and also drops hooks and plugins. `--strict-mcp-config` with an empty `--mcp-config` gives 36,935. `--disable-slash-commands` gives 36,482. All three together give 26,273. `--tools ""` grows the floor to 91,744.
- `--bare` refuses subscription login. It reads only an API key.
- Two identical fresh calls share the whole prefix: the second reads 41,010 from cache. A different working directory shares only about 10k.
- The first `--resume` onto a fresh session rewrote about 29k of cache in one early probe. Seven runs in the transport series wrote only the new turn (about 5.3k), so it did not reproduce.
- `total_cost_usd` is cumulative across a resumed session. `usage` is per call. Measured again 2026-09-26 on 2.1.283: `modelUsage` is cumulative too, and the top-level `usage` sums every request inside one call. The recorded pair is in `fixtures/`.
- A call killed within its first second leaves no transcript. `--resume` onto it prints "No conversation found with session ID" and exits 1 with no JSON, and `--session-id` can take the same id again. Once a transcript exists, `--session-id` refuses the id as already in use.
- `/compact` works under `-p`. The result carries `local_command: "compact"` and `num_turns: 0`. Context went from 125,122 to 54,484 on the next turn, which wrote a fresh 42.6k cache. `/compact <instructions>` is accepted.
- Plugin skills under `-p`, measured 2026-09-29 on Claude Code 2.1.285 with Haiku 4.5, one sample each. A `--plugin-dir` plugin loads under `--setting-sources project`, and `-p "/<plugin>:<skill> <args>"` runs the skill even with `disable-model-invocation: true`, on a fresh session and on `--resume` alike. Multi-line arguments reach it whole. An unknown skill, or a `--plugin-dir` that doesn't exist, is no error: the call succeeds and the model answers that the command "isn't available". A plugin manifest's `skills` list does not load an absolute path outside the plugin's folder. A copied skill answers to both its folder's name and its `SKILL.md` name.
- Trimming unused features, measured 2026-10-01 on Claude Code 2.1.286 with Sonnet, floor as above, two samples each, identical. A reviewer's settings file (`deny` of `Agent`, `Task` and `Bash`) gives 16,093. The same file with `disableBundledSkills`, `disableWorkflows`, `disableClaudeAiConnectors` and `disableArtifact` set, and the plan-mode, cron, design and worktree tools added to `deny`, gives 9,011: 7,082 fewer on every turn. A bare tool name in `deny` removes the tool's definition, where a scoped rule only blocks the call.
- Two concurrent `--resume` calls on one session both succeed and run one after the other. `--fork-session` gives a new session id and a separate transcript.
- Flags missing from `--help` but present in the binary: `--max-budget-usd`, `--task-budget`, `--autocompact`, `--session-id`, `--resume-session-at`, `--channels`, `--dangerously-load-development-channels`.
- The CLI parses rate-limit data into `five_hour` and `seven_day` windows (plus `seven_day_opus` and `seven_day_sonnet`), each with a utilization and a reset time. `-p --output-format json` does not carry it, stream-json does as `rate_limit_event`, and headless `claude -p "/usage"` reads it for free.

### How messages reach sessions

Read from the desktop app's bundle and the CLI binary, 2026-09-25.

- Desktop app sessions run through the Agent SDK: the app spawns `claude --input-format stream-json --output-format stream-json` and holds its stdin. Its session tools are an in-process SDK MCP server with no socket or port. Sending a message writes a user turn into the target's stdin. An outside program cannot reach a desktop session.
- CLI sessions each register `~/.claude/sessions/<pid>.json` with a messaging socket (`/tmp/cc-socks/<pid>.sock`) and a 0600 peer token file. `SendMessage` is JSON lines over that socket, with an auth line first. The protocol is undocumented.
- `claude agents --json` lists live sessions, interactive and background, with their status. It is meant for scripting and needs no TTY.
- Background sessions: `claude --bg` prints an id that `claude attach`, `logs`, `stop` and `rm` take. `--bg --resume <id>` continues a session in the background.
- An MCP server can push `notifications/claude/channel` into a session, which would wake it. It is gated per organisation and off on Bedrock and Vertex.
- A socket message wakes an idle background session, about 5 seconds, 3 times out of 3. It arrives framed as a message from another Claude session.

### Usage limits

- Weekly limits were never tied to time of day. Anthropic announced in March 2026 that 5-hour limits drain faster on weekdays between 5 and 11am PT. Secondary sources report that was removed for Claude Code on Pro and Max on 2026-05-06.
- `/usage` reports the share of usage spent while four or more sessions ran in parallel, and says queueing uses the shared limit more evenly. Parallelism is about timing against the 5-hour window, not a surcharge.
- Headless `/usage`, measured 2026-09-26 on Claude Code 2.1.283 (recorded in `fixtures/usage-result.json`): `total_cost_usd` 0, `num_turns` 0, `local_command: "usage"`, about 1.5 to 3 seconds. The `result` text has one line per window, `Current session: 2% used · resets Sep 27 at 3:40am (America/New_York)`, and a `Current week (all models)` line beside per-model ones (`Current week (Fable)`). Percentages are whole numbers.
- Reset times carry no year and are rounded to the minute. The same weekly reset printed as `Sep 25 at 10:59pm` on two reads and `Sep 25 at 11pm` on a third, so a weekly reset that moves by under an hour is the same week. A reset later today may print as time only.
- `--setting-sources ""` and `--no-session-persistence` both leave `/usage` working, so the read runs none of the maintainer's hooks and writes no transcript.

### The local model's placement

Built in shep-pm/shep-kelpie#145, after a model loaded on the CPU instead of the GPU ran review-sized prompts at a twentieth of normal speed on 2026-09-29 and nothing noticed for 14 minutes.

- Ollama's `GET /api/ps` lists each loaded model with its `size` and `size_vram` in bytes, its `context_length` and its `expires_at`. A model is on the GPU when `size_vram` equals `size`, and `size_vram / size` is the share on it. Recorded shape: `fixtures/ollama-ps.json`, written by hand from Ollama's documented response, since the maintainer's host did not answer from the worker's sandbox.
- It cannot say how busy the GPU is: there is no utilization, so a model on the GPU that another round is using looks the same as an idle one. That is the GPU metrics ticket's job, not this check's.
- It lists only loaded models. A model not loaded yet is not checked, and the check cannot say where it will go when the round's first request loads it. A model that loads spilled in the middle of a round is not caught until the next round.
- Kelpie reads `/api/ps` only where it holds the GPU lock around the round (a reviewer whose file names a `lease`; `gpu_lease = true` when this was built), after taking it and before the round. Without the lock the read races whoever holds it: it would rule on another session's spill that a round would have queued behind, and could pass just before the holder reloads the model spilled. The default command round, `qwen-review.sh`, takes the lock itself, so it is not checked, and `ollama` on a command without a `lease` is refused when the settings load, with that reason. An endpoint with no `lease` is skipped the same way. The host is the endpoint's `url` without `/v1`, or the command's `ollama`. A command names its model with `ollama_model`, and only that model is checked. Without it every model the host has loaded is looked at, and one spilled for another reason fails the round, and each yes runs into it again until it unloads (two hours by default). Model names match without regard to case. A model partly or wholly on the CPU fails the round without running it, and raises a ruling that says which model and how much is on the GPU, so it reaches the maintainer's webhook. A yes runs the same round again. A 404, or a reply that is not `/api/ps`'s, means the server is not Ollama and skips the check. A reply that lists models with no readable `size` is Ollama-shaped, so the runner logs how many were left unchecked. A host that cannot be reached fails the round, and the runner retries it as any failed round.
- `status` shows `local_model` from the last read: the name, the percent on the GPU, the context length and when it unloads. It is absent until a round has read one, and it is the last round's view, not live.

### The shep surface kelpie leans on

- `Request::Trigger` becomes an `action` message on a sheep's shepherd channel (fd 3), answered with an `action-reply`. `ready`, `metric` and `action-reply` are all republished on the bus as `channel.*`.
- `SendLine` (`shep whisper`) writes one line to a sheep's stdin.
- A lamb is a pid and an executable name, found by walking the process tree, never argv. The stop ladder kills the process group.
- On shep up to 0.12.3, a sheep with `shutdown_with_message` that exits on the message never reaches the stop ladder, so its lambs are orphaned. Seen 2026-09-26: `shep restart` left the worker running beside the resumed one. Until shep-pm/shep-kelpie#319 the runner stopped its `claude` children itself before it exited: SIGTERM, then SIGKILL after 3 seconds.
- Shep has two stop caps. `kill_timeout` (1.6s by default) covers `stop`, `restart`, `delete`, the daemon's own automatic restarts and the engine-wide shutdown. `graceful_timeout` (8s) covers only a reload's drain. Read from shep's source (`LadderCap` in the supervisor's reload module and the defaults in the app behavior config) on 2026-09-28, not measured. With `shutdown_with_message`, a sheep still running when `kill_timeout` runs out gets SIGKILL on its process group (`kill_process` in shep-daemon's `kill.rs`, read 2026-10-06). A runner's stop with its own ladder needed about 7s, so entries carried `kill_timeout = "10s"`; without the ladder it fits the default.
- shep 0.12.4 sweeps a sheep's lambs after its leader exits, on every stop and crash (shep-pm/shep#688, shep-pm/shep#691): it walks the ppid tree, SIGTERMs what is left, waits up to `kill_timeout` and SIGKILLs the rest, whatever group or session each is in. Measured 2026-10-06 with `a_stop_of_a_runner_leaves_none_of_its_lambs_running` in `tests/dog_smoke.rs`, on macOS: a stand-in runner with `shutdown_with_message` left two lambs that ignore SIGTERM, one leading a process group and one a session (`setsid`), and exited on the message. Under a shep 0.12.4 shepherd both were gone after `shep stop`; under 0.12.1 both were still running 15 seconds later.
- shep 0.12.4's sweep finds lambs by walking parent pids from the sheep, so a member of a call's process group that was reparented to init before the stop (`nohup devserver &` from a shell that has exited) is not swept. The runner's SIGTERM to each call's group reaches it, so one that ignores SIGTERM can outlive the stop. Read from shep-pm/shep#691's description on 2026-10-06, not measured.
- A dog is an ordinary sheep with a marker. Wildcard selectors never touch a dog. A dog's `--schema` feeds lookout's settings pane.

### `shep kelpie upgrade`

Built for shep-pm/shep-kelpie#143. Before it, an upgrade was a sequence of hand steps (build, copy, sign, relink, restart the runners between steps and, for a new shep minor, save, kill and muster the shepherd), and on 2026-09-29 one of them deleted the dog's sheep until it was restarted by hand.

- The maintainer's install-layout call (2026-10-01) is to do it the way shep upgrades itself, with no link and no re-adopt. The installed kelpie is whatever program the adopted dog runs, read from the shepherd (`~/.cargo/bin/shep-kelpie` for the README's install), and a runner started by `shep kelpie add` runs the same path. `shep kelpie upgrade --ref <git ref>`, `--release <version>` or `--binary <path>` writes the new build beside that file and renames it over, so the running file's bytes are never edited in place and the fresh inode needs no re-signing by the system. On macOS a Mach-O copy is still signed ad hoc (`codesign --force --sign -`) before the rename; a script (the tests' stand-in builds) is not.
- Before the swap the file it replaces is copied into `<kelpie home>/builds/shep-kelpie.previous`, resolved if the installed path is a symlink: the link stays a link, its target gets the new build, and the copy is a regular file of the old bytes. `--rollback` stages that copy beside the installed file and renames it over the same way, keeping the build it replaced as the previous, so a second rollback undoes the first. Running the same build again changes no file, so finishing an upgrade that stopped part way does not push the real previous build out.
- Measured 2026-10-01 on the maintainer's macOS: a cargo-built binary (`Signature=adhoc`, linker-signed) copied with a plain `cp` to a new path ran `version --json` with no `codesign` run on the copy. The signing step stays for a release build that is not linker-signed; this run did not measure one.
- Every sheep the upgrade restarts must run the dog's path, since a restart cannot move a sheep onto another binary. One that does not stops the upgrade before a file changes or a sheep restarts, naming the sheep and its path. A stopped sheep on another path does not block it, and is said to stay behind.
- A build says which shep it is made with through `shep-kelpie version --json` (`{ "kelpie": ..., "shep": ... }`, the second being `SHEP_VERSION`). The upgrade runs it on a staged copy of the new build, with a 20s limit that kills a build that hangs and a refusal of a non-zero exit, and compares it with the shepherd's version: the same minor, at the build's patch or later, as a runner checks (shep-pm/shep-kelpie#319). The shepherd's is read through a connection that does not apply the running kelpie's own pin, since a kelpie on the old minor must be able to install a build for the new one after the shepherd moved. A difference stops the upgrade before a file changes or a sheep restarts, and the message says which side to move: a build for a newer shep than the shepherd's means upgrade shep and reload its shepherd, then run the new build's own `upgrade` (printed with the build's path, since the old installed kelpie refuses the new shepherd); an older one means install a kelpie built for the shepherd's line. The same check gates `--rollback`. A previous build from before `version --json` cannot answer it: the rollback goes ahead and says the minor is unchecked.
- `--binary` given a file without its executable bits is refused, naming the `chmod +x` that fixes it. Two upgrades at once are refused by a lock file, `<kelpie home>/upgrade.lock`, holding the pid of the upgrade that took it. A lock left by a process that is gone is taken over.
- Restarts go dog first, since every runner asks it for leases, then each runner in name order, one at a time. A sheep restarts only when its `status` shows no work item in `merge`, or in `done` with its pull request merged, and the dog only when no runner has one. A `status` that shep delivered and that timed out is not an answer of no merge: shep reports it as `TimedOut`, apart from a sheep that is not running, and the upgrade waits on it like a merge. It asks again every 500ms for up to an hour, saying what it waits on, then fails naming the runner and restarts nothing for it. A restarted sheep must answer `status` in 60s before the next goes down. A merge can still begin between a `status` and the restart that follows; the runner's own stop lets the step in flight finish first. A sheep that is stopped stays stopped and starts on the new build. The flock is read again after the build and right before each restart, because the wait can last an hour: a runner stopped meanwhile stays stopped (reproduced with a probe in review before the fix). A `Starting` sheep counts as running; an `Errored` or `WaitingRestart` one is left alone and named.
- Since shep-pm/shep-kelpie#335 an upgrade drains each runner before its restart, since a stop ends every call in flight (by design since shep-pm/shep-kelpie#319) and the work item then resumes from its session, losing the turn in progress and anything uncommitted. A runner's `drain` trigger holds back every call it would start next: a worker's turn, a reviewer's session or local round, and the project manager's wake. The rest of each pass goes on, so a merge in flight finishes, CI is read, a bot is summoned (it reviews on the forge, where a restart does not cut it short) and the board may open a work item whose first turn then waits. `drain` answers the status with a `draining` object: `calls`, those still running (`{"issue": 7, "role": "worker"}`, `"reviewer"`, or `{"role": "pm"}`), and `ceiling`, the turn ceiling in seconds, or the project manager's 10 minutes when longer. Draining lives in memory only, so a restart ends it, as `undrain` does, and the state file does not change. The upgrade drains a runner after the dog's restart and before that runner's merge wait, asks `drain` again every 500ms until no call runs, saying what it waits on, then runs the merge wait as before and restarts it. A drained runner starts no call, so the two waits in turn reach a moment with neither. The wait for calls is bounded by the ceiling plus a 5-minute margin, counted from when the wait began; until the runner first answers, it is `patience.merge`, as for a runner that does not answer `status`. The bound is not a guarantee: a turn's ceiling counts from when it got the lease it waited for, and a reviewer's session has no ceiling at all, only the margin past the turn ceiling, so either can outrun it. Past it the runner is sent `undrain` and named, and stays on the old build with nothing restarted for it. Any other way out while a runner drains sends `undrain` too: a merge wait that runs out, a failed restart, a shepherd error, and a Ctrl-C or SIGTERM, which the upgrade listens for from the first runner's drain on. Only a shepherd it cannot reach leaves a runner drained, so each drain prints `shep kelpie undrain -p <project>` as it starts, and `shep kelpie status` marks a draining runner `(draining)`. Runners drain one at a time, so the next keeps working while the one before it drains. A runner from before `drain` answers it with shep-channel's plain `unknown action` while it answers `status`. A runner still opening its channel can do the same once, so the upgrade asks `drain` again after a `status` that answered, and reads a second plain answer as an old build: it says the restart cuts its calls short and restarts it as before. `--now`, first or last among the arguments, skips the drain and keeps the merge wait. The dog is never drained, since the calls are its runners'.
- A failure after the swap leaves the new build installed, and the error says so with the command that finishes the restarts, `upgrade --binary <installed path>`, which finds the bytes equal, moves no file and restarts. A `--rollback` run again would swap the builds back instead. The same line prints before the restarts, so a Ctrl-C leaves it on screen. `--rollback` goes ahead without a minor check only for a previous build that ran and exited 2 on `version`; one that cannot start, hangs or dies is refused.
- Not done: the runner's stop can still cut a merge that begins between the idle `status` and the restart (`JOIN_BOUND` is 2s), and the lock's stale take-over checks and then acts.
- `--ref` keeps a clone of the repo in `<kelpie home>/upgrade/source` (`KELPIE_SOURCE` names another repo than shep-pm/shep-kelpie), checks out the remote's branch, tag or commit detached, and runs `cargo build --release --locked` with its own `CARGO_TARGET_DIR`. Measured 2026-09-30: a nested cargo that inherits the maintainer's `CARGO_TARGET_DIR` puts the binary there, not in the clone's `target`, and the build reported success with no file where kelpie looked.
- `--release <version>` runs `gh release download v<version>` for the asset `shep-kelpie-<arch>-<os>.tar.gz` (`aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`) and unpacks `shep-kelpie` from it. This repo has no release workflow yet, so the asset name is a decision and not a measurement; the build inside must say it is that version or nothing is installed.

## Test series

In order: transport, model calibration, work split, then code. Each series gets its own spec when it starts.

### Transport

- T1: `claude -p --resume`, one process per turn. The measured baseline.
- T2: a long-lived `claude --input-format stream-json --output-format stream-json` worker, held by a project runner.
- T3: `claude --bg` plus socket messages, attached with `claude attach`. Needs a permission rule for reading the target's peer token.
- T4: kelpie-served tools. In-process MCP over the stream-json control protocol, against a small stdio MCP binary that relays to kelpie over shep.
- T5: MCP channel push, if the account has channels.
- Lease round trip, runner to dog: a "wants" metric, then `status` and `grant` triggers, against a direct `shep trigger` to the dog if that reaches one. Latency, a dropped metric, and reclaim when a runner dies holding a lease.
- Rate limits: whether stream-json carries the utilization windows.

Measure each: cache write and read per turn, wake latency on an idle worker, a 100 KB output line through the runner, recovery after a crash, subscription auth, and whether the maintainer can take a worker over.

### Model calibration

Extend the maintainer's local model-calibration harness, which has only scored local models, to Opus, Sonnet, Haiku and Fable at two or three effort levels each. Reviewer and checker roles reuse its frozen sets: planted bugs, real false findings, and clean diffs for false alarms. A new implementer set of small shep specs with hidden tests scores tests passing, review findings, units and wall clock.

### Work split

Run the same real work items as inline, inline with compaction, a phased chain with handoffs, a crew of subagents working from an implementation doc, and agent teams (only if a long-lived transport wins, since teams do not spawn under `-p`). Run each with and without codebase-memory-mcp.

The model to fit: one session's cache reads grow with the square of its length. Splitting it into k pieces cuts reads about k times and adds a fixed cost per piece, so the best k is about √(0.025 × calls × growth ÷ per-piece cost). Worked example with guessed inputs (150 calls, a 41k floor, 500 output tokens a call): inline to 650k is about 6.9M units, three quarters of it cache reads; five phases, each with a 10k handoff and 30k of re-reading, is about 4.6M. The tests measure the real inputs.
