# The shep surface kelpie leans on

- `Request::Trigger` becomes an `action` message on a sheep's shepherd channel (fd 3), answered with an `action-reply`. `ready`, `metric` and `action-reply` are all republished on the bus as `channel.*`.
- `SendLine` (`shep whisper`) writes one line to a sheep's stdin.
- A lamb is a pid and an executable name, found by walking the process tree, never argv. The stop ladder kills the process group.
- On shep up to 0.12.3, a sheep with `shutdown_with_message` that exits on the message never reaches the stop ladder, so its lambs are orphaned. Seen 2026-09-26: `shep restart` left the worker running beside the resumed one. Until shep-pm/shep-kelpie#319 the runner stopped its `claude` children itself before it exited: SIGTERM, then SIGKILL after 3 seconds.
- Shep has two stop caps. `kill_timeout` (1.6s by default) covers `stop`, `restart`, `delete`, the daemon's own automatic restarts and the engine-wide shutdown. `graceful_timeout` (8s) covers only a reload's drain.
  - Read from shep's source (`LadderCap` in the supervisor's reload module and the defaults in the app behavior config) on 2026-09-28, not measured.
  - With `shutdown_with_message`, a sheep still running when `kill_timeout` runs out gets SIGKILL on its process group (`kill_process` in shep-daemon's `kill.rs`, read 2026-10-06).
  - A runner's stop with its own ladder needed about 7s, so entries carried `kill_timeout = "10s"`; without the ladder it fits the default.
- shep 0.12.4 sweeps a sheep's lambs after its leader exits, on every stop and crash (shep-pm/shep#688, shep-pm/shep#691): it walks the ppid tree, SIGTERMs what is left, waits up to `kill_timeout` and SIGKILLs the rest, whatever group or session each is in.
  - Measured 2026-10-06 with `a_stop_of_a_runner_leaves_none_of_its_lambs_running` in `tests/dog_smoke.rs`, on macOS: a stand-in runner with `shutdown_with_message` left two lambs that ignore SIGTERM, one leading a process group and one a session (`setsid`), and exited on the message. Under a shep 0.12.4 shepherd both were gone after `shep stop`; under 0.12.1 both were still running 15 seconds later.
- shep 0.12.4's sweep finds lambs by walking parent pids from the sheep, so a member of a call's process group that was reparented to init before the stop (`nohup devserver &` from a shell that has exited) is not swept. The runner's SIGTERM to each call's group reaches it, so one that ignores SIGTERM can outlive the stop. Read from shep-pm/shep#691's description on 2026-10-06, not measured.
- A dog is an ordinary sheep with a marker. Wildcard selectors never touch a dog. A dog's `--schema` feeds lookout's settings pane.
- A sheep under the pinned shep 0.10.1 starts with only `HOME`, `LANG`, `PATH`, `USER` and its `SHEP_*` variables, read with `ps eww` on 2026-09-26. `TMPDIR` and `SHEP_HOME` are not among them, though the shepherd itself has both.
  - So `${TMPDIR:-/tmp}` names `/tmp` under the shepherd and macOS's per-user temporary folder in the maintainer's shell: two different GPU locks.
  - Kelpie falls back to `getconf DARWIN_USER_TEMP_DIR`, the folder macOS sets `TMPDIR` from at login, and whatever runs a qwen script for kelpie must pass it on as `TMPDIR`.
- shep emits `restart` after the new process is spawned, with the new pid in its info (read from shep-daemon 0.10.0's `actor_lifecycle.rs`). A crash that will restart emits `exit` first.
- Kelpie's lease round trip through the pinned shepherd, three runs of `tests/dog_smoke.rs` on 2026-09-26: want to grant 1, 6 and 11 ms, and a SIGKILLed holder to the next grant 8, 11 and 9 ms.
- A dog restarted with `shep restart kelpie` while a runner held a lease came back with the same book and made no second grant, and one stopped while the holder restarted reclaimed its lease on start: three runs of `a_restarted_dog_keeps_its_book` in `tests/dog_smoke.rs` on 2026-09-27, each under a second. The same test fails with the book load taken out.
- `shep trigger <sheep> <action> [params]` takes params as one argument, passed through verbatim (read from shep 0.10.0's `cli/sheep.rs`). So an answer with more than one word is quoted: `shep trigger webapp rule '3 no rename the flag'`. Unquoted, clap refuses the extra arguments.
- A test that writes a script and runs it at once fails on Linux about once in 80 runs, with `Text file busy (os error 26)` (ETXTBSY): a child another test forks while the file is still open for writing holds it, and `exec` of the file fails.
  - Measured 2026-09-28 in a `rust:latest` container, the unit tests run 40 times at 16 threads: 1 failure in 80 runs on `main` (a fake `claude`), none in 80 with the fix.
  - The fix is `crate::test::write_script`, which runs the script once with `KELPIE_TEST_PROBE` set, retrying on ETXTBSY, before a test uses it. The binary's own tests run the fake `shep` as `sh <script>`. Renaming the file into place does not help, because the child still holds the same inode.
- An adopted dog, measured 2026-09-29 on a scratch home with the pinned shep 0.10.1 and a probe script that records its argv, environment and open descriptors (shep-pm/shep-kelpie#110): kelpie's dog, which answers `status`, `take` and `return` as triggers, cannot be an adopted dog on 0.10.1.
  - `shep adopt <path> --name probe` ran the binary with `--version` and then `--schema` before recording it.
  - Started by the shepherd after `shep enable probe`, it got no argv, `SHEP_HOME`, `SHEP_DOG_NAME=probe`, `SHEP_NAME=probe`, `SHEP_INSTANCE` and `SHEP_ENVIRONMENT`, and no `SHEP_CHANNEL_FD`: fd 3 was not the channel. So it cannot answer a trigger: `Request::Trigger` on it came back `NoChannel`.
  - `SetSheepField` on it, to set `channel`, was refused ("probe is a dog, and a dog's config comes from `shep adopt` rather than from a Flockfile"), and a new shepherd started it the same way.
  - Run as `shep probe hello world`, it got `hello world` as its argv, the caller's working folder and whole environment, plus `SHEP_HOME` and `SHEP_DOG_NAME`, and no `SHEP_NAME`.
- Same day: an adopted dog left disabled and a sheep of the same name live side by side. With `probe` adopted and disabled, a Flockfile sheep named `probe` with `channel = true` started, and `shep probe from-cli` still ran the adopted binary with that argv. `shep enable probe` then refused: "a sheep is already registered as `probe`; rename it or give the dog another name".
- The same on shep 0.11.0, measured 2026-09-29 on a scratch home for shep-pm/shep-kelpie#110: an adopted dog still starts with no channel, and a trigger on it comes back `NoChannel`.
  - Adopted and disabled, it lives beside a channel sheep of its name, and `shep probe <args>` still runs the adopted binary.
  - `shep disable probe` run while that sheep was up deleted the sheep, and the control session saw the same on kelpie's own shepherd, where `shep adopt --name kelpie` was also refused while a sheep named `kelpie` ran. A new shepherd brought the sheep back from the muster roll and left the dog disabled.
- An adopted dog with the channel, measured 2026-09-30 on a scratch home with shep built from shep-pm/shep's merge commit 9f96113 (#657, released as 0.12.0) and this branch's build, in `tests/dog_smoke.rs` (shep-pm/shep-kelpie#180).
  - `shep adopt <kelpie> --name kelpie` read `shep-channel: true` and started kelpie with the channel: its flock row is `DogSource::Adopted { channel: true }`, it stayed online with no restarts, and `shep kelpie lease take`, `status` and `return` reached it as `kelpie`. `shep restart kelpie`, `disable` and `enable` all bring it back on its saved book.
  - shep gives an adopted dog only `HOME`, `USER`, `LANG`, `TZ` and `PATH` from its own environment, plus its `SHEP_*` variables (`crates/shep-daemon/src/assemble/environment_inheritance.rs`), so the dog's book is `$HOME/.kelpie/dog/book.json` whatever `KELPIE_HOME` a shell sets, and its GPU lock is under the user's own temp folder, as a runner's is.
  - `Delete` on a sheep answers once it has exited, so a left-over `kelpie-dog` removed by the adopted start never writes the book after the dog opens it: with the maintainer holding a lease, the book file was byte for byte the same after the move, and the dog answered with the maintainer as holder.
- The adopted dog's handshake, measured 2026-09-30 with shep 0.12.0 in `tests/dog_smoke.rs` on a scratch home (shep-pm/shep-kelpie#189).
  - shep lists a dog `silent` until a connection names it in the handshake, and `ProcessInfo::handshook` is the fact, with `dog_stale` for a dog it has restarted once and given up on.
  - The dog's two connections now use `ReconnectingClient::connect_as` with `SHEP_DOG_NAME`: the flock row shows `handshook: Some(true)`, `dog_stale: Some(false)` and no restarts. With the name taken out of the handshake the same test timed out at its 10s wait for the dog to answer.
  - A bus stream ends with its connection and is not re-armed by the reconnect, so the dog subscribes again and reads the flock when its stream ends, and exits only when the new shepherd refuses it or stays away for 30s.
  - `shep kelpie doctor` has a `dog` line, and `start` and `add` refuse a silent dog, both from the row's `handshook` and `dog_stale`.
- `shep kelpie add|start|status|pause` end to end, measured 2026-09-29 with this branch's build on a scratch shepherd (shep 0.11.0) and a scratch kelpie home, on a clone of the public scratch repo shep-pm/kelpie-scratch, whose three labels were already there and whose board was empty.
  - `add` found the labels, registered the runner and `kelpie-dog` stopped, and a second `add` changed nothing.
  - The first `start` came back `unknown action: start` from a runner still opening, which is why `start` waits, and then `cannot write state file ...: entity not found`, since the project had no folder.
  - With both fixed, `start` answered `"run":"running"`, `status` listed the project, and `pause` answered `"run":"paused"`. `shep kelpie lease status` reached `kelpie-dog`. A new shepherd brought both sheep back up.
  - shep 0.11.0 refuses a trigger on a name no sheep has with `NotFound` ("selector matched no registered sheep"), never an empty list of replies, so `kelpie lease` reads that as the cue to ask the old name `kelpie` (the control session's review; `a_dog_still_named_kelpie_answers_the_lease_commands` in `tests/dog_smoke.rs` fails without it).
  - On the same harness, `the_dog_moves_to_kelpie_dog_with_its_book_and_frees_the_name`: with a runner holding a lease from a dog named `kelpie`, `shep adopt --name kelpie` was refused, the move left `kelpie-dog` running with that runner still the holder, and the adopt then went through.
  - Against a scratch shep 0.8.2 shepherd, `kelpie status` refused: "runs shep 0.8.2, and kelpie is built for shep 0.11.0 and takes only a 0.11.x shepherd".
- Kelpie's tables on shep 0.11.0, measured 2026-09-29 on a scratch shepherd home with two throwaway runners on this branch's build (shep-pm/shep-kelpie#114), never kelpie's own:
  - A runner reads its `[app.dogs.kelpie]` table at start with no notice, and one with no table loaded its old file and logged the notice naming `kelpie settings move` (both removed since, #332).
  - A table edited in the Flockfile and applied with `shep start --reset=file` reached the running runner without a restart: same pid, and `settings changed: merge_authority now in effect` in its log 10s later, at its next board look. A plain `shep start` of the edited file changes nothing for a sheep already running.
  - `kelpie settings move` wrote the table, and a second run found it equal, so shep hands a table back as it was written. After a restart the runner logged no notice.
  - shep refuses `SetDogConfig` for a dog it does not know (`NotFound: no dog named kelpie`), so the `[kelpie]` section moves only once kelpie is adopted.
  - `shep adopt <kelpie> --name kelpie` read kelpie's `--version` and `--schema` answers with no `dog_schema_unreadable` notice, and also started it, with no arguments. That start exits 2 and waits to restart, so `shep disable kelpie` follows the adopt: lookout lists adopted dogs whether enabled or not. `SetSheepDogSettings` marks the sheep's config overridden (`*1` in `shep flock`'s `CFG` column).
- shep 0.11.0 shipped both of kelpie's asks: shep-pm/shep#623 (an opaque per-dog settings table on a sheep) and shep-pm/shep#624 (a sheep labels its own lambs).
- A runner refused by the old-home guard crash-looped under shep's default restart policy (live smoke, shep-pm/shep-kelpie#344): 14 restarts in 30 seconds, each logging the same refusal, with `max_restarts` 16 and a backoff that starts at 100 ms and grows by 1.5 to a cap of 15 s (shep-core 0.12.4's `AppConfig` docs).
  - `stop_exit_codes`, a list of exit codes that shep treats as a clean stop with no restart, is the lever shep gives, and the runner entry sets it to `[78]` for the refusal's exit code (shep-pm/shep-kelpie#345).
  - Read from shep-core 0.12.4's config and pinned by a test on the entry kelpie writes; not yet run against a live shepherd.
- shep's protocol across releases, read 2026-10-22 from the published crates and shep's source (ADR 0016):
  - `PROTOCOL_VERSION` is 11 in shep-core 0.15.0, 0.15.1, 0.15.2 and 0.16.0. `MIN_SUPPORTED`, the oldest protocol a shepherd accepts, is 8.
  - A shepherd refuses a client only below `MIN_SUPPORTED` (`crates/shep-daemon/src/server/conn_protocol.rs` in shep), so it takes a newer client. Its `HelloAck` carries `protocol` and `min_supported`, and shep-client refuses no shepherd on its own.
  - The same day `shep kelpie finish` refused a shep 0.16.0 shepherd: "kelpie is built for shep 0.15.0 and takes only a 0.15.x shepherd from 0.15.0 on".
  - `PROTOCOL_VERSION` is 12 in shep-core 0.17.0, with `MIN_SUPPORTED` still 8 (read 2026-10-25). Kelpie's pin moved to 0.17.0 and its floor with it, so a 0.16 shepherd is refused as one before the floor.
- shep-channel 0.17.0 runs each action handler on a thread of its own (shep-pm/shep#1071), read 2026-10-25 from its source (`loops.rs`, `lib.rs`):
  - Up to 32 handlers run at once. Past that, and for a shutdown, the reader answers on its own thread. Each reply carries the id of the action it answers, so replies land on the right trigger in whatever order the handlers finish. `action_timeout` (3s by default) is still one handler's budget.
  - Before it, one reader thread ran every handler, so a trigger that waited on the runner's lock held `status` behind it. `status` is still answered from the posted copy while a pass holds the lock: a thread of its own would wait on the same lock.
  - shep-channel's own test `a_fast_action_is_answered_while_a_slow_one_is_still_running` holds the property. `shep-client`'s stand-ins fake the shepherd's socket, never the channel to a sheep, so kelpie's test is the runner's: `status` sent after a trigger that waits for the pass's lock is answered at once.
- shep 0.17.0 `DogSource` carries a dog's `grants` (`None` for a dog that declared nothing, which keeps full access), read 2026-10-25. Kelpie's `Probe` declares no permissions, so its dog stays undeclared; declaring them is a separate ask.
- An adopted dog's `env` reaches it only when `shep enable` spawns it, seen 2026-10-28 on shep 0.19.0 (shep-pm/shep#1295). `shep daemon reload` re-reads `shep.toml` and leaves the dog running on its old env, and a restart through the shepherd keeps it too. The env's `{{secret:...}}` values resolve at that enable, which refuses a name the store lacks and leaves the dog stopped.
- A dog's section and secrets, read 2026-10-23 from shep-client 0.16.1's source (shep-pm/shep#1075):
  - `Client::dog_config` asks `DogConfigResolved`, so a `{{secret:...}}` in the section arrives resolved. Plain `DogConfig` returns the text as written.
  - Against a shepherd that does not know `DogConfigResolved` it falls back on `DogConfig`, and refuses a section that still holds a reference with `RpcErrorCode::Unsupported`.
  - Kelpie reads its `[kelpie]` section through it, in the runner (`shepherd::read_section`) and in the dog (`settings`). Run against a stand-in daemon that answers the two requests differently, not yet a live shepherd.
