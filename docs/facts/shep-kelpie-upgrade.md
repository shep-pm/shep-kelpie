# `shep kelpie upgrade`

Built for shep-pm/shep-kelpie#143. Before it, an upgrade was a sequence of hand steps (build, copy, sign, relink, restart the runners between steps and, for a new shep minor, save, kill and muster the shepherd), and on 2026-09-29 one of them deleted the dog's sheep until it was restarted by hand.

- The maintainer's install-layout call (2026-10-01) is to do it the way shep upgrades itself, with no link and no re-adopt.
  - The installed kelpie is whatever program the adopted dog runs, read from the shepherd (`~/.cargo/bin/shep-kelpie` for the README's install), and a runner started by `shep kelpie add` runs the same path.
  - `shep kelpie upgrade --ref <git ref>`, `--release <version>` or `--binary <path>` writes the new build beside that file and renames it over, so the running file's bytes are never edited in place and the fresh inode needs no re-signing by the system.
  - On macOS a Mach-O copy is still signed ad hoc (`codesign --force --sign -`) before the rename; a script (the tests' stand-in builds) is not.
- Before the swap the file it replaces is copied into `<kelpie home>/builds/shep-kelpie.previous`, resolved if the installed path is a symlink: the link stays a link, its target gets the new build, and the copy is a regular file of the old bytes.
  - `--rollback` stages that copy beside the installed file and renames it over the same way, keeping the build it replaced as the previous, so a second rollback undoes the first.
  - Running the same build again changes no file, so finishing an upgrade that stopped part way does not push the real previous build out.
- Measured 2026-10-01 on the maintainer's macOS: a cargo-built binary (`Signature=adhoc`, linker-signed) copied with a plain `cp` to a new path ran `version --json` with no `codesign` run on the copy. The signing step stays for a release build that is not linker-signed; this run did not measure one.
- Every sheep the upgrade restarts must run the dog's path, since a restart cannot move a sheep onto another binary. One that does not stops the upgrade before a file changes or a sheep restarts, naming the sheep and its path. A stopped sheep on another path does not block it, and is said to stay behind.
- A build says which shep it is made with through `shep-kelpie version --json` (`{ "kelpie": ..., "shep": ... }`, the second being `SHEP_VERSION`).
  - The upgrade runs it on a staged copy of the new build, with a 20s limit that kills a build that hangs and a refusal of a non-zero exit, and compares it with the shepherd's version: the same minor, at the build's patch or later, as a runner checks (shep-pm/shep-kelpie#319).
  - The shepherd's is read through a connection that does not apply the running kelpie's own pin, since a kelpie on the old minor must be able to install a build for the new one after the shepherd moved.
  - A difference stops the upgrade before a file changes or a sheep restarts, and the message says which side to move: a build for a newer shep than the shepherd's means upgrade shep and reload its shepherd, then run the new build's own `upgrade` (printed with the build's path, since the old installed kelpie refuses the new shepherd); an older one means install a kelpie built for the shepherd's line.
  - The same check gates `--rollback`. A previous build from before `version --json` cannot answer it: the rollback goes ahead and says the minor is unchecked.
- Since shep-pm/shep-kelpie#1260 each build names the commit it was made from.
  - `crates/core/build.rs` runs `git rev-parse --short=7 HEAD` and `git --no-optional-locks status --porcelain --untracked-files=no` in the crate's own folder and bakes the answer in as `KELPIE_COMMIT`: seven characters, with `-dirty` on the end when a tracked file holds changes that commit does not. `--no-optional-locks` keeps the status call from taking the index lock a git command run beside the build is holding. Untracked files are left out because they are not what a build compiles: a new file reaches the build only through a tracked one, and that tracked file is watched and counted.
  - Measured 2026-10-25 in this repo. A build script is rerun only for the paths it lists, so the script lists what its dirty check inspects: `build.rs`, `git rev-parse --git-path HEAD`, `git rev-parse --git-path <branch>`, and every entry `git ls-tree --name-only HEAD` tracks at the top of the checkout, which cargo scans as a directory for any change inside it. Editing `src/main.rs`, a file under `crates/`, or a file under `docs/`, and rebuilding moved the baked value from `c613b60` to `c613b60-dirty` and the built binary's own answer to `shep-kelpie 0.0.0+c613b60-dirty`; undoing the edit, and deleting and restoring a tracked top-level file, moved it back. Listing only `build.rs` and the two refs left it put, which is how a build from a tree with edits reported the clean commit. A branch whose ref is packed into `packed-refs` has no loose file to watch, and cargo then runs the script again for every build, which costs two git calls and stays correct.
  - No git on the `PATH`, or a tree that is not a checkout: the script prints no `KELPIE_COMMIT`, `option_env!` reads `None`, and every reader says the build names no commit rather than guessing one. A build copied out of a checkout carries its commit with it, since it is baked into the binary.
  - `version --json` answers with it under `commit`, and `--version` (shep's probe) with it as semver build metadata, `0.0.0+1f2e3a4`. shep reads the version as the last field of line 1 and only uses it to name the build (shep-core 0.16.1's `parse_version_answer`), so the `+` costs nothing there.
  - A runner's `status` carries it under `commit`, beside the `build` stamp the handover wait reads: the stamp says which file the runner started from, the commit says which source that file was built from. Two names are the same build when they are the same string, `-dirty` included: a build made from changes on top of the installed commit is a different binary, and a name carries nothing beyond the commit, so two builds made from two uncommitted trees of one commit cannot be told apart.
- `--binary` given a file without its executable bits is refused, naming the `chmod +x` that fixes it. Two upgrades at once are refused by a lock file, `<kelpie home>/upgrade.lock`, holding the pid of the upgrade that took it. A lock left by a process that is gone is taken over.
- Restarts go dog first, since every runner asks it for leases, then one canary runner, then every other running runner together (shep-pm/shep-kelpie#1671, `docs/design/upgrade.md`).
  - A sheep restarts only when its `status` shows no work item in `merge`, or in `done` with its pull request merged, and the dog only when no runner has one.
  - A `status` that shep delivered and that timed out is not an answer of no merge: shep reports it as `TimedOut`, apart from a sheep that is not running, and the upgrade waits on it like a merge. It asks again every 500ms for up to an hour, saying what it waits on, then fails naming the runner and restarts nothing for it.
  - A restarted sheep must answer `status` in 60s: the canary before the rest go down, any other without holding the others back. A merge can still begin between a `status` and the restart that follows; the runner's own stop lets the step in flight finish first.
  - A sheep that is stopped stays stopped and starts on the new build. The flock is read again after the build and right before each restart, because the wait can last an hour: a runner stopped meanwhile stays stopped (reproduced with a probe in review before the fix).
  - A `Starting` sheep counts as running; an `Errored` or `WaitingRestart` one is left alone and named.
- Since shep-pm/shep-kelpie#335 an upgrade drains each runner it does not hand over (above) before its restart, since a stop ends every call in flight (by design since shep-pm/shep-kelpie#319) and the work item then resumes from its session, losing the turn in progress and anything uncommitted.
  - A runner's `drain` trigger holds back every call it would start next: a worker's turn, a reviewer's session or local round, and the project manager's wake. The rest of each pass goes on, so a merge in flight finishes, CI is read, a bot is summoned (it reviews on the forge, where a restart does not cut it short) and the board may open a work item whose first turn then waits.
  - `drain` answers the status with a `draining` object: `calls`, those still running (`{"issue": 7, "role": "worker"}`, `"reviewer"`, or `{"role": "pm"}`), and `ceiling`, the turn ceiling in seconds, or the project manager's 10 minutes when longer.
  - Draining lives in memory only, so a restart ends it, as `undrain` does, and the state file does not change.
  - The upgrade drains a runner after the dog's restart and before that runner's merge wait, asks `drain` again every 500ms until no call runs, saying what it waits on, then runs the merge wait as before and restarts it. A drained runner starts no call, so the two waits in turn reach a moment with neither.
  - The wait for calls is bounded by the ceiling plus a 5-minute margin, counted from when the wait began; until the runner first answers, it is `patience.merge`, as for a runner that does not answer `status`.
  - The bound is not a guarantee: a turn's ceiling counts from when it got the lease it waited for, and a review call's own hour is not in the `ceiling` `drain` answers with, so either can outrun it. Past it the runner is sent `undrain` and named, and stays on the old build with nothing restarted for it.
  - Any other way out while a runner drains sends `undrain` too: a merge wait that runs out, a failed restart, a shepherd error, and a Ctrl-C or SIGTERM, which the upgrade listens for from the first runner's drain on.
  - Only a shepherd it cannot reach leaves a runner drained, so each drain prints `shep kelpie undrain -p <project>` as it starts, and `shep kelpie status` marks a draining runner `(draining)`.
  - Neither `drain` nor `status` wakes the runner's loop (shep-pm/shep-kelpie#394), so the wait's polls cost the runner no pass and no forge call.
  - Measured 2026-10-15 on the maintainer's `shep` runner with 6 work items open: during one `upgrade --ref main` the upgrade reported `` `shep` did not answer `drain` `` 17 times before its restart, alternating with answers that named the worker turns running, and after that restart `shep kelpie status -p shep` timed out on every try for about 19 minutes, while every other runner answered throughout. The trigger handler took the same lock a pass holds through its forge calls, each of which waits its turn behind the login's pace, so the polls waited on GitHub and missed shep's 60s `action_timeout`. Since shep-pm/shep-kelpie#916 `status`, `drain` and `undrain` are answered from a copy the loop posts along the pass (`crates/runner/src/runner/posted.rs`, and the decision in `docs/design-log.md`).
  - Only the runners that restart together drain together, after the canary has passed; the canary drains alone, and the rest keep working meanwhile.
  - A runner from before `drain` answers it with shep-channel's plain `unknown action` while it answers `status`. A runner still opening its channel can do the same once, so the upgrade asks `drain` again after a `status` that answered, and reads a second plain answer as an old build: it says the restart cuts its calls short and restarts it as before.
  - `--now`, first or last among the arguments, skips the drain and keeps the merge wait. The dog is never drained, since the calls are its runners'.
- Since shep-pm/shep-kelpie#718 an upgrade hands each online runner over to the new build before it drains or restarts it. The `handover` trigger replaces the runner's image in place and keeps its calls running (shep-pm/shep-kelpie#656), so a handed over runner loses no turn and shep sees no stop.
  - The runner's `status` carries `build`, the size and modification time of the file it started from, in the form `builds/installed.seen` uses, taken before anything can replace the file and again by each new image. The upgrade stamps the installed file after the swap and waits for a `status` showing that stamp.
  - A handover that succeeds is never answered, since the process that would answer is gone: the trigger comes back `TimedOut`, or `{"handover": "waiting for the runner's quiet point"}` when the quiet point is held. Neither is a result: only `build` is.
  - The wait for the new build is `patience.start` (60s), counted from the trigger. It is a handover that did not land in time, and the runner is drained and restarted as below. The line says what the last `status` showed: the old build, no `build` at all (the runner could not read its own file, which it also prints to its log), or no answer.
  - A handover that did not land in time may still be queued in the old image, waiting for its quiet point, where it would land in the middle of the drain (draining lives in memory, so the new image does not keep it). The upgrade sends `withdraw_handover` before it drains: `{"handover": "withdrawn"}` dropped the request, `{"handover": "none waiting"}` means the loop had taken it, and the upgrade then waits for the new build once more. A build with `handover` and no `withdraw_handover` answers it as a plain `unknown action`, and the line says the handover may still land.
  - A runner the shepherd no longer has running during the wait stays stopped and starts on the new build. A runner still opening its channel, which takes neither `handover` nor `status`, is asked again until `patience.start`, then drained like one that refuses.
  - A Ctrl-C or SIGTERM during the wait stops the upgrade; nothing is drained, so there is nothing to undo.
  - A refusal answers `{"error": "handover refused: <why>"}` within about 2.5s. A runner from before `handover` answers it with shep-channel's plain `unknown action` while it answers `status`; as for `drain`, the upgrade asks `status` and `handover` again before it reads that as an old build.
  - For each runner that refuses, predates the trigger or does not show the new build in time, the upgrade says why and falls back to the drain and restart above, unchanged. The dog keeps its plain restart, after the merge wait.
  - A handover waits for no merge: the runner acts at its quiet point, where none is in flight, and the merge goes on in the new image. Neither the drain nor `undrain` is sent on this path.
  - `--now` skips the handover as it skips the drain: a plain restart after the merge wait.
- A failure after the swap leaves the new build installed, and the error says so with the command that finishes the restarts, `upgrade --binary <installed path>`, which finds the bytes equal, moves no file and restarts.
  - A `--rollback` run again would swap the builds back instead. The same line prints before the restarts, so a Ctrl-C leaves it on screen.
  - `--rollback` goes ahead without a minor check only for a previous build that ran and exited 2 on `version`; one that cannot start, hangs or dies is refused.
- Since shep-pm/shep-kelpie#249 a bare `upgrade` restarts onto the installed file as `cargo install` left it: the same `Build::of` and shepherd-minor checks as `--binary <installed path>`, then the restarts, with no staging and no swap.
  - After every upgrade that finishes its restarts, kelpie writes the installed file's size and modification time to `builds/installed.seen`. A bare run that finds them equal says nothing changed and restarts nothing, and no record counts as changed.
  - A different file restarts and says `--rollback` has no copy of the build cargo replaced. The record is written only after the last restart, so a run that stopped part way is finished by the next bare run.
- Not done: the runner's stop can still cut a merge that begins between the idle `status` and the restart (`JOIN_BOUND` is 2s), and the lock's stale take-over checks and then acts.
- `--ref` keeps a clone of the repo in `<kelpie home>/upgrade/source` (`KELPIE_SOURCE` names another repo than shep-pm/shep-kelpie), checks out the remote's branch, tag or commit detached, and runs `cargo build --release --locked` with its own `CARGO_TARGET_DIR`. Measured 2026-09-30: a nested cargo that inherits the maintainer's `CARGO_TARGET_DIR` puts the binary there, not in the clone's `target`, and the build reported success with no file where kelpie looked.
- `--release <version>` runs `gh release download v<version>` for the asset `shep-kelpie-<arch>-<os>.tar.gz` (`aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`) and unpacks `shep-kelpie` from it. This repo has no release workflow yet, so the asset name is a decision and not a measurement; the build inside must say it is that version or nothing is installed.
