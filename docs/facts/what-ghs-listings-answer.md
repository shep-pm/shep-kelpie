# What gh's listings answer

- `gh issue list --json` and `gh issue view --json` answer no `authorAssociation`, measured 2026-10-16 on gh 2.96.0: `gh issue list --repo shep-pm/shep-kelpie --json number,authorAssociation` exited 1 with `Unknown JSON field: "authorAssociation"` and the list of the fields it does answer (`assignees`, `author`, `blockedBy`, `blocking`, `body`, `closed`, `closedAt`, `closedByPullRequestsReferences`, `comments`, `createdAt`, `id`, `isPinned`, `issueType`, `labels`, `milestone`, `number`, `parent`, `projectCards`, `projectItems`, `reactionGroups`, `state`, `stateReason`, `subIssues`, `subIssuesSummary`, `title`, `updatedAt`, `url`). Asking for a field it does not have fails the whole listing, so a key kelpie needs has to be one the command answers.
- The REST endpoint `GET /repos/{owner}/{repo}/issues` answers `author_association` on every item, and answers `user.type` as `Bot` for a bot account, where gh's own listing says `is_bot`. It answers a repo's pull requests beside its issues, each pull request carrying a `pull_request` object, so a listing that wants issues alone has to drop what carries one. One page holds at most 100 items. Measured 2026-10-16 with an unauthenticated `curl` of `https://api.github.com/repos/shep-pm/shep-kelpie/issues?per_page=2`, which answered 200 with two items: `author_association` `CONTRIBUTOR` on both, `pull_request` on the one that is a pull request, and `user.type` `User`. Kelpie's guard hook refuses `gh api` for a worker, saying it runs no `gh api` for a worker and to use gh's own commands, so the call was made with `curl` and not through the adapter.
- That endpoint answers no way to ask for issues alone. `?type=issue` answered 422 `Validation Failed` naming `resource: "Issue"`, `field: "type"`, `value: "issue"`, `code: "invalid"`: `type` is the issue's own issue type, not a filter. So the open-issue listing counts its ceiling in issues and bounds the pages it reads, and a repo whose open pull requests crowd those pages out loses its oldest issues, the way `gh` loses them at its own 1000 ceiling. Measured the same way.
- `GET /repos/{owner}/{repo}/commits/{ref}/check-runs` answers null for `completed_at` and for `conclusion`, and a null `title` and `summary` inside `output`, on a run that is `queued` or `in_progress`. Measured 2026-11-04 with an unauthenticated `curl` of `https://api.github.com/repos/shep-pm/shep-kelpie/commits/refs/heads/main/check-runs?per_page=100`, which answered 200 with 16 runs on main's head while its CI ran: 14 `completed` each with a time and a conclusion, `test-macos` `queued` and `windows` `in_progress` with neither. A completed Actions run answers `output.title` null as well. `fixtures/gh-check-runs-head-with-ci.json` holds the four that carry the shape. So a read of a head's check runs holds every part a filter can drop as optional and drops it before parsing any time: a page with a job still running is a page of runs, not an unreadable one.
