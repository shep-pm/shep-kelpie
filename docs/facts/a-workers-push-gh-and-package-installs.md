# A worker's push, `gh` and package installs

Measured 2026-09-26 on Claude Code 2.1.283, gh 2.96 and bun 1.4.0, from a sandboxed worker on a private bun, Vite and TypeScript project, the playground.

- `git push origin <branch>` reaches GitHub through the system's osxkeychain credential helper. With `refs/remotes` denied, the push lands but the tracking ref fails to write. So `refs/remotes` is no longer denied: kelpie fetches `origin/main` before cutting a branch, and a fetch forces tracking refs.
- `git push -u` cannot write `config`, which stays denied. Workers push with `git push origin HEAD`.
- `gh` will not start without `~/.config/gh/config.yml`, so that folder is no longer read-denied. It holds no token on the maintainer's machine; the token is in the keychain. Writes there are still refused. `gh` will not start without `hosts.yml` either, so it cannot be denied alone. On a machine where `gh` keeps its token in a file rather than the keychain, `hosts.yml` holds the token, and the folder must stay denied.
- On Windows `gh` keeps its config in `%APPDATA%\GitHub CLI`, and `hosts.yml` there holds no `oauth_token` (measured on the crabpot Windows VM): the token is in Credential Manager. srt runs the worker as its own sandbox user, which cannot read the maintainer's Credential Manager, so a Windows worker with no App token gets the login as `GH_TOKEN` and no gh folder is granted.
- `gh auth` is denied, since `gh auth token` prints the maintainer's token.
- Inside the sandbox, `gh` fails TLS verification with `x509: OSStatus -26276`. Claude Code's docs name this for Go tools on macOS. `sandbox.enableWeakerNetworkIsolation` fixes it and keeps `gh` inside the write fence and the domain allowlist. `excludedCommands` would have run `gh` unsandboxed.
- A cold `bun install` reaches only `registry.npmjs.org`. Inside the sandbox it fails with "unable to write files to tempdir: EPERM", because bun stages downloads in `~/.bun/install/cache`. With `BUN_INSTALL_CACHE_DIR` in the build folder it installed 733 packages in 9.7 seconds, and the project's tests and typecheck passed.
- The sandbox refused deleting `.idea` folders that a bun install outside it had left in `node_modules`. Installing them from inside worked.
- Final fence, for every worker:
  - Writable: the worktree, the build folder, the common git dir's `objects`, the worktree's own git dir, and the branch's ref, lock and reflog under both `refs/heads` and `refs/remotes/origin`.
  - Denied inside the git dir: `config`, `hooks`, `info`, `modules`, `HEAD`, `index`, `packed-refs` and `refs/tags`.
  - Domains: `github.com` and `api.github.com`. Also denied: the clone's `refs/heads/main`.
  - That is the linked worktree's fence. Since #1517 a work item's worktree is a clone: writable are the worktree, the build folder and the clone's git dir whole, denied inside it `config`, `hooks`, `info`, `modules` and `objects/info`. The worker writes none of the checkout's git, and its push to GitHub is unchanged, from the clone's copy of `remote.origin.url` and `pushurl`. The clone has no `remote.origin.fetch`, so a push leaves no `origin/<branch>` in it and `git fetch origin <branch>` needs a refspec to make one.
  - Gap, not measured: a clone borrows the checkout's objects. A fork remote's force-push that drops commits from the checkout's refs leaves the clone borrowing objects the checkout's gc may prune. The checkout keeps `refs/heads/kelpie/<n>` until the work item is removed, and workers run with `gc.auto=0`, which covers the branch's own history and not a base the fork rewrote.
  - Denied commands, besides merge, ready and the `review please` label: `gh api`, `gh auth`, a push naming `main` as `origin main`, `HEAD:main` or `refs/heads/main`, and a push carrying `--mirror`, `--all`, `--delete`, `-d`, `--force`, `-f` or a `+` refspec.
  - Those are pattern rules over the command text, so a script can get past them, and `kelpie guard` refuses the same commands in any shape it reads (Worker profile and sandbox); a token scoped to a worker's needs would be a real fence.
- Measured 2026-10-10 on gh 2.96 and git 2.50.1, from a kelpie worker's own session (shep-pm/shep-kelpie#420): the sandbox does not stop a worker asking the keychain for the maintainer's login.
  - `security find-generic-password -s gh:github.com` found the maintainer's `gh` login in the keychain from inside the worker's sandbox, and a file rule cannot stop that, since securityd reads the files. With `HOME` pointed elsewhere the same command found nothing, which is no fence for a worker that needs its home.
  - A `gh` pointed at a config folder with no token falls back to that keychain entry, and `git credential fill` printed the maintainer's token that way in a test, so the login file is written before a covered call starts and the call does not start without it.
  - With the token in `hosts.yml` under the host and under `users`, and `version: "1"` in `config.yml`, `gh` answers with the token in the folder, not the keychain's, and does not ask GitHub whose it is. A `hosts.yml` of the older shape, the token directly under the host, made `gh` try to migrate it first.
  - `git credential fill` for github.com, with a global config naming a helper that answers as the maintainer and the env a covered worker gets, answers with the token in the folder, and the maintainer's helper is not asked (`git_pushes_with_the_token_and_asks_none_of_the_helpers_the_maintainer_set_up`).
  - Not measured: that GitHub refuses a worker's token a comment, a review, an approval, a merge and a push to a protected `main` while it takes a push of the worker's branch (the test machine had no App; what GitHub grants the token is checked at each mint instead).
  - The keychain entry is reachable by `security` through the sandbox's Mach lookups. Two kinds of entry hold the login: `gh`'s, a generic password for service `gh:github.com`, and git's osxkeychain helper's, an internet password for github.com, which Apple's git turns on in its system config. `security find-internet-password -s github.com` found it on the maintainer's machine, and a covered worker could run `git credential-osxkeychain get` or `git -c credential.helper=osxkeychain credential fill` for it.
  - `security`, `git credential`, `git credential-*`, `git -c credential*` and `~/Library/Keychains/**` are denied as guardrails against a mistake, not as the boundary.
  - The keychain itself is closed by shep-pm/shep-kelpie#429, which blocks it inside a covered call's sandbox (the maintainer decided 2026-10-10, keeping the login in the keychain); this pull request does not check for a login there and does not ask the maintainer to move it.
- Measured 2026-09-28 on Claude Code 2.1.284: under `bypassPermissions`, a sandboxed `curl` to a host outside `allowedDomains` got its 200. Claude Code's settings reference says so: without `sandbox.network.strictAllowlist`, bypass mode allows a host outside the list rather than asking. With `strictAllowlist: true` in the worker's `--settings` file, the same `curl` was refused ("host is not on the allow list"), so every worker's settings carry it.
- Per project, `worker.allowed_domains` adds domains (shep: `crates.io`, `index.crates.io`, `static.crates.io`; the playground: `registry.npmjs.org`), and `worker.build_env` points tool caches into the build folder (the playground: `BUN_INSTALL_CACHE_DIR`).
