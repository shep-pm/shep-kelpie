# The pass over a contribution's green head

How the reviewers in `contributions.reviewers` read a contribution, and what is recorded. Settings and detection are in `contributions.md`, the security read in `contribution-security.md`. #623

## The pass

- `Runner::run_pass` (`runner/contributions/pass.rs`) starts for a head that is `passed`, `is_green` and has no `pass`. It is a call in flight like the security read (`Job::Pass`, sharing `Flights.securing`): one contribution call at a time, a slot while it runs, #621's budget and order rules, after the security read in `contribution_due`.
- It walks `contributions.reviewers` from the start point. The first reviewer to answer, findings or `CLEAN`, ends the pass. A local reviewer's answer is posted (below); a bot's is not.
- Rotation: the start point is the reviewer after `last_answered`, wrapping round, or the front with none. A push clears `pass` and keeps `last_answered` and `local_failures`, so the reviewers take turns over a contribution's pushes. A pass that ends unread leaves `last_answered` alone.
- Skipped: a reviewer with `paths` the change leaves alone (`touches`, from `changed_files` and `matches`, `runner/review/lineup/mod.rs`), a local one that reviewed nothing twice (`local_failures`, `LOCAL_FAILURES_DOWN`), for one pass, after which its count restarts. A bot's turn is `contributions.md`'s, and a call reads the reviewers up to the next bot, then hands the walk back in `walking`. A reviewer whose call fails `ROUND_FAILURES` (3) times in a row is passed over. With no answer the pass ends unread and `pass.unread` names why. A call ended past the pass's one ceiling (15 minutes) ends it unread at once, with the cost kept, and the runner stopping leaves the head to the next poll. It is not retried until the next push.
- The reviewers read a detached worktree of the fetched `refs/pull/<n>/head` at `<project folder>/reading/<n>` (`worktree::contribution_checkout`, no hooks), after the agents' own files in it are checked against `main`'s (`fence::differ`): a difference ends the pass unread. A session gets the diff fenced as data and `Tools::Review` only; a local reviewer holds its lease as a work item's does. The worktree is removed when the pull request leaves the record.
- `contributions[].pass` is `{ head, ran, answered?, unread?, findings?, nits?, review?, note? }`, with `walking`, `last_answered` and `local_failures` beside it, all left out while empty. `nits` are a bot's open threads that are nits. State version 58.

## Posting

- `follow_posts` (`runner/contributions/post.rs`) runs each poll after `follow_bots`, on a covered repo only. It posts for a pass over the current head that a listed reviewer which is no bot answered. An unread pass, a bot's answer and a reviewer no longer listed post nothing. #627
- Findings post as one review (`Voice::review`: `event` `COMMENT`, `commit_id` the head) with a comment on each finding whose line the head's diff shows (the new side, `diff_against` the base). Other findings, and all of them when the diff is unreadable, go in the body in their own words, added by code under the representative's text. `pass.review` keeps the review's id, `0` when the forge took it and named none.
- The representative words it in one call (`Runner::represent`), as JSON `{ body, comments }` with a comment per line finding, in finding order. Text that is no such JSON, or whose count is wrong, falls back to the findings' own words.
- A 422 for a line comment retries once as a body-only review, in `AppVoice`. `GuardedVoice` runs the `publish` hooks, local paths and flock over the body and each comment first.
- A clean pass posts one short note in the representative's words, and `pass.note` keeps its id.
- A push clears the pass, so each head is posted once, across a restart too. A failed wording or post is told once per head in the log and tried at the next poll. The wording is kept in memory, so a failed post is not worded again, unless a hook or local-path check refused its text. After `POST_TRIES` (5) failures it is given up for the head, until a push or a restart, and the log says so. A forge that is busy or rate limited is not counted. An id the state could not save is kept in memory and saved first at the next poll, so the post is not repeated; it never fails the poll, and nothing is posted as the maintainer.
