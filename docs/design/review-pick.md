# Review pick

How a pass chooses each round's reviewer. The pass it sits in is in review.md.

- Each round asks the agent board (`board_picks`) for a reviewer: the item's kind, tier and slack, no pin, as candidates every reviewer file `agents.allow` holds but `contributions.security_reviewer` that can run (`paths`, a down local, a bot's `rounds`), and the pass's reviewers left out, with every bot the project left out as one its repo cannot run within the last 7 days. It takes the first ranked one the pacer lets start (`Scope::Turn`) and, for a bot, whose window is open now; a held one or a bot with a closed window is skipped, not waited on, and a bot is passed over (`bots_skipped`, so a late review is still read). A board that cannot be reached leaves the round to ask again next poll, with no fallback. A reviewer counts toward `need` once its round ran, not a bot passed over or a reviewer that kept failing. The pass goes to CI at `need` reads or when the board ranks none left; every held one waits on the first hold. ADR 0018, #1539, #1541, `runner/review/lineup/mod.rs`
- A board that ranks none of the candidates that could run, with nobody having read, marks the item `unreviewed` (a ruling, not CI and an auto merge): a tier no reviewer file fits or a file the board does not know yet cannot send a pull request through unread. A bot kelpie itself left out is none the board was asked to rank, so the reason names it as left out with when it comes back. After a read it only ends the pass. `runner/review/lineup/mod.rs`
- The start's, the reread's and `doctor`'s checks (a local reviewer that does not answer, a review bot that has never reviewed on the repo, a reviewer on a gateway kelpie cannot route) hold only the reviewers `agents.allow` names, and a reread runs them when the naming changed or a named reviewer's file did. A named CodeRabbit on a repo that is not public is no refusal: the start and the reread log one line and go on (the reread when it newly names it), as for an implementer no turn can run on. It stays a candidate whose round is passed over as not public, as an unnamed one is, and `doctor` still names it. A candidate it named no is passed over at its round, by the repo's visibility or as down, and one on a gateway kelpie cannot route is no candidate at all. A reviewer, named or not, whose gateway key the runner lacks is left out of every round and logged once (`reviewer <name> is left out of the agent board's ask: <reason>`) at the start and at a reread that newly leaves it out, as an implementer is. That is a missing key only: a gateway kelpie's settings lack is a settings error, and it stops a project that named the reviewer. `runner/reviewers_check.rs`, `settings/reviewers/mod.rs`, `doctor/project.rs`. #1544
- A work item that changes only docs runs `reviews.light` reviewers in place of `reviews.need`, once `light` is set below `need` (a `light` above `need` reads as `need`, and with none below it no item is weighed). `choose_reviewer` weighs the diff each round (`Runner::weigh`, saved as `WorkItem.weight`, state file version 96, 97 with `Heavier::High`, and 98 with `Lighter::Pm`): light when every changed file matches `light_paths` (`["**/*.md", "docs/**"]` when absent, `[]` turns it off), full otherwise. Always full: an adopted item, an empty diff, a workflow file under `.github/workflows/`, a lockfile or manifest of a `package_managers::MANAGERS` entry at any depth, a harness's own file (`fence::owner`) and a `full_paths` match, each checked before `light_paths`. `need_of` gives the count that `enough_read`, `pass_unread` and `after_round_in` read, and `after_round_in` weighs the worktree again first (`reweighed`), so a fix turn that pulls a light item into `src/` or a manifest ends the pass at the full count, and a diff git cannot take leaves the stored weight and the pass in review, so the next round's `choose_reviewer` reports the failure instead of a stale light weight ending the pass. A HIGH finding in `held` (every finding above a nit sent to the worker, across passes) also makes the weight full (`Heavier::High`, shown as `full (stepped up: HIGH finding)`), checked after an adopted item and before the diff, so a light round that finds one keeps the item full for the rest of its rounds. No flag is stored: the weight is derived from the diff and `held` each time, and a review bot's threads are not read for severity. A small change that touches code can run the light count too, when the project sets `reviews.pm_lightens` (off when absent) and the project manager tagged the pick `light: true` (`WorkItem.pm_light`): `weigh` reads `changed_lines` (added plus deleted from `git diff --numstat --no-renames` over every changed file, the same range as `changed_files`) and the weight is `Lighter::Pm { lines }`, shown as `light (PM, 6 lines)`, when that is at most `reviews.light_max_lines` (a `NonZeroU32`, 10 when absent). A binary file counts as over the ceiling, and a change that is all `light_paths` stays `Docs` whatever the tag or the ceiling. Every always-full case and `full_paths` is checked first and beats the tag, the step-up is unchanged, and the lines are read only when a tagged item and the setting both allow it. Like docs, it does nothing until `light` is below `need`. The prompt's `pick` paragraph says kelpie checks the diff itself and ignores the tag when the change is larger or the project does not allow it. A light weight makes the ask's tier `light`, so the project manager's tier no longer rules out a cheaper reviewer, and the cost order within the slack is as before; a full one asks its own tier. The fix turn, local rounds, review bots and `contributions.reviewers` are untouched. #1676, #1677, #1680, `runner/review/lineup/weight.rs`, `core/work_item/weight.rs`
