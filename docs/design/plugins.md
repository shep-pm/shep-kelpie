# Repo plugins

The plugins a project turns on, the copy kelpie makes of each, and how every harness loads them. The step skill and the vendored copy are in skills.md, the fence that lets a worker read them in fence.md.

- Plugins enabled in `.claude/settings.json` on `origin/main` reach every Claude Code agent (skills, agents, commands, hooks, MCP), and a pi, Codex or goose agent's skills and MCP servers (a Codex server as a `-c mcp_servers.<name>` override, one it cannot load dropped with a note, `crates/adapters/src/adapters/codex/mcp.rs`; a goose server as a `--with-extension` or `--with-streamable-http-extension` flag of a new session, none on a resume, so a server added later is not seen, one it cannot load dropped with a note, its tools let through the fence hook by `<key>__`, `crates/adapters/src/adapters/goose/mcp.rs`), never from a worker branch. Sources: plain git transports, no `-` or `::` addresses, no links or `..` (default branch settings aren't maintainer's alone). #569, #570
- The repo's own `.claude/skills`, `agents`, `commands` and the `hooks` of `.claude/settings.json`, read from `origin/main`, are one more plugin, `kelpie-repo`, for the worker, the reviewers and the project manager; a Claude Code call in a worktree whose agent files equal `main`'s (`fence::matches_main`) loads them there and skips it. A skill of it that names `${CLAUDE_PLUGIN_ROOT}` gets that copy's folder in place of it, as a repo plugin's skills do. #591, `crates/core/src/skills/repo/own.rs`
- A pi call loads the `skills/` folder of every plugin it is given, the step skill's own folder first so its name wins a collision, after `--no-skills` (nothing of `~/.pi`, `~/.agents` or the worktree loads) and with `--no-approve`. A pi worktree's `.claude` is never read, so the `kelpie-repo` plugin reaches a pi call even in a worktree that matches `main`. A call with no tools gets only its step skill; every other keeps `read`, the way to a skill that names another. Plugin commands, agents and hooks do not reach pi. #763, `crates/adapters/src/adapters/skills.rs`
- A Codex `Tools::Work` call gets every skill folder of every plugin it is given linked into `<call's CODEX_HOME>/skills/<name>` by `prepare`, the first plugin winning a name and the last call's links removed. The call cannot write that folder, so it cannot plant a skill; `~/.agents` stays unread, and `plugins` and `skill_mcp_dependency_install` stay off. A call with no shell cannot open a `SKILL.md`, so it keeps its step skill pasted into the prompt and gets no links. Not measured live (`docs/facts/codex-as-an-agent.md`). #772, `crates/adapters/src/adapters/codex/skills.rs`
- A goose call gets `--with-builtin skills` and a skills folder of its own, `<GOOSE_PATH_ROOT>/config/skills`, which `prepare` empties and rebuilds on every call: a link to each skill folder of every plugin the call is given, named by the `name` line of its `SKILL.md`, the step skill first, then the plugins in order, the first of a name winning (folders inside one plugin go by name). A skill with no `name`, or a `/` in it, is not linked. goose's two builtin skills, `web-search` and `goose-doc-guide`, are shadowed by a stub each that says it is not available, so no worker spends turns on `uvx` or docs it cannot fetch (delete the stubs to bring them back). `~/.agents/skills`, `~/.claude/skills` and `~/.config/agents/skills` are unreadable to the call and its own skills folder unwritable; the worktree's committed skill folders load as on Claude Code, and `.claude`, `.agents` and `.goose` are write-fenced. The step's prompt is goose's command `/<name> <rest>`, so goose injects the skill, unless the skill's text holds `$ARGUMENTS` or `$` and a number, where goose would split `<rest>` like a shell and end the turn on an unbalanced quote: then the prompt stays as written and the model uses `load_skill`, which the fence hook lets through for every kind. A call in `GOOSE_MODE=chat` (no shell, no MCP server) cannot call `load_skill`, so its prompt is the skill's text with the placeholders filled in, and `ARGUMENTS: <rest>`. A skill the worktree's `.agents/skills`, `.goose/skills` or `.claude/skills` holds one of the same name beside is sent as its text too, since goose reads those folders first and the repo's would run in its place. A skill named like a goose command (`help`, `clear` and so on) keeps the prompt as written, since goose would run the command instead. Not run on a model (`docs/facts/goose-as-an-agent.md`). #793, `crates/adapters/src/adapters/goose/skills.rs`
- A plugin's copy holds every top-level folder of the plugin and the files it keeps at its own root, not only the four part folders: a skill names a file under the plugin's root (`${CLAUDE_PLUGIN_ROOT}/docs/rules.md`, or `RULES.md` there), and the name reaches nothing where the copy leaves it out. `.claude-plugin`, `mcp-root` and `.mcp.json` are aside, and the fingerprint covers them, so a merge that changes only a file outside the parts is copied over: `.mcp.json` sits in `mcp-root` for a server that runs a file of it, and never beside the copy, whose trimmed manifest and kelpie's own `mcpServers` already carry the servers. `${CLAUDE_PLUGIN_ROOT}` in a copied `SKILL.md` is the copy's folder (pi passes a skill's text as written; `mcp.rs` already fills it for a server), and a worker reads the project's skills folder (`fence.md`). A copied `SKILL.md` whose frontmatter is not valid YAML is told as a plugin that cannot load is, a notice naming the file and the parser's message, and listed under `unreadable` in `status`: pi refuses one and its warning reaches no log kelpie keeps, Claude Code tolerates it. The plugin loads and its other skills with it. A `SKILL.md` that is no text at all is copied as it stands and filled in with nothing, since a failed install skips the plugin whole and takes its siblings' skills, agents, hooks and servers with it. #1258, `crates/core/src/skills/repo/mod.rs`
- A plugin's MCP servers and `.mcp.json` on `origin/main` join the call's `--mcp-config` and `permissions.allow`; not `Retro` calls. #573, `crates/adapters/src/adapters/claude/mcp.rs`
- `repo_setup` narrows nothing (ADR 0020): the repo's `.claude` files decide, and `plugins`, `own`, `roles`, `parts` and `skip` load, read by nothing, until #1833 removes them. A plugin's hooks stay in its own `hooks/hooks.json`, so they cannot replace kelpie's. `prepared` keeps one rule in code: only `Role::Worker`, `Role::Reviewer` and `Role::Pm` get repo plugins or servers. `extra` adds ids with a one-string source (`github:o/n#ref`, `git:url`, `directory:dir`) that lookout can edit. #571
