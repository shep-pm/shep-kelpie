# Fence

What a worker may touch, run and write, and what only kelpie does. The runner
loop and turns are in workers.md, agent files and harnesses in agents.md, what a
call reads is in fence-reads.md.

- Workers start `--setting-sources project` + kelpie-written settings file; maintainer's hooks, plugins, skills don't load (on goose, the call's plugins' skills are linked into its own `config/skills`, `plugins.md`). #98, `crates/core/src/profile/mod.rs`
- Kelpie's guard in every worker's settings; `worker.guard_hooks` adds Claude Code hooks; an unresolvable hook stops the runner at start and refuses a reread. #108, `runner/guard_hooks.rs`
- Project `hooks` run own commands at `publish`, `commit`, `push`, `handover`, `command`, `write`, `turn_start`, `turn_end`, notices on every harness (`guard_hooks` reach Claude Code alone). A changed table is live: one `SharedHooks` handle held by the guarded ports and the runner, replaced by reread. ADR 0009, #454, #1120, `crates/core/src/hooks/`
- Workers run `bypassPermissions` over `main` ruleset + OS sandbox + `kelpie guard` denylist; no auto mode (classifier outages blocked work). `crates/core/src/profile/mod.rs`
- Sandbox and `kelpie confine` hold writes to worktree + build folder, hosts to GitHub, the model, `allowed_domains`, and the package registries of the call's worktree (`fence-reach.md`). `crates/core/src/profile/mod.rs`
- Guard denies what only kelpie does (merge, ready, `review please`, `gh api`, pushes to `main`, credential reads); a worker's `git fetch` is answered (merge.md); label or ready change kelpie didn't make parks the worker. A goose reviewer or retro: `--goose --read-only` (agents.md). `crates/core/src/guard/mod.rs`
- Agent files in worktree (`.claude`, `.mcp.json`, `.codex`, `.agents`, `.pi`, `.goose`) fenced, checked before each call; change parks `agent-files` (a review could plant a hook). #98
- Every call runs whole inside kelpie's OS sandbox (`Sandbox` port), hooks and MCP included; Claude Code's own sandbox off (macOS can't nest). #128
- On every platform that sandbox is crabpot, linked into kelpie's binary: `SandboxRuntime::wrap` returns `<kelpie> --crabpot --settings <file> -- prog args` and `crabpot::run_from_args` first in `main` runs it, so no node `srt` is chosen anywhere, neither the runner's and `add`'s startup check (`SandboxRuntime::check`) nor `doctor`'s `sandbox` line asks for one, and `@anthropic-ai/sandbox-runtime` is off `tools install` (#1217). Linux needs `bwrap` alone, no `socat` (shep-pm/shep-kelpie#1199). Windows fences with the WFP filter engine and needs a one-time `crabpot windows-install`: the install fixes one loopback mode for every session after it and srt-win refuses a session that asks for the other (exit 19), so on Windows the settings ask for the install's mode, read from `crabpot::windows_status` on every wrap, and every worker on an `--allow-loopback` install gets `allowLocalBinding`, whatever its policy: on such an install a direct connect reaches every service on the machine's own address, the widening `docs/facts/the-second-harness.md` measured for `allowLocalBinding`, and `doctor` recommends a closed install unless a project it was asked about runs the browser's dev server, the only policy that listens, which needs a launch file on its base branch. A policy that listens on a closed install is refused at the wrap (`SandboxError::Loopback`) with that hint. On Windows `allowRead` holds only paths with a drive letter below its root (#1470): the profile read grant already gives the home and default ACLs the system drive, and crabpot refuses a read grant on a root or above a profile exclusion (`.ssh`, `.config\gh`), which the `/` that `/bin/sh` and `/bin` lead to in a script's shebang would be. On Windows no deny names a path that is missing when the call starts (#1487): srt-win makes an empty placeholder for one and never deletes it, which `fence::differ` then reads as a harness file and the runner's old-home check as a settings file. A `~/` path is read under the user's home, a glob is kept, and a harness file made in the worktree during the call is left to `differ`, which also scans `.config/goose`. A covered call (`Policy.no_keychain`) writes `network.denyMachLookup` for `com.apple.securityd.xpc` and `com.apple.SecurityServer`. A test binary has no `run_from_args`, so a test that runs the wrapped command uses the built `shep-kelpie` (`SandboxRuntime::run_by`). `crates/adapters/src/adapters/srt/mod.rs`
- `[app.dogs.kelpie.code_graph] enabled` (off) gives reviewers and the triager on every harness codebase-memory-mcp, and `Work` turns too only with `worker` (off: the server's 17 tool definitions ride in every request of a turn and no worker session recorded so far, on Claude Code or pi, has answered one, `docs/facts/mcp-servers.md`): `tools install` fetches a pinned release, `Runner::prepared` names the server in the call's reach and the call's thread (lock let go, a stop ends it) indexes the worktree into `<project>/code-graphs/<issue>` before each call that is given it (UI off, daemon in `<project>/cbm/<issue>`), Claude Code a per-call `--mcp-config` allowing its tools, pi in its home's `mcp.json`, Codex as `-c` overrides, goose as `--with-extension` flags (`plugins.md`). Its sandbox writes and binds only there and its `/tmp` scratch, opening the folders above (#948). No binary or failed index: a logged skip and a `doctor` line. Its `install` never runs. #599, #991, `runner/code_graph/`, `crates/core/src/ports/mcp.rs` (the servers), `crates/adapters/src/adapters/mcp/mod.rs` (the fence)
- Guard refuses `claude`, `codex`, `pi` as programs (a nested session runs without hooks). `crates/core/src/guard/mod.rs`
- Linux: the sandbox skips `denyWrite` globs (measured under srt, and pinned under crabpot from #1199 by the `sandbox` CI job), so `fence::deny_write` also lists nested harness folders present at call start (`crates/core/src/fence/nested.rs`); one made during a call is caught by the check against `main` after it. It also refuses every Unix socket, so no worker reaches the dog's door and `cargo-test` runs unleased; `doctor` says so. #488 srt 0.0.80 and later also block the user namespaces a command makes itself, and `allowNestedUserNamespaces` stays off (#1180).
- A Claude Code, pi, Codex or goose worker's tests may bind and connect Unix sockets in the call's own scratch folder, the one its `TMPDIR` names, on macOS: `Policy.socket_folders` lists the real path under srt's `network.allowUnixSockets` (`bind_in_scratch`, `crates/adapters/src/adapters/claude/sandbox.rs`). `/tmp`, any other call's folder, the dog's folder and loopback TCP stay refused, and no role but `Work` gets it. On Linux the sandbox refuses every Unix socket whatever it lists, so there they stay CI only. #956, #1084
- Each harness declares run-code + login files; fence holds all, so no call plants or reads another harness's. #233
- A work item's worktree has its packages installed before the turn's call, once the turn's job has made the worktree: each folder (the root and those directly under it) that keeps a lockfile of npm, pnpm, yarn or bun and holds no `node_modules`, or whose install left `install-unfinished` in the build folder, is installed from the frozen lockfile with `--ignore-scripts` and its cache in the build folder (the dev server's plan, `browser-dev-server.md`). It runs as a `TestRunner` call under the worker's own fence with its registries (#1314), with no `cargo-test` lease and 300 seconds, and is logged as a `packages-installed` step with the folders and why it failed. This runner installs a work item once, so an install that leaves no `node_modules` (Yarn's Plug'n'Play, no dependencies) is not planned every turn. A failed install does not stop the work item: the turn's prompt says why, the mark stays for the dev server's install, and a worker's own install is not wiped by another. The dev server's install then finds `node_modules` and skips. #1317, `runner/dev_server/install/`, `runner/git_reads.rs`
