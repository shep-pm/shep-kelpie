# Fence: the package install

The install of a work item's packages runs under the worker's fence, less what a package needs to
write. The fence is in fence.md.

- A work item's worktree has its packages installed before the turn's call, once the turn's job has made the worktree: each folder (the root and those directly under it) that keeps a lockfile of npm, pnpm, yarn or bun and holds no `node_modules`, or whose install left `install-unfinished` in the build folder, is installed from the frozen lockfile with `--ignore-scripts` and its cache in the build folder (the dev server's plan, `browser-dev-server.md`). It runs as a `TestRunner` call under the worker's own fence with its registries (#1314), less the `**` globs of `fence::deny_write` (`fence::install_deny_write` keeps the harnesses' root files), since a package may ship a `.claude` folder, and started in the build folder with a `cd` into each folder, since the sandbox's own always-on refusal of `.vscode`, `.idea` and `.claude/commands` (crabpot's `DANGEROUS_DIRECTORIES`) stands below the folder it starts in and no setting lifts it (#1605), with no `cargo-test` lease and 300 seconds, and is logged as a `packages-installed` step with the folders and why it failed. This runner installs a work item once, so an install that leaves no `node_modules` (Yarn's Plug'n'Play, no dependencies) is not planned every turn. A failed install does not stop the work item: the turn's prompt says why, the mark stays for the dev server's install, and a worker's own install is not wiped by another. The dev server's install then finds `node_modules` and skips. #1317, `runner/dev_server/install/`, `runner/git_reads.rs`
