# Fence: the package install

The install of a work item's packages runs under the worker's fence, less what a package needs to
write. The fence is in fence.md.

- A work item's worktree has its packages installed before the turn's call, once the turn's job has made the worktree: each folder (the root and those directly under it, less hidden ones and `node_modules`, `target` and `vendor`) that keeps a lockfile of npm, pnpm, yarn or bun and holds no `node_modules`, or whose install left `install-unfinished` in the build folder, is installed from the frozen lockfile with `--ignore-scripts` and its cache in the build folder (the dev server's plan, `browser-dev-server.md`). It runs as a `TestRunner` call under the worker's own fence with its registries (#1314), less what `fence::deny_write` adds beyond the harnesses' root files (`fence::install_deny_write` keeps those): the `**` globs on macOS and Linux and, on Linux and Windows, the nested harness folders it lists by path (Windows has no globs), since a package may ship a `.claude` folder, and started in the build folder with a `cd` into each folder, since the sandbox's own always-on refusal of `.vscode`, `.idea`, `.claude/commands` and `.claude/agents` (crabpot's `DANGEROUS_DIRECTORIES`) stands below the folder it starts in and no setting lifts it (#1605), with no `cargo-test` lease and 300 seconds, and is logged as a `packages-installed` step with the folders and why it failed. This runner installs a work item once, so an install that leaves no `node_modules` (Yarn's Plug'n'Play, no dependencies) is not planned every turn. A failed install does not stop the work item: the turn's prompt says why, `status` shows the output's first line that names an error as the item's `install_failed` until a good install of it or its leaving clears it (in memory only, with `install_ran`, which its leaving clears too), the mark stays for the dev server's install, and a worker's own install is not wiped by another. The dev server's install skips only after a successful install removed the mark: while the mark stays, it installs again even where `node_modules` exists. #1317, #1704, `runner/dev_server/install/`, `runner/git_reads.rs`
- Each folder a call's env names under the build folder is made as its reach is built, a project's `build_env` entry included, and again for an install's own caches as the plan merges them: pnpm 12 keeps its store operation lock in `XDG_RUNTIME_DIR`, runs without it where that folder is missing, and makes none itself. A worker's own `pnpm install` runs where kelpie planned none, with no lockfile yet or one below the folders its plan reads, so the folders come with the reach and not with the install. pnpm names `PNPM_CONFIG_STORE_DIR`, `PNPM_CONFIG_CACHE_DIR`, `PNPM_CONFIG_STATE_DIR` and `XDG_RUNTIME_DIR` beside the `NPM_CONFIG_STORE_DIR` older pnpm reads. The fence is unchanged: no `scratch` entry for `/private/tmp`, and `install_deny_write` stands. Measurements: `docs/facts/a-workers-push-gh-and-package-installs.md`. #1702, `profile::make_build_folders`, `runner/turn/mod.rs`, `runner/dev_server/install/`, `runner/git_reads.rs`
