# Handover

A runner replaces its own image with the installed build while worker turns run, and `upgrade` drives it. The agent calls themselves are in agents.md.

- A `handover` trigger replaces the runner's image with the installed build via `shep_handover`, keeping pid, children and shepherd channel, so shep sees no stop. The loop acts at its quiet point (between passes, no `git`/`gh`/merge child; after each pass too when passes follow one another with no wait, #1327), and a call whose stdin is still being fed (`adapters::feeding`) or a notice hook running or queued on its own thread (`Runner::notices_running`) or a reply a forwarder is relaying (cut by the exec) holds it. Only worker turns this image started cross (Claude Code, pi, Codex and goose), each as `Adopted` (pid, record path, `harness`, for pi and goose `Kept`, for Codex the `session` id that names its thread record; `FORMAT` is 6, since an image reading 4 would not know the lease totals, as one reading 3 would not know goose as a `harness`, and 6 carries each turn's ticket id where 5 carried an issue number, with the field's older name kept as a serde alias so a 5 blob loads); a build reads 4, 5 and 6) plus its ledger line in `Carry`, which also holds the runner's lease totals and what it holds (`AskerCarry`); a PM, labelling, retro, reviewer or already-adopted flight refuses it, and so does a live pi, goose or Codex `attach`, which holds a drain too (a Codex one because its end, in this image's memory, removes the folder trust the terminal session was given). Before the exec `Processes::seal` stops reaping, so a call ending then is read by the new image, and refuses while one is being read. The new image waits on each pid with `wait_for_child` and finishes the turn as the old would: output, cost, usage line. The probe checks the target reads `Carry`'s `FORMAT`; the `Fitness` gate starts the target once with `KELPIE_HANDOVER_CHECK` set, as a runner that stops after reading its settings (`starts`), so a build that fails there is refused with the old image running, and then refuses a feed or relay that began meanwhile. A build that still fails after the exec ends the carried calls' groups before the runner exits (`end_groups`), and shep restarts it. A turn whose call's record is gone (`NotAdopted::RecordGone`) is most likely a call that just ended, whose end the loop has not heard yet, since the quiet point comes before the next pass (it can also be a call that has not yet written its record, which looks the same and waits the same): `Runner::carry_calls` answers `NotCarried::Waiting` and the request stays queued, like a feed, so the next pass hears the end and the attempt runs again. The wait is bounded by `CARRY_WAIT` (10s) from when `carry_calls` first found that record gone (`Flight::record_gone`, which ends with the flight); after it the request is refused with the usual text, `the turn of #<n> cannot be carried: the call's record <path> cannot be read: ...`. A record that is there and cannot be parsed, and every other carry error, is refused at once. Any refusal leaves the old image running; the trigger's answer names why, or says `waiting` after 2.5s and the log has a later refusal. Fd 3 needs no carrying: the shepherd passes it without close-on-exec and `SHEP_CHANNEL_FD` stays set. A pi or goose turn's `Kept` has its forwarder socket, model server and lease id, never the key: the new image reopens the forwarder at that path (`Forwarder::reopen`) with its own gateway settings, and `ModelGateway::resume` renews the lease at once and releases it when the call ends, so no second take, eviction or early release; a chat request in the gap before the reopen is refused. The totals cross because the dog acts only on a total above the last it saw from a run, and a handover keeps the pid, which is the run's epoch: an `Asker` that began at 0 would ask below what the dog recorded and go unheard. A handover from a build that carried no totals starts the `Asker` from the dog's saved book for this run (`Asker::from_book`), or at 0 when the book has none. Either way the new image also takes as held what the book says this run holds and asks for (`Asker::reconcile`): the dog saves its book before it delivers a grant and never retries one, so a grant that reached the old image after its totals were taken, or in the gap of the exec, would otherwise leave the runner waiting on a hold it already has. A kind is taken only where the book has heard the run's latest totals for it, since a book that trails may show a hold the dog is about to end. The runner reads the book once more (`ShepLeases::reconcile`) after it takes `grant` triggers, since a grant the dog delivered before the handler was up is only in the book. Adopted turns have no idle watch, unreachable retry or login refresh. A goose turn is carried as pi's is, with one more read: the session's token totals are a file in the call's goose root, so the new image counts the call's usage from them, and the worker's fence plugin and config are files there too, so nothing else is in memory. A Claude Code, pi or Codex turn also carries a `Mark` of its transcript (`CarriedTurn::requests`, absent from an older image's carry), so the new image counts the turn's requests as `runner/transcript_count/` does. A pi turn on the API (`login: api`, `Adopted.api` true, absent from an older image's blob) is carried with no `Kept`, only its `session` id, since it has no forwarder or lease, and the new image finishes it as `run` does. That field raised `Carry::FORMAT` to 7, so a build that reads 6 refuses the carry and the old image keeps its turn. A Codex turn holds no lease and has no forwarder, so it carries nothing else but that mark and the new image finishes it as `run` does (thread record, usage). `crates/adapters/src/adapters/pi/adopt.rs`, `crates/adapters/src/adapters/goose/adopt.rs`, `crates/adapters/src/adapters/codex/adopt.rs`, `src/sheep/handover/mod.rs`, `runner/flight/carry/`, `crates/adapters/src/adapters/process/adopt/mod.rs`, #717, #752, #753, #791, #850, #1010, #1331. `Carry` also names the old build, so the new image logs `took over` with both (log-lines.md). #854
- `shep kelpie upgrade` hands each online runner over before it drains or restarts it, and waits for its `status` `build` (stamp of the file it started from, `upgrade::seen`) to match the installed file. A refusal, a build from before `handover` or no new build in `patience.start` (after a `withdraw_handover`) drains and restarts it as before, saying why. The dog is restarted plainly; `--now` skips the handover. `src/upgrade/handover.rs`, #718
- Each build names the commit it was made from, and every line that names a build names that commit. `crates/core/build.rs` reads it from git and bakes it into `KELPIE_COMMIT`; `home::COMMIT` reads it and `Build` carries it as `version --json`'s `commit`, absent from a build made where git could not answer, and ending in `-dirty` when the tree held changes that commit does not. `--version` answers with it as semver build metadata (`0.0.0+1f2e3a4`, `src/schema.rs`), and a runner's `status` carries it under `commit` beside its `build` stamp: the stamp says which file the runner started from, the commit which source that file was built from, and only the commit survives a rebuild of the same path. `status` prints each runner's as its `build:` line and marks it `not the installed <commit>` when it differs from the build at the program the adopted dog runs (`src/flock/control/plain.rs`, `control::installed_build`), and `upgrade` names the commit of the build it installs and, after the restarts, each running runner still on another one or naming none (`upgrade::restart::still_behind`). The two names are compared as they stand, `-dirty` included, so a build made from a tree with changes on top of the installed commit is named as behind it: it is a different binary. A name carries nothing beyond the commit, so two builds made from two uncommitted trees of one commit cannot be told apart. `home::build`, `crates/core/build.rs`, #1260
