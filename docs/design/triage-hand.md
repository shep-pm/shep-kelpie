# The swap a `taken` record owes

What is left of taking back the maintainer's hand-labelled `ready-for-agent` issues (#1179): the swap a saved `TriageStep::Taken` record owes. The check that decides is in `triage-check.md`, the settings and the pick rule in `triage.md`, one issue's pass in `triage-pass.md`.

- The issue check decides. A maintainer's `ready-for-agent` issue it refuses is held off the board by `check_holds` and owed the triager whatever label the maintainer put on, and one it passes is ready as it stands. Kelpie starts no take-back and saves no `Taken` record: `triage.hand_ready` is read by nothing. A `TriageStep::Taken` record saved at state version 82 or later still loads and still finishes. `runner/triage/hand.rs`
- `apply_poll` (`poll_read.rs`) runs `take_back_ready` on the listing, before the due list is made and so before the board's pick in that poll. Each listed issue with a `taken` record an older build saved, and a listing showing `ready-for-agent` on or `needs-approval` off, has `ready-for-agent` come off and `needs-approval` go on, and the poll's own listing is changed to match, so the issue is untouched in the same poll and `triage_due` starts its research ahead of the board's pick. None is finished where the issue has a work item, was given up on, an open pull request closes it, or the listing shows a triage decision other than `needs-approval`: a `needs-info` or `wontfix` put on by hand after the swap stopped stands, as it did under `hand_ready`. The check reads no `taken` record's issue while the record is unfinished (`triage_busy`, `triage-check.md`), so a body rewritten after the swap stopped is still swapped and still gets its owed pass, its result becomes `ran`, and the next poll's check reads the new body and makes it ready. The record is already there, with `seen` as the swap leaves the labels, `needs-approval` among them, so `triage_labelled_by_hand` does not read the `needs-approval` kelpie put on as a hand label. A failed swap counts as a triage failure and is tried at the next poll, doing only the half the listing shows undone, so a stop between the two writes is finished too, and the board may start the issue meanwhile, since the label is its signal. `first_pass_owed` is the due test: no record, a `taken` one, or a finished one the check says was edited since. The comment the pass posts replaces the record, after which the ready path puts `ready-for-agent` back and a record at `ready` or `done` is never taken back. A `taken` record is not a finished one, so a prune keeps it. A pull request listing that fails, or is not read (it is read only where a `taken` record is saved and a listed issue owes the swap its record says), leaves the swap for the next poll, and so does `app_covers()` being false, as `triage_due` starts nothing then and no pass would put `ready-for-agent` back. Whether an App covers the repo is asked only where a `taken` record is saved or a swap is owed, since the ask mints an installation token
- A maintainer's failing `ready-for-agent` issue keeps its label beside any `needs-approval` its pass puts on, until an edit passes. `IssueCheck::ready_seen` is what keeps a label the maintainer took off off, and `swap_ready` clears it when kelpie's own swap takes the label off (`triage-ready.md`)
