# Contribution talk

What a contributor says on their pull request, as kelpie records it and answers it. Settings, detection and the security review are in `contributions.md`. #625, #626, #628

## Hearing

- Kelpie records what a contributor says; `## Answering` replies. `ProjectState.contributions[].heard` is the contributor's, `context` the maintainer's, each the last 50 `Said`: `{ kind, id, at }`, kind `comment`, `reply` or `push` (a push carries `head` in place of `id`). No text is kept, a prompt reads it again, fenced by `runner/untrusted.rs`. Both left out while empty. State version 48. `crates/core/src/state/contributions.rs`
- The author decides, by login ignoring case. The contribution's author is heard, the maintainer's go to `context`, and a bot, a third party and a comment kelpie posted through `gh` (`posted` ids) are dropped. A review reply carries no posted id, so one by the login `gh` acts as is dropped too, the maintainer's own included when that is their login. A comment and a review reply are numbered apart, so an id counts with its kind.
- One `comments_since` read per board poll serves rulings' replies and contributions: `thread_job` reads when a ruling waits or a contribution is followed. Review threads come from `Forge::thread_replies_since`, one GraphQL read per followed pull request, first 100 threads and 100 comments each, through the login. `runner/thread_replies/`, `runner/contributions/heard.rs`
- The read reaches back `SLACK` behind the last, and what is on record is not heard again. Nor is a comment written before all a full list still holds, since it was kept once and has dropped off; a push is never refused. A review thread is read from the contribution's `reviews_from`, saved in the state file, and moved to `SLACK` behind a read that worked. A failed one is told once and read again from where it began, restart or not, apart from the repo's comments.
- A push is heard by `follow_contributions` as the head moving, stamped when the board saw it. A reaction is read on kelpie's release ask, the contributor's (`contribution-release.md`), and on the representative's clean-pass note, the maintainer's (`contribution-merge.md`).
- When the maintainer's or `gh`'s login cannot be had, nothing is recorded and the place the comments are read to is held, so the next read hears all of it.

## The quiet clock

- `contributions[].waiting_since` is when kelpie began to wait on the contributor for the current head, left out while it waits on no one. State version 53. `runner/contributions/clock.rs`, `crates/core/src/state/contributions.rs`
- `follow_clock` runs at the end of `follow_contributions`, once a poll, with `waits_on_contributor`: CI red on the head, or its pass has findings or a bot's open threads (nits too). It starts the clock at the poll's time from the runner's `Clock` port, keeps a running one's start, and clears it when the head waits on no one: green CI, no findings and no open bot thread leaves the maintainer's move.
- Reset: a contributor's comment or review reply newly heard restarts a running clock at now, unless it was written before the clock began (a late read of an old reply). A push is a new head, which clears it, and the head's own results start it again. A reaction does not move it, and the maintainer's, a bot's and a stranger's words are not the contributor's, so none moves it. A clock that is not running is not started by a comment.
- `Clock::due(now)` is nothing, `Nudge` once `nudge_days` whole days have passed since `waiting_since`, or `Quiet` once `quiet_days` have, never sooner than `quiet_days - nudge_days` whole days after an open ask went out, one when the two settings are equal (`contribution-release.md`). The release stage acts on it, and red CI before a release gets no comment.
- `status` shows `waiting_since` and `clock: { waiting_for, days_to_nudge, days_to_quiet, due? }` for a contribution with one running, the days whole and 0 once reached. The plain `status` adds a line.

## Answering

- `follow_answers` runs after `follow_posts`, once a poll. For each heard comment or review reply not in `contributions[].answered` (the last 50 `Said`, never a push, left out while empty), one tool-less representative call is given the text, read again from the forge and fenced as data, the reviewers' findings on the head, the current head's diff from `main` (fetched, so not an earlier head's checkout; cut at 60000 bytes) and the maintainer's last five `context` comments, fenced and marked as context only. It replies JSON: `{ kind: "answer", text }` or `{ kind: "decision", question }`. `runner/contributions/answer.rs`
- An answer is posted as a comment through `Voice::post`, then its id goes in `answered`. A bot's comment is never heard, and the maintainer's is context and never answered. The prompt forbids promising a merge: only a ruling decides one.
- A decision raises the contribution ruling `question { asked }` (one line, 600 characters at most) and posts nothing. `contributions[].deciding` is `{ said, asked, answer? }`, left out while none waits, and holds the item until the maintainer answers with `shep kelpie rule <pr> answer <text>`. The answer is saved in `deciding`, the representative words it for the contributor in a second call, and that is posted. The ruling never goes on the pull request or to the project manager (`pm_decides`), and a closed pull request withdraws it. A push does not: the question is not about a head. Any ruling on the pull request, a security or over-budget one too, holds every answer until it is answered, since the ruling's id is the pull request's. A relay given up after five failures no longer holds the comments behind it. A file saved before version 58 loads with everything already heard marked answered, so an upgrade replies to no old comment. A relay given up leaves its `deciding` open, and a later comment that asks for a decision then counts as a failure and is never allowed to overwrite it. State version 58.
- Each call's cost is added to the contribution's `spend`, so answers stop at `budget.per_item_usd` with the same over-budget ruling, and nothing is asked while a ruling holds the pull request.
- A call that fails, or a reply that is not that JSON, is told once in the log and tried at the next poll, as are a post the forge refuses and a read that fails. A worded answer is kept in memory so a refused post is not worded twice. Five failures give an item up until kelpie restarts. A post the forge took whose save failed is recorded at the next poll and never sent again.
