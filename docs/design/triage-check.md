# The issue check on every issue

ADR 0018, cut 3: the board runs the issue check (`work.md`) on every new or edited open issue, and the triager runs only on one that fails. The settings and pick rule are in `triage.md`, and one issue's pass is in `triage-pass.md`.

- Every triage poll lists the open issues through `ports.tickets`, whatever `triage.pick` says, `off` included. `check_issues` then checks each issue a bot did not open that is new to `checks`, whose key changed, or whose triage ended since. An issue under a pass waits for a listing made after the pass ends (`triage_busy`: an unfinished record, a reply or comment not yet posted, or the call in flight). A pass given up on is not under way. Under `off`, a listing that fails waits for the next poll, so the check asks the forge at most once a poll. `runner/triage/{checks,poll_read}.rs`
- Before it checks a new or edited issue whose title starts with a kind (`guard::conventional_type`, one of `board::check::kinds()`, so not `build` or `revert`; `feat!:` gives `feat`) and that has no `kind:` label of any value, the board adds `kind:<type>` through `ports.tickets`, made first if the repo lacks it, and checks with it in place. The key takes it in, so the next listing is the same edit. A write that fails leaves one note and the issue is checked as it stands. It costs one of the poll's writes.
- A poll's check makes at most 20 forge writes (`CHECK_WRITES`), so a project's first check does not label every open issue under the runner's lock. An issue it does not reach keeps no new result and is checked at the next poll. A busy forge stops the poll's check. Each label is made at most once a poll, and the maintainer is read once.
- `ProjectState.checks` (state version 89) holds one `{issue, key, failures, triage}` per listed issue. An issue that leaves the listing is dropped.
  - `key` is `board::check::key`, an FNV-1a hash (`check::fnv1a`, the one the `local` wait uses) over the trimmed title, the trimmed body, and the priority and `kind:` labels, lowered and sorted. The priority and `kind:` labels go in on purpose: one put on by hand sets off a new check. No other label goes in, so kelpie's own `TRIAGE_LABELS`, `in-progress` and `agent:` labels never set off a new check. The priority and kind a pass puts on change the key too, and `ran` is what keeps that from looping: the end of a pass is checked once, and a failure there is told rather than triaged again.
  - `failures` holds each `check::Failure` in the check's words. It is empty for a pass.
  - `triage` is `owed` (it failed and no triager has run since), `edited` (it failed on an edit made after its triage ended), `ran` (the triager ran on this edit, and its end is checked again), or left out.
  - A write that fails keeps the old result, so the next poll tries again. A save that fails keeps the results in memory and leaves a note. `crates/core/src/state/checks.rs`
- A pass needs no triager call. The maintainer's issue (`Runner::maintainer()`, ignoring case) gets `ready-for-agent`, made if the repo lacks it, and loses `needs-triage`. One an open pull request closes is left alone and checked again at the next poll, so the poll reads the open pull requests while the check may pass an issue. Anyone else's gets `needs-triage`, unless `pick` is `off`, and waits for the maintainer to label it by hand, as `hand_ready` says: kelpie never labels it ready. An issue with any other triage label, or with a work item, is left as it is.
- A failure is owed the triager, which the pick rule reaches as before: none under `off`, the maintainer's under `maintainer`, everyone's under `all`, and only after `since` and above `pruned_through`. An issue with a triage record and no earlier result was triaged before this check existed, and is owed nothing until it is edited. An edit made after its triage ended is `edited`, which `first_pass_owed` reads as owing a new first pass on a `done` or `ready` record.
- A `ready-for-agent` issue that failed is held off the board, whatever `hand_ready` says. `check_holds` gives it the `check` skip (`board::Skip::Check`, shown under `skipped` in `status` with `reason: check` and the failures) while its result is for the text the board read or its triage is `ran`. A ready issue with no such result, one the poll has not reached or has carried, is checked where the board picks, so none passes unread. A finished or dropped ticket is not held. The check needs a priority and a kind, so a hand-labelled ready issue with neither is held until the triager reaches it, or forever under `off` until it gets them. For the due list, `ready-for-agent` is no decision unless the issue is being worked on: a `taken` record, a work item, an open pull request that closes it, or pull requests that were not read. `runner/dispatch/mod.rs`, `runner/briefing/`
- The triager's end is checked again: a result at `ran` is checked on the next listing, whatever its key.
  - A pass needs nothing more.
  - A failure whose key changed, on the maintainer's issue with no triage label put on by hand, gets one comment. It names each failure and says the issue waits at `needs-triage` until it is edited. The result is then plain, and the issue is not triaged again until its key changes.
  - That comment ends in a `kelpie:check` marker naming the key. Before posting, the check reads the issue's comments, and a marked one counts as said, so a crash or a lost reply never posts it twice. A comment the forge refuses three times (`CHECK_TRIES`) is given up; a busy forge counts for nothing.
  - A failure whose key did not change (a pass that wrote nothing the check reads, as silence leaves it) gets no comment.
  - Another person's issue gets no such comment, since the check's words are not plain and its triage comment already handed it to the maintainer.

## Today's triage steps

- `ready` stays. The check's pass now reaches it, and the `sure` rule is gone (`triage-pass.md`).
- `needs-triage` stays as the queue label. A rewrite that still fails goes under the maintainer's text and ends there, and so does another person's passing issue.
- What kelpie writes under an issue's text sits between `<!-- kelpie:under -->` and `<!-- /kelpie:under -->` (`ask::under_text`). A later pass replaces that section and leaves the text around it.
- A body is never written over an edit the pass did not read. The record keeps `begun`, the hash of the body the call was made from, and the issue is read once more just before the write. A changed body gets no write and a notice, ends at `needs-triage`, and loses its `ran`, so the next poll checks the edit.
- A priority the issue carries when its pass begins stands, as a `kind:` label does: the pass puts none on.
- `triage.pick`, `triage.since` and `pruned_through` stay, but they decide only which failing issues reach the triager. The check runs whatever they say.
- `hand_ready` keeps its meaning for another person's passing issue, which waits, and for the take-back swap. The maintainer's failing hand-labelled issue is held and triaged under either value (`triage-hand.md`).
- The author's round, `wait_days` and `local` stay, now only for questions the triager has no good answer for.
