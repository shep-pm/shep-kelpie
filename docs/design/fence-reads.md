# Fence reads

What each role's call may read, and how those folders are granted. The write fence,
the guard and the hooks are in fence.md, and the measured facts behind these are in
`docs/facts/worker-profile-and-sandbox.md`.

- Every role's sandbox denies the machine's home folder whole and allows back what the work needs. `WorkerProfile` names `home`, and `reach` denies the outermost of the three homes (`profile::home_denials`), then carves back the worktree, the build folder, kelpie's binary, the git common dir, the toolchain homes (`dep_sources::toolchain_homes`: cargo's, rustup's and bun's whole, and Go's `GOPATH/bin` and module cache, since a tool cannot exec under a deny of its own folder, and none that holds the home), git's global files (`profile::git_config`: `~/.gitconfig` and the `config`, `ignore` and `attributes` files of `~/.config/git`, since cargo lists a package's files through gix, which fails on an ignore file it cannot read; that folder's `credentials` stays denied), `~/.config/gh` on the maintainer's login (on Windows, with no App token, no gh folder: the worker gets the login as `GH_TOKEN`, read with `gh auth token` for each call, and a call whose read fails does not start), its plugin skill copies, and #952's sources. A credential named beside them stays denied by name, and each cargo home the fence reads back whole names its own `credentials` and `credentials.toml`, wherever `CARGO_HOME` moved that home (`dep_sources::cargo_credentials`); Go's and bun's homes hold no credential, and the files their registry tokens sit in, `~/.netrc`, `~/.npmrc` and `~/.bunfig.toml`, lie outside them and stay denied. The home's Go module cache is read-only: a project that downloads modules names a build-local `GOMODCACHE` in `build_env`, and a module `go.sum` lacks still fails on `GOPATH/pkg/sumdb`; `GOCACHE`, `GOLANGCI_LINT_CACHE` and `BUN_INSTALL_CACHE_DIR` name folders of the build folder, as `CARGO_TARGET_DIR` does, since `go build`, `golangci-lint` and `bun install` write their caches on every run, and a project's `build_env` may move each. A call with no fence (a reviewer, a retro) and the pm's fence deny it the same way. A call with no fence takes its carve-backs at the harness rather than the profile: `harness::unfenced_reads` allows back its own folder, the git common dir its `git` runs through (a linked worktree's `.git` file names a gitdir outside the worktree), the toolchain homes under each denied home, and the same git files. Every one of them carves kelpie's own binary back as well: a hook runs it inside the fence (the pm's `confine --append` on its notes), and exec needs file-read of the file it runs. A new toolchain grant comes with its fixture: a tiny project of that ecosystem in `fixtures/ecosystems/`, which `adapters::claude::ecosystems` and `adapters::pi::ecosystems` build, test, lint and push from inside the real sandbox in the `sandbox` CI job, with the toolchain's home under a fake home the fence denies. The fence's tests modelled only cargo until Go, bun and a `golangci-lint` pre-push hook each refused a live worker (#1412, #1414, #1417). #1259, #1420, `crates/core/src/profile/mod.rs`, `crates/adapters/src/adapters/claude/ecosystems.rs`
- Every call reads the installed sources and docs of its dependencies and toolchains: cargo's `registry/src` and `git/checkouts`, and each rustup toolchain's `lib/rustlib/src` and `share/doc`, each folder from the tool's own variable or its default home. A folder not on the machine adds nothing, and a variable that names a folder relative to wherever the tool was run names nothing, since each call runs its tool from a folder of its own. They are found as they are granted, not once when the runner starts: a machine gains a toolchain and a project gains its first git dependency while the runner runs, and a call rendered before that was granted neither. `Runner::prepared` puts them in the call's read list and the fence's read carve-outs, and a call built without it (a triager, a contribution's security reviewer and its pass reviewers) is granted the machine's own, having no build folder of its own: a contribution is named by its pull request, so `paths.build` of it would be another work item's folder. Claude Code's `additionalDirectories` and the sandbox's `allowRead` both let them through; the write list is untouched, and `CREDENTIALS` still denies what sits beside them. A call that works an item also gets the crates and the standard library of the `CARGO_HOME` and `RUSTUP_HOME` its `build_env` points into the build folder, and kelpie makes each of those folders as it grants it, since a harness judges its grants when the call starts and the call's own tool is what fills them. A build-local rustup home with no toolchain installed is granted as its whole `toolchains` folder, since no toolchain name is known until the call installs one. An answer reads none of them. #952, `crates/core/src/dep_sources.rs`, `runner/turn/dep_reads.rs`
- Each harness names what it reads to run, since the home deny would otherwise refuse the harness's own program (`harness::program_folder`), which names the program, what a link of it runs, the folder each runs from and the install folder above a `bin`, and for a bare name such as the default `claude` the `PATH` folder that holds it, read through the `Env` port so a test can name one. A script also names what its shebang runs, since the kernel execs that: `pi` is Node, and a version manager keeps `node` under the home. No grant opens the denied home whole, since a folder holding the harness's own home is the home itself or above it. Claude Code reads nothing of the home's `~/.claude` or `~/.claude.json`: each call sets `CLAUDE_CONFIG_DIR` to `claude/<ticket>/<role>/` under the project's kelpie home (`claude/<role>/` with no work item), reads and writes it, and keeps its transcripts at `projects/<slug>` there, so a `--resume` finds the file its last turn wrote. The folder outlives the work item, as `~/.claude/projects` did, and a session from before the move is copied into it on its first call. The folder holds no login, so a call with no `CLAUDE_CODE_OAUTH_TOKEN` fails with the fix instead of running logged out (#1421). Its `Read` denies carve around the fence's read carve-outs and the call's read list, so a granted folder is not denied by the home rule. The carve-out and what it denies around it are named as given and with their links resolved, since Claude Code matches a `Read` against the path its tool names (#1374). #1259, `crates/adapters/src/adapters/harness/policy.rs`
- A worker reads the project's skills folder, where kelpie writes every plugin of the call: a skill names a file under its plugin's folder (`${CLAUDE_PLUGIN_ROOT}/docs/rules.md`, `plugins.md`), and it reaches nothing while kelpie's home is unreadable whole. No other role is given it. #1258, `crates/core/src/profile/mod.rs`
- A fenced call reads the files its hooks run, since the guard runs the project's `hooks` inside the sandbox, and Claude Code runs `worker.guard_hooks` there too. For each command `harness::hook_files` grants its program, found as the shell finds it, the interpreter a script's shebang names, and every later word that names a file, after `~/` and `$HOME/` expansion, each as spelled and where its links lead, with the folder each sits in, since a script loads its neighbours and its `package.json` from there. Never the home or a folder above it, so `node ~/.claude/hooks/gate.js` opens `~/.claude/hooks` and `~/gate.sh` only itself. The worker reads what its hooks read, being in the same sandbox. A path under a credential deny of the fence, or under any harness's login, is not granted. Every harness starts from `call_policy`, so each gets it. `crates/adapters/src/adapters/harness/hook_reads.rs`
- On Windows a read folder above an exclusion of the profile read grant (`~\.cargo` over `credentials`) is written as its entries less the excluded one, from the list `windows_status` reports; one equal to or inside is left out with a stderr note, and a link is cut as its target (#1505). `crates/adapters/src/adapters/srt/profile.rs`
