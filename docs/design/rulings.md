# Rulings

What a runner asks the maintainer, and how an answer comes back. The pass they sit in is in review.md.

- Seven kinds: `merge`, `question`, `stuck` (reason), `agent-files`, `foreign-change`, `follow-up` (findings wait for a yes), `contribution` (with reason: `security`, `over-budget`, `question`, `waiting`, `no-edits`, `cannot-adopt`, `merge`; see `contribution-release.md`, `contribution-merge.md`). ADR 0006, #330, `runner/ruling/`
- A `contribution` ruling has no work item and posts nothing on the contributor's pull request (it would accuse them and tip off an attacker): webhook, `status` and `rule` only. Nor to the PM (`contribution-merge.md`, `github-app.md`). #620, #629, #630
- `merge` in `rulings.pm_decides` is the one key for unattended merging (#1762): set `true`, the project manager's yes merges a head that passed every gate. Its yes holds at the gates: where the ruling warns of an unreviewed pass, open review bot threads, an unread head, an unread fix (`note_fix`, `late_fix`) or a borrowed head (`Ruling.borrowed`), the yes is refused and the ruling goes to the maintainer with the project manager's pick. A send-back or rework is not refused, and a ruling for `rivals` or a refused comment holds none of these. Only the maintainer's yes merges past a warning. Where a project manager rules on the item's threads, an unreviewed pass, an unread head or an unread fix never reaches a merge ruling at all: the gate sends it back through a pass of the review (gate-unread.md), so a ruling carrying one of these warnings is a project with no project manager's or a contribution's, and its question says so (#1826). `merge = false` raises the ruling, and `merge = true` merges a head that passed every gate with none (#1828); neither changes who answers it. ADR 0020, #1761, `runner/pm/rulings.rs`
- A `turn-timeout` or `turn-failed` ruling keeps `Ruling.stuck_head`: the commit its item's worktree stood at when it was raised, read by `pm_noticed` with `worktree::head` of the local clone, so a worker's unpushed commits count. Set after `pm_noticed`'s `agents.pm` check and before `pm_asked` in the same pass: it is the one place that sees every raise where a project manager runs, and `failed` and `timed_out` keep their eight call sites in four files. A project with no project manager keeps none, since nothing it runs would read one, so a ruling it raised before one was set has no head and a later case says the last kept none. A head git cannot read leaves none, the ruling stands, and a note says why. No other kind keeps one, and `Ruling::new` sets none. `Record.head` carries it into `rulings.jsonl`, which names no `deny_unknown_fields`, so a line an older build wrote reads with none. State file version 104. #1819, `core/state/ruling.rs`, `runner/pm/wakes.rs`, `runner/ruling/history.rs`
- `STALLED_RESUMES` (2, no setting): the most `turn-timeout` and `turn-failed` rulings one item's head earns the project manager. `turn_stalled` reads `rulings.jsonl` newest first, counting this item's lines of either kind while `Record.head` equals `Ruling.stuck_head` and stopping at the first line at another head, so a head that moved starts the count again and two lines with no head count with each other. Past it: `pm_answers_ruling` is false, so the ruling posts at once and wakes no `Wake::Answer`; `pm decide` is refused and `settle` refuses `Action::Retry`, so `unstick` `retry` is dropped and named, under `rulings.pm_decides = false` too since `unstick` reads no map; `ask` and `re-scope` still work, and the maintainer's `yes` still resumes, with the next ruling at that head theirs until it moves. The card says why it came: `stalled_effects` is the kind's `phrases` with "2 resumes at this head moved nothing" on the `Yes` line, set on the ruling by `pm_noticed` after the head, since `timed_out` and `failed` save and post with no `word_effects`. `pm_answered_before` and `Record::decided_by_pm` are gone, replaced by this; `Record.stem` stays, so an older line reads and a case says why each turn failed. #1821, `runner/pm/{rulings,asked,act,wakes}.rs`, `runner/effects.rs`
- Ruling = log line + `status` entry + webhook post, one question; `no <note>` is worker's next turn. #89
- A ruling is named by its ticket id where the maintainer reads it: `#<pr>`, `#<issue>` before there is a pull request (a question waits for its draft, `workers.md`), or `k12` locally. The question, the webhook title, kelpie's GitHub comment and card and `status`'s `id` show it, and a reply starts with it. #508, #509, #1010
- `rule <ruling> <answer>` (`rule 427`, `rule k12`; one ruling per item within a project), refuses an answer older than the ruling. An answer file left under an old counter id is read once, then refused. #509. Each trigger is `shep kelpie <verb>`, project from folder unless `-p`. #119, #507
- `rule` reaches a stopped runner via `<kelpie home>/<project>/answers/<ruling>` files applied next pass. `runner/trigger/`
- One webhook (`discord` or `ntfy`) until shep carries questions; URL is a credential, passed to `curl` on stdin. ADR 0005, #333, `crates/core/src/webhook.rs`
- ntfy reply carries TOTP (RFC 6238): a code posted on the alert sat on the topic it guarded. #111
- `shep kelpie totp`: secret under `<kelpie home>/totp/` (0700, 0600); every code seen in any post spent first; used steps hard-linked claims (runners agree); 5 wrong codes disable ntfy answers until `--unlock` at terminal. RFC 4226, #111
- Topic read every 15s while alerted ruling waits, backing off to 5 min. Limits fail closed: topic writer can lock answers or fake alerts, not act without code. #111
- `trusted` webhook with `token` needs codes only for merge yes. #298
