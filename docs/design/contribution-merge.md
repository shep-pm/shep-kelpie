# Contribution merge

Nobody but the maintainer merges someone else's work, so `git.merging = "auto"` does not reach a contribution. #630

## The ruling

- `follow_merge` (`runner/contributions/merge.rs`) runs once a poll, after `follow_clock`. A contribution whose pass has ended on the current head, whose CI is `green` on that head, and that has no `ruled` and is not being closed (`Contribution::awaits_merge_ruling`) gets one `contribution` ruling, reason `merge`: `Held::Merge { head }`, id the pull request, no work item. It names the findings and nits the pass recorded, and says the bot threads among them are still open when a review bot answered.
- Raised under `ask` and under `auto` alike. Nothing is merged, so no notice is sent: the ruling's alert is the only post. It is never posted on the pull request and never goes to the project manager. `RulingName::ContributionMerge` is `contribution-merge`, and `rulings.pm_decides` setting it `true` is refused at load. `crates/core/src/settings/rulings.rs`
- Options are `yes`, `no <note>` and `rework <note>` (`Wants::Merge`, the same three kelpie's own merge ruling takes). A `rework` takes the pull request over at once, without waiting for the contributor to release it (`contribution-release.md`). #634 On a pull request whose fork is not `pushable` (an organization owns it, edits are off, or it was deleted) the ruling is raised with `Held::Merge { rework_off: true }`: `Wants::of` gives `YesOrNo`, the card and the question offer no `rework` and say why, and `decide` refuses a `rework` with `RuleError::Choice` and leaves the ruling. A `no <note>` can ask the contributor to merge `main` into their branch or push the change themselves. A pull request the forge cannot be read for is raised with the option. State version 90. #1375
- It holds nothing: the asks, the clock and the reviewers go on while it waits (`ruling_waits` and `over_budget` skip it). Any other ruling on the pull request takes its place and it is raised again once that is answered, except that the maintainer's thumbs on the clean-pass note answers the merge ruling while only a question waits.
- A new head, or a closed, merged or unfollowed pull request, withdraws it with no post (`withdraw`), and the new head's pass raises another.

## The answer

- `apply` records it as `contributions[].ruled = { head, verdict }` (`rule_merge`) and the next poll carries it out, so a restart loses none of it. A new head clears `ruled`. Version 61.
- `verdict` is `{ yes: { merged?, thanked? } }`, `{ no: { note? } }` or `{ rework: { note? } }`. A no or a rework with no note, or the placeholder `NO_NOTE` a reaction, a tick or the card's choice gives, has no `note`: the worker is sent to the pull request and is told nothing made up.
- Yes: `Forge::merge(repo, number, head)` with the head the ruling named, so a head that moved is refused by the forge. A refusal is logged and tried at the next poll, and after `POST_TRIES` counted refusals the ruling is raised again; a busy or rate-limited forge is not counted. Then the representative posts thanks (`merged:<n>`). A call or a post that fails is logged, never holds the merge back and is not tried again, since the merged pull request leaves the record.
- No with a note: the representative words the note for the contributor and posts it (`declined:<n>`), then the note is cleared. No with no note posts nothing.
- The maintainer may answer the waiting ruling with a reaction on the representative's clean-pass note (`pass.note`, posted by `post_note`). That note exists only when a listed reviewer that is no review bot answered the pass and found nothing: a pass with findings posts a review, and a bot's pass posts nothing, so its ruling is answered by the terminal, the webhook or `shep kelpie rule`. `post_note` ends the note with `REACT`, a fixed line of kelpie's, added after the wording is kept so a retry does not double it. Notes posted before it existed work too, since the reading does not depend on the wording.
- The reading (`answer_by_reaction`, in `merge_one`) runs while `ruled` is none, the ruling for the pull request is `Held::Merge { head }` for the current head or a `Held::Question` on a pull request that `awaits_merge_ruling` and is not released, the pass is for that head with a `note`, and `app_covers` holds. It reads `Forge::comment_marks` on the note and counts only thumbs by `git.maintainer`, else the `gh` login, ignoring case: the contributor's and anyone else's count for nothing. A down wins over an up. An up is `voice::thumbs` for the ruling, a yes for the head it names. A down is `Answer::No(NO_NOTE)`, which records no note, so nothing is posted. It is answered through `rule_by(.., Settler::Thread)`, so the first answer from any channel wins and a later reaction finds no ruling. On a question, the maintainer's thumbs takes the question out and clears `deciding` (`withdraw_question`), edits its comment where one was posted, raises the merge ruling for the head and answers it as above; the contributor is told nothing, since the question was marked answered when it was raised. A new head replaces the pass, so a reaction on an older head's note is never read. A reaction answers once per note: kelpie remembers in memory that it did, so a ruling raised again for the same head (after a merge that failed every try) is not answered by the reaction that is still on the comment. A restart forgets it. A read that fails, or an answer that is refused, is told once and tried at the next poll. GitHub's timestamp on the reaction is not read, as `Thumb` carries none.
- Neither runs a fix turn. `ruled` stays until a push, so the same head is not asked about again.
- Rework merges nothing and posts nothing. The next poll records `released { how: rework }` (`take_it_over`), which is all adoption needs, and the same poll's `follow_adoption` queues the pull request for a work item (`contribution-release.md`). Its work item starts with a worker's turn and the project's full pass queued behind it (`Phase::Implement`, `resume: Review::first()`), not at the pass a release starts at: a clean pass over the contributor's own head would let the change the maintainer asked for go undone. Its note goes on `contributions[].rework` and not on `ruled`, so a contributor who pushes before the work item starts leaves it there: the answer is about the head it was given on, the note is about the pull request. The work item's start reads it into the adopted file, and it is repeated in the log. Version 66.
- A contribution with `released` is asked about merging no more: `raise_for` skips one, whatever its head does before its work item starts.
- The thanks and the note need the App (`app_covers`); without it nothing is posted.
- A maintainer's comment is `context` for the representative and does not reset the contributor's clock (`contribution-talk.md`).
