# The review

Each pull request goes through a review before the merge gate, and no reviewer reads a head until CI has passed on it: the worker's push, and the head of each fix turn after it, wait for a green run before the next reviewer starts or a bot is summoned. A red run goes to the worker's CI fix turn first, counted toward `ci.fix_attempts`, and its fix comes back to the review. With `ci.block` off the review starts at once. The draft pull request needs CI to run while it is a draft, so `doctor` names a repo whose workflows all skip drafts (`ci on drafts`). A repo with no workflow that runs on a pull request has no run to wait for at all: the review goes on at once, `doctor` names it (`ci on pull requests`), and when a workflow does run on pull requests but no check appears in `ci.queued_minutes` the work item asks you with a `no-checks` ruling. A project names no reviewers: a pass's candidates are every agent file whose `role` is `reviewer` that `agents.allow` holds, review bots included, but the one `contributions.security_reviewer` names (see [Agents](agents.md#agents)). The agent board picks each round's reviewer from the candidates that can run, and `reviews.need` (2 by default) says how many read a work item, each once. The pass ends sooner when no candidate can run. A reviewer whose call fails three times in a row is passed over for the rest of the pass, and `status` lists it under `reviewers_skipped`. One that finds anything sends the worker all of its findings, at its own severity, for one fix turn, and the next reviewer reads the fix. A round of nothing goes straight to the next reviewer. A round of nits gets its fix turn too, and that fix starts nothing new: the pass goes on to the next reviewer as after any fix, and a bot that read the pull request before has its nits on the head that fix pushed left open, so a bot that reviews every push cannot loop on nits. A fix turn that pushes nothing parks on a ruling, unless the worker deferred every finding it was sent, or disputed it with a reason, or every one was a nit, in which case the next reviewer reads the pull request as it stands: a ruling over nits would ask you about what never holds a merge. A worker that shows a finding is wrong copies it into its disputed findings file with its reason on the next line, indented by two spaces, and the next reviewer is shown each dispute and raises the finding again only if the reason is wrong. Where no reviewer follows, kelpie posts the disputes on the pull request as one comment, and the merge ruling names it. A finding disputed a second time parks the work item on `fix-not-pushed`, whose question names what the worker disputed and deferred. A file the review script skipped for its size is cut into hunks and reviewed again, and what those hunks find goes to the fix turn as any finding does; only the notice for a file it still could not review is reported with its round and never sent, since no fix of the worker's reviews it. A pass that ends with no reviewer having read the pull request, because one was down, kept failing or reviewed no file, marks the work item unreviewed: `status` shows why, the merge ruling's question says so, and under `auto` it gets the merge ruling instead of merging. No candidate, or reviewers whose `paths` all miss the change, is your choice, and the log says so once. Every round reads the head on `origin`, which is what CI and the merge take: before one runs, the worker's worktree must hold nothing uncommitted and have that head checked out. If it does not, the worker gets one turn to push or discard, and a worktree still off the pushed head after it parks on a `stuck` ruling for `unpushed`, naming the files, and both heads when they differ, whose yes gives the worker another such turn. After the last one the pull request goes to CI. There is no judge and no second pass: whatever the last fix leaves is what CI and the merge see. The merge takes only a head a round read, or one kelpie sent to CI unread on purpose: a fix turn's push, for review findings or red CI or a conflict, a pass no candidate can read, or its own catch-up with `main` of such a head; an adopted pull request's head as it arrived counts too. Any other head, such as one pushed by hand, is named in the merge ruling, and under `auto` gets the ruling instead of merging. A pass starts again from the top only on new code that needs the whole review, such as the change a merge ruling's `rework` asks for, a change you accept that someone else pushed, or a rework of the pull request. The fix a merge ruling's `no` asks for goes to CI and back to the merge ruling, with no new pass. A project whose `agents.allow` holds no reviewer file reviews nothing. When `ci.test_command` is set, a reviewer on any harness may attach a failing test to a finding (see [Agents](agents.md#agents)). Each attached file is checked as the round's findings are taken: it must be a regular file the reviewer left, not a link and at most 1 MiB, at a path the worktree does not already hold. A finding that fails the check keeps its text and loses the test, and the step report says why. When the reviewer left no such file, the named path goes back into the finding's `why`, since a pipe in the `why` can read as a path. A checked file is copied to `review-tests-<issue>` in the worker folder, which the worker cannot write, and the worker reads the original in the build folder. Kelpie runs each kept test twice and blocks nothing on either run: once in `send_findings` at the head the reviewer read, once after the fix turn when the fix moved the head and the worktree holds the pushed head, the worker's own commit. A run puts the kept copy in the worktree at its path, runs `ci.test_command` there with `{test}` and `{name}` filled in, and takes the file out again, so the worktree is as clean as it was. A file already at that path with the reviewer's exact text, the copy the worker committed with its fix, is run as it is and left; one with other text is not run over, and the run is `not-run`. While a test is in the worktree a record of it stands in the worker folder, so a kelpie stopped mid-run takes the file out when the next round starts and says so in its notes. The command runs in the same sandbox the agents use, under the worker's fence and never the maintainer's reach, holds the `cargo-test` lease while it runs, and is killed after 10 minutes. A path with characters a shell would read is not run. Each result is `passed`, `failed` (the last 2 KiB of output), `timed-out` or `not-run` (with why). Each check is kept in the work item's `test_checks`, which `status` shows with both outcomes per finding, and the fix turn's step report carries the round's. Failed then passed reads as verified. Passed before the fix means the test does not reproduce the finding. Failed after the fix sends the worker back once: it gets one more fix turn, told the test's path in its build folder and the end of the output, and to change the code and leave the test alone, and the check is marked `sent_back`. Once that turn pushes, the test runs again. Passed then is verified. Failed again raises a `stuck` ruling for `test-still-fails`, naming every test of the round still failing, with the review round and the head. A `no` ends the check and sends the worker the note, and a commit that turn pushes is a fix turn's push, which kelpie vouches for. A turn that pushes nothing raises `fix-not-pushed` first. A timed-out or `not-run` result never sends the worker back or raises a ruling. A head pushed by someone else is not run, and the report says how many tests were not. Nothing is posted on the pull request.

A finding the worker leaves as out of scope goes into its deferred findings file; one it shows is wrong goes into its disputed findings file and is never filed. Once the pull request merges, `git.issues` decides what becomes of each one above a nit, whatever `git.merging` is: under `ask` a `follow-up` ruling comes first and a yes files each as a `ready-for-agent` issue linking the pull request, onto the board, since your yes is its triage. Under `file` they are filed with no ruling as `needs-triage`, which keeps them off the board until you read them and label them `ready-for-agent`; a repo without `needs-triage` gets it before the first one is filed. The one `follow-up` ruling `file` can raise comes when the forge has refused to take them for six hours: a yes there retries the filing, and they still go out `needs-triage`. Under `skip` nothing is filed and they stay in the review. A nit left there is dropped.

When a fix turn settles, kelpie journals what became of each finding it was sent in `journal.jsonl`: `pushed`, `disputed`, `deferred` or `nit-declined`, and for a review bot's thread `fixed`, `declined` or `not-addressed`. `pushed` means the turn pushed and the worker neither disputed nor deferred the finding, which is not proof it was fixed. Nothing new is asked of the worker.

A reviewer runs in one of four ways, by its file's `harness`:

- `claude-code`, `codex` or `pi`: a fresh session on its `model` and `effort`, which reads the worktree with Read, Grep and Glob and runs no command. The file's body is its prompt.
- `command`: a command of your own that keeps the contract below, and takes no body.
- `endpoint`: shep-kelpie's own reviewer, for any OpenAI-compatible server such as Ollama, LM Studio or llama.cpp's server. Its body is optional. With none, kelpie sends its own prompt. With one, the body replaces kelpie's opening line and its list of what to report, so it can say what the project cares about and what counts as a finding. Kelpie always adds, after the body, how the chunked, line-numbered diff looks and the answer format (`SEVERITY|file:line|what|why`, or `CLEAN` alone), then the issue's acceptance criteria. A body that asks for another answer format is still read in kelpie's. Kelpie cuts the diff into chunks, so a body naming `{{BASE}}` or `{{DIFF}}` is refused.
- `bot`: a pull request review bot, CodeRabbit, cubic or Codex, summoned on the pull request (see [Review bots](#review-bots)), and takes no body.

A session's prompt is its file's body with the commit the change is against at `{{BASE}}` and the diff at `{{DIFF}}`. A body with no `{{DIFF}}` gets the diff after it. The body asks for kelpie's format, one finding per line as `SEVERITY|file:line|what|why`, or `CLEAN` alone. Every reviewer's prompt carries the issue's acceptance criteria: the section under an "Acceptance criteria" heading, or the whole body without one. `paths` limits a reviewer to pull requests that change a file under one of its globs, and the review skips it elsewhere. `second_look: true` runs a session twice: the second fresh session is shown what the first found and asked only for what it missed, and the worker gets one fix turn for both lists. With `ci.test_command` set, a `claude-code` reviewer also has `Write`, a `pi` reviewer `write` (and no `edit` or `bash`), a `goose` reviewer `write` (its `edit` stays refused, and its shell is read only), and a `codex` reviewer `apply_patch` (it has no shell), each held to one folder, `review-tests` in the work item's build folder, and is asked to leave one failing test per finding there, at the path the test should have in the repo, named as a fifth field: `SEVERITY|file:line|what|why|tests/flag.rs`. A fifth field that is not a relative path with no `..` and no spaces stays part of `why`. A `command` or `endpoint` reviewer, or any reviewer without the setting, is read as before.

shep-kelpie ships `defect-hunter-lite`: Opus 5.5 at medium effort reading the whole pull request for defects, meaning a trigger and an effect a failing test could be written from, and not for style or naming, in one session. `defect-hunter` is the same prompt at high effort with a second look. `iq3-xxs-review` is an endpoint reviewer on the model `iq3_xxs` behind a gateway named `paddock`.

A contribution with no `contributions.reviewers` runs `defect-hunter-lite`, and `iq3-xxs-review` before it where kelpie's settings hold a gateway named `paddock` (see [Gateways](agents.md#gateways)). `qwen` runs `~/.claude/scripts/qwen-review.sh`, an optional local review script, and is never a default.

`standards` and `spec` are the two axes of the vendored `code-review` skill, one reviewer each, since the skill runs them as parallel sub-agents and kelpie's workers spawn none. Both are baselines that need a binding, read once with no second look, and answer in the same `SEVERITY|file:line|what|why` lines. They do not replace `defect-hunter-lite`. Once bound, they are candidates wherever `agents.allow` holds them, and the agent board may pick either toward `reviews.need`.

- `standards` reads `CODING_STANDARDS.md`, `CONTRIBUTING.md` and `CLAUDE.md` where the repo has them, and checks the diff against them and against the skill's twelve code smells, such as Duplicated Code and Speculative Generality. It covers the verbose and repeated code `defect-hunter` is told to skip. A documented standard overrides a smell, what tooling enforces is skipped, and a smell is never above `LOW`, since each is a judgement call.
- `spec` checks the diff against the issue's acceptance criteria, which are cut at 4,000 bytes. It reports a requirement that is missing or partly done, behaviour nobody asked for, and a requirement that looks done but is wrong, quoting the criterion for each.

A local model and a deeper read of the paths where it pays can be candidates alongside the defect hunter. A project names no reviewers of its own: `agents.allow` names the agents it may use, so it holds the reviewers it wants and its implementers too:

```toml
[app.dogs.kelpie.agents]
allow = ["sonnet-high", "gpu-box", "defect-hunter-lite", "merge-reader"]
```

```markdown
---
role: reviewer
harness: endpoint
url: http://localhost:11434/v1
model: qwen2.5-coder:14b
context: 32768
---
```

```markdown
---
role: reviewer
harness: claude-code
model: claude-opus-5-5
effort: high
paths: ["src/auth/**", "migrations/**"]
---

Read the change against {{BASE}} for ways it lets the wrong account in. Output
one finding per line as SEVERITY|file:line|what|why, or exactly CLEAN.
```

A missing command or an endpoint that doesn't answer stops the runner at start.

## Review bots

A review bot reads the pull request on the forge, as a candidate like every other reviewer file, once a pass. shep-kelpie ships a file for each, `coderabbit`, `cubic` and `codex`, which `add` writes out. A project that names the agents it may use runs a bot only while `agents.allow` holds it:

```toml
[app.dogs.kelpie.agents]
allow = ["sonnet-high", "defect-hunter-lite", "coderabbit"]
```

```markdown
---
role: reviewer
harness: bot
bot: coderabbit
reviews: 1
hours: 1
---
```

A bot's file is named for its bot, since `reviews` in `hours` is its account's window, which the dog books from that file when it starts and every project shares. A bot whose window is closed is passed over at the pick. Its round marks a draft ready, since a bot may skip drafts, takes the bot's lease, and summons it: CodeRabbit by the `review please` label, or by `@coderabbitai full review` on a pull request it read before that would otherwise find nothing new, cubic and Codex by their comments. A summon with no sign of being heard in fifteen minutes goes out once more. Once a review covers the head, the bot's open threads are its findings, and go to one fix turn as any reviewer's do. A refusal hands the window back to the dog and the round asks again. A window that opens more than an hour on, by the dog's book or by the bot's refusal, passes the bot over for the pass, and so does a bot that gives no review in its file's `review_wait` after its summon (minutes, 45 when unset), a bot that gives no sign of its summon in ten minutes and has never posted a review on the repo (its note says it may not be installed there), a status that declines the summon (CodeRabbit's `Review skipped: automatic reviews are disabled` or `Review skipped: excluded by label configuration`, which its `.coderabbit.yaml` sets and passes the bot over at once), as long as `review_wait` its round could not summon it, a bot `agents.allow` stops holding mid-round, and CodeRabbit on a repo the forge reports not public, which is checked just before each summon; `status` lists each under `bots_skipped`, and a pass nobody else read is marked unreviewed. A bot passed over that reviews the head anyway is still read: at the start of each later round, when CI goes green, and every five minutes while the merge ruling waits. Its review gets a round of its own, and its threads go to one fix turn as any review's. Once the pass has ended, that fix goes back to the merge ruling with no new pass, after the round of any other passed-over bot that has reviewed late too, and the ruling says no reviewer read it and comes to you even under `auto`. A merge ruling already waiting is withdrawn for it, which the log and the webhook say, and the work item takes a free slot for the round or waits for one. A bot that already read the pull request this pass and reviews a later head is not sent again: its open threads are named in the merge ruling, and under `auto` any above a nit hold the merge. Open nits are named in the merge ruling on their own, as in `3 nits left open (cubic)`, and never hold a merge. `rounds: 1` lets a bot read a work item's pull request once, whatever its passes, counting its reviews from before a rework or an adoption, and is unset by default. An adopted pull request goes through a pass of the candidate bots alone, and until each bot answers a summon of shep-kelpie's own, none of its reviews from before the adoption stands for its read. Codex's `reviews_on_ready: true` says it reviews a pull request when it leaves draft, as the repo's Codex settings may have it: then marking ready, under its lease, is the summon, with no comment, and it is never asked again by comment. In `contributions.reviewers`, list it before any other bot, whose mark-ready would draw its review outside its lease: the runner refuses the other order.

A project that names the agents it may use runs only the bots `agents.allow` holds. Absent or empty, `agents.allow` allows every agent, including the shipped bots. Kelpie passes over a bot its repo cannot run. A bot passed over because it has never reviewed there and did not answer, or because the repo is not public, is left out of picks for 7 days and returns sooner if kelpie sees it reviewing. A bot passed over for its window or later silence stays a candidate. CodeRabbit's free plan reviews public repos only, so a repo GitHub marks private cannot name `coderabbit` in `agents.allow`; it can name `cubic` or `codex` instead. shep-kelpie asks CodeRabbit for a review by putting the `review please` label on, so the repo's `.coderabbit.yaml` must review only labelled pull requests. Without that, CodeRabbit reviews every push on its own and spends the hour a round is waiting on:

```yaml
reviews:
  auto_review:
    labels:
      - "review please"
```

Every thread a review bot leaves open goes to the worker as a finding. The fix turn's prompt asks the worker to end its reply with one line per finding, numbered as its line in the findings file is (`thread 1|MEDIUM|...`): `thread 1: fixed`, or `thread 2: declined: <the reason>`. shep-kelpie, not the worker, writes to the pull request: it replies on each thread and resolves the ones the worker fixed once the fix moves the head. A declined thread gets the worker's reason as a reply and stays open. A thread the reply does not mention gets a reply saying it was not addressed and stays open, and so does a thread the worker calls fixed in a turn that pushed nothing. Open threads are still the merge ruling's to name, so a declined or unaddressed thread is counted there. This holds for every fix turn a bot's threads go to: a review pass's rounds, a late round, and the new pass a merge ruling's `no <note>` starts when the ruling warns of open threads. A nit fix that pushes nothing (the worker declined the nits) gets the same replies. If the forge refuses a reply or a resolve three steps in a row, the review goes on with the rest open and the bot's next read sends them again.

## Comments from people

Comments on the pull request from people with write access to the repo (its owner, an organisation member or a collaborator) reach the worker. Kelpie reads them where it already reads the pull request: at the start of a review round, when CI goes green, and every five minutes while a merge ruling waits. New comments and review threads are batched into one resumed turn, each numbered as a request. A review thread is answered as a review bot's is: the worker ends with `thread 1: fixed` or `thread 2: declined: <the reason>`, and kelpie replies on the thread and resolves the fixed ones. A comment on the conversation gets no reply. A comment from an App other than a listed review bot, or from anyone without write access, is ignored and logged once.

- A comment the worker judges ambiguous or architectural ends its turn with a question block, which raises a `question` ruling. Your answer goes to the worker.
- The fix goes to CI and back to the merge ruling with no new pass of the review. The ruling says its head is the worker's fix for a note or comment, and comes back to you even under `auto`.
- A comment that lands while a merge ruling waits withdraws the ruling and is handled as that ruling's `no <note>`. A reply in the ruling's own GitHub thread that opens with a number, `yes`, `no` or `rework` is still answered as a ruling's reply. On a merge ruling, any other comment from the login it mentions is the `no <note>`. On any other ruling, such a comment is told how to reply, and a worker's question takes any text as its answer.
- A work item gets three of these rounds. A fourth comment raises a `question` ruling that says so, and your answer is what the worker then gets.
- The comments already on a pull request kelpie adopts or reworks, or that were there when a work item in flight was upgraded to this version, are marked heard at the first read and sent to no one.
- A turn that declines every request pushes nothing, and that is fine: kelpie replies on the threads as declined and the work item goes on.
- Review summaries with no inline thread are not read, and neither are comments that land while a turn runs; the next read finds them.

## Local reviewers

An endpoint takes `url` (the base, up to and including `/v1`) or a `gateway` (see [Gateways](agents.md#gateways)), `model`, and `context`, the context size in tokens the server gives that model. Kelpie diffs the pull request, cuts the diff to fit that context, and sends each piece with its own review prompt. Set `context` to what the server really uses: Ollama gives its OpenAI-compatible endpoint a small default context unless `OLLAMA_CONTEXT_LENGTH` says more, and drops whatever doesn't fit without saying so.

A command is run as `<command> --dir <worktree> --round <n> --diff <base>`, where `<base>` is the commit the branch started from (the merge base of the project's base and the head), so a diff of it against the worktree holds the pull request's own change, with:

- `QWEN_REVIEW_OUT`: the folder to write in
- `KELPIE_REVIEW_HEAD`: the commit under review
- `TMPDIR`: the temporary folder the maintainer's shell has (macOS's per-user folder when the runner has none), where the script builds its own GPU lock
- `KELPIE_REVIEW_CRITERIA`: a file holding the issue's acceptance criteria

It writes `round-<n>.txt` in that folder, one finding per line as `SEVERITY|path:line|what|why` with `HIGH`, `MEDIUM` or `LOW`, and then an empty `round-<n>.txt.done`. Kelpie reads nothing without the marker, and nothing from stdout. A nonzero exit fails the round. A command that writes `LOW|<path>:0|not reviewed: <n> lines exceeds the chunk limit|...` is run again with `--files <hunk file>` in place of `--diff`, on that file alone. If that run fails, its file is left unreviewed, as below, with the failure as the reason; only when kelpie cannot cut the hunk with `git diff` does the placeholder stay as the finding. Any other `LOW|<path>:0|not reviewed: <why>|...` line, as the script writes when the model cannot be reached, is a file left unreviewed and not a finding. A round with nothing but those lines reviewed nothing, and the review goes on to the next reviewer. A round that leaves the same files unreviewed as the same reviewer's last round counts against it too, and one that leaves none clears its count. A second such round in a row, which takes two passes, leaves the reviewer out of the review for the rest of the work item, and `status` lists it under `local_reviewers_down`. Another local reviewer, on another command or server, still runs. A round with real findings and some `not reviewed:` lines keeps its findings.

Kelpie holds no lock around a round, and a `lease` key in an agent file is refused. A server shared with other callers goes behind a `gateway`, which queues its rounds. A command that needs the GPU to itself takes its turn from paddock, with `shep paddock run --model <model> -- <command>`.

Kelpie reads no `/api/ps`: a model that spilled to the CPU is no longer checked or parked on a ruling.

### Kept rounds

A local round's files go with its work item's build folder, so kelpie copies them out when the round ends, however it ends: to `local-rounds/<issue>-r<round>-<UTC time>/` in the project's kelpie folder, beside a `round.json` with the pull request, the base and head commits, the reviewer, its model, the `max_tokens` asked for, the start and end times, how it ended (`answered`, `cut_off`, `unreadable`, `busy`, `unreachable` or `failed`) with the reason, and how many findings went to the worker. A round is about 250 KB.

Kept rounds older than 30 days are removed when the runner starts and after each kept round, and nothing else in the folder is touched. Three keys in `local_rounds` change it: `keep = false` keeps nothing, `keep_days` sets the days (0 keeps every round), and `folder` is an absolute path to keep them in instead. `shep kelpie set local_rounds.keep false` turns it off.
