# Commands

shep-kelpie runs in your own shepherd, beside your other sheep. The adopted dog holds the leases every runner asks before a summon, and it asks shep for the channel the lease commands reach it on. `add` and `start` say how to bring the dog up when it is not running with its channel.

```sh
shep kelpie add        # labels, settings, agent files, and the runner, stopped
shep kelpie add --base next  # the same, for work that goes into `next` instead of the default branch
shep kelpie start      # starts the runner, which runs the project
shep kelpie pause      # stops it once its calls end, or at their next tool call
shep kelpie finish     # stops it once its open work items end, picking nothing new
shep kelpie finish --all  # the same for every project
shep kelpie status     # every project, or --json for the runner's whole object
shep kelpie doctor     # what each project still needs on this machine
shep kelpie agents list   # every agent, the files that bind nothing, and the baselines that bind nothing and have no file
shep kelpie agents new pm --harness claude-code --model claude-opus-5-5 --effort high
shep kelpie agents init claude-code   # a bound file for every role claude-code serves
shep kelpie agents init pi --gateway paddock   # or --url <url>, for a harness that runs its model on a server
shep kelpie agents init --detect   # each role on the first harness found that serves it
shep kelpie agents migrate   # write into each stub the binding its baseline shipped with
shep kelpie settings migrate   # write into each project's table the kinds of ruling it is missing
shep kelpie rule 14 yes
shep kelpie issue check 7   # whether issue 7 holds every part an implementer builds from
shep kelpie issue check --draft issue.md --label "priority: P4"   # the same for a draft, its title the first line
shep kelpie attach 7   # steer issue 7's worker in this terminal
shep kelpie watch      # follow the runner and its sessions live, or `watch 7`, `watch pm`
shep kelpie ticket new "<title>" --label ready-for-agent   # a local project's ticket, prints its id
shep kelpie upgrade --ref main
shep kelpie tools install
shep kelpie github setup   # once per repo owner, with --org <org> for an organization
shep kelpie totp       # once, to answer rulings from ntfy
shep kelpie lease status
shep kelpie get git.merging        # one setting of the project's table, or all of it with no key
shep kelpie set git.merging auto   # changes one setting
shep kelpie get -p '*' git.merging   # one line per project whose name matches the quoted glob
shep kelpie set -p 'shep*' git.merging auto   # the same in every one of them, or in none if one refuses
shep kelpie version    # this build, the commit it was made from and the shep it is made with, or --json for one line
```

The verbs with flags of their own:

- `upgrade` takes `--ref <git ref>`, `--release <version>`, `--binary <path>` or `--rollback`, and `--now` to restart the runners with no handover or drain: see [Upgrading](upgrading.md#upgrading)
- `github setup` takes `--org <org>` for an organization's App, `--name <app name>` for the App's name (`kelpie-<owner>` when left out) and `--replace` to register a new App in place of the one kept for the owner
- `totp --rotate` draws a new secret, and `totp --unlock` turns answers from ntfy back on after too many wrong codes
- `lease run <kind> -- <command>` waits for a lease, runs the command and returns the lease when it exits. `lease take <kind>` holds one until `lease return <kind>`. `lease e2e` runs the project's end-to-end tests on its host: see [Leases and end-to-end tests](leases-and-e2e.md)
- `ticket` alone lists these forms. `ticket new "<title>" [--body <text>] [--label <label>]... [--parent <id>] [--blocked-by <id>]...` files a local ticket and prints its id. `ticket list [--all]` and `ticket show <id>` read them, `ticket edit <id> [--title <text>] [--body <text>] [--label <label>]... [--unlabel <label>]... [--parent <id>] [--no-parent] [--blocked-by <id>]... [--unblock <id>]...` changes one and `ticket close <id> [--not-planned] [--duplicate]` closes it: see [Local tickets](tickets.md)
- `agents list` prints a line for each agent (its name, role, harness, model and effort), and for an implementer or reviewer its `tier` (`standard` when its file names none), its `kinds` when the file sets them and its `description` when it has one, last and on one line, then each agent file that binds nothing with the command that binds it, then each baseline that binds nothing and has no file. `agents migrate` deletes each file that extends `kelpie:advisor` or `kelpie:researcher`, roles that went with the ruling panel, or `kelpie:issue-writer`, which went with the issue writer, when it holds only `extends`, `harness`, `model` and `effort` and no body (`advisor.md: deleted, its role went with the ruling panel`), and names any other such file it leaves, and any file whose own `role` is one of them. It writes into each file that extends one of the seven baselines the harness, model and effort (and `second_look` for `defect-hunter`) that baseline shipped with before baselines carried none, after its `extends` line, and prints a line for each file written (`pm.md: wrote claude-code claude-opus-5-5 medium`), then each file it skipped and why, or `nothing to migrate`. A file that sets another session `harness` than the baseline's (not `claude-code`) but not a `model` and `effort` is skipped. It is safe to run again, and `shep kelpie upgrade` and the dog's start run it too. `agents new <role> --harness <harness> --model <model> --effort <effort>` writes `<baseline>.md` as `extends: kelpie:<baseline>` and those keys. `--baseline <name>` picks the baseline, which `reviewer` needs since it has four (`defect-hunter`, `standards`, `spec` and `security-reviewer`). `--name <file name>` names the file, and an `implementer`, which has no baseline, needs it. `--second-look` sets `second_look`, `--gateway <name>` or `--url <url>` says where a model is served, and `--context <tokens>` sets `context`. It reads the text as the loader does first, so a binding the loader refuses writes nothing, and it writes over no file except one that binds nothing: see [Agents](agents.md)
- `agents init <harness>` writes a bound file for the implementer and for every baseline of every role that harness serves, from kelpie's own models file, and names each role it skips and what the harness lacks. A pi or goose row needs `--gateway <name>` or `--url <url>`, and `init` on a harness with no rows there refuses naming the file. `agents init --detect` takes no harness and no `--gateway` or `--url`: it looks for each CLI kelpie runs on the `PATH`, asks each gateway in kelpie's own settings for the models it serves, and gives each role the first harness in the file's `order` that was found and serves it, saying why a role got none. Neither writes over a file that is there, and neither touches a project's settings or prints a `shep kelpie set` line, since the agent board picks the implementer and each round's reviewer from the agent files `agents.allow` holds: see [Agents](agents.md)
- `settings migrate` writes into every project's table each kind of ruling `rulings.pm_decides` is missing, at its default (`true` for the operational kinds), after turning an old `rulings.pm_alone` list into the map. That is every kind, not only those the list named, and a kind deleted from the map is written again, and prints a line for each project written (`project koji: wrote rulings.pm_decides.rebase = true`), or `nothing to migrate`. It never changes a key the table has, and a table the runner would refuse is not written and is named with its reason. It also deletes the panel's old `rulings.decide`, `rulings.full_panel_paths`, `agents.advisor`, `agents.researcher` and `[researcher]` table, and `advisor` and `researcher` from `repo_setup.roles`, and the issue writer's `agents.issue_writer`, `issue-writer` from `repo_setup.roles` and the `unlabelled` kind from `rulings.pm_decides` and the old list, and the `agents.implementers`, `agents.implementer_choice` and `agents.fallback_after` the agent board replaced, naming each on the project's line, a deleted key with the value it held so a rollback can write it back (`removed rulings.decide = "panel", agents.fallback_after = 15, advisor from repo_setup.roles`). `shep kelpie upgrade` runs it too: see [Rulings the project manager answers](rulings.md#rulings-the-project-manager-answers)
- `get [<key>]` and `set <key> <value>` read and change the project's settings: see [Settings](settings.md)
- `issue check <ticket>` reads the issue through the project's ticket source and checks its structure, not its quality: a `Touches:` line naming files in backticks, on it or in a list under it, or a `Touches` heading over them, a `## What to build` section, a `## Acceptance criteria` section of `- [ ]` items, a `Harness reach:` line when it touches one harness's adapter, a `Blocked by:` line that names an issue when it has one, one priority label, and a kind: one `kind:<type>` label, `<type>` one of `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `ci`, `chore` or `style`, else a title that starts with one, as `fix(board): ...`. `bug` and `enhancement` are not kinds. It prints that the issue passes and exits 0, or each part it lacks and exits 1, and exits 2 when it could not read the issue or the file, so a script can tell a failing issue from a failed read. `issue check --draft <file> [--label <label>]...` checks an issue not yet filed, the file's first line its title and the rest its body, with the labels given: it reads no settings, shepherd or network and needs no `SHEP_HOME`, so a worker can run it in its sandbox. Any other words after `issue` are refused: the issue writer that took a request is gone, and the refusal names the `issue` skill that writes an issue (see [Writing issues](issues.md#writing-issues))

`status` prints a short block per project: its run state, the build its runner runs, each work item with its phase, turn and pull request, the rulings waiting, and the pacer.

```text
$ shep kelpie status
koji (finishing)
  run: finishing
  build: 1f2e3a4
  work items:
    #7 Add a thing: phase ruling, turn ended, PR #71
    #9 Fix the other: phase implement, turn running, no PR
  rulings waiting: 1
    ruling 1: merge, #7, PR #71
  pacer: on
    claude: session 3%, week 15%, 15% of the week spent today of 14.3% allowed
    claude holding (allowance): today's allowance is spent
```

The `build:` line is the commit that runner's own build was made from, which is not the build on disk: a runner an upgrade left behind keeps naming the one it runs, and the line then reads `build: 1f2e3a4, not the installed 9c8b7a6`. A build made from a tree with uncommitted changes names `1f2e3a4-dirty`, and is marked against the clean commit it was made on top of, being a different binary from it. A runner on a build from before a build named its own says `build: not recorded`.

`status --json`, before or after `-p`, prints each runner's whole object on one line, which the rest of this README names its fields from (`work_items`, `pacer`, `forge_held_until`, `board_poll_secs` and the others). `lock` is the longest time the runner's lock was held since it started, in seconds, by the source line that took it; it is left out until a hold is recorded. Read it with `shep kelpie status -p koji --json | jq .pacer`, or `shep trigger koji status`. Without `-p`, a project that is not running, or still starting, is one line either way.

Every trigger a person sends the runner is also a verb: `add <ticket>`, `rework <pr>`, `adopt <pr>`, `triage <issue>`, `gate [<ticket>]`, `drop [<ticket>]`, `timings [<n>]`, `board`, `board move <issue> <position>`, `board top <issue>`, `tell "<note>"`, `pm`, `rule`, `drain`, `undrain` and `finish`. Each reaches the project whose repo holds the folder you run it in, a worktree of it included, or the one `-p <project>` (or `--project <project>`) names anywhere in the line. Run from your own clone of a project's repo, it finds the project whose `git.remote` is that clone's `origin`; two projects sharing one `origin` are named and `-p` is asked for. From anywhere else it lists the projects and guesses nothing. `shep trigger` still works. A `<ticket>` is an issue's number, or `k` and a counter such as `k12` for a local ticket; kelpie reads only GitHub issues so far, so a local one is refused, and no project can be registered under a name shaped like one. `add <ticket>`, `gate`, `drop`, `timings`, `board`, `tell`, `drain`, `undrain` and `finish` print plain text, and the runner's JSON with `--json`, as `status` does; a refused answer prints its reason and fails either way. Where the runner gave no object to print, a `finish` on a stopped runner or a `tell` that timed out, `--json` prints `{"sheep": ..., "message": ...}` with the sentence the plain form prints.

- `add`, `rework`, `adopt`, `triage` and `rule` read GitHub, so a runner in the middle of a pass queues them and answers at once with its status, which does not show the verb's outcome yet. The pass takes them up first. A refusal then shows in the runner's log, and in `status --json` under `standing` until the same verb is asked again and goes through; plain `status` does not print it. `rule` is the exception: an id no ruling waits on is refused in the reply, since the runner already knows it. With the runner between passes the verb applies at once and a refusal is the reply, as before. The plain line says "queued" either way. `timings` and `board` answer from the runner's last posted copy while a pass holds the lock
- `drain` holds back every call the runner would start next, and answers the status with the calls still running under `draining`. `undrain`, or a restart, lets calls start again. `shep kelpie upgrade` drains each runner itself: see [Upgrading](upgrading.md#upgrading)
- `drop [<ticket>]` ends a work item without merging it. Its worktree, local branch and build folder go, and its pull request stays, labelled `ready-for-human`. The board leaves the dropped issue be while it is labelled `ready-for-agent` and its title and body read as they did, and says in its briefing and in `status` that it was dropped. Editing the issue returns it to the board on the next read. Once the runner has read the issue without the label (at most once a minute, even while the board is shut), putting the label back returns it to the board; `shep kelpie add <ticket>` takes it back at once, or queues it for the next free slot when every slot is held, unless the board would pass it over for another reason, its pull request still open among them
- `handover` (`shep trigger <project> handover`, no verb) replaces the runner's image with the installed build in place, keeping its pid and the worker turns running. The runner acts between passes, and waits while a call's stdin is still being written, a notice hook is running or queued, or a queued `add`, `rework`, `adopt`, `triage` or `rule` has not been taken up. It starts the installed build once first, as a runner that stops after reading its settings and agent files, so a build that would refuse them is refused while the old image runs. A refusal leaves the old image running and the answer says why, for example a build that cannot read the state, or a call that is not a worker's turn from this image. A request that has to wait for a quiet point (a feed, a pass) is answered `waiting` after 2.5 seconds, and a refusal after that is in the runner's log only. A handover that happens gets no answer, since the process that would give it is replaced
- `gate [<ticket>]` sends a work item whose worker's turn ended with a pull request into the review gate, when it was never entered
- `tell "<note>"` and `pm` reach the project manager: see [The project manager](board.md#the-project-manager)
- `timings [<n>]` totals where the time went over the last `n` finished work items (10 when left out), in six phases: `worker`, `review`, `ci`, `ruling`, `merge` and `other` (every second lands in exactly one), and prints the table, so `shep kelpie timings 20` shows it. With `--json` it prints the runner's object, the totals under `seconds` and the same text under `table`. `status` shows each open item's split under `timings`, and the ten most recent finished items under `history`. The state file keeps the last 100

`usage` reads the project's usage ledger, `<kelpie home>/<project>/usage.jsonl`, here, without the shepherd. Each model call adds a line to it as it ends: the runner writes the worker's turns, every reviewer's sessions and local rounds, the project manager's wakes, compactions and batch retros, and the representative's and the triager's calls. Each line has the call's four token counts, its units, its dollars where the harness reports them, and the pacer's last reading where there is one (imported lines have none). A finished work item adds a line of its own, which counts the findings above a nit its worker was sent (`held`, by severity) beside the findings it disputed (`disputed`) and deferred (`deferred`), each once per round it was sent and left out at zero. `shep kelpie usage [<project>] [--since <date>]` prints, for each merged pull request, its units, dollars and the calls those dollars leave out because their harness reported no cost, wall time, rulings and the worker's and reviewers' shares of the units, with their medians, the loaded units per merged pull request (every call, the project manager's, the retired roles' and those of work items dropped or closed with no change included, over the merged count), the work items that ended with their issue closed with no change and those dropped, then the project manager's totals, and the retros' when any ran, and a `retired roles` line when the ledger holds calls of a role kelpie no longer has, such as the ruling panel's `advisor` and `researcher` or the `issue-writer`, naming each role with its calls; those calls count in the loaded figure too. Every dollar figure says how many unpriced calls it leaves out, as in `$4.20 + 3 unpriced calls`; with no project it prints every project that has a ledger. Units weigh tokens as the control room was measured: cache read 0.1, one-hour cache write 2, five-minute cache write 1.25, output 5, uncached input 1. `shep kelpie usage [<project>] --openmetrics` prints the ledger's call and finished lines as OpenMetrics counters with timestamps, under the names and labels of kelpie's live series (see [Metrics](metrics.md)), to load into Prometheus with `promtool tsdb create-blocks-from openmetrics`. `shep kelpie usage <project> --import <steps file>` adds the turns a runner logged but the ledger lacks, its `ended` and `asked` lines in `<kelpie home>/<project>/steps.jsonl`, skipping any the ledger already holds. Baselines to compare with, such as the control room's own units per merged pull request, can go in `<kelpie home>/baselines/baselines.json`, which stays on your machine; `usage` holds each against kelpie's loaded figure and its median, as kelpie over the baseline, so below 1 is cheaper.

Three more reports join the ledger to the transcripts of its sessions, with no shepherd asked. Each takes a project, and `--json` prints one JSON object in place of the text, which is also what to paste into a bug. A transcript is found by the session id the ledger names, in the folder the runner's `session-started` step logged in `<kelpie home>/<project>/steps.jsonl`, so a call from before that step, or whose transcript was deleted, is counted as having none. Requests are read from Claude Code's, pi's and Codex's transcripts, and goose keeps no whole transcript. `--reads` shows no files for Codex, whose rollout names none.

- `usage <project> --item <issue>` lists the work item's calls in the order they ended: time (UTC), role, kind, harness, model, the four token counts, units, dollars (`-` where the harness reported none), seconds and how each ended. Below, each session with its transcript's path and how many requests it holds. `--json` has `calls`, the ledger's lines as written, and `sessions`.
- `usage <project> --context [--since <date>]` shows, per role and harness, how big the requests were, as input plus cache reads plus cache writes: the median over sessions of a session's first request, the median and largest of all requests, and the share of all their tokens (output included) that were cache reads and cache writes. A session counts under the role and harness of its first call in the window, whole, and once however many times it was resumed; a request counts once however many lines Claude Code wrote for it. A subagent's requests are left out. Sessions with no readable transcript, and those whose transcript holds no request, are counted apart, below the table.
- `usage <project> --reads [--since <date>]` shows what workers read before their first edit, per harness: the median number of files, and the files read, counted once per session, split into those the session then edited, neighbours (in the folder of an edited file, or of the Rust module it names), other code, and docs (`.md`, `.mdx`, `.txt`, `.rst`, `.adoc`, or under a `docs` folder of the checkout the session began in), each first of those it fits. Only reads of files by the harness's own read tool count, not a `cat` in a shell. A worker session that edited no file is counted apart and left out of the split.

`usage --forge [--since <date>]` reads the forge ledger, `<kelpie home>/forge.jsonl`, here, without the shepherd. Every project's runner appends to the one file: a line for each call through the forge port (the maintainer's login, or the GitHub App's for the reads it makes) and each write or token of the GitHub App's voice, with its time, project, kind (`pull_request`, `reviewed`, `review_bot`, `app_comment` and so on), `rest` or `graphql`, `by` (`login` or `app`, whose rate budget the call spent; a line from before this field reads as `login`), milliseconds, and how it ended: `ok`, `failed`, `held` (never made, because an earlier answer had the limit used up) or `used-up` (GitHub said a rate limit is used up). A line is one port call, and a port call can ask GitHub more than once, so the counts are a lower bound on requests. A call that asks both APIs counts as GraphQL. The report prints the calls made, held and used up, then calls per project, per identity and per kind (calls, minutes with a call, the average over those minutes, the busiest minute), the ten busiest minutes with every project and kind in them, and each used-up answer, with `app` after its API where it was the App's budget, and the calls made in the 60 seconds before it (read from the whole ledger, so `--since` does not cut the window). The read of when a used-up limit resets (`rate_limit_reset`) is a call too, and is recorded. A minute is a clock minute in UTC, and held calls are left out of every count. Each line is one write to the end of the file, so runners appending together do not mix lines. A ledger that cannot be written is told once on stderr and costs no call. The runners count the same lines as `kelpie_forge_calls_total` by API, identity and how each ended, and set `kelpie_forge_rate_used` and `kelpie_forge_rate_reset_timestamp_seconds` from GitHub's own count of the login's `core` and `graphql` limits, read once a minute (that read is a `rate_limit` line here, and counts in no total); the kind breakdown is only here (see [Metrics](metrics.md)).

`watch [<issue> | pm] [--back <n>] [--full]` follows a project live, in one stream, without asking the runner. Each line is a time, who, and one of the prompt kelpie sent, what the agent said or thought, a tool it called, a tool's result, or a runner step. Who is `runner`, `pm`, or `#<issue> <role> (<agent>)` for a worker or a reviewer. It starts at the end of the stream, or `--back <n>` lines before it, sorted by time. `watch 7` shows only issue 7's sessions and steps, and `watch pm` only the project manager's. A line is one clipped row; `--full` shows prompts, results and thinking whole. It reads the runner's steps, `<kelpie home>/<project>/steps.jsonl`, and the transcripts of the sessions they name, so it works for Claude Code, Codex and pi sessions alike, and from any terminal. A session is attributed by the id in the runner's `session-started` step, logged as its call starts, so a session started before this step existed shows its runner steps only. A project written by a runner from before `steps.jsonl` has none of its steps there, and `watch` shows nothing for them.

## `add` and `doctor`

`add` is step 4 of [Getting started](../../README.md#4-add-your-project), and the settings it writes are in [What `add` writes](settings.md#what-add-writes). `start`, `pause` and `finish` find the project from the checkout, or take its name.

`doctor` changes nothing and prints one line per check, each missing piece with its fix, then exits non-zero if a project needs something it lacks. It checks that `claude` is installed and logged in, that `gh` is logged in and may push to each project's repo, the sandbox runtime every agent runs in, the shepherd's version, each project's checkout, the implementers the agent board may pick and labels, any old keys its table holds that nothing reads, where its tickets come from (GitHub's issues, or how many a local store holds), that kelpie's GitHub App is installed on each project's repo and mints a token, that a worker there holds a token that pushes and nothing more rather than your own `gh` login, which identity reads each project's board, pull requests, reviews and checks (the App, or your `gh` login, with the permissions an older App lacks), and that a ruling on a repo it covers has a login to mention (`git.maintainer`, else the one `gh` acts as) there, and, on macOS, the login token a covered project's `claude` needs, CodeRabbit where a project lists it, each project's reviewers, in order, with any command or endpoint among them checked as a runner's start checks it, Codex's usage for a project that spends it, `rg` and `fd` on the `PATH` for a project with an agent on pi, which pi's own `grep` and `find` tools run, each project's e2e host, where it names one, as `ssh` and `rsync` being on the `PATH`, and which webhook, if any, rulings post to. `shep kelpie doctor <project>` checks one project. `--test-alert` posts one test alert to the webhook, which is the only post it ever makes. A line marked `unsure` could not be settled, and does not fail the run: CodeRabbit is one, since a repo it has not yet reviewed looks the same as a repo without it. The GitHub App's line is `unsure` when GitHub is out of reach, busy or rate limited, and when the owner has no App, since kelpie then posts as it always did.

## Pausing and finishing

`pause` starts no new call, lets the calls already running finish and a merge found in flight land, then has shep stop the runner, so `shep ls` shows it `stopped`. It says what it waits on meanwhile. A worker turn on Claude Code or pi does not run on to its end: it ends at its next tool call and resumes at the next start with a fresh turn ceiling, and `pause` names those work items. A tool call still running after 10 minutes is stopped as `shep stop` stops it. A Codex or goose call runs on to its end. A session you attached keeps running in your terminal. A ruling still waiting can be answered with `shep kelpie rule` while the runner is stopped, and it acts on the answer when it starts. `shep kelpie start` runs it again. A merge a ruling starts in the moment between that check and the stop can still be cut short, and its work item resumes when the runner starts. If a wait runs out, you interrupt it or shep refuses the stop, the runner keeps running. It stops mid-item, where `drain` only holds back new calls and never stops anything. `finish` lets every open work item run on to its end, through review, CI, rulings and the merge, picks nothing new from the board, then stops the runner the way `pause` does once the last item has merged, closed or been dropped and any merge notice has been posted. An item parked on a ruling is still open, so finishing waits until its ruling is resolved. With nothing open it stops at once. `finish --all` sends `finish` to every project's runner in turn: a project whose runner is stopped counts as done, one that refuses or does not answer prints its reason while the rest still finish, and the verb then exits non-zero. It takes no project, and with `--json` prints one line per project as `status` does. Meanwhile `status` shows `run: finishing` with the items still open, `shep kelpie status` marks the project `(finishing)`, the board briefing says so, and `add <ticket>`, `adopt <pr>` and `rework <pr>` are refused, in the reply or, when queued, in the log. Pull requests already adopted and waiting for a slot stay waiting until the next start, and `finish` names them. A runner restarted while finishing comes back finishing, and `shep kelpie start` cancels it, so the board picks again, except while the runner is already stopping itself: start it once it has stopped. A `pause` during finishing is the stronger stop: it ends finishing too, so the runner comes back picking when it starts.
