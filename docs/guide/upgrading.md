# Upgrading

```sh
cargo install --git https://github.com/shep-pm/shep-kelpie --locked
shep kelpie upgrade                     # restart the dog and the runners onto the installed build
shep kelpie upgrade --ref main          # build shep-kelpie at a git ref and install it
shep kelpie upgrade --release 0.3.0     # install a release (none is published yet)
shep kelpie upgrade --binary ./kelpie   # install a build made by hand, as it is
shep kelpie upgrade --rollback          # put back the build the last upgrade replaced
shep kelpie upgrade --ref main --now    # restart the runners with no handover or drain
```

The installed shep-kelpie is whatever program the adopted dog runs, which the shepherd knows (`~/.cargo/bin/shep-kelpie` for the install above), and `shep kelpie add` registers runners that run the same path. An upgrade writes the new build beside that file and renames it over, as shep upgrades itself, so the running file's bytes are never edited in place. Before the swap it copies the file it replaces into `$SHEP_HOME/kelpie/builds` (resolved first if the path is a symlink), and `--rollback` puts that copy back the same way. Then it restarts the dog and each running runner one at a time, never while a work item is merging: it waits, and says what it waits on. A runner that does not answer `status` is waited on too, and named if it never does. A restarted runner that does not answer `status` in 60s (its first pass can hold the lock that long) does not hold the runners after it back: the upgrade restarts them first, then asks it again for 60s, and fails only if it is still silent or no longer running, naming it with `shep bleats <name>`. The dog is waited on for its 60s alone, since every runner needs it. A runner you stop while the upgrade waits stays stopped, and so does one stopped before it. A stopped runner starts on the new build when you start it.

The merge wait includes a merged item whose cleanup is pending. When its `status` carries `failing`, the wait and its timeout name the failure count and reason: "`koji` is merging #7, whose cleanup has failed 8 times: cannot delete branch kelpie/7: checked out in another worktree". The wait still lasts up to an hour.

After the build is installed and before the restarts, `upgrade` migrates the agent files, then the projects' settings. A bare `upgrade` runs both steps itself. `--ref`, `--release` and `--binary` run `<installed path> upgrade migrate`, which runs every step the installed build knows, since the running build predates it, and print its lines. `--rollback` skips both. The agent step: each file in `$SHEP_HOME/kelpie/agents` that extends one of kelpie's eight shipped baselines gets the harness, model and effort that baseline shipped with, so it keeps running as before (kelpie's baselines carry no binding now). A file that sets another session `harness` than the baseline's and lacks a `model` or `effort` is left alone and named. An agent step that fails is said and the restarts go on. The dog runs the same step at its start, which covers the upgrade that first brings it, run by a build without it. `shep kelpie agents migrate` runs it by hand; see [Commands](commands.md).

The settings step writes each kind a project's `rulings.pm_decides` is missing at its default, `true` for the operational kinds, and turns an old `rulings.pm_alone` list into the map. It deletes the old reviewer list under `agents`, naming the value it held, and adds each name it held to `agents.allow` when that is already a non-empty list, so the reviewers a project named stay allowed; where `allow` is absent or empty nothing is written, and every reviewer file `agents.allow` holds is a candidate for each round. It writes those same names into `contributions.reviewers` when the project names none there, since a contribution's pass reads that key and not the old reviewer list, and its runner would not open on a listed `allow` that leaves kelpie's default contribution reviewers out. It deletes the ruling panel's settings too, `agents.advisor` and `agents.researcher` among them, which the new build refuses. If it fails, or finds a table the check refuses, the upgrade stops before any restart and names each project and why, since a runner whose settings the new build refuses is better left on the old one. Put the table right, run `shep kelpie settings migrate`, then `shep kelpie upgrade --binary <installed path>` to restart onto the build. A build from before `upgrade migrate` answers it with its usage: the upgrade says so and goes on. So installing a build that has `agents migrate` but not `upgrade migrate` migrates nothing, and `shep kelpie agents migrate` and `shep kelpie settings migrate` run by hand cover it. Likewise an upgrade run by such a build runs only the steps it knew, and one from before the settings step runs only `agents migrate`. A build from before `rulings.pm_decides` refuses the key, so going back to one, by `--rollback` or any other way, needs `rulings.pm_decides` taken out of each project's table, or a `rulings.pm_alone` list put back in its place.

kelpie no longer writes `~/.shep/kelpie/<project>/issues/`, so you can delete that folder.

Each build names the commit it was made from, and every line `upgrade` prints about a build names it: `installed kelpie 0.3.0 (shep 0.19.0, built from 1f2e3a4) as ~/.cargo/bin/shep-kelpie`, and the same for the build `--rollback` puts back. A build made from a tree with uncommitted changes names it with `-dirty` on the end, and is named against the clean commit it was made on top of, being a different binary from it. After the restarts, `upgrade` names each running runner whose `status` still shows another commit, or none at all, as `` `koji` still runs 1f2e3a4, not the installed 9c8b7a6 ``: that runner is on the old build, and `shep kelpie status` says the same on its `build:` line until it is restarted. A runner that answers nothing is not named twice: the restarts already said what they found of it.

Each running runner is first handed over to the new build: the upgrade sends it `handover`, the runner replaces its own image at its quiet point with its pid, its shepherd channel and the worker turns in flight kept, and the upgrade waits for the runner's `status` to show the new build (60s at most). A handed over runner is neither drained nor restarted, and a merge goes on in the new image. A runner that refuses, runs a build from before `handover`, or does not show the new build in time is drained and restarted instead, and the upgrade says why for each. The dog is restarted as ever, and `--now` skips the handover.

A runner that is not handed over is drained, so the restart cuts no worker's turn short. The runner's `drain` trigger tells it to start no new call (a worker's turn, a reviewer's session or local round, the project manager's wake), while the calls it has running go on to their end and its merges go on as ever. The upgrade asks again until the runner shows no call running, saying what it waits on, then waits out any merge and restarts it. It waits no longer than the runner's turn ceiling (or the project manager's, if longer) plus five minutes, counted from when the wait began. A turn's ceiling counts from when it got the lease it waited for, and a reviewer's session has no ceiling, so either can outrun that bound. Past it the upgrade sends the runner `undrain`, so it starts calls again on the old build, names it, and restarts nothing for it, as for a merge that outlasts its wait. A runner on a build from before `drain` is restarted as before, and the upgrade says the restart cuts its calls short. `--now`, first or last, restarts without a handover or a drain, for when you want the build in place at once; the merge wait still holds. The dog is never drained, since the calls are the runners'. A restart ends draining. So does a Ctrl-C or SIGTERM to the upgrade, or any failure, while a runner drains: the upgrade sends it `undrain` before it exits. Only a shepherd it cannot reach leaves one drained. The upgrade prints `shep kelpie undrain -p <project>` as each drain starts, for that case, and `shep kelpie status` marks a draining runner `(draining)`.

A bare `upgrade` is for after `cargo install`, which has already put the new build at the installed path. It runs the same checks as `--binary <installed path>` (the build's shep line against your shepherd's) and then restarts, with no staging and no swap. Kelpie records the installed file's size and modification time in `$SHEP_HOME/kelpie/builds/installed.seen` after every upgrade that finishes its restarts, and a bare run compares against it. If the file is the same, it says nothing changed since the last upgrade and restarts nothing. With no record, it counts as changed. If the file differs, it restarts and says that `--rollback` has no copy of the build cargo replaced (the previous build kept is the one before it), while `--ref`, `--release` and `--binary` keep one. `--now` and the drain apply as for the other forms.

If an upgrade stops after the swap (a merge or a call that outlasts the wait, a sheep that does not come back, Ctrl-C), the new build is already installed and the message says so. `shep kelpie upgrade --binary <installed path>` finishes the restarts and touches no file. `--rollback` does not: it swaps the two builds again. After a `--rollback` that stops, the older build is the one installed, and the same command finishes its restarts.

The upgrade reads the flock again just before the restarts, since the wait for a build or a merge can be long, but a sheep can still change after that read. A stop that lands between the re-read and the restart is undone: the restart starts that sheep again. A sheep started during the wait stays on the old build. In both cases run `shep kelpie upgrade --binary <installed path>` again, which restarts every running sheep and touches no file.

A project's state file carries a format version, and a build refuses a file whose version is newer than it reads, whatever the file holds. So going back by `--rollback` or any other way leaves the older build unable to read a file this build wrote. An older build also never knew a work item that holds no slot: parked, waiting for one, or going on without one. Finish or drop those before going back. Draining only stops new calls and leaves them in the state file.

Rulings were once named by an id of their own, a counter shared by every project, and are now named by the number of their pull request or issue. The first load of a state file saved before that change renames its open rulings by their work item. Old ids then stop working: `shep kelpie rule 3 yes` for a ruling that was 3 is refused unless 3 is also the number of a ruling's pull request or issue. An answer file `shep kelpie rule` left in a project's `answers` folder under an old id while its runner was stopped is read once, by the first pass after the upgrade, and answers the ruling that id became. A file left under an old id after that is refused. Messages that told you an old id, a webhook post or a pull request comment, name the number already, as since #508.

State version 73 keys the file's work by ticket id. A work item's `issue`, a ruling's `id` and `issue`, `finished`, `dropped` and the saved `order` hold the string `"427"`, or `k12` for a local ticket, where they held the number 427. A file saved before loads unchanged, its numbers read as the GitHub ids of those numbers, and saves at 73. `status`, `board` and `drain` print the ids as the file holds them, and each reads a runner of the other shape too, so a `shep kelpie` from before this still reads a newer runner's numbers and a newer one reads an older runner's.

State version 74 adds a work item's `ceiling_resumes`, how many turns past their ceiling were resumed with no ruling. A file saved before loads with 0, and a build from before cannot read a file saved at 74.

Every sheep it restarts must run the dog's path. If one does not, the upgrade stops before it changes anything and names the sheep and its path. A `--binary` without its executable bits is refused with the `chmod +x` that fixes it, and only one upgrade runs at a time: a second refuses while the first holds `$SHEP_HOME/kelpie/upgrade.lock`. The swap changes the file for every shepherd that adopts the same path, with no check against their shep.

Before it changes anything it asks the new build which shep it is made with (`shep-kelpie version --json`) and compares it with your shepherd's. A shepherd on the build's shep or a later one is taken. If your shepherd is on an earlier shep than the build's, it stops before restarting anything and prints the steps: upgrade shep and reload its shepherd, then run the new build's own `upgrade` with `SHEP_HOME` set to your shepherd. The upgrade prints the exact line. If your shepherd no longer accepts the protocol the build speaks, which the build names in the same answer, it stops too and says to install a kelpie built for your shep. `--rollback` checks the previous build the same way.
