# CI and the merge

After the review's last reviewer, kelpie waits for CI on the pull request's head. A red run is the worker's next turn, naming the failed checks; a second red run on a head the worker left alone asks you. Before it spends that turn, kelpie reads the end of the failed runs' logs with your `gh` login, and when none of them names a file the branch changed (a panic location, a `--> path` line, a compiler error) it reruns that head's failed jobs once with `gh run rerun --failed`, since the worker's credential cannot, and sends no turn. `status` shows the head under `rerunning` while the rerun runs, and the log has a `ci-rerun` step. A head that fails again after its rerun goes to the worker as any red run does, and the prompt says the failure repeated, so the worker does not call it a flake. A log kelpie cannot read, one that names a file the branch changed, a rerun the forge refuses, and a head already rerun all go to the worker with no rerun. A rerun costs no fix turn, so `ci.fix_attempts` does not count it. `ci.fix_attempts` caps those fix turns for a work item: once the worker has had that many, the next red run asks you instead, and `0` asks on the first. `-1`, the default, sets no cap. A check that stays `queued` or `in progress` for `ci.queued_minutes` (60) of the wait, which GitHub sometimes does on a finished run, gets its whole run rerun once with `gh run rerun`; still waiting after another `ci.queued_minutes`, it asks you with a `check-queued` ruling. GitHub refuses a rerun of a run still going, so a check that is really running is not rerun for being slow. A head the forge reports no check on is read from `origin/main`'s `.github/workflows`: when no workflow there runs on a pull request, no check will ever appear, so the head goes on as skipped at once and `merge = true` merges it as it merges a skipped run, and `doctor` names the repo (`ci on pull requests`); when one does, the head waits `ci.queued_minutes` for a check to start and then asks you with a `no-checks` ruling, whose yes passes that head as skipped. A green run on a branch without the latest `main` is caught up first: kelpie rebases its own commits onto `main` and pushes with a lease, or merges `main` in where the branch holds a merge or commits that are not its own, and a conflict is the worker's next turn. A project with `ci.block = false` reads no checks, and `ci.fix_attempts` does not apply. The review waits on CI as [The review](review.md#the-review) says.

`rulings.pm_decides.merge` decides whether a head that passed every gate merges unasked, with or without a project manager. A project with `merge = false`, the default, gets a ruling before every merge, and a yes merges only the head it was asked about, while CI on it is green and it has the latest `main`. A project with `merge = true` merges its pull requests without asking once every gate passes, and posts a notice after; a project manager, where one is named, may then answer the rulings that remain. The merge rulings that remain under `merge = true` are raised by another open pull request closing the same issue, a head carrying another pull request's commits, and a comment kelpie's guard refused; every other ruling still asks, each a safety gate, not a setting, and the ruling names which one raised it. On a project that names `agents.pm`, an open review thread is not among them: every open thread of its own work item, nits included, and each deferred finding above a nit go to the project manager before the merge, and the head merges only after it rules (see [The review](review.md#the-review)). While that answer is out, or the project manager is down or held by a drain, the item waits at the gate with `held_up` naming why. On a project with no `agents.pm`, an open thread above a nit is one of those gates, and the merge ruling names it. A contribution's threads are the maintainer's to read whatever `merge` says, and its merge ruling names them. On a project that names `agents.pm`, a head no reviewer read goes back through a pass of the review instead of coming to you: a pass nobody read, a head no round read, the fix a merge ruling's `no` asked for, and the fix for a bot's late round. Only a reviewer reading it clears that. While no reviewer can, the work item waits at the gate with `held_up` saying why, no review round runs and no ruling is raised, and kelpie starts one new pass every 30 minutes; when the first 30 minutes end with nothing read it wakes the project manager once. On a project with no `agents.pm`, and on someone else's pull request, those same heads still come to you as a merge ruling. The merge is always a merge commit of the head the gates passed, never a squash, and kelpie then removes the worktree, both branches and the build folder. With a merge queue on `main`, kelpie queues the pull request and waits on the queue.

A commit someone else pushes to a work item's branch, or a label or ready state kelpie did not set, parks it on a `foreign-change` ruling. A pull request that changes agents' own files, such as `.claude` or `.mcp.json`, parks it on an `agent-files` ruling. A pull request you merge by hand ends its work item; one closed without merging parks it. A work item already parked on a ruling reads its pull request at most once every five minutes: a merge ends the item and withdraws its ruling, and a close replaces its ruling with a `closed` one, except for the follow-up ruling after kelpie's own merge, which is not read. An item parked on that `closed` ruling is read on, and a pull request reopened and merged ends it.

## A branch behind `main`

Each merge leaves every other open pull request lacking the latest `main`. `git.catch_up` says what kelpie does then:

- `always`, the default: kelpie catches the branch up with `main` (a rebase, or a merge where the commits are not kelpie's to rewrite), and CI runs again on the new head before the merge.
- `conflicts`: kelpie catches the branch up only when merging it into `main` conflicts, or when git cannot say, which includes any git before 2.38, whose `merge-tree` has no `--write-tree`. A head that merges cleanly goes on as it stands: the merge ruling, the review's catch-up and the merge itself treat it as current, and nothing runs again. The combination of the head and the new `main` is tested by the merge queue's own run, or by `main`'s CI after the merge, which a red `main` already sends to the project manager.

The dependency rules follow bumps by their own up-to-date check and do not read `git.catch_up`.

## A red `main`

kelpie reads the latest run of each workflow on `main` every 15 minutes and reruns the failed jobs of each new red head once, with `gh run rerun --failed`. A head that is red again after its rerun is the project manager's: it reads the failed log, which kelpie writes into its folder, and either opens a fix work item at the front of the board or asks you with the log lines it read. A project without `agents.pm` gets the one webhook notice and nothing more. It may still start issues clear of the failing area. `status` lists each red workflow with what is being done about it under `red_workflows`, and the board shows the same under `## Red on main`.
