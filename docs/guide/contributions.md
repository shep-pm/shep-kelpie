# Contributions

A pull request from someone else is a contribution. The runner sees one before it does anything with it. It lists it, and reads each new head for security before anything of the contributor's runs. It posts nothing and runs nothing for a contribution.

- A contribution is open, not a draft, and not opened by the maintainer (`git.maintainer`, else the login `gh` acts as), by the account kelpie acts as, or by a bot. Logins compare ignoring case. The author decides, never the branch: a fork's branch named `kelpie/5` is still a contribution
- `contributions.pick` sets which ones. `"label"` takes those labelled `ready-for-agent`, `"all"` every one, and `"off"`, the default, none
- A change to the `contributions` table reaches a running runner at its next wake, checked as a start checks it: an App that does not cover the repo, or an agent file that is missing, refuses it, the log names the setting, and the old settings stay. A call already running finishes on the reviewer it started with. Turning `pick` to `"off"` drops the contributions followed, as a start with it off does
- Once a minute, whether or not a slot is free, the runner records each contribution with its author and head, and drops the record of one that is closed, merged, a draft again, or, under `"label"`, no longer labelled. A new head updates the record. `status` lists them under `contributions`, and the plain `status` prints a line each
- A quiet clock runs while kelpie waits on the contributor for the current head: from the poll that finds the head's findings recorded, a review bot's threads open (nits included) or CI red. The contributor's comment or review reply written after it began, or a push, starts it over, and a push also clears it until the new head's own results start it again. A reaction (but see the release ask below) and the maintainer's comment do not touch it. A head with green CI, no findings and no open bot thread clears it, since kelpie then waits on the maintainer. `contributions.nudge_days` and `quiet_days` set when it is due: `status` shows each contribution's `waiting_since` and a `clock` with `waiting_for` (seconds), `days_to_nudge`, `days_to_quiet` and `due` (`nudge` or `quiet`), and the plain `status` a line under it. Red CI before a release gets no comment
- A contributor is asked for a release before kelpie takes their pull request over. When the clock reaches `nudge_days`, kelpie posts one comment, in the representative's words, that lists the review bots' open threads and asks whether it may take the pull request from here. The contributor answers in a comment, or with a thumbs up (yes) or a thumbs down (no) on that comment; a reaction on any other comment counts for nothing. A reply is read as yes, no or other, and other is answered like any comment. A yes, a thumbs up, or no answer by `quiet_days` is a release: kelpie says the pull request is its now and `status` shows `released` with `at` and `how` (`yes`, `thumbs-up`, `silence`, `maintainer` or `rework`). A release does not merge anything yet: it hands the pull request to kelpie, which opens a work item on its branch, files an issue from the pull request's title and body when it closes none (and adds `Resolves #<n>` to the body), and has the project's reviewers read it. A `rework` has a worker change it first and the reviewers read what it pushed. `status` then shows it as a work item, and its contribution record is gone. A no restarts the clock and kelpie asks once more after the next quiet window, and silence after the second ask is a release. A second no followed by quiet raises a ruling, `waiting`, on the pull request: answer `shep kelpie rule <pr> answer keep waiting` to start the clock and the count over, `answer adopt anyway` to record a release by you, or `answer close with thanks` to have kelpie thank the contributor and close the pull request. Like the ruling for a decision, it is never posted on the pull request and never goes to the project manager. A released pull request kelpie cannot start a work item on, because it merges into another branch or its issue is labelled for an agent kelpie has no implementer file for, raises a ruling `cannot-adopt` naming why: answer `answer leave it open` to stop following it or `answer close with thanks`; retargeting the pull request or fixing the label adopts it at the next poll and the ruling goes
- Under `pick = "label"` or `"all"`, `ready-for-agent` on another person's pull request, a draft included, does not adopt it, so a fork's pull request is not refused as one. Under `"off"` it is refused as before. A rework request on a fork's pull request is still refused
- A contributor's code does not run on your machine until something has read it. Each new head gets a security review: kelpie fetches `refs/pull/<n>/head` into the project's checkout (objects only, nothing is checked out) and reads the change since the last head that passed, or the whole change from `origin/main` for a first head or after a force push. `contributions.security_reviewer` (`security-reviewer`, which flags build scripts, workflows, install hooks, network calls, anything near secrets, obfuscated code and text aimed at agents) reads it in a scratch folder under the project's folder that is removed when the call ends, with read tools only, and the diff in the prompt marked as data and never instructions. Kelpie flags in code, without asking a model, a binary change, a symlink, a submodule change and a diff over 200000 bytes, and never passes them. A clean reply records the head as passed, findings record it as flagged with each file, line and why, and a call that fails or answers in no shape leaves the head unread until the next poll. `status` shows each contribution's `security` and `passed`. A flagged head raises a ruling, `security`, naming each file, line and why. It is never posted on the contributor's pull request and never goes to the project manager: it reaches you by the webhook, `status` and `shep kelpie rule`. A yes names the head it trusts, `shep kelpie rule 30 yes <hash>` with 7 or more characters of it, so a late yes meant for an earlier head cannot trust a later one; it counts as passed; a no leaves it unpassed, runs nothing and posts nothing. A new push, or the pull request closing or merging, withdraws the ruling with no post, and a late answer to it is refused as stale. Nothing yet runs a passed head
- A contributor's comment or review reply on their pull request is answered once, as a comment from the App in the representative's words, from the findings kelpie holds and the diff. Your comments are context for the answer and are not answered, and a bot's are never heard. When the contributor asks for a decision, such as whether it will be merged, kelpie posts nothing and raises a ruling, `question`, with what to decide. Answer it with `shep kelpie rule <pr> answer <text>`: the representative words your answer for the contributor and posts it. It never promises a merge, which only a ruling decides. Like every call on a contribution, answers stop at `budget.per_item_usd`, and a call that fails is tried again at the next poll. The ruling is never posted on the pull request and never goes to the project manager
- A contribution is never merged by kelpie alone, whatever `rulings.pm_decides.merge` says. Once the reviewers' pass has ended and CI is green on the same head, you get a merge ruling that names the findings and the review bot threads still open. It is raised whether `merge` is `true` or `false`, goes to the webhook, `status` and `shep kelpie rule` only, and nothing is posted on the pull request. It holds nothing: the clock and the asks go on while it waits. A `yes` merges that head and the representative thanks the contributor. A `no <note>` has the representative put your note to the contributor, and a `no` alone posts nothing. A `rework <note>` takes the pull request over at once, without waiting for the contributor: kelpie opens a work item on its branch, has a worker finish it and the project's reviewers read what the worker pushed, with your note for the worker, or none where you gave none. No fix turn runs for any of the three. A new head withdraws the ruling and its pass raises another. `rulings.pm_decides` refuses `contribution-merge` set `true`
